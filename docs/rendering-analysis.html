  • HLSL은 런타임 컴파일. D3DCompileFromFile이 상대 경로 L"BasicVertexShader.hlsl"을 읽습니다. Visual Studio에서 실행할 때는 작업 디렉터리가 프로젝트 폴더라서 동작하지만, x64/Debug의 exe를 직접 실행하면 파일을 찾지 못합니다.

  • vcpkg 매니페스트 없음. DirectXTK/DirectXTex/ImGui가 vcpkg 전역 설치에 의존해 저장소만으로는 재현 빌드가 안 됩니다.
  • Debug Layer 활성. _DEBUG에서 D3D11_CREATE_DEVICE_DEBUG를 켭니다. 리소스 누수·바인딩 경고가 출력 창에 나오니 활용할 가치가 큽니다.

3.초기화 과정

main()이 TestApp::Initialize()를 부르면 AppBase::Initialize()가 아래 순서로 실행됩니다. 어느 단계라도 실패하면 false가 돌아와 프로그램이 종료됩니다.

3.1 윈도우 생성 AppBase::InitMainWindow

  • WNDCLASSEX를 CS_CLASSDC 스타일로 등록합니다. 윈도우 프로시저는 전역 함수 WndProc이고, 이것이 전역 포인터 g_appBase를 통해 멤버 함수 MsgProc으로 위임합니다.
  • 클라이언트 영역이 정확히 1280×720이 되도록 AdjustWindowRect로 프레임 두께를 보정한 뒤 CreateWindow합니다.
  • MsgProc은 ImGui의 Win32 핸들러에 먼저 메시지를 넘기고, WM_SIZE에서 스왑체인이 있을 때만 Device::Resize와 Camera::SetAspectRatio를 호출합니다. 최소화(SIZE_MINIMIZED)는 건너뜁니다.

3.3 셰이더 컴파일과 상수버퍼 Shader::ShaderCreate

  1. ShaderLoad()가 BasicVertexShader.hlsl을 vs_5_0, BasicPixelShader.hlsl을 ps_5_0으로 D3DCompileFromFile에 넘깁니다. 컴파일 플래그는 0이라 디버그 정보도 최적화 지시도 없습니다.
  2. VS 바이트코드(pVSCode)는 InputLayout 생성용으로 멤버에 보관하고, PS 바이트코드는 객체 생성 후 바로 해제합니다.
  3. VSSetShader / PSSetShader를 한 번 호출합니다(매 프레임 ShaderUpdate에서 다시 하므로 여기서는 사실상 불필요).
  4. Device::CreateConstBuffer로 두 개의 상수버퍼를 만듭니다. 크기는 16바이트 경계로 올림 처리됩니다.
    • pCB — sizeof(ConstBuffer) = 320바이트 (행렬 5개)
    • pLightCB — sizeof(LightBuffer) = 688바이트 (LightData 80B × 8 + 48B)
컴파일 에러가 보이지 않는 구조

ShaderCompile은 ppErrorMsgs로 받은 pError Blob을 출력하지 않고 바로 Release()합니다. HLSL에 오타가 나면 "셰이더 컴파일 실패"라는 한 줄만 보이고, 어떤 줄이 문제인지는 알 수 없습니다. 작업 예정 목록 2단계에 이미 적혀 있던 항목이지만 아직 반영되지 않았습니다.

3.4 구 메시와 GPU 버퍼 Renderer::DataLoading → ObjLoad

Mesh::CreateSphere(5.0f, 32, 16, white)가 CPU 메모리에 정점·인덱스 배열을 만듭니다. 구조는 Frank Luna의 GeometryGenerator와 같은 방식입니다.

정점 수
북극 1 + 링 15개 × (32+1) + 남극 1 = 497개. 각 링에서 마지막 정점은 첫 정점과 위치가 같은 이음새 복제입니다(UV를 붙일 때를 위한 구조).
인덱스 수
상단 캡 32×3 + 몸통 14링 × 32 × 6 + 하단 캡 32×3 = 2,880개 → 960 삼각형
정점 포맷
VERTEX = float3 위치(12B) + float4 색(16B) + float3 노멀(12B) = 40바이트. 노멀은 단위구 좌표 그대로라 정확합니다.
감기 방향
상단 캡이 (0, i+1, i) 순서라 왼손 좌표계에서 밖을 향하는 면이 시계 방향(CW)이 되고, FrontCounterClockwise=false인 RasterizerState와 맞아 후면 컬링이 정상 동작합니다.

이어서 sphereObject의 Transform을 위치 (0, 5, 0), 스케일 1로 두고 MeshRenderer::Initialize를 호출합니다. 여기서 세 GPU 리소스가 만들어집니다.

  • VertexBuffer — USAGE_DEFAULT, 초기 데이터로 정점 배열 복사. CPU 접근 불가.
  • IndexBuffer — 32비트 인덱스(R32_UINT). 497개 정점이면 16비트로 충분하지만 지금은 단순함을 택했습니다.
  • InputLayout — POSITION(0) / COLOR(12) / NORMAL(28) 오프셋으로 VERTEX 구조와 정확히 일치. VS 바이트코드로 시그니처 검증을 받습니다.

마지막으로 RasterStateCreate가 Solid / Wireframe × CullNone / CullBack 조합 4개의 ID3D11RasterizerState를 만듭니다. 모두 MultisampleEnable=true, AntialiasedLineEnable=true인데 스왑체인에 MSAA가 없어 실제 효과는 없습니다.

4.프레임 루프

AppBase::Run()은 PeekMessage 기반의 전형적인 게임 루프입니다. 메시지가 없을 때마다 한 프레임을 처리하며, Present(0, 0)이라 수직동기 없이 GPU가 허용하는 최대 속도로 돌아갑니다(스크린샷 기준 약 13,000 FPS). 아래는 한 프레임 동안 실제로 호출되는 순서를 파일 경계를 넘어 펼친 것입니다.

그림 2. 한 프레임의 호출 시퀀스. ①과 ②에서 같은 렌더타깃을 두 번 클리어합니다. ①은 아무것도 그려지기 전이라 무해하지만, 두 Clear 사이에 무언가를 그리기 시작하면(예: 스카이박스, 배경 패스) ②가 그 결과를 지워 버립니다. 색도 다릅니다. Device는 (0.1, 0.1, 0.3)을 쓰고 Renderer의 g_ClearColor(0, 0.125, 0.3)는 사용되지 않습니다.

프레임 단계별 설명

T-1

시간 갱신

gameTimer.Tick()으로 델타타임을 계산해 지역 변수 GameTime gameTime에 넣습니다. 그런데 이 지역 변수는 클래스의 static GameTime gameTime 멤버를 가리기(shadowing) 때문에 TestApp::Update()에서는 갱신된 값을 볼 수 없습니다. 정적 멤버는 정의(.cpp의 GameTime AppBase::gameTime;)도 없어서 실제로 참조하면 링크 에러가 납니다. 지금은 Update()가 비어 있어 드러나지 않을 뿐입니다.

T-2

클리어 ①과 ImGui 프레임 시작

RTV를 클리어한 후 ImGui의 DX11/Win32 백엔드 NewFrame을 호출하고 "Information" 창에 ImGui가 자체 계산한 FPS를 표시합니다. UpdateGUI()로 파생 앱의 위젯(현재는 조명 패널)을 추가하고 ImGui::Render()로 드로우 리스트를 확정합니다. 이 시점에는 아직 GPU에 아무것도 제출되지 않습니다.

T-3

파이프라인 상태 재바인딩

Shader::ShaderUpdate()가 VS/PS와 상수버퍼 슬롯을 다시 묶고, Renderer::RenderModeUpdate()가 RasterizerState를 설정합니다. 매 프레임 재바인딩하는 이유는 ImGui 백엔드가 RenderDrawData에서 자기 셰이더·블렌드·래스터 상태로 파이프라인을 바꿔 놓기 때문입니다(7/6 로그의 결정). 다만 ImGui 백엔드는 자신이 바꾼 상태를 백업·복원하므로 실제로는 안전장치 성격입니다.

T-4

상수버퍼 갱신

MeshRenderer::UpdateConstantBuffer가 Transform의 월드행렬과 카메라의 뷰·투영행렬로 ConstBuffer를 채우고 UpdateSubresource로 b0에 올립니다. Renderer::UpdateLightConstantBuffer는 조명 배열을 복사하면서 방향 벡터를 정규화(영벡터면 아래 방향으로 대체)하고 카메라 위치·앰비언트·스페큘러 설정을 채워 b1에 올립니다. 두 버퍼 모두 USAGE_DEFAULT라 CPU 쓰기마다 드라이버 내부 복사가 일어납니다. 지금은 드로우 1개라 문제없지만, 오브젝트가 늘면 USAGE_DYNAMIC + Map(WRITE_DISCARD)가 정석입니다.

T-5

클리어 ②와 드로우

Renderer::Render() 내부에서 다시 Clear()를 호출한 뒤 MeshRenderer::Draw()가 IA 단계 상태를 설정하고 DrawIndexed(2880, 0, 0) 한 번을 발행합니다. 이 프레임에서 씬 지오메트리에 관한 드로우콜은 이것 하나뿐입니다.

T-6

ImGui 드로우와 Present

ImGui_ImplDX11_RenderDrawData가 UI를 같은 백버퍼 위에 그리고, Present(0, 0)이 백버퍼를 화면에 넘깁니다. SyncInterval 0이라 프레임 페이싱이 없어 GPU 사용률이 100%에 붙습니다. 학습 중에는 FPS 수치가 보여 편리하지만, 노트북에서는 발열·소음의 원인이 되므로 ImGui 토글로 Present(1, 0)을 선택할 수 있게 해두는 편이 좋습니다.

5.GPU 파이프라인 단계별 추적

드로우콜 하나가 GPU 안에서 어떤 단계를 거치고, 각 단계에 이 프로젝트가 무엇을 바인딩해 두었는지를 따라갑니다. 사용하지 않는 단계(Hull/Domain/Geometry Shader, Stream Output)는 생략했습니다.

그림 3. 파이프라인 단계와 현재 바인딩. 테셀레이션·지오메트리 셰이더 단계는 비어 있습니다.

Input Assembler

MeshRenderer::Draw가 슬롯 0에 정점버퍼(stride 40, offset 0), 32비트 인덱스버퍼, InputLayout, 삼각형 리스트 토폴로지를 설정합니다. IA는 인덱스 3개씩 읽어 정점버퍼에서 40바이트 레코드를 가져오고, InputLayout에 따라 POSITION은 float3, COLOR0은 float4, NORMAL0은 float3로 풀어 VS 입력 시그니처에 전달합니다. HLSL 쪽 VSInput.position이 float4로 선언되어 있어도 문제없습니다. IA가 없는 성분은 (0,0,0,1) 규칙으로 채우고, VS가 다시 w = 1을 명시합니다.

Vertex Shader BasicVertexShader.hlsl

VSOutput VS_Main(VSInput vsInput)
{
    vsInput.position.w = 1.0f;
    vsOutput.position      = mul(vsInput.position, mWVP);                    // 클립 공간
    vsOutput.col           = vsInput.col;
    vsOutput.worldPosition = mul(vsInput.position, mWorld).xyz;              // 조명용 월드 위치
    vsOutput.normal        = normalize(mul(float4(vsInput.normal, 0), mWorldInverseTranspose).xyz);
}

정점당 행렬 곱 세 번입니다. mul(벡터, 행렬) 형식은 행벡터 규약이며, DirectXMath도 행벡터·행 우선(row-major) 규약이라 두 쪽의 수학은 일치합니다. 그런데 HLSL 상수버퍼는 기본적으로 열 우선(column-major)으로 메모리를 해석하므로, CPU에서 XMMatrixTranspose로 전치해서 올려야 셰이더가 같은 행렬을 보게 됩니다. MeshRenderer::UpdateConstantBuffer가 다섯 행렬을 모두 전치하는 이유가 이것입니다.

역전치 행렬의 "이중 전치"는 맞게 동작합니다

코드는 worldInverseTranspose = Transpose(Inverse(world))를 만든 뒤 다시 Transpose해서 올립니다. 결과적으로 메모리에는 Inverse(world)가 그대로 올라가고, 셰이더가 열 우선으로 읽으면 Inverse(world)ᵀ, 즉 원하던 역전치 행렬이 됩니다. 다른 네 행렬과 같은 "전치해서 올린다" 규칙을 일관되게 적용한 결과라 수학적으로 옳습니다. 다만 이름과 코드가 헷갈리기 쉬우니 주석 한 줄이 필요합니다. 현재 스케일이 (1,1,1)이라 역전치가 없어도 결과는 같지만, 비균등 스케일을 쓰기 시작하면 이 행렬이 노멀을 올바르게 유지해 줍니다.

VS 출력은 네 개의 보간 속성(SV_POSITION, COLOR0, NORMAL0, TEXCOORD0=월드 위치)입니다. 월드 위치를 TEXCOORD0 시맨틱에 실어 보내는 것은 D3D11에서 흔한 관례이며, 나중에 실제 UV를 추가하면 TEXCOORD1 등으로 자리를 옮기면 됩니다.

Rasterizer

RM_DEFAULT = RM_SOLID | RM_CULLBACK이므로 RenderModeUpdate는 RS_CULLBACK 상태(솔리드 채움, 후면 컬링, 시계 방향이 앞면)를 바인딩합니다. 래스터라이저는 클립 공간 좌표를 w로 나눠 NDC로 만들고, 뷰포트 변환으로 1280×720 픽셀 좌표를 얻고, 화면 밖 삼각형을 클리핑하고, 뒤를 보는 삼각형(구의 뒷면 약 480개)을 버립니다. 살아남은 삼각형의 각 픽셀에 대해 VS 출력 네 속성을 원근 보정 보간합니다. DepthClipEnable=true라 near/far 밖의 지오메트리도 잘립니다.

Pixel Shader BasicPixelShader.hlsl

픽셀 셰이더는 보간된 색을 알베도로 쓰고, 조명 배열을 순회해 Blinn-Phong 결과를 누적합니다. 텍스처 샘플링은 없습니다. 구조는 다음과 같습니다.

  1. 보간으로 길이가 줄어든 노멀을 SafeNormalize로 재정규화하고, 카메라 위치에서 뷰 벡터 V를 구합니다.
  2. finalColor = albedo × ambientColor로 시작합니다.
  3. [loop]로 min(lightCount, 8)개 조명을 돕니다. 조명 타입에 따라 표면→광원 방향 L과 감쇠를 계산합니다.
  4. 각 조명에 대해 (albedo × N·L + specularColor × spec) × color × intensity × attenuation을 더합니다.
  5. 알파는 정점 색의 알파를 그대로 출력합니다(블렌딩이 꺼져 있어 실질적 의미는 없음).

Output Merger

DepthStencilState와 BlendState를 명시적으로 설정한 적이 없으므로 D3D11 기본값이 적용됩니다. 기본 DepthStencilState는 깊이 테스트가 켜져 있지만 DSV가 바인딩되어 있지 않으면 깊이 테스트는 조용히 생략됩니다. 기본 BlendState는 소스 색을 그대로 씁니다(불투명). 따라서 OM은 픽셀 셰이더 출력을 그리는 순서대로 RTV에 덮어씁니다.

6.리소스 수명과 해제

D3D11 객체 관리 방식이 계층마다 다릅니다. Device는 ComPtr로 자동 해제하고, Shader·Renderer·MeshRenderer는 생 포인터와 SafeRelease 템플릿을 씁니다. 종료 시 실제로 일어나는 일은 다음 순서입니다.

  1. main()이 반환되며 TestApp 소멸자 → AppBase 소멸자 본문 실행: ImGui DX11/Win32 셧다운, 컨텍스트 파괴, DestroyWindow.
  2. 멤버가 선언 역순으로 소멸: gameTimer → camera → shaderClass → renderer → graphicsDevice.
  3. Shader에는 소멸자가 없고 ShaderRelease()를 부르는 곳도 없습니다. VS, PS, VS 바이트코드, 상수버퍼 2개가 해제되지 않습니다. Debug Layer가 종료 시 D3D11 WARNING: Live Object를 출력할 것입니다.
  4. Renderer 소멸자가 DataRelease()로 MeshRenderer의 VB/IB/IL과 RasterizerState 4개를 해제합니다. 이 시점에는 Device가 아직 살아 있어 안전합니다.
  5. Device의 ComPtr들이 해제됩니다. ReleaseDevice()(ClearState + Flush)는 호출되지 않습니다.

프로세스가 종료되므로 실질적 피해는 없지만, 나중에 리소스 리로드(셰이더 핫리로드, 씬 교체)를 구현할 때 같은 패턴이 실제 누수로 이어집니다. 해결책은 단순합니다. 모든 계층에서 ComPtr을 쓰고 SafeRelease를 없애는 것입니다.

적용 결과 — 2026-09-10

위 5단계 중 3번이 사라졌습니다. 모든 계층이 ComPtr을 쓰고 SafeRelease와 helper.h는 삭제됐습니다. Shader는 소멸자를 추가하지 않았습니다. 멤버가 ComPtr이라 필요 없고, 호출처가 없던 ShaderRelease()는 지웠습니다. 4번의 Renderer 소멸자는 남아 있으나 이제 Reset()만 부르므로 Device 생존 여부와 무관하게 안전합니다.

종료 시 Live Object가 D3D11 31개·DXGI 1개에서 둘 다 0개가 되었습니다. 커밋 867c380을 별도 worktree에 빌드해 직접 비교한 수치입니다. 5번의 ReleaseDevice()가 호출되지 않는 점은 그대로지만, ComPtr이 전부 정리하므로 누수는 없습니다.

0. 선행 작업 — 소스 인코딩 통일 (D17)

편집 도구가 파일을 UTF-8로 다시 쓰면 CP949로 저장된 한글 주석이 전부 깨지므로, 코드를 건드리기 전에 인코딩부터 통일했습니다. 스크립트로 SherlockEngine/의 .h·.cpp·.hlsl 30개를 읽어, 엄격 모드 UTF-8 디코딩이 성공하면 그대로 두고 실패하면 CP949로 디코딩한 뒤 UTF-8 BOM으로 다시 썼습니다. 21개가 CP949였습니다. 이어서 SherlockEngine.vcxproj의 네 구성 모두에 /utf-8을 넣었습니다.

여기서 한 번 실수했습니다

HLSL에도 BOM을 붙였더니 D3DCompileFromFile이 error X3000: Illegal character in shader file로 거부했습니다. 셰이더 두 개는 순수 ASCII였으므로 BOM을 다시 제거해 원래 바이트로 되돌렸습니다. HLSL은 BOM 없이 유지해야 합니다. C++ 소스에만 BOM을 붙입니다.

1. 깊이 버퍼 (#1, 1단계 항목)

Device에 ComPtr<ID3D11Texture2D> m_depthStencilBuffer를 추가하고, 선언만 있던 m_DSView를 실제로 채우도록 CreateDepthStencilView()와 BindRenderTargets() 두 함수를 새로 만들었습니다.

  • 포맷과 크기 — D24_UNORM_S8_UINT, 크기는 m_screenWidth·m_screenHeight, SampleDesc는 카운트 1·품질 0으로 스왑체인과 맞췄습니다. 이 셋 중 하나라도 백버퍼와 다르면 OMSetRenderTargets가 거부합니다.
  • 바인딩 분리 — 기존에는 CreateRenderTargetView()가 생성과 OMSetRenderTargets를 같이 했습니다. 바인딩을 BindRenderTargets()로 떼어내, RTV와 DSV가 둘 다 준비된 뒤에 한 번만 묶어 걸도록 했습니다.
  • Resize — 기존 순서(RTV 언바인드, 해제, ResizeBuffers, 재생성)에 DSV를 끼워 넣었습니다. RTV를 Reset()하는 자리에서 m_DSView와 깊이 텍스처도 함께 Reset()하고, 재생성 뒤 다시 바인딩합니다.
  • Clear — Device::Clear()에 깊이 1.0, 스텐실 0으로 ClearDepthStencilView를 추가했습니다.

DepthStencilState는 일부러 만들지 않았습니다. D3D11 기본 상태가 이미 깊이 테스트 켜짐, 비교 함수 LESS, 쓰기 전체 허용이라 DSV만 걸리면 바로 동작합니다. 명시적 상태 객체는 1단계의 PSO 에뮬레이션이 소유할 물건이므로, 지금 개별 OMSetDepthStencilState 호출을 넣으면 나중에 되돌려야 합니다.

2. 프레임당 Clear 한 번 (#2)

Renderer::Render() 안의 Clear() 호출 한 줄을 지웠습니다. 이제 이 함수는 오브젝트 갱신과 드로우만 합니다. 어디서도 읽지 않던 Renderer::g_ClearColor도 함께 제거해, 클리어 색 상수가 Device::Clear() 한 곳에만 남도록 했습니다.

D4가 제시한 방향, 즉 클리어와 Present를 Renderer::BeginFrame·EndFrame 안으로 옮기고 AppBase를 얇게 만드는 재구성은 이번에 하지 않았습니다. 지금은 AppBase가 클리어를 소유합니다. 프레임 경계 재구성은 RenderPass가 생기는 시점에 함께 하는 편이 낫습니다.

3. ComPtr 통일 (D1, #4, #6, #18, #19)

Shader 5개, MeshRenderer 3개, Renderer의 래스터라이저 상태 배열 4개까지 소유 핸들 12개를 전부 ComPtr로 바꾸고 helper.h를 삭제했습니다. pch.h에 wrl/client.h와 using Microsoft::WRL::ComPtr;이 이미 있어 추가 include는 필요 없었습니다.

세운 규칙은 한 줄입니다. 소유하면 ComPtr, 생 포인터면 소유하지 않음. 그래서 Device*·Shader*·Camera*·Mesh* 같은 역참조와, 게터가 돌려주는 ID3D11Device*는 생 포인터 그대로 두었습니다. 게터는 반환형을 바꾸지 않고 본문에서 .Get()만 붙였으므로 호출부는 손대지 않았습니다.

생성 함수 시그니처

Device의 네 팩토리를 이중 포인터 출력 인자에서 ComPtr<T> 값 반환으로 바꿨습니다. 실패하면 비어 있는 ComPtr을 돌려줍니다.

// 이전
void CreateConstBuffer(int size, ID3D11Buffer** ppCB);

// 이후
ComPtr<ID3D11Buffer> CreateConstBuffer(UINT size);
ComPtr<ID3D11Buffer> CreateVertexBuffer(const void* pData, UINT size, UINT stride);
ComPtr<ID3D11Buffer> CreateIndexBuffer(const void* pData, UINT size);
ComPtr<ID3D11InputLayout> CreateInputLayout(const D3D11_INPUT_ELEMENT_DESC* desc, UINT num, ID3DBlob* pVSCode);

참조 출력 인자 대신 값 반환을 고른 이유는 7단계에서 BufferHandle CreateBuffer(desc) 형태로 옮기기 가장 자연스럽기 때문입니다. 앞으로 텍스처·샘플러·깊이 상태 생성 함수를 추가할 때도 같은 형태를 따릅니다. 덤으로 호출부에서 const_cast가 사라졌습니다. 팩토리가 const void*를 받기 때문입니다.

  • 경고도 출력 — 컴파일이 성공해도 Blob에 내용이 있으면 경고로 찍습니다.
  • 중복 제거 — ShaderCompile과 ShaderLoad가 같은 문구를 두 번 찍고 있었습니다. 이제 컴파일 실패는 ShaderCompile이 한 번만 보고합니다.
  • 컴파일 플래그 (#16) — Debug에서 D3DCOMPILE_DEBUG와 D3DCOMPILE_SKIP_OPTIMIZATION, Release에서 D3DCOMPILE_OPTIMIZATION_LEVEL3을 줍니다. include 핸들러도 널에서 D3D_COMPILE_STANDARD_FILE_INCLUDE로 바꿔, 앞으로 HLSL 안에서 #include를 쓸 수 있게 했습니다.

5. Release 빌드 (#7)

ExcludedFromBuild가 Debug|x64에만 걸려 있어, 다른 구성에서는 MSBuild가 HLSL을 기본 진입점으로 컴파일하려다 error X3501: entrypoint not found로 실패했습니다. 셰이더는 런타임에 D3DCompileFromFile로 컴파일하므로 빌드 시 FXC를 돌릴 이유가 없습니다. 조건을 없애고 전 구성에서 제외했습니다.

7절이 제시한 다른 선택지, 즉 FxCompile로 .cso를 굽고 런타임 로딩으로 전환하는 방향은 고르지 않았습니다. 셰이더 핫리로드를 남겨 두는 편이 지금 단계에 맞고, .cso 전환은 경로 정책과 함께 결정할 문제이기 때문입니다.

  • dxgi.lib pragma — 직접 부르는 dxgi export가 없습니다. 스왑체인은 D3D11CreateDeviceAndSwapChain이 만들어 주므로 d3d11.dll만 있으면 됩니다. 헤더는 남겼습니다.

  • 추가한 것 — <string>, <vector>, <memory>. 특히 <string>은 Shader.cpp가 쓰면서도 <iostream>을 타고 우연히 들어오던 상태였습니다. 잠재적 파손이라 명시했습니다.

수학 타입은 DirectXMath로 확정

문서가 "SimpleMath를 주 수학 타입으로 쓸지 DirectXMath 원형을 쓸지 하나를 정하라"고 했는데, DirectXMath로 정했습니다. 코드가 이미 전부 그쪽이고 SimpleMath 사용이 0건이라 결정이랄 것도 없었습니다. 문서가 걱정한 XMFLOAT3 ↔ Vector3 변환 코드는 애초에 생기지 않았습니다.

전역 using 제거

D18이 지목한 진짜 문제입니다. pch.h의 using namespace DirectX;를 없애고 두 갈래로 처리했습니다.

  • 헤더 6개(struct.h, Camera.h, Transform.h, Renderer.h, Mesh.h, MeshRenderer.h)는 DirectX:: 접두어를 붙였습니다. 55개 심볼입니다.
  • .cpp 6개는 include 아래에 파일 지역 using namespace DirectX;를 한 줄 두었습니다. 본문은 손대지 않았습니다.

이제 헤더가 이름공간을 새지 않으므로, 나중에 자체 Color나 Plane 타입을 만들어도 모호성 오류가 나지 않습니다. 문서가 걱정한 "수십 곳에 접두어가 붙어 코드가 길어짐"은 헤더 선언부에만 생겼고 구현부는 그대로입니다.

헤더 자립화

pch.h에서 GameTimer.h·enum.h·struct.h를 빼면서 숨어 있던 의존성이 드러났습니다. struct.h는 LightType·MAX_LIGHTS·XMMATRIX를 쓰면서 enum.h도 DirectXMath.h도 include하지 않고 있었습니다. pch.h의 include 순서 덕에 우연히 컴파일되던 것입니다. enum.h도 UINT 때문에 windows.h가 필요했습니다. 각 헤더가 자기 의존성을 직접 include하도록 고쳤습니다.

후속 (2026-09-10) — Log.h가 이 검사에서 빠져 있었습니다. 같은 세션에서 새로 만든 파일이라 위 자립화 점검 대상에 들어가지 않았고, <string>만 include한 채 HrToString(HRESULT)에서 HRESULT를 쓰고 있었습니다. HRESULT는 windows.h에서 오고 그것은 pch.h에만 있으므로, struct.h가 그랬던 것과 똑같이 "pch.h가 먼저 include된 상태"에 우연히 기대고 있던 헤더였습니다. windows.h를 통째로 끌어오는 대신 <winerror.h> 하나를 넣어 해결했습니다. HRESULT의 typedef가 _HRESULT_DEFINED 가드 안에 거기 있고, winerror.h는 SAL 주석 때문에 필요한 specstrings.h를 스스로 include하므로 단독으로 성립합니다.

확인은 pch.h 없이 Log.h만 include하는 파일을 만들어 cl /std:c++17 /utf-8 /EHsc /c로 컴파일해 봤습니다. 오브젝트 파일이 경고 없이 나왔습니다. 이런 종류의 의존은 빌드가 성공하는 한 드러나지 않으므로, 새 헤더를 추가할 때마다 pch 없이 단독 컴파일되는지 확인하는 것이 가장 확실합니다.

덤으로 잡은 구성 불일치

PCH를 손대다 보니 LanguageStandard와 PrecompiledHeader 설정이 Debug|x64에만 있는 것이 보였습니다. Release|x64는 조용히 C++14로, PCH 없이 빌드되고 있었습니다. 같은 코드를 다른 표준으로 컴파일해 배포하는 셈이라 네 구성 모두에 stdcpp17과 PCH를 넣어 통일했습니다. 빌드 로그(CL.command.1.tlog)로 Release에 /std:c++17과 /Yu"pch.h"가 들어간 것을 확인했습니다.

D16은 문서가 "0단계 일부, 10단계"로 나눠 둔 항목입니다. 이번에는 0단계 몫만 했습니다. 레벨 필터, 파일 싱크, ImGui 콘솔, ThrowIfFailed류 예외 정책은 10단계에 그대로 남깁니다.

Log 파사드

Log.h/Log.cpp를 만들고 std::cout 29곳을 전부 옮겼습니다. 싱글턴 객체가 아니라 자유 함수 네임스페이스입니다. 지금 필요한 것은 "직접 호출을 한 곳으로 모으는 것"뿐이고, 10단계에서 Logger 클래스로 바꿀 때 호출부를 다시 안 고치려면 이 형태가 낫습니다.

  • Log::Info / Warn / Error — printf 서식. 접두어 [정보] / [경고] / [실패]를 자동으로 붙입니다.
  • 출력은 콘솔과 OutputDebugStringW 양쪽으로 갑니다. VS 출력 창에서 D3D Debug Layer 메시지와 같은 곳에 나옵니다. OutputDebugStringA는 시스템 ANSI 코드페이지로 해석해 한글이 깨지므로 UTF-16으로 변환해 W 버전을 씁니다.
  • Log::HrToString(hr) — FormatMessageW로 0x80070002 (지정된 파일을 찾을 수 없습니다.) 형태를 만듭니다. HRESULT를 찍던 자리에 전부 적용했습니다.
  • Log::ToUtf8 — Shader.cpp의 익명 네임스페이스 헬퍼를 여기로 옮겼습니다.

추가 (2026-09-10) — Log.h의 namespace Log, Log.cpp의 이름 없는 namespace, 그리고 Log.cpp에서 namespace Log를 다시 여는 자리 세 곳에 namespace를 왜 이렇게 썼는지를 주석으로 남겼습니다. 요지는 세 가지입니다. (1) namespace는 전역 함수를 만드는 장치가 아니라 이미 전역인 이름을 묶어 충돌을 막는 장치이며, 저장 기간과 링키지는 건드리지 않는다. (2) 그러므로 가시성을 넓히지 않는다 — Log.h를 include하지 않은 번역 단위에서는 Log::를 쓸 수 없고, Log.h는 pch.h에 없으므로 쓰는 .cpp마다 직접 include해야 한다. (3) Log.cpp 위쪽의 이름 없는 namespace는 정반대로 이름을 파일 안에 가두는 쪽이고(내부 링키지), 상태 없는 자유 함수 묶음에 클래스 정적 멤버 대신 namespace를 고른 이유는 같은 namespace를 헤더와 .cpp에서 나눠 열 수 있기 때문이다.

서식 문자열 함정

컴파일러가 뱉은 텍스트를 Log::Error(compilerText)처럼 넘기면 안 됩니다. 메시지에 %가 들어 있으면 서식 지정자로 해석됩니다. Log::Error("%s", compilerText)로 인자에 실어 보냅니다.

콘솔 코드페이지 (D17 잔여)

Log::Init()이 SetConsoleOutputCP(CP_UTF8)를 한 번 부르고, main() 첫 줄에서 호출합니다. 소스가 /utf-8로 컴파일되어 문자열 리터럴이 UTF-8 바이트인데 콘솔은 CP949였으므로, 그동안 한글 로그가 실제로 깨지고 있었습니다. D17의 "발전 방향"에 적혀 있던 마지막 조각입니다. .editorconfig도 함께 추가해 새로 만드는 파일이 같은 인코딩을 따르게 했습니다. HLSL만 BOM 없음이라는 규칙을 파일에 명시했습니다.

실패를 전달했더니 드러난 잠재 버그

초기화 실패가 실제로 main까지 올라가자 종료할 때 죽었습니다. 원인이 셋이었고 모두 이전부터 있던 문제입니다. 그동안은 Initialize가 사실상 항상 성공한 셈이라 이 경로에 도달한 적이 없었을 뿐입니다.

  1. WndProc이 전역 g_appBase를 널 검사 없이 역참조합니다.
  2. ~AppBase가 g_appBase = nullptr을 먼저 하고 DestroyWindow를 불렀습니다. DestroyWindow는 WM_DESTROY를 동기적으로 보내므로 방금 널로 만든 포인터를 건드립니다. Release에서 접근 위반(0xC0000005)이었습니다.
  3. ~AppBase가 ImGui 초기화 여부와 무관하게 ImGui_ImplDX11_Shutdown()을 부르고, MsgProc도 ImGui_ImplWin32_WndProcHandler를 무조건 불렀습니다. GUI 초기화 전에 실패하면 컨텍스트가 없어 단언에 걸립니다.

고친 방법: WndProc에 널 가드를 두고 없으면 DefWindowProc으로 넘깁니다. 소멸자는 창을 먼저 파괴한 뒤 g_appBase를 지웁니다. 초기화 단계별로 bool 플래그를 남겨 실제로 초기화한 것만 되돌리고, MsgProc도 그 플래그를 보고 ImGui에 넘깁니다.

생 포인터 + SafeRelease와 ComPtr 혼용

적용 완료 · 2026-09-10
현재 Device는 ComPtr, Shader·Renderer·MeshRenderer는 생 포인터와 SafeRelease 템플릿. Shader에는 소멸자가 없어 실제로 누수가 있습니다(7절 #6).

왜 고민해야 하나. 두 방식이 섞이면 "이 포인터는 누가 해제하나"를 매번 파일을 열어 확인해야 합니다. 셰이더 핫리로드, 씬 교체, Resize 시 재생성처럼 리소스를 다시 만드는 코드가 늘어나는 순간 수동 해제는 누수와 이중 해제의 온상이 됩니다. 함수 중간에서 return false하는 경로가 많은 초기화 코드는 특히 위험합니다.

발전 방향. 모든 D3D 인터페이스 포인터를 ComPtr<T>로 통일하고 SafeRelease와 helper.h를 삭제합니다. 생성 함수는 ComPtr<ID3D11Buffer>를 반환하거나 ComPtr&를 받도록 시그니처를 바꿉니다. 소유가 아닌 참조(Device*, Shader*)는 그대로 생 포인터로 두어 "생 포인터 = 소유하지 않음"이라는 규칙을 세웁니다.

장점
  • 소멸 순서와 예외·조기 반환 경로가 자동으로 안전해짐
  • Debug Layer의 Live Object 경고가 사라져 진짜 누수를 찾기 쉬워짐
  • "생 포인터는 참조"라는 한 줄 규칙으로 코드 읽기가 빨라짐
단점 · 주의
  • GetAddressOf()(기존 값 유지)와 ReleaseAndGetAddressOf()(해제 후 받기)를 혼동하면 재생성 시 누수. 규칙: 출력 인자로 넘길 때는 항상 후자
  • 배열로 넘기는 API(IASetVertexBuffers)에는 .Get()을 모아 담은 임시 배열이 필요해 코드가 한 줄 늘어남
  • 참조 카운트 증감 비용은 무시할 수준
적용 결과

소유 핸들 12개를 전환하고 helper.h를 삭제했습니다. 생성 함수는 두 선택지 중 ComPtr<T> 값 반환을 골랐습니다. 7단계에서 핸들 반환 형태로 옮기기 가장 자연스럽기 때문입니다.

실제로 걸림돌이 된 것은 예상대로 주소 획득 메서드 구분이었습니다. 다만 위 서술보다 경우가 하나 많았습니다. 출력 인자에는 ReleaseAndGetAddressOf(), 입력 배열에는 GetAddressOf()가 필요합니다. VSSetConstantBuffers·PSSetConstantBuffers·IASetVertexBuffers가 그 자리이며, 여기에 전자를 쓰면 바인딩 직전에 버퍼가 해제됩니다. 컴파일은 통과하므로 자동으로 걸러지지 않습니다.

배열 API에 임시 배열이 필요할 거라는 예상은 빗나갔습니다. 지금은 모두 원소 1개짜리 바인딩이라 GetAddressOf()만으로 충분했고 코드가 늘지 않았습니다. 원소가 여러 개가 되는 시점에 임시 배열이 필요해집니다.

종료 시 Live Object가 31개에서 0개가 되었고, 7절 #4·#6·#18·#19가 함께 해결됐습니다. 적용 기록 참고.

Shader가 상수버퍼를 소유하는 구조

전환 권장
현재 Shader가 pCB(변환)와 pLightCB(조명)를 생성·바인딩하고, 내용은 MeshRenderer와 Renderer가 각각 채웁니다. Shader.cpp 32번째 줄의 주석("상수 버퍼를 여기서 업데이트 하는것이 맞나?")이 이미 이 고민을 담고 있습니다.

왜 고민해야 하나. 셰이더는 프로그램이고 상수버퍼는 데이터입니다. 셰이더가 데이터를 소유하면 같은 셰이더로 오브젝트 100개를 그릴 때 버퍼는 하나뿐이라 매 드로우마다 덮어써야 하고, 두 번째 셰이더를 추가하면 같은 View/Proj를 또 한 벌 만들게 됩니다. 4단계에서 Material이 들어오면 "재질 파라미터 버퍼는 누가 갖나"라는 질문에 답이 없습니다.

발전 방향. 상수버퍼 소유를 갱신 빈도에 따라 나눕니다. PerFrame(View·Proj·카메라 위치·시간)은 Renderer, PerObject(World·WIT)는 MeshRenderer 또는 Renderer의 재사용 풀, PerMaterial은 Material, Lights는 LightManager(또는 Scene). Shader는 "b0은 PerFrame, b1은 PerObject"라는 슬롯 규약만 문서화하고 버퍼 자체는 모릅니다. ConstantBuffer<T> 템플릿 래퍼로 생성·갱신·바인딩을 한곳에 모으면 코드 중복도 줄어듭니다.

장점
  • 셰이더를 몇 개 추가해도 View/Proj 업로드는 프레임에 한 번
  • Material·조명 등 새 데이터가 들어올 자리가 명확
  • Shader 클래스가 "컴파일 + 객체"로 얇아져 4단계 분리가 쉬워짐
단점 · 주의
  • 슬롯 번호를 C++와 HLSL 양쪽에서 맞춰야 하는 계약이 하나 늘어남. 공용 헤더(ShaderSlots.h)에 상수로 두고 HLSL에서 #include하는 방식으로 완화
  • 버퍼가 여러 클래스에 흩어지면 "이 프레임에 무엇이 바인딩되어 있나"를 추적하기 어려워짐. RenderDoc 활용 전제
D3

Renderer가 씬·조명·ImGui 패널을 함께 소유

전환 권장
현재 Renderer가 구 오브젝트·메시·조명 배열·앰비언트/스페큘러 설정을 멤버로 갖고, UpdateGUI()에서 ImGui 위젯까지 그립니다.

왜 고민해야 하나. "무엇을 그릴지"(씬)와 "어떻게 그릴지"(렌더러)와 "어떻게 편집할지"(UI)가 한 클래스에 있으면, 씬을 파일에서 불러오거나 UI 없는 빌드를 만들거나 렌더러를 다른 씬에 재사용하는 일이 전부 Renderer 수정이 됩니다. 지금은 오브젝트가 하나라 문제가 없지만, 3단계에서 오브젝트 목록이 들어오면 Renderer가 첫 번째로 비대해지는 클래스가 됩니다.

발전 방향. Scene(GameObject 목록, 조명 목록, 환경 설정)을 만들어 데이터를 옮기고, Renderer는 Render(const Scene&, const Camera&)처럼 입력으로 받아 그리기만 합니다. ImGui 패널은 DebugUI 또는 각 패널 클래스(LightPanel, RenderSettingsPanel)로 분리하고 TestApp이 조립합니다. RasterizerState 등 렌더 설정은 Renderer에 남습니다.

장점
  • 씬 저장/로드(11단계), 씬 여러 개 전환이 Renderer 수정 없이 가능
  • UI 코드가 렌더러를 오염시키지 않아 원래 메모의 "렌더링 구조가 먼저" 원칙을 지킬 수 있음
  • 단위 테스트 가능성: Scene은 D3D 없이도 만들 수 있음
단점 · 주의
  • 파일이 3~4개 늘고 초기에 "왜 이렇게 나눴지"가 부담스러울 수 있음
  • Scene이 렌더 자원(GPU 버퍼)까지 소유하면 다시 결합됨. Scene은 CPU 데이터, GPU 자원은 Renderer 측 캐시(Mesh → GpuMesh)로 두는 경계가 필요
  • 과추상화 위험. Scene 하나, 카메라 하나로 시작하고 인터페이스는 만들지 않는 것이 안전
D4

프레임 시작/끝의 소유권

전환 권장중복 Clear만 적용
현재 AppBase::Run이 Clear → ImGui → Render() → ImGui 드로우 → Present를 직접 나열하고, Renderer::Render가 다시 Clear를 부릅니다. 7절 #2의 중복 Clear는 이 소유권이 정해지지 않아 생긴 증상입니다.

왜 고민해야 하나. 6단계에서 그림자 패스가 들어오면 "렌더타깃을 바꾸고, 클리어하고, 그리고, 다시 백버퍼로 돌아오는" 일이 프레임에 여러 번 일어납니다. 클리어와 타깃 설정이 App 계층에 있으면 그때마다 AppBase를 고쳐야 하고, Renderer가 자기 패스를 스스로 관리할 수 없습니다.

발전 방향. Renderer::BeginFrame()(백버퍼·깊이 바인딩, 클리어) / RenderScene() / EndFrame()(UI 드로우, Present)으로 프레임 경계를 Renderer 안으로 옮기고, AppBase::Run은 Update → renderer.BeginFrame → app.Render → renderer.EndFrame만 부릅니다. 나중에 RenderPass 객체가 생기면 BeginFrame 내부에서 패스를 순회합니다.

장점

유지

왜 고민해야 하나. HLSL 쪽에 #pragma pack_matrix(row_major) 한 줄을 넣으면 C++의 전치 다섯 번이 전부 사라져 "왜 전치하지?"라는 질문이 없어집니다. 그러나 column-major가 셰이더에서 더 빠릅니다. mul(v, M)이 column-major 행렬에 대해 dot 연산 4번으로 컴파일되는 반면 row-major는 mad 연산 체인이 되어 명령 수가 약간 늘어납니다. 대부분의 상용 엔진과 교재(Luna 포함)가 전치 업로드를 쓰는 이유입니다.

발전 방향. 현재 방식을 유지하고, 대신 ConstantBuffer<T> 래퍼나 StoreTransposed(XMFLOAT4X4&, XMMATRIX) 헬퍼로 전치를 한 곳에 모아 실수 여지를 없앱니다. 규약은 부록 B에 문서화되어 있습니다.

장점 (현재 방식)

단점
  • "전치를 두 번 했나 안 했나"류의 실수가 가능. 역전치 행렬 코드가 이미 그 경계에 있음. 헬퍼로 완화

SimpleMath를 주 수학 타입으로 쓸지(연산자 오버로드가 편리) DirectXMath 원형을 쓸지(SIMD 명시적) 하나를 정하는 것도 이때 함께 결정합니다.

장점
  • 이름 충돌 예방, 각 파일의 의존성이 include 목록에 드러남
  • 수학 타입을 하나로 정하면 XMFLOAT3 ↔ Vector3 변환 코드가 사라짐
단점 · 주의
  • 수십 곳에 DirectX:: 접두어가 붙어 코드가 길어짐. .cpp 상단의 using으로 대부분 상쇄
  • PCH를 줄이면 개별 .cpp 컴파일이 약간 느려질 수 있음. 실측으로 판단
적용 결과

pch.h가 48줄에서 30줄이 되었습니다. DirectXTK 5개와 DirectXTex를 지웠고, 이들은 심볼 사용이 0건이었을 뿐 아니라 링크 수준에서도 두 실행 파일이 해당 DLL을 import하지 않던 것으로 확인됐습니다.

수학 타입은 DirectXMath로 확정했습니다. 문서가 남겨 둔 이 선택은 고민할 것이 없었습니다. SimpleMath 타입이 코드에 한 번도 나오지 않고 88줄이 전부 XM*였기 때문입니다. SimpleMath 헤더와 using을 함께 지웠고, 덕분에 문서가 걱정한 XMFLOAT3 ↔ Vector3 변환 문제는 생기지 않았습니다.

전역 using 제거가 이 항목의 본체였습니다. 헤더 6개는 DirectX:: 접두어를 붙이고(55개 심볼), .cpp 6개는 include 아래에 파일 지역 using namespace DirectX;를 한 줄 두었습니다. 구현부 코드는 한 글자도 길어지지 않았습니다. 단점으로 적힌 "수십 곳이 길어짐"은 헤더 선언부에만 해당했습니다.

부수적으로 struct.h가 enum.h와 DirectXMath.h에 의존하면서 include하지 않던 문제가 드러나 헤더들을 자립시켰습니다. 또 stdcpp17과 PCH 설정이 Debug|x64에만 있어 Release가 조용히 C++14로 빌드되고 있던 것을 발견해 네 구성 모두 통일했습니다. 이건 D18과 무관하지만 PCH를 건드리다 보인 문제입니다.

vcpkg 전역 설치 의존

적용 완료 · 2026-09-10
현재 DirectXTK, DirectXTex, ImGui가 vcpkg 전역(classic mode) 설치에서 자동 링크됩니다. 저장소에는 어떤 패키지의 어떤 버전인지 기록이 없습니다.

왜 고민해야 하나. 다른 PC에서 클론하면 빌드가 안 되고, 몇 달 뒤 vcpkg를 업데이트하면 ImGui API 변경으로 컴파일이 깨질 수 있습니다. 로그와 이미지를 꼼꼼히 남기는 프로젝트인데 의존성만 기록이 없는 상태입니다.

발전 방향. 저장소 루트에 vcpkg.json(매니페스트)을 두고 "dependencies": ["directxtk", "directxtex", {"name": "imgui", "features": ["dx11-binding", "win32-binding"]}]와 builtin-baseline을 기록합니다. vcxproj에 VcpkgEnableManifest=true를 켜면 빌드 시 자동 설치됩니다. 10단계 로드맵에 있지만 작업량이 30분 수준이라 0단계에 앞당길 만합니다.

장점
  • 클론 즉시 빌드, 의존성 버전이 Git에 기록됨
  • 나중에 assimp, EnTT, nlohmann-json 등을 추가할 때 한 줄로 끝남
단점 · 주의
  • 첫 빌드 시 패키지를 프로젝트 로컬(vcpkg_installed/)에 다시 빌드해 시간이 걸림. .gitignore에 이미 해당 폴더가 있음
  • baseline 고정은 보안 패치도 막으므로 주기적 갱신이 필요
적용 결과

문서가 제시한 그대로 vcpkg.json과 VcpkgEnableManifest=true를 넣었습니다. builtin-baseline은 작업 시점 vcpkg HEAD인 1f5e0348089e8a9b187f57d42866ebc871e815da입니다. 작업량이 30분 수준이라는 예상도 맞았습니다.

효과가 예상보다 하나 더 있었습니다. 전역 설치를 쓸 때는 링커가 installed\x64-windows\lib\*.lib 와일드카드로 이 PC에 깔린 boost 55개와 glm까지 링커에 넘기고 있었습니다. 매니페스트로 바꾸니 이 프로젝트가 선언한 네 개만 남았습니다.

단점으로 적힌 "첫 빌드에 시간이 걸림"은 이 PC에서는 문제가 되지 않았습니다. vcpkg 바이너리 캐시가 이미 있어 6개 패키지를 130ms만에 복원했습니다. 캐시가 없는 새 PC에서는 여전히 몇 분 걸립니다.

directxtk와 directxtex는 D18에서 include를 다 지워 지금 코드가 쓰지 않지만 매니페스트에는 남겼습니다. 5단계 텍스처 작업에서 바로 필요하고, 그때 버전이 이미 고정되어 있는 편이 낫습니다.

검증은 vcpkg_installed/를 통째로 지우고 빌드해 새 클론을 흉내 내는 방식으로 했습니다. MSBuild가 스스로 vcpkg를 불러 설치하고 빌드까지 마쳤습니다.

RHI 추상화의 형태와 도입 시점

전환 권장 (7단계에서 확정, 3단계부터 준비)
현재 추상화 층이 없습니다. Shader·Renderer·MeshRenderer가 Device*를 통해 ID3D11DeviceContext를 직접 호출하고, ID3D11Buffer* 같은 API 타입이 헤더에 노출되어 있습니다. 최종 목표가 RHI이므로 "어떤 형태로, 언제"가 가장 큰 설계 결정입니다.

왜 고민해야 하나. RHI 형태는 세 갈래이고 한 번 정하면 되돌리기 어렵습니다. (a) 가상 인터페이스: class IBuffer { virtual ... }를 백엔드가 상속. 런타임 백엔드 교체가 되지만 리소스마다 vtable 포인터와 힙 할당이 생기고 호출 코드에 포인터가 노출됩니다. (b) 핸들 + 백엔드 풀: 리소스는 struct BufferHandle { uint32 index, generation; }, 실제 객체는 백엔드의 배열에. bgfx·sokol·WebGPU가 이 방식입니다. (c) 컴파일 타임 선택: using Buffer = D3D11Buffer;를 빌드 구성으로 바꿈. 오버헤드 0이지만 한 빌드에 한 백엔드만 들어가고, 두 백엔드를 나란히 비교하기 어렵습니다. 도입 시점도 문제입니다. 너무 이르면 D3D11 하나만 보고 만든 인터페이스가 D3D12에 맞지 않고, 너무 늦으면 이식할 코드가 많아집니다.

발전 방향. 리소스는 핸들(b), Device와 CommandList만 가상(a)인 혼합형을 권장합니다. 드로우콜당 가상 호출 몇 개는 D3D API 호출 자체의 비용에 묻히고, 리소스가 값 타입 핸들이면 Renderer·Material·Mesh 코드에 API 타입이 전혀 보이지 않아 7단계 인터페이스 추출 때 호출 코드가 바뀌지 않습니다. 시점은 로드맵대로, 3단계부터 이름과 시그니처를 RHI 최종형으로 지으면서 D3D11 전용 클래스로 만들고, 6단계(그림자·RenderPass·CommandList)까지 기능 표면이 갖춰진 뒤 7단계에서 선언과 구현을 분리합니다. 인터페이스는 "D3D12 의미론을 기준으로, D3D11에서 no-op인 것을 허용"합니다(배리어, 펜스, 프레임 인덱스).

장점 (핸들 + 얇은 가상 인터페이스)
  • 호출 코드가 API 타입을 모름. 백엔드 추가·교체가 RHI/ 폴더 안의 일
  • 핸들은 4~8바이트 값이라 복사·비교·직렬화(씬 저장)가 쉬움. 세대 카운터로 해제 후 사용을 assert로 잡음
  • 런타임 --backend= 전환으로 두 백엔드를 나란히 비교 가능. RHI 검증(8단계)의 전제
  • D3D12 개념을 기준으로 잡으면 나중에 Vulkan 백엔드도 같은 인터페이스에 들어감
단점 · 주의
  • 핸들 → 객체 조회가 매 호출마다 배열 인덱싱 한 번. 무시할 비용이지만 코드가 한 줄 늘어남
  • RHI가 두꺼워지는 유혹. 재질·정렬·프레임 그래프는 RHI 위에 두고 RHI는 "API 차이만" 감춰야 두 백엔드 모두에 자연스럽게 맞음
  • D3D11에만 있는 편의(즉시 Map, 자동 밉맵 생성, 암묵적 동기화)를 인터페이스에 넣으면 D3D12 구현이 억지스러워짐. 반대로 D3D12에만 있는 것(다중 큐, 번들)은 RHI 밖에
  • ImGui 공식 백엔드가 API별이라 RHI 위 자체 ImGui 렌더러(약 300줄)가 필요하거나 백엔드별 어댑터를 유지해야 함
  • 너무 일찍 인터페이스를 뽑으면 D3D11 편향이 굳음. 6단계까지는 "RHI 모양의 D3D11 클래스"에 머무는 것이 안전
D22

D3D11 위 PSO 에뮬레이션

전환 권장 (1단계에서)
현재 파이프라인 상태가 세 곳에 흩어져 있습니다. VS/PS는 Shader::ShaderUpdate, RasterizerState는 Renderer::RenderModeUpdate, InputLayout과 Topology는 MeshRenderer::Draw. DepthStencil·Blend는 설정하지 않아 기본값입니다. 상태 조합이 "지금 무엇이 바인딩되어 있나"를 추적해야만 알 수 있습니다.

왜 고민해야 하나. D3D11은 상태를 하나씩 바꾸도록 설계되어 있고, 이것이 "어떤 상태가 남아 있는지 모른다"는 고전적 버그(ImGui가 바꿔 놓은 블렌드 상태로 씬을 그리는 등)의 원인입니다. D3D12는 셰이더·InputLayout·Rasterizer·DepthStencil·Blend·Topology·RT 포맷을 생성 시점에 하나의 불변 객체로 묶어 이 문제를 없앴고, 대신 조합마다 객체를 미리 만들어야 하는 비용을 프로그래머에게 넘겼습니다. RHI가 D3D12를 품으려면 PSO가 인터페이스여야 하고, 그러면 D3D11 백엔드는 PSO를 흉내 내야 합니다. 이것을 1단계에서 바로 하느냐, 나중에 RenderState 클래스에서 PSO로 다시 바꾸느냐의 선택입니다.

발전 방향. 1단계에서 바로 PSO를 만듭니다. PipelineStateDesc(값 타입, 해시 가능)에 D3D12가 요구하는 항목을 전부 넣습니다. D3D11이 쓰지 않는 RTV/DSV 포맷과 샘플 수도 포함합니다. D3D11 구현은 Desc에서 ID3D11RasterizerState·DepthStencilState·BlendState·InputLayout을 만들어 보관하고, Bind에서 7개 Set 호출을 한 번에 합니다. PipelineStateCache가 Desc 해시로 중복 생성을 막고, 같은 RasterizerDesc를 쓰는 PSO들은 하위 캐시로 D3D11 상태 객체를 공유합니다. 드로우 루프는 "PSO 바꿈 → ResourceSet 바꿈 → 버퍼 바꿈 → Draw"만 남습니다.

장점
  • 상태 오염 버그가 구조적으로 사라짐. 모든 드로우가 어떤 상태인지 Desc 하나로 설명됨
  • D3D12 백엔드에서는 Desc를 D3D12_GRAPHICS_PIPELINE_STATE_DESC로 옮기기만 하면 됨. 1단계에서 RT 포맷을 넣어 둔 것이 여기서 갚아짐
  • 상태 전환 비용이 "PSO 포인터 비교 한 번"으로 단순해져 드로우 정렬(4단계)과 상태 캐시(D5)가 자연스럽게 따라옴
  • PSO 수·전환 수가 에디터 통계로 바로 나와 성능 지표가 됨
  • 셰이더 핫리로드가 "해당 PSO 무효화"로 깔끔하게 정의됨
단점 · 주의
  • 조합 폭발: 재질 × 정점 포맷 × 렌더 모드 × 패스(그림자/메인)가 곱해짐. D3D12도 같은 문제라 회피가 아닌 관리(캐시, 지연 생성, 조합 수 통계)가 답
  • D3D11에서 상태 객체는 어차피 따로 만들어지므로 성능 이득은 없음. 이득은 정확성과 이식성이며, 이를 목표로 인정해야 함
  • D3D11에는 PSO에 없는 상태가 남음: 뷰포트, 시저, 스텐실 참조값, 블렌드 팩터. 이것들은 CommandList의 동적 상태로 분류하고 PSO에 넣지 않음(D3D12·Vulkan도 동적 상태)
  • Desc의 해시·비교 코드를 직접 작성해야 하고, float 필드(DepthBias 등)의 비교에 주의
  • 런타임에 처음 만나는 조합에서 PSO 생성 지연(hitch)이 생김. D3D11에서는 수 ms 수준이지만 D3D12는 수십 ms가 될 수 있어, 로딩 시점에 미리 만드는(warm-up) 경로를 인터페이스에 남겨 둠
우선순위 정리

22개 중 지금 당장 손대면 좋은 것은 비용이 낮고 되돌릴 일이 없는 D1(ComPtr 통일), D17(UTF-8), D20(vcpkg 매니페스트), D18(PCH 정리)입니다. 네 가지 모두 2026-09-10에 적용됨 D2·D3·D4·D9는 로드맵 3~4단계의 핵심 작업 그 자체이고, D5·D11·D13·D14·D19는 지금 방식이 옳으니 한계만 기억해 두면 됩니다. D6·D7·D10·D15는 "규모가 커지면"이라는 조건이 붙는 항목으로, 측정 없이 미리 바꾸면 복잡도만 늘어납니다. RHI 목표와 직접 연결된 D21·D22는 각각 7단계와 1단계의 핵심 작업이며, 특히 D22(PSO 에뮬레이션)는 1단계에서 바로 시작해야 이후 모든 단계가 그 위에 쌓입니다.

9.발전 로드맵 — RHI와 PSO를 향해

이 프로젝트의 최종 목표는 RHI(Render Hardware Interface, 그래픽 API를 감추는 추상화 층)와 PSO(Pipeline State Object, 파이프라인 상태를 하나의 불변 객체로 묶는 구조)입니다. 이 목표는 로드맵의 순서보다 각 단계를 어떤 모양으로 만드는가를 바꿉니다. 깊이 버퍼, Material, 텍스처, 그림자는 어차피 필요하지만, 그것들을 "D3D11 호출을 직접 부르는 코드"로 만들면 나중에 RHI로 옮길 때 전부 다시 써야 합니다. 반대로 처음부터 RHI 모양의 래퍼 뒤에서 만들면 RHI 추출은 인터페이스를 뽑아내는 작업으로 끝납니다.

설계 원칙: D3D12 의미론으로 설계하고 D3D11로 구현한다

D3D11은 상태를 하나씩 설정하고 드라이버가 동기화를 알아서 해 주는 API입니다. D3D12는 상태를 PSO로 묶고, 리소스 바인딩을 루트 시그니처로 선언하고, 프레임 동기화와 리소스 상태 전이를 프로그래머가 책임지는 API입니다. RHI는 두 API를 모두 담아야 하므로 더 명시적인 쪽(D3D12)의 개념을 인터페이스로 삼고, D3D11 백엔드에서는 그 개념 중 일부를 no-op으로 구현합니다. 반대 방향(D3D11 개념을 인터페이스로 삼고 D3D12에서 흉내 내기)은 성능도 나쁘고 코드도 뒤틀립니다. 이것이 로드맵 전반에서 "PSO를 먼저 만든다", "바인딩 레이아웃을 선언한다", "프레임 인덱스를 노출한다" 같은 선택이 나오는 이유입니다.

목표 구조

그림 5. 목표 계층. 위 두 층은 그래픽 API 헤더를 include하지 않습니다. RHI가 인터페이스를 정의하고 백엔드가 구현합니다. D3D12 백엔드는 필수가 아니지만, "RHI가 정말 API를 감추고 있는가"를 증명하는 유일한 방법입니다.

PHASE 4

Material과 바인딩 레이아웃

3~4일

D3D12의 루트 시그니처에 해당하는 BindingLayout을 도입합니다. "이 파이프라인은 상수버퍼 b0·b1·b2, 텍스처 t0·t1, 샘플러 s0을 쓴다"를 선언하고, Material은 그 선언에 맞는 ResourceSet(실제 핸들 목록)을 채웁니다. D3D11 백엔드에서는 선언이 슬롯 번호표일 뿐이지만, D3D12에서는 이것이 루트 시그니처와 디스크립터 테이블로 변합니다.

작업
  • BindingLayoutDesc: 슬롯별 {타입(CBV/SRV/Sampler), 셰이더 스테이지, 레지스터 번호}. PSO Desc에 포함
  • ResourceSet: BindingLayout에 대응하는 핸들 배열. CommandList::SetResourceSet(set)이 D3D11에서는 슬롯별 *SSetConstantBuffers/ShaderResources/Samplers로 풀림
  • Material = PipelineHandle + ResourceSet + MaterialConstants(Buffer). specularColor·shininess를 LightBuffer에서 여기로 이동
  • 정점 포맷 열거(VertexPNT 등)와 offsetof 기반 레이아웃 (8절 D9). InputLayout은 PSO 안에서만 생성
  • 셰이더 리플렉션으로 BindingLayout 자동 생성 (수동 선언과 대조해 불일치를 assert)
  • ShaderCompiler: fxc/dxc 사전 컴파일 .cso + Debug 핫리로드 (8절 D12). 핫리로드는 PSO 캐시 무효화로 구현
  • 드로우 정렬: PSO → Material → Mesh 순
D3D12를 미리 고려할 점
  • BindingLayout에 슬롯 수 상한을 둡니다(예: CBV 4, SRV 16, Sampler 8). 루트 시그니처는 64 DWORD 한도가 있습니다
  • "프레임마다 바뀌는 것(PerFrame CB)"과 "재질마다 바뀌는 것(텍스처)"을 다른 ResourceSet으로 나눕니다. D3D12에서 디스크립터 테이블을 갱신 빈도별로 분리하는 관례와 같습니다
  • HLSL은 SM 5.0 문법 안에서 D3D12 dxc로도 컴파일되도록 유지합니다. register(b0, space0) 표기는 D3D11 fxc가 무시하므로 지금부터 써도 됩니다
완료 기준 — 같은 구 메시를 다른 Material로 여러 개 그리고, HLSL 저장 시 PSO가 재생성되어 즉시 반영된다.
PHASE 5

텍스처와 색공간

2~3일

3단계의 Texture 래퍼를 실제 에셋으로 채우고 감마 보정을 잡습니다. RHI 관점에서는 "SRV를 ResourceSet에 넣어 그린다"가 처음 실전에 쓰이는 단계입니다.

작업
  • WIC/DDS 로더 → TextureDesc + 초기 데이터. 밉맵 생성
  • SamplerDesc → Sampler 핸들 (Linear Wrap/Clamp, Anisotropic, Point, ShadowCompare)
  • 백버퍼 RTV를 _SRGB로. ImGui는 별도 UNORM RTV 또는 선형화
  • UV가 있는 프리미티브, 체커보드로 UV 검증, 중간 회색 128 검증
D3D12를 미리 고려할 점
  • 텍스처 초기 데이터 업로드를 UploadTexture(handle, data) 함수로 감춥니다. D3D11은 UpdateSubresource, D3D12는 업로드 힙 + CopyTextureRegion + 배리어로 갈립니다
완료 기준 — 텍스처 큐브·구가 올바른 감마로 표시되고 밉맵이 원거리에서 반짝임 없이 보인다.
PHASE 6

그림자 · RenderPass · CommandList

4~6일

RHI의 마지막 조각 두 개를 만듭니다. RenderPass는 "어느 타깃에 어떤 클리어로 그리기 시작하고 끝내는가"를, CommandList는 "GPU 명령을 어디에 기록하는가"를 추상화합니다. 그림자 매핑은 두 조각을 처음으로 실전에 쓰는 사례이고, 동시에 첫 렌더-투-텍스처입니다.

작업
  • RenderPassDesc{컬러 타깃 배열 + Load(Clear/Load/DontCare)/Store, 깊이 타깃 + Load/Store, 뷰포트}. CommandList::BeginRenderPass(desc) / EndRenderPass(). D3D11은 OMSetRenderTargets + Clear*View + RSSetViewports
  • CommandList: ImmediateContext 래퍼. SetPipelineState, SetResourceSet, SetVertexBuffer, SetIndexBuffer, DrawIndexed, Barrier(no-op), CopyBuffer. Renderer의 모든 GPU 호출이 이것을 통과
  • 프레임 구조를 BeginFrame → [ShadowPass → MainPass → UIPass] → EndFrame(Present)로 고정 (8절 D4)
  • Directional Shadow Map: 깊이 전용 Texture(2048², R32_TYPELESS, DSV+SRV), 깊이 전용 PSO(PS 없음, DepthBias), 광원 ViewProj, PCF 3×3, ShadowCompare 샘플러
  • 노멀 매핑(탄젠트 + TBN), 조명 8개 전부 ImGui 편집
D3D12를 미리 고려할 점
  • 그림자 맵은 "DSV로 쓰고 → SRV로 읽는" 상태 전이가 있는 첫 리소스입니다. Barrier(texture, DepthWrite → ShaderRead) 호출을 지금부터 넣습니다. D3D11에서는 빈 함수지만 D3D12로 갈 때 어디에 배리어가 필요한지 이미 코드에 적혀 있게 됩니다
  • 같은 텍스처를 DSV와 SRV로 동시에 바인딩하면 D3D11은 경고 후 SRV를 unbind합니다. RenderPass 종료 시 SRV 슬롯을 정리하는 로직을 CommandList에 둡니다
완료 기준 — 바닥에 그림자가 떨어지고 광원을 움직이면 따라오며, Renderer 코드가 ID3D11DeviceContext를 직접 참조하지 않는다.
PHASE 7

RHI 인터페이스 추출

핵심 · 4~6일

1·3·4·6단계에서 만든 조각(PipelineState, Buffer/Texture/Shader/Sampler, BindingLayout/ResourceSet, RenderPass/CommandList)은 이미 RHI의 모양을 하고 있지만 D3D11 클래스입니다. 이 단계에서 API 중립 선언(Desc 구조체, 핸들, 인터페이스)과 D3D11 구현을 물리적으로 분리합니다. 기능 추가는 없습니다. 분리 후 화면이 이전과 픽셀 단위로 같아야 합니다.

작업
  • 폴더 분리: RHI/(선언만, D3D 헤더 include 금지) / RHI/D3D11/(구현)
  • 공용 열거형·Desc 정의: Format(DXGI_FORMAT을 감춤), BufferUsage, TextureBindFlags, CompareFunc, CullMode, PrimitiveTopology 등. D3D11/D3D12 매핑 테이블은 각 백엔드에
  • 핸들 타입: BufferHandle, TextureHandle, SamplerHandle, ShaderHandle, PipelineHandle, BindingLayoutHandle. 세대(generation) 카운터로 해제 후 사용 검출
  • RHI::Device 인터페이스: Create*/Destroy*, BeginFrame/EndFrame, GetCommandList, Present, Resize. 백엔드 선택은 팩토리 CreateDevice(Backend::D3D11, hwnd, desc)
  • RHI::CommandList 인터페이스: 6단계 메서드 집합 그대로
  • D3D11 백엔드가 인터페이스를 구현. 리소스 풀(vector<D3D11Buffer> + free list)로 핸들 → 객체 변환
  • ImGui 백엔드: imgui_impl_dx11은 D3D11 전용이므로 RHI 위에 자체 ImGui 렌더러를 쓰거나(권장, 소형), 백엔드별로 ImGui impl을 갈아 끼우는 얇은 어댑터
  • 디버그 이름(SetPrivateData(WKPDID_D3DDebugObjectName))을 Desc의 debugName으로 통일해 RenderDoc에서 읽기 쉽게
설계 결정 (8절 D21 상세)
  • 가상 인터페이스 vs 핸들+백엔드 함수 테이블 vs 컴파일 타임 선택. 권장은 "Device/CommandList만 가상, 리소스는 핸들". 드로우콜당 가상 호출 몇 개는 D3D11 API 호출 비용 대비 무시할 수준이고, 리소스가 핸들이면 호출 코드에 포인터가 안 보임
  • RHI는 얇게. 재질 시스템, 드로우 정렬, 프레임 그래프는 RHI 위 Renderer의 일. RHI는 "API 차이만" 감춥니다. 두꺼운 RHI는 두 백엔드 어디에도 잘 맞지 않게 됩니다
  • 셰이더 바이트코드는 백엔드별(DXBC/DXIL). ShaderCompiler가 Backend에 따라 fxc/dxc를 고르고, 캐시 키에 백엔드를 포함
완료 기준 — RHI/ 밖에서 d3d11.h·dxgi.h include가 0건, Renderer·Material·Mesh 코드가 변경 없이 컴파일되며, 이전 단계와 같은 화면이 나온다.
PHASE 8

D3D12 백엔드 (RHI 검증)

선택 · 2~3주

RHI가 정말 API를 감추고 있는지는 두 번째 백엔드를 붙여 봐야 압니다. D3D12는 D3D11과 셰이더 언어·좌표계·DXGI를 공유해 가장 비용이 낮은 두 번째 백엔드이고, PSO·루트 시그니처·배리어·펜스라는 목표 개념이 네이티브인 API입니다. 이 단계를 건너뛰어도 로드맵은 이어지지만, 그 경우 RHI는 "D3D11 래퍼"에 머물 위험이 있습니다.

작업 (최소 구성)
  • Device·CommandQueue·SwapChain(FLIP, 백버퍼 3장, 백버퍼별 RTV)
  • 프레임별 CommandAllocator + 단일 GraphicsCommandList, 펜스로 프레임 N-2 완료 대기
  • 디스크립터 힙: RTV·DSV(CPU 전용), CBV/SRV/UAV(셰이더 가시, 링 할당), Sampler. 3단계의 프레임 인덱스가 여기서 링 할당의 기준이 됨
  • BindingLayout → RootSignature 생성 (CBV는 루트 디스크립터, SRV/Sampler는 테이블)
  • PipelineStateDesc → D3D12_GRAPHICS_PIPELINE_STATE_DESC. 1단계에서 RTV/DSV 포맷을 넣어 둔 것이 여기서 필요
  • Buffer: Default 힙 + 업로드 힙 스테이징. Dynamic은 프레임별 업로드 링버퍼에서 서브할당
  • Texture: 업로드 힙 → CopyTextureRegion → 배리어. 밉맵은 컴퓨트 셰이더로 생성(D3D12에 GenerateMips 없음)
  • Barrier: 6단계에서 no-op으로 넣어 둔 호출을 ResourceBarrier로 구현. 리소스마다 현재 상태 추적
  • ShaderCompiler: dxc로 DXIL(SM 6.0). HLSL 소스는 그대로
이 단계가 드러내는 RHI 결함들
  • D3D11에서 편하게 쓰던 "Map 후 즉시 사용"이 D3D12에서는 프레임 지연을 고려해야 함. 3단계 프레임 인덱스 설계가 맞았는지 검증됨
  • "같은 텍스처를 읽고 쓰는" 코드가 배리어 누락으로 즉시 깨짐. Debug Layer + GPU 기반 검증(GBV)을 켜고 진행
  • ImGui: imgui_impl_dx12는 디스크립터 힙 하나를 요구. 7단계에서 자체 ImGui 렌더러를 택했다면 그대로 동작
  • D3D12 특유의 개념(스플릿 배리어, 다중 큐, 번들, 메시 셰이더)은 RHI에 넣지 않습니다. D3D11에서 표현할 수 없는 개념은 RHI 밖에 둡니다
완료 기준 — 실행 인자 --backend=d3d12로 같은 씬(그림자 포함)이 픽셀 단위로 같게 나오고, Debug Layer·GBV 경고가 0건이다.

  7. RenderPass + CommandList + Directional Shadow Map

B. 좌표계와 행렬 규약 정리

좌표계
왼손 좌표계(LH). XMMatrixLookAtLH, XMMatrixPerspectiveFovLH 사용. +Z가 화면 안쪽.
앞면 판정
시계 방향(CW) = 앞면. FrontCounterClockwise = false.
벡터 규약
행벡터. CPU v × M, HLSL mul(v, M). 월드행렬 = S × R × T.
상수버퍼 업로드
모든 행렬을 XMMatrixTranspose해서 올림 (HLSL 기본 column-major 대응). 대안: HLSL에 #pragma pack_matrix(row_major)를 선언하면 전치를 없앨 수 있음.
깊이 범위
0(near) ~ 1(far). 뷰포트 MinDepth/MaxDepth. 2026-09-10부터 D24_UNORM_S8_UINT 깊이 버퍼 사용, Clear 값 1.0.
NDC
x, y ∈ [-1, 1], y는 위가 +. 뷰포트 변환에서 y 반전.
