1. 왜 Gerstner 파도인가

1-1. 풀려는 문제

요청은 "플레이어가 멈춰 있는 배 위에서 전투를 하고 배경으로 잔잔한 바다가 보이는 장면"이었습니다(rendering-analysis 20.29, 구현 기록 머리말). 바다는 배경이라 CPU 가 파도 높이를 읽을 일이 없고(부력 없음), 수평선까지 보여야 하며, TAA·모션 블러와 맞으려면 속도 버퍼에 제대로 된 값을 써야 합니다. 사용자와 정한 것은 "Gerstner 만, 배는 고정, 잔잔한 배경 바다" 세 가지입니다(계획 3.2).

2. 원리

2-1. 한 파도의 식

평면 위 원래 위치를 x₀ = (x, z), 파도 i 의 진행 방향(xz 단위 벡터)을 Dᵢ, 파수를 kᵢ = 2π / Lᵢ, 진폭을 Aᵢ, 경사를 sᵢ, 위상을 φᵢ 라고 합니다. Shaders/Ocean.hlsli 의 GerstnerPosition 이 계산하는 식은 이것입니다(Y 가 위).

θᵢ   = kᵢ (Dᵢ · x₀) − φᵢ
P.xz = x₀ + Σ (sᵢ / kᵢ) Dᵢ cos θᵢ     // 수평 변위
P.y  =      Σ  Aᵢ          sin θᵢ     // 높이

φᵢ 가 시간에 따라 커지면 같은 θ 를 갖는 자리가 Dᵢ 쪽으로 옮겨 가므로 파도는 Dᵢ 방향으로 나아갑니다. 평면의 점 하나만 보면 수평으로 반지름 sᵢ/kᵢ, 수직으로 반지름 Aᵢ 인 타원을 돕니다. 마루(sin θ = 1)에서는 cos θ 가 0 근처를 지나며 부호가 바뀌어 주변 점이 마루 쪽으로 모이고, 골에서는 흩어집니다. 그래서 마루가 뾰족하고 골이 넓어집니다.

궤도가 원이 되는 것은 sᵢ/kᵢ = Aᵢ, 곧 sᵢ = kᵢAᵢ 일 때이고, 이것이 고전적인 트로코이드(trochoid) 파도입니다. 우리 엔진은 sᵢ 와 Aᵢ 를 따로 정합니다. 기본값에서는 sᵢ = 0.0667, kᵢAᵢ = 0.0491 이라 수평 반지름이 수직의 약 1.36 배인 가로로 긴 타원입니다 계산값. 계획 2장은 "점을 원을 그리며 움직인다"고 설명하지만 코드의 궤도는 타원입니다. 계획도 "sᵢ 는 수평으로 얼마나 모이는지를 따로 정하는 값이라 두 값을 독립으로 둡니다"라고 적었습니다(계획 2장).

2-2. GPU Gems 의 Q 와 꼬임 조건

GPU Gems 1권 1장(Finch, 참고 문서)의 식 기준으로, 수평 변위는 Qᵢ Aᵢ Dᵢ cos(…) 입니다. 우리 식의 sᵢ/kᵢ 와 맞추면 Qᵢ = sᵢ / (kᵢAᵢ) 입니다. Gems 는 Qᵢ = Q / (kᵢ Aᵢ × 파도 수) 로 나눠 Σ Qᵢ kᵢ Aᵢ = Q ≤ 1 을 지키는데, 이것은 우리 식의 Σ sᵢ ≤ 1 과 같은 조건입니다. 높이를 sin, 수평을 cos 로 두는 짝도 Gems 와 같고, 위상 부호만 다릅니다(GPU Gems 1권 1장의 식 기준으로 Gems 는 + φt, 우리는 − φ).

조건이 나오는 이유는 수평 방향의 늘어남입니다. 파도 하나를 x 방향으로 보면 ∂P.x/∂x₀ = 1 − s sin θ 이고, 마루(sin θ = 1)에서 1 − s 입니다. s > 1 이면 이 값이 음수가 되어 이웃 점의 순서가 뒤집히고 표면이 고리로 꼬입니다. 여러 파도의 마루가 같은 방향으로 겹치는 최악의 경우가 1 − Σ sᵢ 이므로 Σ sᵢ ≤ 1 이면 안전합니다. Ocean::BuildWaves 는 steepness 를 [0, 1] 로 자르고 파도 수로 똑같이 나눕니다.

물리적인 가파름은 kA 입니다. 기본값은 모든 파도가 kA ≈ 0.049 로 같고, 파고/파장(2A/L = kA/π)으로 약 1.6 % 입니다 계산값. 깊은 물의 파도는 이 비가 약 1/7(Stokes 한계, H/L ≈ 0.142)에 이르면 부서지므로(참고 문서) 기본값은 잔잔한 바다 쪽입니다.

2-3. 편미분과 노멀

노멀은 변위된 표면을 원래 x·z 로 편미분한 두 벡터의 외적입니다. GerstnerSampleFiltered 가 파도마다 더하는 항은 이렇습니다.

∂P/∂x = ( 1 − Σ sᵢ Dᵢx² sin θᵢ,   Σ kᵢAᵢ Dᵢx cos θᵢ,   − Σ sᵢ Dᵢx Dᵢz sin θᵢ )
∂P/∂z = ( − Σ sᵢ Dᵢx Dᵢz sin θᵢ,  Σ kᵢAᵢ Dᵢz cos θᵢ,   1 − Σ sᵢ Dᵢz² sin θᵢ )
N     = normalize( cross(∂P/∂z, ∂P/∂x) )    // 평평할 때 (0, 1, 0)

외적 순서는 Y 가 위일 때 평평한 면이 (0, 1, 0) 이 나오는 순서이고(cross(ẑ, x̂) = ŷ 는 손 방향과 상관없는 대수 결과입니다), check_gerstner_normals.py 가 유한 차분으로 확인합니다(10장 E1). 탄젠트는 메시 탄젠트(UV u 방향)를 월드로 옮긴 xz 성분 (t.x, t.z)로 ∂P/∂x · t.x + ∂P/∂z · t.z 를 만들어 정규화합니다(OceanSurfaceTangent). 바다 오브젝트를 요로 돌려도 노멀 맵 방향이 UV 와 맞게 하려는 선택이고, 계획의 T = ∂P/∂x 에서 바뀐 점입니다(기록 2장).

2-4. 깊은 물의 분산 관계

파도의 속도는 마음대로 정하지 않고 깊은 물의 분산 관계 ω = √(g k) 를 씁니다(Ocean::BuildWaves, g = 9.81). 위상 속도 c = ω/k = √(g L / 2π) 라 긴 파도가 빠릅니다. 파장마다 속도가 달라 파도들이 서로 미끄러지며 겹치므로, 같은 무늬가 그대로 흘러가는 느낌이 줄어듭니다. speed 는 ω 에 곱하는 배율이고 0 이면 파도가 멈춥니다.

5-2. 위상을 CPU 가 double 로 감는 이유

셰이더는 ω·t 를 곱하지 않습니다. CPU 가 φ = fmod(ω·t + φ₀, 2π) 를 double 로 구해 [0, 2π) 범위의 float 로 넘깁니다. 셰이더가 보는 각 k(D·x₀) − φ 는 k(D·x₀) 의 크기만큼만 커지므로 float 정밀도가 위치 쪽 몫에만 걸립니다.

5-3. 지난 위상과 속도 버퍼

속도 버퍼에는 정점의 이번 위치와 지난 프레임 위치가 모두 필요합니다(속도 버퍼 학습). 바다는 지난 위치를 "지난 World 로 옮긴 평면 정점 + 지난 위상의 파도"로 다시 계산합니다(VS_Ocean 의 basePrev, GerstnerPosition(…, OCEAN_PHASE_PREV)). 지난 위상의 시간은 지난 프레임에 실제로 쓴 시간을 저장해 둔 m_oceanPrevTime 입니다(time − dt 로 추정하지 않음). 다음 경우에는 지난 = 이번(속도 0)으로 둡니다.

  • 처음 프레임, 바다가 없던 프레임 뒤(m_oceanHasPrev 거짓), Renderer::ResetTemporalHistory 뒤
  • 바다 오브젝트가 바뀐 프레임(m_oceanPrevObject 가 다름)
  • --ocean-time=초 로 시간을 고정했을 때(RenderSettings::oceanTimeOverride, AppBase 가 읽음). 이때 바다의 속도는 카메라 움직임만 남으므로 디버그 뷰 17(속도 오차)이 바다 위에서 검정이어야 합니다

일시정지에서는 totalTime 이 멈추므로 따로 처리하지 않아도 속도가 0 이 됩니다.

6. 셰이더 — 정점 변위, 픽셀 노멀, 대역 제한

6-1. VS_Ocean: 월드 xz 에서 계산

평면 정점을 먼저 world 로 옮긴 뒤 월드 xz 에서 파도를 더합니다. 바다 오브젝트를 옮기거나 요로 돌려도 파도 방향은 월드 기준으로 남고, 노멀을 worldInvTranspose 로 바꿀 필요가 없습니다. 대신 피치·롤은 지원하지 않습니다(파도는 늘 월드 Y 로 솟음). 출력은 공용 VSOutput 뒤에 TEXCOORD4 하나(변위 전 xz, 월드 메시 탄젠트의 xz)를 붙인 OceanVSOutput 이라 다른 픽셀 셰이더의 입력 시그니처는 그대로입니다.

6-2. 픽셀에서 노멀을 다시 계산 (3단계)

정점 노멀을 보간하면 격자 간격보다 짧은 파도의 기울기가 정점 사이에서 사라지거나 계단이 됩니다. OceanPixelInput 은 픽셀마다 변위 전 xz 로 GerstnerSampleFiltered 를 다시 불러 노멀·탄젠트만 바꾼 VSOutput 을 만듭니다. OceanPixelShader.hlsl 은 BasicPixelShader.hlsl 을, OceanGBufferPixelShader.hlsl 은 GBufferPixelShader.hlsl 을 통째로 include 하고 PS_Main·PS_GBuffer 를 함수로 부릅니다. 바다 전용 셰이딩 코드가 없고, 바다도 일반 불투명 표면과 같은 포워드·G-buffer 셰이더 본문을 탑니다(디퍼드 G-buffer 학습). ddx·ddy 를 쓰므로 분기 밖에서 불러야 합니다.

6-3. 대역 제한: 픽셀보다 짧은 파도의 기울기를 뺌

2단계 화면에서 먼 바다(약 80~300 m)에 점이 반짝였습니다. 실험해 보니 격자를 촘촘하게 해도 점은 그대로였고, 짧은 파도를 빼면 줄었습니다(기록 9.3). 원인은 픽셀 크기였습니다. 멀리서는 픽셀 하나가 파장 여러 개를 덮는데, 픽셀 중심 한 점에서 노멀을 뽑으면 그 점이 마루 비탈에 걸리느냐에 따라 해 반사가 켜졌다 꺼졌다 합니다. 신호 처리로 말하면 나이퀴스트(픽셀당 0.5 주기)를 넘는 신호가 겹쳐 보이는 에일리어싱입니다.

// Ocean.hlsli 의 OceanBandLimit. dx0·dy0 = ddx·ddy(변위 전 xz)
cyclesPerPixel = kᵢ · length(float2(dot(dx0, Dᵢ), dot(dy0, Dᵢ))) / 2π
band           = 1 − smoothstep(0.1, 0.25, cyclesPerPixel)
// 노멀·편미분의 kᵢAᵢ 와 sᵢ 에만 band 를 곱함. 위치에는 곱하지 않음 (PS 는 위치를 쓰지 않음)

파도 방향으로 잰 주기 수라, 비스듬히 볼 때 깊이 방향으로만 성긴 픽셀은 그 방향으로 진행하는 파도만 지웁니다. 정점 셰이더는 dx0·dy0 = 0 으로 불러 band = 1 입니다(GerstnerSample).

측정은 OceanHorizon.json 에서 TAA 를 끄고 했습니다. 깜빡임 = --ocean-time 10.0 과 10.0167 두 장의 휘도 차가 16 이상인 픽셀 수(수평선 아래 전체), 외딴 점 = 수평선 아래 띠(240~330 행)에서 주변 5×5 중앙값과 12 이상 다른 픽셀 수입니다. 확인함 (2026-11-23) 기록 9.3

7. 넓은 평면, 거리 감쇠, 수평선

7-1. 가운데 촘촘·가장자리 성긴 평면

수평선까지 보이려면 평면이 커야 하지만, 균일 격자로 10 km 를 배 주변 간격에 맞추면 정점이 너무 많아집니다. Mesh::CreatePlane 의 spacingGrowth(g)는 정점 번호로 정한 t ∈ [−1, 1] 을 휘어서 가운데를 촘촘하게 둡니다.

x = half · sign(t) · ((1 − g)|t| + g|t|⁷)     // 기울기: 가운데 (1 − g), 끝 (1 + 6g)

간격 비는 (1 + 6g)/(1 − g) 이고 g = 0.93 이면 94 배입니다 계산값. g = 0 이면 예전 균일 식을 그대로 타서 비트 단위로 같은 정점이 나옵니다. 씬 파일에서는 평면 메시의 params[2] 가 g 입니다(MeshSource::Plane, MeshSource::CreatePrimitive). 에디터에 메시 출처 편집 UI 가 없어 JSON 으로만 넣습니다. UV 는 g 와 상관없이 정점 번호에 대해 균일합니다.

7-2. 거리 감쇠

OceanFade 는 바다 원점에서의 거리로 진폭과 경사를 fadeStart~fadeEnd(기본 80~300 m)에서 1 → 0 으로 줄입니다(1 − smoothstep). 가장자리의 성긴 격자가 짧은 파도를 담지 못해 생기는 계단과 물결무늬를 막고, 먼 바다는 평평한 거울처럼 하늘을 비춥니다. 기준점이 바다 원점이어서 이번·지난 위치에 같은 배율이 곱해지고 속도가 틀어지지 않습니다. 노멀은 이 배율의 기울기를 무시하는데, 감쇠 구간(220 m)이 파장(최대 32 m)보다 훨씬 넓어 차이가 작다고 보았습니다(Ocean.hlsli 주석). fadeEnd ≤ fadeStart 면 감쇠하지 않습니다.

7-3. 먼 평면과 씬 저장

OceanHorizon.json 은 한 변 10 km 라 카메라 far 를 5000 m 로 둡니다. 에디터 씬 카메라의 far 를 둘 곳이 없어서 SceneSerializer 가 camera.farZ 를 저장·복원하게 했습니다. 기본값 kDefaultSceneCameraFar(1000 m)와 같으면 쓰지 않아 기존 씬 파일은 저장만으로 바뀌지 않고, 키가 없으면 1000 으로 돌아갑니다. 기록에 따르면 바다는 far 에서 잘리고 갑판 8 m 에서 그 자리는 수평선보다 약 0.09° 아래입니다(기록 7장). 화면에서도 틈이 보이지 않았습니다(수평선 아래 첫 행 밝기 164, 하늘 194) 확인함 (2026-11-23) 기록 9.2.

10. 실험

E1 은 Python 스크립트, E2·E3 은 에디터 실행 인자, E4·E6 은 Inspector(E4 의 꼬임 확인은 코드 수정), E5 는 셰이더 수정으로 합니다. 에디터를 띄울 때 공통 인자는 --project=…/SherlockTestScenes.sherlock --scene=Ocean.json 입니다.

E1. 노멀 식 검사 확인함 (2026-11-23)

python check_gerstner_normals.py 는 BuildWaves 를 옮겨 해석 노멀과 유한 차분 노멀을 비교하고, 평평한 면에서 cross(dP/dz, dP/dx) = (0, 1, 0) 인지 봅니다. 기록에서 각도 차 0.00001° 미만으로 통과했습니다(기록 9.1). --steep 1 은 마루에서 야코비안이 0 에 가까워지는 최악의 경우입니다.

E2. 시간 고정 + 카메라 회전 확인함 (2026-11-23)

--ocean-time=10 --debug-view=17 --cam-orbit=0.5 로 찍으면 바다의 움직임이 없으므로 속도 오차 뷰의 바다 영역이 0 이어야 합니다. 기록에서 Ocean.json 은 두 백엔드 모두 바다 영역 0 픽셀(기록 9.1), OceanHorizon.json 은 0/200,750 픽셀이었습니다(기록 9.2). 감쇠가 이번·지난 위치에 같게 걸린다는 확인이기도 합니다.

E3. 백엔드와 경로 비교 확인함 (2026-11-23)

--backend=d3d11 과 d3d12, 디퍼드와 포워드(--deferred=0, App/AppBase.cpp)를 바꿔 같은 프레임을 찍습니다. D3D11 = D3D12 는 0 픽셀 차였습니다. 디퍼드 대 포워드 최대 차는 1단계에서 5(기록 9.1), 3단계 뒤 4(기록 9.3)였고 G-buffer 양자화 때문입니다.

E4. 경사를 1 로 예상

Inspector 에서 steepness 를 1 로 올리고 와이어프레임으로 봅니다. 정점이 마루로 몰리고 마루가 뾰족해지지만 뒤집히지는 않습니다(2-2 의 조건). 기록은 0.4·1 에서 뒤집힘이 없다고 남겼습니다 확인함 (2026-11-23) 기록 9.1. 코드를 잠깐 고쳐 자르기를 [0, 2] 로 풀면 마루에 고리 모양 꼬임이 보일 것입니다. 확인한 뒤 되돌립니다.

E5. 대역 제한 끄기 예상

OceanBandLimit 이 1 을 돌려주게 잠깐 바꾸고 OceanHorizon.json 을 TAA 없이 봅니다. 6-3 표의 "대역 제한 끔" 줄처럼 먼 바다(80~300 m)에 점이 늘어나고 두 프레임 사이 깜빡임이 149 픽셀 수준이 될 것입니다. 확인한 뒤 되돌립니다.

E6. 감쇠 거리 바꾸기 예상

Inspector 에서 fadeEnd 를 fadeStart 이하로 두면 감쇠가 꺼집니다. OceanHorizon.json 에서 300 m 바깥의 성긴 격자(6 m 이상 간격)에 짧은 파도가 계단과 물결무늬로 보일 것입니다.

에디터 피킹이 파도와 어긋남변위 전 평면으로 맞춤진폭 0.25 m 수준이라 무시
가까이서 표면이 너무 매끈함디테일 노멀 맵 없음범위 밖

범위 밖으로 남긴 것: FFT 스펙트럼, 거품·물보라, 굴절·투명, 전용 물 셰이딩(심도 색·SSS), 부력, 테셀레이션, 디테일 노멀 맵(기록 10장). 1080p GPU 시간과 시간이 흐를 때 속도의 방향·크기는 기록에서도 확인하지 못한 항목입니다(기록 9.6).
