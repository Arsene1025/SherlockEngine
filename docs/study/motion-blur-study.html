1. 셔터와 모션 블러

1-1. 카메라는 시간 구간을 찍는다

필름이나 센서는 셔터가 열려 있는 동안 들어온 빛을 모두 더합니다. 그 사이에 물체가 움직이면 한 점의 빛이 여러 픽셀에 나뉘어 쌓이고, 움직인 방향으로 늘어난 줄무늬가 남습니다. 영화 카메라는 셔터 각도로 이 시간을 정합니다. 180° 셔터는 프레임 시간의 절반 동안 열려 있다는 뜻이고, 24 fps 라면 1/48 초입니다.

래스터화는 한 순간의 장면을 찍습니다. 셔터 시간이 0 인 카메라와 같아서 빠른 물체가 프레임마다 다른 자리에 선명하게 찍히고, 눈은 그 사이를 이어 붙이지 못해 끊겨 보입니다(스트로빙). 모션 블러는 이 사이를 번짐으로 채웁니다.

1-2. 왜 흉내 내는가

정확한 방법은 셔터 시간 안의 여러 시각을 따로 그려 평균하는 것입니다(누적 버퍼, 시간 슈퍼샘플링). 8 시각이면 장면을 8 번 그려야 해서 실시간에는 쓰기 어렵습니다. 게임은 한 번 그린 화면과 픽셀마다 "한 프레임에 얼마나 움직였나"를 담은 속도 버퍼만 가지고, 그 방향으로 색을 끌어다 섞어 번짐을 만듭니다. 비용은 픽셀마다 샘플 몇십 개로 고정됩니다.

누적 (시간 슈퍼샘플링)셔터 구간 안 N 시각을 다 그려 평균장면 N 번실시간에 비쌈

속도 버퍼는 TAA 도 같이 씁니다. 한 번 만든 속도 RT 를 두 효과가 나눠 쓰는 것이 이 방법이 흔히 쓰이는 이유 중 하나입니다. 속도 버퍼가 어떻게 만들어지는지는 속도 버퍼 학습에 있습니다. 여기서는 Shaders/Temporal.hlsli 의 LoadVelocityPixels 가 UV 단위 속도에 화면 크기를 곱해 픽셀 단위로 바꿔 준다는 것만 알면 됩니다.

2. 재구성 필터의 원리

2-1. 가운데 속도만 쓰면 생기는 일

가장 단순한 블러는 이 픽셀의 속도 vc 방향으로 샘플을 늘어놓고 평균하는 것입니다. 이러면 두 가지가 틀립니다. 움직이는 전경 픽셀이 뒤의 정지한 배경까지 같은 무게로 섞어 배경이 앞으로 새어 들어오고, 정지한 배경 픽셀은 속도가 0 이라 옆을 지나가는 빠른 물체의 꼬리를 받지 못합니다. McGuire 2012("A Reconstruction Filter for Plausible Motion Blur")는 샘플마다 깊이와 그 샘플 자신의 속도를 보고 "이 샘플의 색이 가운데 픽셀까지 번져 오는가"를 따지는 가중치로 앞의 문제를 풉니다(계획 2.3). 뒤의 문제는 원 논문에서 타일 최대 속도 패스(TileMax·NeighborMax)가 맡는데, 우리 엔진에는 이 패스가 없습니다(2-4).

2-2. 샘플 배치와 IGN 지터

PS_MotionBlur 는 샘플 count(4~32, 기본 12)개를 t = (i + 0.5 + jitter) / count − 0.5 자리에 둡니다. t 는 −0.5 ~ 0.5 라 샘플은 픽셀 양쪽으로 길이의 절반씩 퍼지고, 자리는 floor(position.xy + t · vc) 를 화면 안으로 자른 픽셀입니다. 샘플은 점 읽기(Load)라 필터링이 없습니다.

샘플 간격이 1 픽셀보다 넓으면 번진 자리에 같은 간격의 띠가 보입니다. jitter 는 InterleavedGradientNoise(position.xy) − 0.5 로, 픽셀마다 샘플 열 전체를 한 칸 안에서 조금씩 밀어 띠를 잡음으로 바꿉니다. 이 노이즈(Jimenez 2014)는 픽셀 좌표만 쓰고 프레임 번호를 쓰지 않습니다. Shaders/MotionBlurPixelShader.hlsl 의 PS_MotionBlur 지터 주석은 이것을 "스크린샷 결정적"이라고 적었고, Shaders/Temporal.hlsli 의 InterleavedGradientNoise 주석은 "프레임과 무관해서 스크린샷이 실행마다 같음"이라고 적었습니다. 무늬가 프레임마다 같으므로 시간에 따라 평균되어 사라지지는 않습니다.

2-3. 샘플별 가중치

가운데 픽셀의 깊이를 zc, 샘플의 깊이를 zs, 가운데에서 샘플까지 거리를 d = |t| · |vc|, 샘플 자신의 번지는 길이를 |vs| 라 하면 가중치는 다음 세 항의 합입니다.

w = SoftFront(zs, zc) · Cone(d, |vs|)            // 샘플이 앞: 샘플이 자기 속도로 여기까지 번져 오는가
  + SoftFront(zc, zs) · Cone(d, |vc|)            // 가운데가 앞: 가운데가 번지며 뒤를 드러내는가
  + Cylinder(d, |vs|) · Cylinder(d, |vc|) · 2    // 같은 물체처럼 둘 다 움직임
함수식뜻
SoftFront(za, zb)saturate(1 − (za − zb) / (0.02 + 0.02 · min(za, zb)))za 가 zb 보다 앞이면 1, 뒤면 0. 경계 폭이 거리에 비례합니다(먼 곳은 깊이 정밀도가 낮음). 깊이는 LinearViewDepth 로 푼 카메라 앞 거리입니다
Cone(d, v)saturate(1 − d / v)길이 v 로 번지는 점이 거리 d 에 주는 몫. 멀수록 줄어 끝에서 0
Cylinder(d, v)1 − smoothstep(0.95v, 1.05v, d)길이 안이면 1, 끝에서 부드럽게 0

가운데 픽셀도 가중치 1 / |vc| 로 더하고 마지막에 가중치 합으로 나눕니다. 길게 번지는 픽셀일수록 자기 색의 비중이 줄어듭니다. 그림 1의 A 는 움직이는 전경의 실루엣 가장자리 픽셀에서 이 식이 내는 값입니다. 전경 샘플은 세 항이 다 살아 3.1~3.9 를 받고, 뒤의 배경 샘플은 둘째 항(가운데의 원뿔)만 남아 0.5~1.0 을 받습니다. 결과는 전경 82%, 배경 18% 입니다 계산값. 전경이 반투명하게 번지며 뒤 배경을 조금 드러내는 모양입니다.

2-4. 실루엣 밖으로는 번지지 않는다

PS_MotionBlur 는 |vc| < 0.5 픽셀이면 가운데 색을 그대로 냅니다. 정지 화면에서 켠 것과 끈 것이 비트 단위로 같게 하려는 분기입니다(셰이더 주석). 또 샘플은 가운데 픽셀의 속도 선 위에만 놓입니다. 그래서 카메라가 멈춰 있을 때 빠르게 지나가는 물체 옆의 정지한 배경 픽셀은 그 물체를 샘플할 기회가 없고(그림 1 B), 번짐은 물체의 실루엣 안에서만 생깁니다. 첫째 항(SoftFront(zs, zc) · Cone(d, |vs|))이 "앞의 샘플이 배경 위로 번져 오는" 경우를 다루지만, 그 샘플이 가운데 픽셀의 속도 선 위에 있을 때만 쓰입니다. 카메라가 움직여 배경 픽셀도 속도를 가질 때가 그런 경우입니다.

원 논문은 화면을 타일로 나눠(계획은 20×20 타일로 적었습니다) 타일마다 최대 속도(TileMax)를 구하고 이웃 3×3 의 최대(NeighborMax)를 픽셀의 샘플 방향으로 씁니다. 그러면 정지한 배경 픽셀도 옆 타일의 빠른 물체 방향으로 샘플합니다. 계획은 이 패스를 "실루엣 안에서만 번지는 것이 눈에 거슬릴 때만" 하는 선택 단계로 남겼고(계획 2단계-3), 지금도 하지 않았습니다(rendering-analysis 22.4).

3. 후처리 체인 속 자리

모션 블러는 Graphics/RendererPost.cpp 의 Renderer::ApplyHdrEffects 안에서 HDR 구간의 둘째 패스로 돕니다. 체인 전체 그림은 후처리 학습에 있습니다.

씬 패스 (hdr + 속도 RT + 깊이)
  → [디버그 뷰 16·17 이면 VelocityDebug 만 그리고 끝]
  → TAA (TaaResolve, TaaCopy)
  → 모션 블러: MotionBlur (hdr·깊이·속도 → scratch.temp), MotionBlurCopy (temp → hdr, PS_Post 모드 0)
  → 가우시안 블러 → 블룸 → 톤 패스
  • TAA 다음. 계획은 "TAA 는 지터가 남은 이미지를 정리해야 하므로 맨 앞에 둡니다(UE 도 TAA → 모션 블러 순서)"라고 적었습니다(계획 3.5). 코드 주석도 "지터가 남은 이미지를 정리한 뒤 번지게 함"입니다. 결과로 모션 블러가 만든 번짐과 IGN 잡음은 TAA 를 거치지 않습니다.
  • 블룸 앞. 계획은 "모션 블러는 블룸 앞에 둬야 밝은 줄무늬가 번진 뒤에 퍼집니다"라고 적었습니다.
  • 제자리 규칙. 결과는 늘 hdr 에 남습니다. 모션 블러는 temporalSet(t13 hdr, t23 깊이, t7 속도)을 읽어 scratch.temp 에 쓰고, 복사 패스로 되돌립니다. EnsurePostScratch 가 모션 블러만 켜져도 temp 를 만들고, 못 만들면 효과만 건너뜁니다.
  • 깊이 상태. 후처리가 깊이를 SRV 로 읽도록 ApplyHdrEffects 가 깊이를 DepthRead 로 바꿔 둡니다. 다음 프레임 씬 패스가 DepthWrite 로 되돌립니다(계획 7.3).
  • 건너뛰는 조건. motionBlurEnabled 이고 motionBlurIntensity > 0 이고 debugView == 0 이고 뷰의 temporalSet 이 있을 때만 돕니다. 디버그 뷰(알베도·노멀·속도 …)는 색이 번지면 읽을 수 없어서 건너뜁니다. 같은 이유로 TAA 도 Renderer::TaaActive 에서 디버그 뷰를 막습니다.
  • 뷰마다. ApplyHdrEffects 는 메인 뷰와 미리보기 뷰에 각각 불리고, 길이 상한은 각 뷰의 높이로 계산합니다. dt 는 두 뷰가 같은 m_frameDeltaTime 을 씁니다.
  • 썸네일. 후처리 단계 썸네일 6칸 중 셋째가 PostStage_Motion("Motion")입니다.

4. 번지는 길이

4-1. 셔터 배율

속도 버퍼는 "지난 프레임 → 이번 프레임" 이동량입니다. BlurVector 는 이 픽셀의 이동량(픽셀)에 postBlur.x 를 곱하고, 길이가 postBlur.y 를 넘으면 그 길이로 자릅니다. 무한대나 NaN 이면 0 입니다. postBlur.x 는 ApplyHdrEffects 가 min(motionBlurIntensity, 1) × fpsScale 로 채웁니다. motionBlurIntensity 0.5 는 한 프레임 이동량의 절반만 번진다는 뜻이고, 1-1 의 180° 셔터에 해당합니다.

4-2. 기준 fps 보정

셔터 배율만 쓰면 번짐 길이가 실제 프레임 시간에 비례합니다. 처음 계획은 실제 카메라처럼 그대로 두기로 했습니다(계획 2단계-1). 구현해 보니 VSync 를 끈 에디터(1600 fps 안팎)에서는 블러가 1 픽셀도 안 되었고, motionBlurTargetFps(기본 60)를 추가했습니다(계획 맨 위 "구현하면서 바뀐 점").

frameDt  = frameDeltaOverride > 0 ? frameDeltaOverride : m_frameDeltaTime
fpsScale = (targetFps > 0 && frameDt > 1e-5) ? 1 / (targetFps · frameDt) : 1
길이     = min(|속도(px/프레임)| × intensity × fpsScale, 상한)

속도가 초당 s 픽셀이면 한 프레임 이동량은 s · dt 이고, 여기에 1 / (targetFps · dt) 를 곱하면 dt 가 지워져 길이는 s × intensity / targetFps 가 됩니다. 실제 fps 와 상관없이 "기준 fps 로 돌았다면 셔터가 열려 있던 동안의 이동량"입니다 계산값.

dt 는 Core/Engine.cpp 의 Engine::Render 가 m_renderer.SetFrameDeltaTime(m_time.GetDeltaTime()) 으로 넘깁니다. 주석은 "이번 프레임에 장면을 움직인 dt"입니다. Time::GetDeltaTime 은 maxDeltaTime(0.25 초)로 자른 값이고, 에디터 재생의 시간 배율(EditorApp 의 m_timeScale)은 scene.Update·FixedUpdate 에 곱해지고(EditorApp::OnUpdate·OnFixedUpdate) 렌더러에 넘기는 dt 에는 들어가지 않으므로 이 dt 와 무관합니다. targetFps 를 0 으로 두면 보정 없이 한 프레임 이동량을 그대로 씁니다.

보정은 속도가 프레임마다 고르다는 가정 위에 있습니다. 위치가 어떤 프레임에서만 바뀌면(고정 스텝 물리, 몰려 들어오는 마우스 델타) 그 프레임의 이동량이 몇 배로 커지고, 보정이 그것을 다시 몇 배 키웁니다. 5장의 번쩍임과 9장의 Rigidbody 계단이 이 경우입니다.

4-3. 길이 상한은 720p 기준의 전체 길이

motionBlurMaxRadius(기본 32)는 이름에 radius 가 들어 있지만 셰이더에서는 번지는 벡터 전체의 길이 상한입니다. 샘플이 −0.5 ~ 0.5 에 놓이므로 한쪽으로는 그 절반까지 닿습니다. 에디터 슬라이더 이름도 "Max length (px @720p)"입니다. 값은 720 픽셀 높이 기준이고 ApplyHdrEffects 가 × h / kReferenceHeight(720)로 출력 높이에 비례시킵니다. 가우시안 블러 반경과 같은 관례입니다. 상한은 순간이동한 물체가 화면을 가로질러 번지는 것을 막습니다.

5. 높은 fps 에서 마우스 회전이 번쩍이던 문제

5-1. 증상과 원인

2026-11-23 커밋 be1ef76 은 VSync 를 끈 높은 fps 에서 마우스로 카메라를 돌리면 모션 블러가 번쩍이던 문제를 고쳤습니다. 같은 커밋이 TaaMotionBlur.json 의 카메라와 motionBlurMaxRadius(32)도 함께 고쳤습니다. 원인은 입력 쪽이었습니다. Core/LookSmoother.h 주석이 적은 설명은 이렇습니다.

  • 마우스 델타는 정수 픽셀이고 WM_MOUSEMOVE 는 마우스 보고 주기(125~1000 Hz)마다 몰려 들어옵니다.
  • fps 가 보고 주기보다 높으면 프레임마다 받는 델타가 0, 1, 3, 0 … 처럼 튑니다. 델타를 그대로 회전에 쓰면 카메라 각속도가 프레임마다 튑니다.
  • 속도 버퍼는 그 프레임의 회전을 그대로 담고, 기준 fps 보정(4-2)이 높은 fps 에서 길이를 몇 배로 늘립니다. 델타가 0 인 프레임은 선명하고 델타가 몰린 프레임은 크게 번집니다.

125 Hz 마우스와 480 fps 라면 보고 한 번이 약 3.84 프레임에 한 번 옵니다. 손이 일정하게 움직여도 넷 중 세 프레임은 회전이 0 이고 한 프레임에 평균의 4 배가 몰립니다. 그 프레임의 블러 길이는 보정 8 배까지 곱해져 상한에 닿기 쉽습니다 계산값. 보정이 없던 때(targetFps 0)에는 같은 튐이 있어도 길이가 1/8 이라 눈에 띄지 않았을 것입니다.

5-2. 쌓아 두고 지수로 꺼내기

LookSmoother 는 받은 회전량을 두 단계 저장소에 쌓고, 매 프레임 각 단계에서 k = 1 − exp(−dt / τ) 만큼 다음 단계로 넘깁니다. τ(timeConstant)는 8 ms 입니다.

Add(x, y):          stage1 += (x, y)
Consume(dt):        k = 1 − exp(−dt / τ)           // τ ≤ 0 이거나 dt ≤ 0 이면 k = 1 (한 번에 냄)
                    mid = stage1 · k;  stage1 −= mid;  stage2 += mid
                    out = stage2 · k;  stage2 −= out
                    |stage1| + |stage2| < 1e-5 rad 이면 남은 것을 out 에 더하고 Reset
  • 총 회전량은 그대로. 쌓은 것을 나눠 내보낼 뿐이라 감도가 바뀌지 않습니다. 주석은 "델타에 dt 를 곱하는 방식은 감도가 fps 에 따라 바뀌므로 쓰지 않음"이라고 적었습니다.
  • fps 에 거의 무관. 한 단계만 보면 exp(−dt/τ) 는 dt 에 대한 지수라, 프레임을 둘로 쪼개도 남는 양이 같습니다(exp(−a) · exp(−b) = exp(−(a+b))). 두 단계는 한 번의 Consume 안에서 이어지므로(1단계에서 넘긴 몫이 같은 프레임에 2단계에서 바로 k 만큼 나감) 프레임이 길수록 조금 빨리 내보냅니다. 회전을 한 번 넣었을 때 1/60 초 안에 나가는 몫은 60 fps 0.766, 480 fps 0.647, 4800 fps 0.619 입니다(연속 시간 극한 0.616) 계산값. 평균 지연은 두 단계라 약 2τ = 16 ms 입니다(주석).
  • 두 단계인 이유. 주석의 시뮬레이션 기록으로는 한 단계(지연 15 ms)가 125 Hz·480 fps 에서 각속도를 평균의 0.7~1.3 배로 남겼고, 두 단계(8 ms × 2)는 0.8~1.2 배, 1000 Hz 마우스는 0.93~1.08 배였습니다. 커밋 be1ef76 메시지에는 dt 지터를 넣은 480 fps 시뮬레이션에서 125 Hz 0~5.8 배 → 0.81~1.17 배, 1000 Hz 0~2.3 배 → 0.93~1.08 배로 적혀 있습니다.
  • 끝 처리. 남은 양이 1e-5 라디안보다 작으면 한 번에 내고 비웁니다. 멈춘 카메라가 끝없이 미세하게 돌아 속도 버퍼가 0 이 안 되는 일을 막는다고 주석이 적었습니다. 0 이 되어야 2-4 의 조기 반환이 걸려 정지 화면이 블러 끈 화면과 같아집니다.

5-3. 어디에 붙어 있나

  • Editor/EditorApp.cpp 의 EditorApp::UpdateCamera: 오른쪽 버튼 회전 중에 델타 × 감도를 m_lookSmoother.Add 로 쌓고, HasPending() 이면 버튼을 뗀 뒤에도 Consume(dt) 로 남은 몫을 마저 camera.Rotate 합니다. 재생 중 게임 카메라 컴포넌트가 카메라를 잡으면(cameraDriven) Reset() 으로 버립니다.
  • 테스트 프로젝트의 Projects/SherlockTestScenes/Scripts/FreeCamera.cpp: 같은 방식으로 m_look.Add·m_look.Consume.

고친 자리는 입력 쪽입니다. 속도 버퍼는 실제로 일어난 회전을 정확히 담았고, 회전 자체가 프레임마다 튀었습니다. 같은 성질 때문에 고정 스텝으로만 움직이는 물체도 높은 fps 에서 계단처럼 번집니다(9장).

8. 실험

테스트 씬은 Projects/SherlockTestScenes/Assets/Scenes 에 있습니다. 후처리 단계 썸네일의 "Motion" 칸과 바로 앞 "TAA" 칸을 비교하면 모션 블러만의 효과가 보입니다.

E1. 정지 화면은 켜도 끈 것과 같다 확인함 (2026-11-23)

카메라·오브젝트를 멈추고 모션 블러를 켠 화면과 끈 화면의 차이가 0 픽셀이었습니다(20.28 검증). 2-4 의 |vc| < 0.5 조기 반환이 이것을 보장합니다.

E2. 기준 fps 보정 확인함 (2026-11-23)

같은 초당 회전을 480 fps 로 돌렸을 때 번진 픽셀 수가 60 fps 와 비슷했습니다(3537 / 3782, 20.28 검증). 직접 해 볼 때는 --frame-dt 로 dt 를 고정하고 --cam-orbit 의 프레임당 각도를 dt 에 비례하게 줍니다(예: --frame-dt=0.016667 --cam-orbit=1 과 --frame-dt=0.0020833 --cam-orbit=0.125, 둘 다 초당 60°). 초당 회전이 크면 두 경우 모두 길이 상한(4-3)에 걸려 비교가 되지 않으므로, 상한보다 짧게 번지는 속도를 고릅니다.

E3. 보정을 끄면 고프레임에서 블러가 사라진다 예상

E2 의 480 fps 쪽에 --motion-blur-fps=0 을 더하면 길이가 1/8 로 줄어듭니다(4-2 표, 상한에 걸리지 않는 속도일 때). VSync 를 끈 에디터에서 Target FPS 슬라이더를 0 으로 내려도 같습니다.

E4. 오브젝트만 번지고 실루엣 밖은 선명하다 예상

MotionBlur.json 에서 카메라를 멈추고 --spin=node_damagedHelmet_-6514,3 으로 헬멧을 돌립니다. 헬멧 안쪽만 원호 방향으로 번지고, 헬멧 옆 배경과 바닥의 경계는 선명합니다. 헬멧의 꼬리가 배경 위로 나가지 않는 것이 2-4 의 한계입니다. 같은 씬에 --cam-orbit 를 더하면 배경 픽셀도 속도를 가져 헬멧 가장자리가 배경 쪽으로도 번집니다.

E5. 카메라를 따라가는 물체는 선명하다 예상

--cam-move=0.1,0,0 --move=node_damagedHelmet_-6514,0.1,0,0 으로 카메라와 헬멧을 같은 벡터로 옮기면 헬멧은 화면에서 움직이지 않아 선명하고 배경만 번집니다(계획 2단계-4의 "따라가는 카메라"). 3인칭 대시 상황입니다.

E6. 길이 상한 예상

--cam-orbit=30 처럼 프레임당 회전을 크게 주면 번짐 길이가 720p 기준 32 픽셀 × (높이/720)에서 멈춥니다. Max length 슬라이더를 64 로 올리면 상한이 두 배가 되고, 샘플 간격이 벌어져 IGN 잡음이 더 보입니다.

E7. LookSmoother 를 끄고 마우스 회전 예상

VSync 를 끄고 TaaMotionBlur.json 을 재생해 FreeCamera 로 둘러봅니다. 코드에서 LookSmoother::timeConstant 를 잠깐 0 으로 바꾸면(받은 만큼 바로 냄) 5-1 의 번쩍임이 돌아옵니다. 125 Hz 마우스일수록 뚜렷합니다. 확인 뒤 8 ms 로 되돌립니다.

E8. 디버그 뷰에서는 건너뛴다 예상

카메라를 돌리면서 디버그 뷰(예: 노멀)를 켜면 번짐이 사라지고, 뷰 16·17 은 속도 시각화만 나옵니다.

9. 함정과 알려진 한계

증상원인이 엔진에서
VSync 를 끄면 블러가 거의 안 보임속도는 한 프레임 이동량이라 fps 가 높을수록 짧음motionBlurTargetFps 로 기준 fps 이동량으로 환산(4-2)
마우스 회전 때 선명·번짐이 번갈아 번쩍임마우스 델타가 보고 주기마다 몰려 와 프레임별 회전이 튀고, 보정이 그것을 키움LookSmoother 두 단계, τ 8 ms(5장). 다른 입력 경로(게임 스크립트의 직접 회전)는 각자 붙여야 함
물리 물체가 고프레임에서 어떤 프레임만 길게 번짐Rigidbody 는 고정 스텝에서만 움직이고 렌더 보간이 없음남은 과제(22.4)
빠른 물체 뒤로 꼬리가 생기지 않음정지한 배경 픽셀은 조기 반환, 샘플은 가운데 속도 선 위에만TileMax·NeighborMax 없음(2-4, 계획 2단계-5)
번진 전경 뒤로 보이는 배경이 정확하지 않음한 장의 화면에는 가려진 뒤쪽 색이 없음. 둘째 항은 샘플 자리의 색(배경이 보이는 곳)만 끌어옴재구성 필터 공통 한계. 전경이 화면 가장자리나 다른 전경에 붙으면 더 틀림
반투명 물체·파티클·빗줄기·디버그 선이 뒤 표면 속도로 번짐속도를 쓰지 않음반투명 PSO 의 rt[1].writeMask = 0(GetPipelineFor), 파티클·빗줄기·튐·본 디버그 선은 RT 1장짜리 Effects 패스(DrawParticles → DrawRain → DrawDebugLines, 계획 7.8, 22.4)
화면 가장자리에서 번짐이 끊기거나 가장자리 색이 늘어남화면 밖 샘플을 가장자리 픽셀로 자름PS_MotionBlur 의 clamp(…, maxPixel), LoadVelocityPixels·LoadDeviceDepth 도 같은 자르기
번진 자리에 고정된 잡음 무늬IGN 은 픽셀 좌표만 써서 프레임마다 같고, TAA 가 모션 블러 앞이라 평균되지 않음샘플 수를 늘리거나 상한을 줄임(4-3 표)
순간이동·씬 교체 직후 한 프레임 화면이 크게 번짐지난 위치가 다른 상태의 것ResetTemporalHistory 가 씬 교체·되돌리기·카메라 컷에서 지난 값을 버림. 게임 코드의 순간이동은 감지하지 않아 직접 불러야 함(22.4). 남은 경우도 상한이 길이를 자름
에디터에서 기즈모로 끌거나 카메라를 움직이면 번짐실제 움직임이라 맞는 동작편집 모드 끔 옵션은 없음(계획 2단계-5)
낡은 서술 주의. 계획 2단계-1은 "프레임 시간 정규화(목표 FPS 기준으로 길이를 맞추기)는 넣지 않습니다"라고 적혀 있지만 지금 코드에는 motionBlurTargetFps 가 있습니다. 2단계-4 검증 표는 MotionBlur.json 을 Sponza 복사본이라고 적었지만 실제로는 DamagedHelmet 복사본입니다. 두 곳 모두 같은 문서 맨 위 "구현하면서 바뀐 점"에는 바로잡혀 있습니다. 셰이더 머리 주석과 Core/LookSmoother.h 머리 주석에 있던 낡은 서술("움직이는 전경은 배경 위로 번지지만", "fps 와 무관하게 같은 반응")은 2026-11-26 주석 정리(1fc0e12)에서 고쳐졌습니다. 지금 셰이더 주석은 "움직이는 물체는 자기 실루엣 안에서만 번지고, 정지한 배경 위로 번져 나가지는 않음"(2-4)이고, LookSmoother 주석은 낮은 fps 에서 조금 빨리 따라온다는 것과 5-2 와 같은 몫(60 fps 0.77, 480 fps 0.65, 4800 fps 0.62)을 적습니다.
