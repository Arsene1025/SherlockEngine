1. 게임 UI 가 왜 따로 필요한가

게임에는 체력 막대, 메뉴, 인벤토리 같은 화면 요소가 있습니다. 이것들은 장면 물체와 요구가 다릅니다. 화면 픽셀에 딱 맞게 선명해야 하고, 창 크기가 바뀌어도 배치가 유지되어야 하고, 마우스·키보드·패드로 누를 수 있어야 하고, 노출이나 톤매핑 때문에 색이 바뀌면 안 됩니다. 그리고 디자이너가 에디터에서 만들어 씬과 함께 저장할 수 있어야 합니다.

엔진에는 이미 ImGui 가 있지만 에디터 도구용입니다. 즉시 모드라 배치가 코드에 있고, 해상도 배율·스킨·씬 저장이 없습니다. 계획 문서의 결정 표는 세 가지 길을 비교했습니다(계획 3.2).

방식얻는 것잃는 것
유니티 uGUI 식 컴포넌트 (선택)UI 요소가 GameObject 에 붙는 Behaviour 라 Hierarchy·Inspector·직렬화·되돌리기·프리팹을 그대로 씀레이아웃을 매 프레임 직접 계산해야 함 (Scene::Update 는 재생 중에만 돎)
UMG 식 별도 위젯 에디터전용 디자이너위젯 트리·디자이너·저장 형식을 새로 만들어야 함
게임 UI 에도 ImGui추가 코드 없음해상도 배율·스킨·씬 저장이 안 됨

그래서 이 엔진의 게임 UI 는 Canvas·CanvasScaler·RectTransform·UIImage·UIText·UIButton … 같은 컴포넌트와, 그것을 매 프레임 읽어 정점 목록을 만드는 UISystem, 그 목록을 GPU 로 그리는 Renderer 의 UI 패스로 나뉩니다. 규칙은 "Scene 쪽(UI/)은 CPU 데이터만, GPU 자원은 Renderer" 입니다(계획 3.1). 글리프 비트맵도 CPU 쪽이 굽고 Renderer 가 올립니다.

2. 프레임 안에서 UI 패스의 자리

코드 순서는 Graphics/Renderer.cpp 의 Renderer::Render 끝부분입니다. ApplyHdrEffects → RenderTonemapPass → RenderCanvasPass(cmd, 0, …) 순이고, 미리보기 블록 안에서 RenderTonemapPass(… "PreviewTonemapPass" …) 뒤에 RenderCanvasPass(cmd, 1, …) 이 옵니다. 그리는 타깃은 톤 패스의 출력과 같습니다. 에디터는 씬 뷰 텍스처(m_mainView.color)에 그리고 끝에 ShaderResource 로 돌려놓아 ImGui 가 샘플링하고, 게임은 백버퍼에 그리고 RenderTarget 으로 두어 다음 BeginUIPass 가 Load 합니다. 에디터와 게임이 같은 경로를 탑니다.

CPU 쪽은 Core/Engine.cpp 의 Engine::Render 에서 매 프레임 m_ui.Build(m_scene, mainView, previewView) 를 부르고 m_renderer.SetUIDrawList(&m_ui.GetDrawList()) 로 넘깁니다. 편집 중에도 부르므로 재생하지 않아도 배치가 보입니다. 업로드는 Renderer::UploadUI 가 프레임에 한 번 합니다.

2.1 왜 톤매핑 뒤인가

계획 문서는 Overlay 패스를 톤매핑 직후에 둔 이유를 "TAA 지터·모션 블러·블룸·노출이 UI 에 묻지 않음. 에디터와 게임이 같은 경로" 로 적었습니다(계획 3.2). 하나씩 풀면 이렇습니다.

UI 를 HDR 구간에서 그렸다면생기는 문제
노출·ACES 를 거침자동 노출이 바뀔 때마다 버튼 색이 밝아지고 어두워짐. ACES 곡선이 흰 글자를 회색 쪽으로, 채도 높은 색을 덜 진하게 바꿈
TAA 를 거침지터로 흔들린 위치를 히스토리와 섞어 글자 가장자리가 뭉개지고, 글자가 바뀌면 잔상이 남음 (TAA 학습)
모션 블러를 거침카메라가 돌면 화면에 고정된 HUD 까지 속도 버퍼 값대로 번짐 (모션 블러 학습)
블룸을 거침흰 글자·밝은 버튼 주변에 빛 번짐

World 캔버스(장면 안에 놓인 패널)도 같은 자리에서 그립니다. World 캔버스는 장면에 가려져야 합니다. 톤 패스 뒤에도 깊이 버퍼가 남아 있으므로 Pass_UIWorld 가 그것을 읽기 전용으로 묶습니다(Renderer::BuildPassDescs: depthEnable = true, depthWrite = false, LessEqual, D24_UNORM_S8_UINT). RenderCanvasPass 는 깊이를 ResourceState::DepthRead 로 두고 .readOnly = true 렌더 패스로 World 명령을 먼저 그린 뒤, 깊이 없는 Pass_UI 로 Overlay 명령을 그 위에 그립니다. 계획 문서의 다른 안은 World 캔버스를 Effects 패스(HDR, 파티클 뒤)에 두는 것이었고, 반투명·파티클과의 앞뒤는 맞지만 노출·ACES·TAA 가 묻어 버리므로 택하지 않았습니다.

2.2 감마 공간 블렌딩

UI 의 색은 sRGB 로 인코딩된 값 그대로 다룹니다. 세 군데가 이것을 맞춥니다.

  • 정점 색: UI/UITypes.h 의 PackUIColor 가 0~1 sRGB 값을 그대로 RGBA8 로 묶고, 입력 레이아웃은 R8G8B8A8_UNORM 입니다.
  • 텍스처: Renderer::UploadUI 가 m_textures.Load2D(name, false, &scene) 로 읽어 sRGB → 선형 변환을 하지 않습니다.
  • 타깃: 파이프라인 RTV 형식이 R8G8B8A8_UNORM 이고 렌더 패스가 .srgbView = false 라 쓸 때도 변환이 없습니다.

블렌드는 색 SrcAlpha / InvSrcAlpha, 알파 One / InvSrcAlpha 이고, 프리멀티플라이하지 않은 알파입니다. 검정 위에 흰색 α 0.5 를 그리면 저장된 바이트끼리 섞여 0.5 × 255 = 128 이 나옵니다 확인함 (2026-11-24)(계획 10장 1단계). sRGB 뷰에 선형으로 섞었다면 선형 0.5 를 다시 인코딩해 약 188 이 됩니다 계산값. 물리적으로는 선형 쪽이 맞지만, 감마 쪽은 포토샵·피그마에서 고른 색과 반투명 겹침, 글자 안티앨리어싱 굵기가 도구와 같게 나옵니다. ImGui 도 같은 방식(UNORM 뷰)입니다. 이 결정의 기록은 계획 3.2 "블렌딩 색 공간", 출력 텍스처의 뷰 구조는 색공간 학습 5장에 있습니다. 디버그용으로 srgbOutput 을 끄면 장면만 어두워지고 UI 는 그대로인 것이 정상입니다(계획 7장).

셰이더는 짧습니다. Shaders/UIVertexShader.hlsl 의 VS_UI 는 정점의 캔버스 번호로 canvasMatrices[] 를 골라 클립 공간으로 옮기고, Shaders/UIPixelShader.hlsl 의 PS_UI 는 클립 사각형 밖이면 discard, 글자 플래그(비트 16)면 float4(color.rgb, color.a × tex.r), 아니면 tex × color 를 냅니다. Common.hlsli 를 include 하지 않고 프레임 셋(b0)도 묶지 않습니다.

UI 가 없는 씬은 이전과 같은 결과여야 합니다. RenderCanvasPass 는 그 뷰의 명령 수가 0 이면 배리어를 걸기 전에 돌아갑니다. DamagedHelmet 에서 바뀌기 전 스크린샷과의 차는 0 이었습니다 확인함 (2026-11-24)(계획 10장 1단계).

캔버스 좌표는 CanvasScaler 를 거친 논리 픽셀이고, 원점은 부모 사각형의 왼쪽 아래, y 는 위가 + 입니다(UI/UITypes.h, 유니티와 같음). 화면 픽셀(y 아래 +)로 바꾸는 일은 캔버스 행렬이 합니다.

World 캔버스의 ViewProj 에는 TAA 지터가 없습니다. 지터는 Renderer::UploadPerFrameConstants 가 b0 의 proj·viewProj·invViewProj 에만 곱하고 Camera 의 행렬은 그대로 두기 때문입니다. 대신 장면 깊이는 지터가 들어간 것이라 깊이 경계가 1 px 안쪽에서 흔들릴 수 있습니다(Renderer::BuildPassDescs 주석, 10장).

캔버스 순서는 UISystem::BuildView 에서 정합니다. World 가 먼저, 같은 모드 안에서는 sortOrder 작은 것부터, 같으면 씬 순서(std::stable_sort)입니다. 캔버스 안에서는 Hierarchy 순서대로 먼저 그린 것이 아래에 깔립니다. 캔버스 행렬은 두 뷰 합쳐 32 개까지이고(kUIMaxCanvases), 넘으면 경고 한 번 뒤 나머지를 그리지 않습니다. 캔버스 아래의 캔버스(중첩)는 지금은 일반 요소로 취급합니다(UISystem::FindCanvas).

3.2 CanvasScaler

CanvasScaler::ComputeScale 은 "캔버스 단위 하나가 출력 몇 픽셀인가" 를 냅니다. ConstantPixelSize 는 scaleFactor 그대로, ScaleWithScreenSize 는 가로 비율과 세로 비율을 로그 공간에서 섞습니다.

scale = 2^( lerp( log2(W / refW), log2(H / refH), match ) )

로그 공간에서 섞어야 가로로 긴 화면과 세로로 긴 화면이 대칭이 된다는 것이 코드 주석의 설명입니다(유니티 CanvasScaler.HandleScaleWithScreenSize 와 같음). 예를 들어 쇼케이스(UiShowcase.json, 기준 1280×720, match 0.5)를 에디터 씬 뷰 732×445 에서 보면 log2(0.5719) = −0.806, log2(0.6181) = −0.694 의 평균 −0.750 → scale 0.5945 이고 루트 사각형은 1231 × 749 캔버스 단위입니다 계산값. 계획 문서가 기록한 "휠 −3 = 60 단위 × 배율 0.5946 = 35.67 px" 의 35.67 px 는 0.5945 쪽과 맞습니다 확인함 (2026-11-24)(계획 10장 5단계).

3.3 RectTransform 계산

RectTransform::ComputeRectWithAnchors 가 부모 사각형에서 자기 사각형을 냅니다. 앵커 두 개가 부모 안의 기준 상자를 정하고, sizeDelta 는 그 상자보다 얼마나 큰가, pivot 은 자기 사각형 안의 기준점(0~1), anchoredPosition 은 앵커 상자의 피벗 비율 지점에서 피벗까지의 거리입니다.

aMin   = parent.min + anchorMin × parentSize
aMax   = parent.min + anchorMax × parentSize
size   = (aMax − aMin) + sizeDelta
pivotP = aMin + (aMax − aMin) × pivot + anchoredPosition
rect   = [pivotP − size × pivot,  pivotP − size × pivot + size]

앵커가 한 점에 모이면 sizeDelta 가 곧 크기이고 부모 크기가 바뀌어도 크기가 그대로입니다. 앵커가 벌어지면 그 축은 부모를 따라 늘어납니다. 창 비율이 바뀌어도 HUD 가 모서리에 붙어 있는 것은 이 규칙 덕분이고, 에디터 씬 뷰 732×445 와 게임 출력 1280×720·1920×1080·2560×1080(2560×1080 은 match 0·0.5·1 각각)에서 계산한 경계와 찍힌 경계의 차는 모두 0 px 였습니다 확인함 (2026-11-24)(계획 10장 1단계, check_ui_rects.py).

캔버스 아래 오브젝트의 위치·크기는 RectTransform 이 정하고, GameObject 의 Transform 에서는 회전 z 와 스케일 xy 만 읽습니다(위치는 무시). UISystem::Visit 은 이것을 피벗 중심 아핀 변환 local = T(pivot) · R · S · T(−pivot) 으로 만들어 UIAffine::Then 으로 부모 변환에 붙입니다. 레이아웃 그룹·Slider·Scrollbar·ScrollRect 가 정하는 자식 사각형은 m_driven 표에 그 프레임에만 덮어쓰고 저장 값은 바꾸지 않습니다(6장).

4. 글자: 글꼴, 글리프 아틀라스, 배치

4.1 글꼴 읽기

UI/Font.cpp 가 stb_truetype 와 stb_rect_pack 의 구현을 정의하는 유일한 파일입니다(vcpkg stb 포트). Font::Load 는 파일 바이트를 m_data 에 들고 stbtt_InitFont 로 엽니다. .ttf 와 .otf(CFF 윤곽) 모두 되지만 가변 글꼴의 축은 읽지 않으므로 정적 글꼴이어야 합니다. 엔진 기본 글꼴은 Assets/Fonts/NotoSansKR-Regular.otf(4.6 MB, SIL OFL)이고, Google Fonts 판은 가변 글꼴이라 정적 SubsetOTF 를 넣었습니다(계획 10장 2단계). FontLibrary::Get 의 이름 규칙은 빈 이름·builtin:font = 기본 글꼴, asset:<경로>, 그 밖에는 Assets\Fonts\ 아래 파일 이름이고, 못 읽으면 경고 한 번 뒤 기본 글꼴을 씁니다.

래스터라이저를 고를 때 계획 문서는 FreeType(품질은 좋지만 의존성·빌드가 큼), DirectWrite(D3D12 에서 11on12 가 필요), ImGui 의 imstb_truetype.h 사본(ImGui 버전에 묶임)과 비교했습니다(계획 3.2). 글꼴을 사용자 PC 의 Windows 글꼴에서 읽지 않는 것은 배포 PC 에 없을 수 있고 맑은 고딕은 재배포할 수 없기 때문입니다.

4.2 비트맵 글리프와 아틀라스

글자는 크기별 비트맵으로 굽습니다. 화면 공간 UI 는 글자 크기가 정해져 있어 비트맵이 가장 선명하고, 한글은 완성형 음절만 11,172 자(자주 쓰는 것만 2,350 자)라 미리 구워 둘 수 없으므로 화면에 나온 글자만 그때그때 굽습니다. GlyphAtlas::Get 의 키는 (글꼴 id ≪ 48) | (픽셀 크기 ≪ 32) | 글리프 번호이고, 픽셀 크기는 round(fontSize × scale) 입니다. fontSize 18 인 글자를 scale 0.5945 에서 그리면 10.70 → 11 px 로 굽습니다 계산값. 창 크기를 바꾸면 scale 이 바뀌고, 새 픽셀 크기의 글리프를 다시 굽습니다.

패킹은 stb_rect_pack 의 스카이라인 방식이고, 글리프마다 오른쪽·아래에 1 px 여백을 둡니다(아틀라스는 0 으로 시작). 처음 크기는 1024²(R8 이라 1 MiB), 최대 2048²(4 MiB)입니다 계산값. 꽉 차면 이렇게 처리합니다(UISystem::Build).

  1. Get 이 nullptr 를 돌려주고 Overflowed() 가 참이 됩니다. 이번 Build 는 그 글자를 건너뜁니다.
  2. Build 가 Grow()(1024 → 2048, 이미 2048 이면 같은 크기로 비움) 뒤 그 프레임을 한 번 더 만듭니다. 두 번째 시도(IsFinalPass)에서도 못 넣은 글자는 □ 로 그리고 경고를 한 번 남깁니다.
  3. 2048² 로 비우고도 넘치면(포화) 매 프레임 비우지 않도록 kSaturatedRetryFrames = 120 프레임 동안 있는 글자만 쓰고, 그 뒤 한 번 다시 해 봅니다.
  4. 가장 큰 아틀라스에도 안 들어가는 글리프(tooLarge)는 넘침으로 치지 않고 □ 로 그립니다. 넘침으로 치면 120 프레임마다 아틀라스를 비우게 됩니다.

키우거나 비우면 Reset 이 version 을 올리고, Renderer 는 새 텍스처를 만들어 전체를 초기 데이터로 올립니다. 옛 텍스처는 DestroyTexture 의 지연 해제로 GPU 가 다 쓴 뒤 풀리고, 그 리소스 셋은 캐시에서 뺍니다. 앞 프레임이 읽고 있는 텍스처를 덮어쓰지 않는 길입니다. 64 px 한글 400 자는 첫 프레임에 1024² → 2048² 로 다시 구워 □ 없이 나왔고, 96 px 한글 1,200 자는 경고 한 번에 120 프레임마다 한 번씩만 다시 구웠습니다 확인함 (2026-11-24)(계획 10장 2단계).

4.3 RHI 의 텍스처 부분 갱신

RHI/Device.h 의 UpdateTexture(handle, x, y, width, height, data, rowPitch) 는 2D 텍스처 밉 0 의 사각형을 덮어씁니다. 블록 압축이 아닌 형식만 받고, 텍스처는 ShaderResource 상태여야 하며 끝나도 ShaderResource 입니다.

백엔드구현 (D3D11Device::UpdateTexture / D3D12Device::UpdateTexture)순서가 맞는 이유
D3D11UpdateSubresource + D3D11_BOX. USAGE_DEFAULT 텍스처라 됨즉시 컨텍스트의 명령 순서대로 처리되므로 뒤의 드로우가 새 내용을 읽음
D3D12사각형 크기로 GetCopyableFootprints(행 간격 256 B 정렬) → 업로드 힙에 버퍼를 만들어 행마다 복사 → RecordUpload 안에서 ShaderResource → COPY_DEST 배리어, CopyTextureRegion, 다시 ShaderResource(D3D12Convert::ToD3D12 에서 PIXEL_SHADER_RESOURCE | NON_PIXEL_SHADER_RESOURCE)업로드 리스트가 이번 프레임 커맨드 리스트보다 먼저 실행되고, 앞 프레임의 읽기는 같은 큐의 앞쪽이라 덮어쓰기 전에 끝남

올리지 못한 프레임이 있으면 ClearDirty 를 하지 않으므로 dirty 사각형이 쌓여 다음 프레임에 올라갑니다. 그릴 명령이 없는 프레임에도 UploadUI 첫머리에서 아틀라스는 올려 둡니다. 실행 중에 "New Text" 를 더해 새 글자 6 개를 부분 갱신으로 올린 화면은 처음부터 그 글자가 있던 씬과 D3D11·D3D12 모두 차 0 이었습니다 확인함 (2026-11-24)(계획 10장 2단계).

4.4 줄 배치

UIComponents.cpp 의 BuildTextLayout 이 UIText::Populate 와 UIText::GetPreferredSize 가 함께 쓰는 배치를 합니다. 픽셀 단위로 계산합니다.

  • UTF-8 을 코드포인트로 풉니다(DecodeUtf8, 잘못된 바이트는 U+FFFD). \r 은 버리고 \t 는 공백으로 바꿉니다.
  • 전진 폭은 stbtt_GetGlyphHMetrics, 커닝은 stbtt_GetGlyphKernAdvance 입니다. stb_truetype 는 kern 표와 GPOS 쌍 조정을 읽습니다. Noto Sans KR 에서 To −74, LT −134, AV·AY·VA −15 (1/1000 em) 를 읽었습니다 확인함 (2026-11-24)(계획 10장 2단계).
  • 줄 높이 = (ascent − descent + lineGap) × lineSpacing. Noto Sans KR 은 ascent 1160, descent −288 (1/1000 em)이라 첫 줄 높이가 1.448 em, 글자 18 이면 26.1 px 입니다 계산값. 기본 상자 160×30 에 24 는 들어가지 않아 기본 글자 크기를 18 로 정했습니다(계획 10장 2단계, UIText::fontSize 주석은 "160×30 에 들어가는 크기"라고만 적음).
  • 줄바꿈은 마지막 공백에서 끊고, 한 낱말이 줄보다 길면 글자 단위로 끊습니다. 띄어쓰기 없는 한글 문장은 글자 단위로 나뉩니다. 공백에서 끊고 넘어온 조각에 이번 글자를 더한 것이 이미 줄보다 길면 이 글자 앞에서 한 번 더 끊습니다.
  • 세로 넘침은 Overflow·Truncate(들어가지 않는 줄은 그리지 않음)·Ellipsis(마지막 줄 끝을 U+2026, 없으면 마침표 셋). 정렬은 9 방향입니다.
  • 화면 픽셀 격자 맞춤: 화면 공간 캔버스이고 로컬 → 캔버스 변환이 이동뿐이면 기준선과 글자마다의 시작 x 를 출력 픽셀로 반올림합니다. 펜은 실수로 쌓으므로 반올림 오차가 줄을 따라 누적되지 않습니다. 회전·스케일이 있으면 맞추지 않습니다.
  • 글꼴에 없는 글자(글리프 0)와 아틀라스에 못 넣은 글자는 흰 텍스처 사각형 네 개로 □ 를 그립니다(글꼴에 U+25A1 이 없을 수 있음).

한글은 글꼴의 cmap 에 완성형 음절로 들어 있어 코드포인트 하나 = 글리프 하나로 그립니다. 셰이핑(자모 조합, 합자, 오른쪽에서 왼쪽으로 쓰는 문자)은 하지 않습니다. 글자 입력칸(InputField)과 IME 조합도 아직 없습니다(계획 8장).

5.2 배치: 드로우가 나뉘는 곳

UIMeshBuilder::AddQuad 는 사각형을 쌓을 때 바로 앞 명령과 텍스처 이름이 같고 인덱스가 이어지면 그 명령의 indexCount 에 6 을 더합니다. 다르면 새 UIDrawCmd 를 만듭니다. 캔버스나 뷰가 바뀔 때는 BreakBatch 로 끊습니다. 즉 드로우 수는 그리는 순서(Hierarchy 깊이 우선)에서 텍스처가 바뀌는 횟수입니다. 순서를 바꾸지 않으므로 겹침은 항상 맞고, 대신 흰 이미지(빈 텍스처 이름) → 글자(builtin:ui-glyphs) → 흰 이미지 처럼 번갈아 나오면 매번 끊깁니다. RenderCanvasPass 는 셋이 바뀔 때만 SetResourceSet 을 다시 부르고 명령마다 DrawIndexed 하나를 냅니다.

리소스 셋은 둘로 나뉩니다. 셋 0 = { b4 UI 상수, s0 LinearClamp } 하나, 셋 1 = { t0 } 를 텍스처마다 만들어 (index, generation) 키로 캐시합니다(Renderer::GetUITextureSet). 샘플러를 텍스처 셋에서 뺀 것은 D3D12 가 샘플러가 든 셋마다 샘플러 힙 칸을 따로 쓰기 때문입니다(Graphics/ShaderConstants.h 의 kCBSlotUI 주석). 텍스처 캐시의 generation 이 바뀌면(씬 바꿈·다시 읽기) 셋 캐시를 비웁니다. 바인딩 구조는 RHI·PSO 학습을 보세요.

요소 1,000 개(UiPerf) Release 에서 CPU UISystem::Build 는 0.48~0.50 ms, GPU UICanvasPass 는 0.07 ms, 쇼케이스 Build 는 0.12 ms 였습니다 확인함 (2026-11-24)(계획 10장 5단계). 비용은 GPU 보다 CPU 쪽이 큽니다. Build 마다 비우고 채우는 맵을 std::pmr::unsynchronized_pool_resource 위에 둔 것이 0.52 → 0.48 ms 를 만든 변경입니다(UISystem.h 주석).

6.1 이벤트 흐름

UISystem::Update 는 재생 중에만 Scene::Update 첫머리에서 돌고, 지난 프레임 Build 가 남긴 히트 목록(m_hitOrder)을 씁니다.

  1. 포인터 → 출력 픽셀: 에디터는 씬 이미지 사각형(SetPointerViewport), 게임은 창 전체입니다.
  2. UISystem::HitTest: 그린 순서의 역순으로 raycastTarget 이 켜진 Graphic 을 찾습니다. Overlay 는 World 뒤에 그리므로 먼저 나오고 맞으면 바로 끝납니다. World 끼리는 투영 w 가 작은(가까운) 것이 이깁니다. PixelToCanvas 가 화면 점과 캔버스 평면의 교점을 2×2 식으로 풀고 카메라 뒤(w ≤ 0)는 버립니다. 장면 물체에 가렸는지는 보지 않습니다(유니티 기본과 같음).
  3. 맞은 Graphic 에서 위로 올라가며 처음 만나는 Selectable 이 누르기·클릭 대상, 처음 만나는 Slider·Scrollbar·ScrollRect 가 드래그 대상입니다. ScrollRect 에서 출력 10 px(kDragThreshold) 이상 움직이면 드래그로 보고 누른 버튼의 클릭을 취소합니다.
  4. 색 전환(UpdateColors): Normal·Highlighted·Pressed·Selected·Disabled 색을 fadeDuration(기본 0.1 s) 동안 섞어 대상 Graphic 의 색에 곱합니다.
  5. 내비게이션(UpdateNavigation): 방향키, (켜면) WASD, D-pad, 왼쪽 스틱이 0.5 를 넘을 때. 다음 요소는 유니티 Selectable.FindSelectable 과 같은 점수(가장자리 점에서 후보 중심으로의 벡터 v, dot(dir, v) > 0 중 dot / |v|² 최대)로 고릅니다. Submit = Enter·Space·패드 A, Cancel = Esc·패드 B. 패드는 Core/Input.cpp 의 XInput 1.4, 0 번 패드뿐입니다.

이벤트(UI/UIEvent.h 의 UIEvent<T>)는 두 종류의 연결을 갖습니다. 코드 리스너(AddListener, 저장 안 됨)와 Inspector 에서 고른 저장되는 연결(UIPersistentCall: 대상 오브젝트 상대 경로 + "컴포넌트.함수")입니다. 저장되는 연결의 함수는 스크립트가 SHERLOCK_UI_ACTION(클래스, 함수) 로 등록하고, 스크립트 DLL 을 내릴 때 ScriptModule::Unload 가 그 타입 이름의 등록을 지웁니다. 스크립트는 IsPointerOverUI()·IsPointerCaptured()·HasSelection() 으로 UI 위의 입력을 피할 수 있습니다(테스트 프로젝트의 FreeCamera 가 그렇게 함).

  • 편집 중 표시. Build 가 편집 중에도 돌고, 씬 뷰 툴바의 UI 토글(Engine 의 m_uiVisible)로 켜고 끕니다. 재생 화면이 곧 씬 뷰라서 별도 Game 창은 없습니다.
  • Rect 툴(Editor::DrawRectTool, 툴바 Rect, 단축키 T): 화면 공간 캔버스 아래 선택한 요소의 부모 사각형, 핸들 8 개, 피벗 원, 앵커 삼각형을 그립니다. 안쪽 드래그 = 이동, 핸들 = 크기(Alt 가운데 기준, Shift 비율 유지), 부모·형제 가장자리에 8 출력 픽셀 스냅(Ctrl 로 끔), 화살표 1 단위(Shift 10). 제자리 클릭은 UISystem::PickElement 로 UI 를 고르고, 같은 자리를 반복해 누르면 아래 요소로 차례로 내려갑니다. 위치 계산에는 UISystem::GetElementGeometry 가 준 부모 공간·변환을 씁니다.
  • Inspector. 앵커 프리셋(DrawAnchorPresets, 유니티 Alt+Shift 동작), 캔버스 아래 오브젝트는 Transform 의 Position 칸 대신 "UI element: position/size in RectTransform …" 안내 줄을 보여 줌(UISystem::IsUnderCanvas), 레이아웃이 정하는 값에는 "driven:" 안내를 붙입니다.
  • 저장. UI 컴포넌트도 Reflect(PropertyVisitor&) 로 씬 JSON 에 들어갑니다. 새 방문자 함수로 Float2, ObjectRef(소유자 기준 상대 경로 문자열 — ".", "../Handle"), Event(UIEventEncode 의 JSON)가 있습니다. 상대 경로라 복제·프리팹 인스턴스·되돌리기 뒤에도 그대로 맞습니다. UIImage 의 종류는 "imageType" 으로 씁니다 — "type" 은 컴포넌트 JSON 의 타입 이름 키라 덮어쓰면 다시 열 때 예외가 났습니다(계획 10장 3단계). 형제 순서가 그리는 순서이므로 SceneSerializer 가 "sibling" 을 저장하고 읽을 때 그 순서로 정렬합니다.

9. 실험

저장소에 남는 UI 씬은 UiShowcase.json 하나입니다. 단계별 검증 씬은 python Projects/SherlockTestScenes/Scripts/Tests/make_ui_test_scenes.py --verify-dir=<폴더> 로 만들고 에디터를 --scene=<절대 경로> 로 엽니다.

E1. 쇼케이스 둘러보기 눈으로

UiShowcase.json 을 열고 재생합니다. 위쪽 제목 띠, 왼쪽 메뉴(버튼·토글 그룹·볼륨 슬라이더), 오른쪽 인벤토리 Scroll View, 아래 체력 막대(Filled 0.65)와 단축칸 격자가 Overlay 이고, 헬멧 위 이름표(Billboard 스크립트가 카메라를 향하게 돌림)와 기둥에 반쯤 가려진 키오스크 패널이 World 캔버스입니다. 창 크기를 바꾸면 match 0.5 배율대로 전체가 커지고 작아집니다 예상. 클릭 수 버튼은 UiClickCounter.Increment 에 저장되는 연결로 묶여 있습니다.

E2. 감마 블렌딩 값 재기 픽셀

검증 씬 UiAnchors 의 반투명 Half(검정 위 흰색 α 0.5) 픽셀을 스크린샷에서 읽습니다. 128 ± 1 이면 감마 공간 블렌딩입니다 확인함 (2026-11-24)(계획 10장 1단계). check_ui_rects.py 가 이 값을 검사합니다. 글자 쪽은 별도 검증 씬 UiText 에서 봅니다. 파란 판 위 빨간 글자는 모든 픽셀이 G = 0, R + B = 255 ± 1 이어야 합니다(check_ui_text.py "Blend").

E3. 아틀라스가 커지는 순간 로그

검증 씬 UiTextAtlas(64 px 한글 400 자)를 열면 첫 프레임 로그에 UI: 글리프 아틀라스 1024² → 2048² 로 다시 구움 과 UI: 글리프 아틀라스 텍스처 2048² (버전 2) 가 나옵니다 확인함 (2026-11-24)(계획 10장 2단계). 64 px 한글 한 칸을 여백 포함 대략 60×60 텍셀로 잡으면 1024² 에는 (1024 / 60)² ≈ 290 자 정도라 400 자에서 넘치는 것이 맞습니다 계산값(칸 크기는 어림, 실제는 글자마다 다름).

E4. 톤매핑 뒤라는 것 확인 비교

쇼케이스에서 노출을 크게 바꾸거나 TAA·모션 블러를 켜고 카메라를 돌립니다. 장면은 밝기가 바뀌고 번지지만 Overlay HUD 의 픽셀은 그대로입니다 예상. World 패널은 TAA + 모션 블러를 켰을 때 패널 영역 최대 차 13(버튼 부근 6)이 기록되어 있고, 원인은 나누어 보지 않았습니다 확인함 (2026-11-24)(계획 10장 8단계). 지터가 들어간 깊이와 지터 없는 패널의 경계 차, 패널 뒤 장면 자체가 TAA 로 바뀐 것 중 무엇인지 나눠 보는 것이 다음 실험입니다.

E5. 전체 자동 검증 스크립트

python Projects/SherlockTestScenes/Scripts/Tests/verify_ui_stages.py --backend=d3d12(선택: --config=Release, --only=click,widgets,layout,nav,rect,world,showcase,regress). 검증 씬을 임시 폴더에 만들고 에디터를 자동화 인자로 띄워 로그·스크린샷을 기대값과 비교합니다. Debug D3D11·Debug D3D12·Release D3D11 에서 32 / 32 통과했고, 뒤에 넣은 "핫리로드가 실제로 일어남"·종료 코드 검사까지 33 항목으로 Debug D3D11 에서 다시 통과했습니다(종료 코드가 0 이 아니면 그것도 실패로 셉니다) 확인함 (2026-11-24)(계획 10장 3~8단계 공통). check_ui_fonts.py 는 Assets/UiTestFonts/Karla-Regular.ttf 가 있을 때만 돕니다(저장소에 없음).

E6. 배치가 끊기는 것 보기 통계

같은 아이콘 텍스처를 쓰는 이미지와 그 이름 글자를 짝으로 열 개 놓으면(Hierarchy 순서 아이콘 → 글자 → 아이콘 …) 텍스처가 매번 바뀌어 명령이 20 개가 됩니다. 겹치지 않는다면 아이콘 열 개를 먼저, 글자 열 개를 뒤에 두는 순서로 바꿔 2 개로 줄일 수 있습니다 예상. RenderCanvasPass 가 명령마다 m_stats.draws 를 하나씩 올리므로 에디터 렌더 통계의 draws 에서 차이를 봅니다.
