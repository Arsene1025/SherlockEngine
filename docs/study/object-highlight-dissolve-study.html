emission' = emission + flash.rgb + rim.rgb · r      // flash = rim = 0 → + 0

2-2. 색 섞기: F0 를 만들기 전에

메탈릭 워크플로에서 F0 는 금속성으로 섞습니다(MaterialSurface.hlsli 의 EvaluateMaterialSurface).

F0  = lerp(dielectricF0, albedo, metallic)     // 유전체 ≈ 0.04, 금속 = 자기 색
kd  = (1 − F) · (1 − metallic)                 // 금속은 확산이 없음

금속(metallic = 1)의 색은 전부 F0, 곧 반사 색에서 나옵니다. 색 섞기를 F0 를 만든 뒤에 알베도에만 하면 금속은 확산이 0 이라 색이 바뀌지 않습니다. 그래서 HighlightAlbedo 를 s.albedo 를 정하는 첫 줄에서 부르고, 그 값이 아래의 F0 계산과 G-buffer gb0 로 그대로 흘러가게 했습니다. 기록에서 금속 상자(D_Metal)가 갈색에서 검붉은색으로 바뀌는 것으로 확인했습니다 확인함 (2026-11-26) 기록 4장.

2-3. 발광 번쩍임

번쩍임은 발광에 색 × 세기를 더합니다. 발광은 조명 계산의 바깥에 있어서 그림자 속에서도 같은 밝기로 보이고, HDR 이라 1 을 넘으면 블룸이 번집니다. 포워드는 ShadeLights 의 시작값(environment + s.emission)으로 더하고, 디퍼드는 G-buffer 패스가 발광 칸(view.hdr, SV_Target0)에 써 두면 라이팅 패스가 그 위에 환경광과 직접광을 더합니다(디퍼드 G-buffer 학습 3-1). 발광 칸은 원래 있던 것이라 G-buffer 배치를 바꾸지 않았습니다.

2-4. 가장자리 빛: 기하 노멀의 1 − N·V

림 라이트는 시선과 노멀이 직각에 가까운 곳, 곧 화면에서 실루엣 근처를 밝힙니다. HighlightEmission 의 식입니다.

V   = normalize(cameraPosition − worldPosition)
rim = pow(saturate(1 − saturate(dot(Ng, V))), max(p, 0.1))
emission += flash.rgb + rim.rgb · rim

Ng 는 노말맵을 적용하기 전의 보간된 정점 노멀(양면 재질의 뒷면이면 뒤집은 것, s.geometricNormal)입니다. 노말맵 노멀을 쓰면 표면의 잔무늬마다 N·V 가 흔들려 가운데에도 반짝이는 점이 생깁니다. 이 효과가 따라야 할 것은 물체의 외형이고, 외형은 정점 노멀이 담고 있습니다. 디퍼드에서도 G-buffer PS 에서 계산합니다. 라이팅 패스는 GB1 의 기하 노멀을 갖고 있지만 그 픽셀의 강조 값을 모르기 때문입니다.

지수 하한 0.1 은 C++(Renderer::BuildDrawList 의 addObject)와 셰이더(max(highlightRim.a, 0.1)) 양쪽에 있습니다. HLSL 의 pow(x, y) 는 exp2(y · log2 x) 로 계산되는데, x = 0 이고 y = 0 이면 0 × (−∞) 라 NaN 이 나옵니다. NaN 에 색 0 을 곱해도 NaN 이라, 강조가 없는 오브젝트의 정면 픽셀(1 − N·V = 0)에서 블룸·TAA 로 번질 수 있습니다. 강조가 없는 오브젝트는 b1 칸이 0 이므로 셰이더 쪽 max 가 실제로 이 경우를 막습니다.

2-5. 디졸브: 노이즈 문턱과 경계 띠

진행도 a ∈ [0, 1], 경계 폭 w ≥ 0, 픽셀의 노이즈 값 n ∈ [0, 1] 일 때 Shaders/Dissolve.hlsli 의 규칙은 이렇습니다.

t = a · (1 + w) − w                          // 문턱. a = 0 → −w, a = 1 → 1
n < t + 0.0001            → clip (버림)
t ≤ n < t + w             → 경계 빛 = edge.rgb · (1 − (n − t) / w)   // 문턱에서 1, 띠 끝에서 0
그 밖                      → 원래 표면

문턱을 a 가 아니라 a(1 + w) − w 로 둔 이유는 띠의 양 끝입니다. a 가 0 보다 조금 클 때 t 는 −w 근처라 버리는 픽셀은 거의 없고 노이즈 값이 가장 작은 곳에 띠만 먼저 나타납니다. a = 1 이면 t = 1 이라 띠까지 모두 사라집니다. 문턱을 그냥 a 로 두면 a = 1 에서도 1 − w 위의 띠가 남습니다. clip 의 0.0001 여유는 노이즈 값이 정확히 1(255)인 픽셀도 a = 1 에서 버리기 위한 것입니다.

이 식에서 버려지는 면적은 t 입니다. 균일 분포에서 버린 면적 = a(1 + w) − w, 버린 면적 + 띠 = a(1 + w) 이고, 두 값과 a 의 차이는 w 보다 작습니다. 기본 w = 0.05 에서 a = 0.5 면 버린 면적은 47.5 %, 띠까지 52.5 % 입니다 계산값. 코드 주석의 "진행도가 사라진 면적의 비율과 거의 같다"는 이 정도의 차이를 뜻합니다.

4-2. 정확히 256 바이트로 맞춘 이유

D3D12 에서 b1 은 Dynamic 상수 버퍼라 리소스가 없고, UpdateBuffer 를 부를 때마다 프레임 업로드 링에서 새 조각을 떼어 그 GPU 주소를 루트 CBV 로 넘깁니다. 코드에는 256 정렬이 두 군데 있습니다.

// D3D12Device::CreateBuffer — 상수 버퍼 크기를 256 의 배수로 올림
buffer.desc.size = (buffer.desc.size + 255) & ~255u;
// D3D12Device::UpdateBuffer → AllocateUpload(buffer->desc.size, …) — 시작 오프셋도 256 정렬
const uint64_t aligned = (ring.offset + 255) & ~255ull;

루트 CBV 주소는 256 바이트 정렬이어야 한다는 D3D12 규칙(D3D12_CONSTANT_BUFFER_DATA_PLACEMENT_ALIGNMENT) 때문입니다. 떼는 크기가 실제로 쓴 바이트가 아니라 올림한 desc.size 이므로, 구조체가 256 을 1 바이트라도 넘으면 드로우마다 512 바이트를 씁니다.

링은 프레임 슬롯마다 kUploadRingSize = 8 MB 입니다. b1 만으로 셈하면 256 B 조각은 프레임당 최대 32,768 번, 512 B 조각은 16,384 번입니다 계산값. 실제 상한은 이보다 낮습니다. 같은 링을 b0·b3·b5(그림자 뷰마다)·b9 와 스킨 드로우의 b7 이 같이 쓰는데, b7 은 앞의 n 개 조인트만 복사해도 desc.size 인 16,384 B 를 통째로 뗍니다. 드로우 수에는 그림자 뷰마다 다시 그리는 드로우도 들어갑니다. 링이 차면 AllocateUpload 가 에러를 한 번 남기고 그 갱신을 버리므로, 그 드로우는 지난 조각의 값으로 그려집니다.

처음 구현은 디졸브에 float4 두 칸을 더해 272 B 였습니다. 다섯 값(진행도, 폭, 경계 색 셋) 중 넷을 dissolveEdge 하나에 넣고, 폭은 번쩍임의 쓰지 않던 a 에 넣어 256 B 로 되돌렸습니다. 셰이더는 DissolveAmount()·DissolveWidth() 로만 읽으므로 칸 배치를 아는 곳은 Dissolve.hlsli 와 addObject 두 곳입니다. 접기 전과 뒤의 디졸브 화면은 픽셀이 같았습니다 확인함 (2026-11-26) 기록 7.6. D3D11 은 Map(WRITE_DISCARD) 로 드라이버가 메모리를 바꿔 주므로 이 제약이 없고, 16 바이트 배수만 지키면 됩니다. 다음에 칸이 더 필요하면 b1 을 512 B 로 키우는 비용(드로우 상한 절반)과 구조화 버퍼·인스턴스 데이터로 옮기는 비용을 비교해야 합니다.

5-1. 강조 함수 (MaterialSurface.hlsli)

{
    return lerp(albedo, highlightTint.rgb, saturate(highlightTint.a));

float3 HighlightEmission(float3 geometricNormal, float3 worldPosition)
{
    const float3 viewDirection = SafeNormalize(cameraPosition - worldPosition, float3(0.0f, 0.0f, -1.0f));

EvaluateMaterialSurface 는 첫 줄에서 s.albedo = HighlightAlbedo(baseColorAlpha.rgb), 마지막 줄에서 s.emission += HighlightEmission(s.geometricNormal, input.worldPosition) + DissolveEdgeEmission(DissolveNoise(input.uv)) 를 합니다. 포워드 PS_Main 과 G-buffer PS_GBuffer 가 이 함수를 같이 쓰므로 두 경로가 같은 값을 만듭니다(디퍼드 G-buffer 학습 3-2). 시선 방향은 포워드 조명과 같은 식이고, SafeNormalize 는 카메라가 표면 위에 있을 때의 0 나눗셈을 막습니다.

5-3. 변형 없이 분기 하나로 둔 비용

강조에는 분기가 없습니다. lerp, 정규화, 내적, pow 몇 개가 모든 메시 픽셀에서 돌고, 값이 0 이면 결과에 0 을 더합니다. 디졸브의 분기 DissolveAmount() > 0 은 상수 버퍼 값이라 한 드로우의 모든 픽셀이 같은 쪽으로 갑니다. 이런 균일 분기는 웨이브 안에서 갈라지지 않아 분기 비용이 거의 없습니다.

노이즈 샘플은 분기 밖에서 늘 합니다. Sample 은 밉을 고르려고 이웃 픽셀과의 UV 차이(암묵적 ddx·ddy)를 쓰는데, 이 값은 웨이브 안의 픽셀이 모두 같은 흐름을 탈 때만 정의됩니다. 클리어코트 텍스처를 분기 밖에서 샘플하는 것과 같은 이유입니다(Dissolve.hlsli 주석). 그래서 디졸브가 없는 모든 메시 픽셀도 256² 노이즈를 한 번 읽습니다. G-buffer·포워드 PS 는 DissolveClip 용과 EvaluateMaterialSurface 안의 경계 빛용으로 같은 좌표를 두 번 부르는데, 컴파일러가 하나로 합쳤는지는 확인하지 않았습니다.

그림자 패스에서는 반대로 변형을 만들었습니다. 그림자 패스는 PS 가 아예 없는 경로라, 분기 하나를 넣으려면 모든 그림자 드로우에 PS 를 붙여야 하기 때문입니다(6장). 메인·G-buffer PS 에는 원래 컷아웃 clip 이 있었으므로 clip 하나를 더해도 셰이더의 성질(깊이를 PS 뒤에 확정하는지)은 바뀌지 않습니다(기록 7.3).

6. 그림자: 알파 테스트 변형

6-1. 깊이만 쓰는 패스에서는 구멍이 뚫리지 않는다

그림자 패스(Pass_Shadow·Pass_ShadowSkin)는 VS 만 있고 렌더 타깃이 없습니다. 깊이는 래스터라이저가 보간한 값이 그대로 깊이 버퍼에 들어가므로 색을 계산할 PS 가 필요 없고, PS 가 없으면 GPU 는 깊이 쓰기만 하는 빠른 경로를 탑니다(그림자 맵 학습, rendering-analysis 11.8). 그 대신 clip 을 실행할 곳이 없습니다. 몸이 사라져도 그림자는 남고, 나뭇잎 같은 컷아웃 재질은 폴리곤 모양 그대로 꽉 찬 그림자를 드리웠습니다.

6-3. 왜 셋이 셋이고, 왜 키 비트가 따로인가

PS 가 알베도 알파(t0), 노이즈(t20), baseColor·alphaCutoff·uvScale(b3)을 읽어야 하므로 재질 셋이 필요합니다. 셋 목록이 달라지면 D3D12 에서는 루트 시그니처가 달라집니다. D3D12Device::GetOrCreateRootLayout 이 루트 레이아웃을 셋 레이아웃 목록의 해시로 캐시하기 때문입니다. 알파 변형의 목록은 메인 패스와 같은 { 프레임, 오브젝트, 재질 } 이라 메인 패스의 루트 시그니처를 같이 쓰고, PS 없는 그림자 PSO 와는 다릅니다(바인딩 학습 5장).

그림자 루프 안에서 두 종류가 섞여 나오면 루트 시그니처가 바뀝니다. D3D12CommandList::SetPipelineState 는 루트가 바뀔 때 꽂힌 셋을 모두 다시 묶을 대상으로 표시하고, 드로우 직전의 ApplyBindings 는 현재 루트 레이아웃의 셋 수만큼만 돌기 때문에, PS 없는 변형으로 돌아갔을 때 셋 2 에 남은 재질 셋은 무시됩니다. 그래서 DrawDepthView 는 PSO 를 고른 뒤 재질 셋을 꽂고, 재질이 바뀔 때만 다시 꽂습니다(DepthDrawState).

PSO 는 Renderer::GetShadowPipelineFor 의 키로 갈립니다. 이 키는 메인 패스 키와 다른 캐시(m_shadowPipelines)라 비트 뜻도 다릅니다. 메인 키(GetPipelineFor)의 비트 10 은 뒷면 컬링입니다.

6-4. 누구에게만 변형을 주는가

모든 그림자 드로우에 알파 PS 를 붙이면 코드는 단순해지지만, 그림자 뷰마다(CSM 캐스케이드 최대 넷, 스팟, 포인트 큐브 여섯 면) 모든 그림자 텍셀에서 PS 가 돌고 텍스처 둘을 읽습니다. PS 에 clip 이 있으면 깊이 쓰기를 PS 가 끝날 때까지 미뤄야 하므로 깊이 전용 패스의 빠른 경로도 잃습니다. 그래서 shadowAlpha 는 컷아웃 재질과 디졸브 중(amount > 0)인 오브젝트에만 켜고, 나머지 불투명 재질과 amount = 0 인 Dissolve 는 PS 없는 경로에 남깁니다. 진행도가 0 에서 커지는 프레임에 PSO 가 바뀌고, 그 조합을 처음 쓰면 그때 PSO 를 만듭니다. 이 비용과 컷아웃이 많은 씬의 그림자 시간은 기록에서도 재지 않았습니다(기록 6장.
