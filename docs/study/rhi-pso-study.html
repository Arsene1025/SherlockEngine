2026-11-25 · 이 프로젝트의 최종 목표인 RHI(Render Hardware Interface)와 PSO(Pipeline State Object)를 한 문서로 모았습니다. 지금까지 이 주제는 rendering-analysis 5장(핸들·풀·Desc), 6장(PSO), 9장(두 백엔드), 19장 설계 결정의 D21·D22, 1단계 기록, RHI 로드맵에 나뉘어 있었습니다. 바인딩(루트 시그니처)은 바인딩 학습 문서, 배리어·펜스·프레임 자원은 GPU 동기화 학습 문서에서 따로 다룹니다.

1. 왜 RHI인가

1-1. 같은 그림, 다른 API 두 개

이 엔진은 D3D11과 D3D12 두 백엔드를 한 실행 파일에 빌드하고, 시작할 때 하나를 고릅니다(Core/Engine.cpp의 engine.backend, 실행 인자 --backend=d3d12). 두 API는 같은 GPU를 다루지만 사고방식이 다릅니다. D3D11은 드라이버가 동기화·메모리 수명·상태 검증을 대신 해 주는 암묵적 API이고, D3D12는 그 일을 프로그램이 직접 하는 명시적 API입니다.

렌더러가 API를 직접 부르면 기능 하나를 두 번 써야 하고, 두 코드가 조금씩 어긋납니다. RHI는 그 사이에 얇은 층을 두어 렌더러가 "무엇을 그릴지"만 말하게 합니다. 재질, 드로우 정렬, 패스 순서는 RHI 위의 Renderer가 한 번만 쓰고, API 차이는 RHI/D3D11/과 RHI/D3D12/ 안에서만 다룹니다.

1-2. 세 가지 모양 중 혼합형

D21은 세 갈래를 비교했습니다. (a) 리소스마다 가상 클래스를 두는 방식, (b) 리소스를 {index, generation} 핸들로 두고 실제 객체를 백엔드 풀에 두는 방식(bgfx·sokol_gfx), (c) using Buffer = D3D11Buffer;처럼 빌드 때 고르는 방식입니다. 고른 것은 리소스는 핸들(b), Device와 CommandList만 가상(a)인 혼합형입니다.

방식얻는 것잃는 것
(a) 리소스마다 가상 클래스런타임 교체리소스마다 vtable·힙 할당, 호출 코드에 포인터가 보임
(b) 핸들 + 백엔드 풀8바이트 값, 복사·비교·해시가 쉬움, 해제 뒤 사용을 세대로 잡음호출마다 배열 조회 한 번
(c) 컴파일 타임 선택오버헤드 0한 빌드에 백엔드 하나. 두 백엔드를 나란히 비교할 수 없음

드로우마다 생기는 가상 호출 몇 번은 API 호출 비용에 묻히고, 같은 실행 파일에서 --backend만 바꿔 픽셀을 비교할 수 있다는 점이 컸습니다. 실제로 기능을 넣을 때마다 "D3D11 = D3D12 픽셀 동일"을 확인 기준으로 씁니다(11장 E3).

1-3. D3D12를 기준으로, D3D11은 빈 동작 허용

인터페이스를 D3D11에 맞추면 D3D12 쪽이 드라이버 흉내를 내야 하고, D3D12에 맞추면 D3D11 쪽 일부가 아무 일도 하지 않게 됩니다. 이 엔진은 뒤쪽을 골랐습니다(rendering-analysis 9.12). 그래서 D3D11에서는 쓸모없는 것이 인터페이스에 남아 있습니다. Barrier는 D3D11에서 상태 기록만 하고, PipelineStateDesc::rtvFormats는 D3D11이 읽지 않으며, bindingLayouts는 D3D11에서 PSO 생성에 쓰이지 않습니다. 반대로 D3D11에서만 편한 것(즉시 Map, 자동 밉 생성, 암묵적 동기화)은 넣지 않았습니다(RHI/Device.h 머리 주석).

이 순서가 맞았는지는 D3D12 백엔드를 붙일 때 시험됐습니다. 8단계 기록에 따르면 RHI::Device·RHI::CommandList의 메서드는 바뀌지 않았고, D3D11이 감춰 주던 다섯 가지(PSO의 렌더 타깃 포맷, 드로우마다 갱신되는 상수 버퍼, 일반 샘플러의 비교 함수, 시저 사각형, 텍스처 초기 상태)만 고쳤습니다(9.11).

2. RHI의 어휘: 핸들, 풀, Desc

2-1. 핸들은 작은 값

RHI/Handle.h의 Handle<Tag>는 uint32_t index와 uint32_t generation 두 칸짜리 값입니다. 실제 객체는 백엔드의 풀 안에 있고, 호출 코드는 D3D 타입을 전혀 모릅니다. Tag는 정의가 없는 빈 선언이며, BufferHandle과 TextureHandle을 서로 다른 타입으로 만들어 섞어 쓰면 컴파일 에러가 나게 하는 역할만 합니다. 별칭은 여덟 개입니다: ShaderHandle, PipelineHandle, ComputePipelineHandle, BufferHandle, TextureHandle, SamplerHandle, BindingLayoutHandle, ResourceSetHandle.

generation 0은 빈 핸들로 예약돼 있어서, 기본 생성한 핸들은 IsValid()가 거짓입니다. 비교는 operator<=> = default 한 줄로 만들고, ResourceHandle 콘셉트가 "Handle<Tag>의 특수화이고 trivially copyable"인 타입만 풀에 들어가게 막습니다.

2-2. 세대가 있는 풀

RHI/ResourcePool.h의 ResourcePool<T, HandleT>는 슬롯 배열과 free list입니다. Remove가 슬롯을 비우면서 세대를 1 올리므로, 해제 전에 받은 핸들은 같은 슬롯이 재사용돼도 Get에서 nullptr가 됩니다. 댕글링 포인터가 "가끔 다른 객체를 가리키는" 대신 "항상 널"이 되는 것이 요점입니다. 세대가 넘쳐 0이 되면 1로 건너뜁니다. 넣을 때는 Add(T&&)로 이동해서, ComPtr의 AddRef/Release와 문자열 복사가 생기지 않게 합니다.

PSO 캐시는 같은 생각을 캐시 단위로 씁니다. 슬롯마다 세대를 두지 않고 캐시 전체에 세대 하나를 두며, 비울 때 그 값을 올립니다(6-4).

2-3. Desc를 넘기면 핸들이 돌아온다

모든 생성 함수는 CreateBuffer(BufferDesc), CreateTexture(TextureDesc, span), CreatePipeline(PipelineStateDesc)처럼 "Desc → 핸들" 한 가지 모양입니다. Desc는 D3D 헤더 없이 uint8_t 열거형과 작은 구조체로만 짜여 있고, 호출 코드는 C++20 지정 초기화로 채웁니다(TextureDesc d{ .width = 2048, ... }). RHI/PipelineTypes.h 주석은 "필드 순서가 계약"이라고 적습니다. 지정 초기화는 선언 순서를 따라야 하므로 필드 순서를 바꾸면 호출 코드가 컴파일되지 않습니다.

Desc를 값 타입으로 두면 같은 구조체가 세 가지 일을 합니다. 생성 주문서, 캐시 키, 그리고 백엔드가 보관하는 원본(PipelineState::m_desc)입니다. 깊은 설명과 C++20 기능은 rendering-analysis 5장에 있습니다.

3. 계층과 두 인터페이스

3-1. Device와 CommandList

RHI::Device(RHI/Device.h)는 프레임 경계(BeginFrame·EndFrame), 리소스 생성·해제, PSO 생성과 무효화(CreatePipeline, CreateComputePipeline, InvalidatePipelines), 바인딩 레이아웃과 리소스 셋, ImGui 어댑터 다섯 메서드를 가집니다. RHI::CommandList(RHI/CommandList.h)는 렌더 패스, PSO·셋·버퍼 바인딩, 드로우와 디스패치(간접 포함), 배리어와 복사, 타임스탬프를 기록합니다. D3D11에서는 즉시 컨텍스트의 얇은 래퍼라 기록이 곧 실행이고, D3D12에서는 커맨드 리스트에 쌓였다가 EndFrame에서 제출됩니다.

4. PSO는 무엇을 왜 묶는가

4-1. D3D11의 따로 놓인 상태

D3D11은 상태를 단계별로 하나씩 바꿉니다. ID3D11RasterizerState, ID3D11DepthStencilState, ID3D11BlendState를 따로 만들어 RSSetState, OMSetDepthStencilState, OMSetBlendState로 걸고, 셰이더·입력 레이아웃·토폴로지도 각자 Set*이 있습니다. 문제는 두 가지입니다.

  • 드라이버 쪽. 하드웨어에서는 단계 사이에 의존이 있습니다(예: 픽셀 셰이더 출력 형식과 렌더 타깃 포맷, 블렌드 상태). 드라이버는 드로우 직전에야 전체 조합을 알 수 있어서, 그때 GPU 코드를 다시 맞추는 비용을 런타임에 치릅니다.
  • 프로그램 쪽. 상태가 하나씩 바뀌므로 "지금 무엇이 걸려 있는가"를 추적해야만 알 수 있습니다. 다른 코드(예: ImGui 렌더러)가 바꿔 놓은 상태로 다음 드로우가 그려지는 버그가 여기서 나옵니다.

4-2. D3D12의 불변 객체

D3D12는 셰이더 바이트코드부터 렌더 타깃 포맷까지를 D3D12_GRAPHICS_PIPELINE_STATE_DESC 하나로 받아 불변 객체를 만들고, 드로우 때는 SetPipelineState 한 번으로 바꿉니다. 드라이버가 생성 시점에 전체 조합을 보고 GPU 코드를 끝까지 컴파일하고 검증하므로, 드로우 시점의 비용과 오류가 앞으로 당겨집니다. 대신 생성 자체가 무겁고(코드 주석의 표현으로 수~수십 ms), 조합마다 객체를 미리 만들어 두는 일이 프로그램 몫이 됩니다.

두 API를 한 인터페이스로 덮을 때, 개별 상태를 인터페이스로 두면 D3D12 쪽이 드로우마다 PSO를 조립하고 캐시해야 하고, PSO를 인터페이스로 두면 D3D11 쪽은 상태 객체 몇 개를 한 클래스에 묶기만 하면 됩니다. 이 엔진이 1단계부터 PSO를 인터페이스로 둔 이유입니다(D22). D3D11에서 성능 이득은 없고, 얻는 것은 "모든 드로우의 상태가 Desc 하나로 설명된다"는 정확성과 이식성입니다.

5. PipelineStateDesc와 해시

5-1. 필드

RHI/PipelineTypes.h의 PipelineStateDesc는 D3D12 desc의 모양을 따르고, 열거형은 모두 uint8_t입니다(키가 작을수록 좋기 때문). 기본값만으로 "불투명, 깊이 테스트 켬, 뒷면 컬링, 솔리드, 트라이앵글 리스트, 출력 R8G8B8A8_UNORM 1장, 깊이 D24_UNORM_S8_UINT"가 됩니다.

5-2. 내용으로 해시하는 이유

렌더러가 드로우 직전에 가진 것은 "원하는 설정"뿐이고 PSO 객체는 아직 없습니다. 그래서 캐시는 "설정 → PSO" 사전이어야 하고 키는 Desc 내용입니다. RHI/PipelineTypes.cpp의 PipelineStateDesc::Hash는 필드를 선언 순서대로 하나씩 섞습니다. 섞는 함수 HashCombine은 boost hash_combine의 64비트판(황금비 상수 0x9E3779B97F4A7C15)이고, 시드만 FNV offset basis를 씁니다. 해시는 unordered_map이 버킷을 고를 때 한 번 쓰이고, 최종 판정은 operator==가 합니다.

구조체를 memcmp나 바이트 해시로 처리하지 않는 이유가 넷입니다.

  1. 패딩. 정렬 패딩 바이트의 값은 정해져 있지 않아서, 같은 내용이 다른 키가 되고 캐시 미스가 계속 납니다.
  2. ±0. -0.0f == 0.0f이지만 비트가 다릅니다. HashFloat가 -0을 +0으로 바꿔 넣습니다.
  3. 쓰는 만큼만. rtvCount 뒤의 포맷, attributeCount 뒤의 속성, bindingLayoutCount 뒤의 핸들은 섞지도 비교하지도 않습니다. 또 independentBlend가 꺼져 있으면 D3D가 rt[0]만 보므로 해시도 rt[0]만 넣습니다(BlendSlotCount).
  4. 접두사 충돌. 배열 길이를 먼저 섞어서 [A]와 [A, B]가 이어지는 값으로 겹치지 않게 합니다.

핸들은 index와 generation을 둘 다 섞습니다. 같은 슬롯을 재사용한 새 셰이더는 다른 키가 됩니다. 불변식은 "a == b이면 Hash(a) == Hash(b)"이고, 그래서 operator==는 해시와 같은 필드를 같은 범위로 비교합니다. 하위 Desc(RasterizerDesc 등)의 ==는 C++20 = default라 필드를 추가해도 비교에서 빠지지 않습니다. PipelineStateDesc 자체는 "쓰는 만큼만" 규칙 때문에 손으로 씁니다.

6. 두 단계 캐시: Renderer의 작은 키, Device의 Desc 키

6-1. 패스 표와 m_passDesc

Renderer는 그래픽스 패스를 Graphics/Renderer.h의 PassId(23개 계산값)로 나누고, Graphics/Renderer.cpp의 kPasses 표에 패스마다 (이름, VS, PS, 레이아웃 목록)을 적습니다. 예: { "Main", Shader_BasicVS, Shader_BasicPS, { Layout_Frame, Layout_Object, Layout_Material }, 3 }. 레이아웃 순서가 곧 셋 인덱스(kSetFrame = 0 등)입니다. 컴퓨트는 ComputePassId(13개 계산값)와 kComputePasses가 따로 있습니다.

Renderer::BuildPassDescs는 이 표와 지금의 셰이더 핸들로 m_passDesc[Pass_Count]를 채운 뒤, 패스마다 다른 고정 부분만 덮어씁니다. 그림자는 rtvCount = 0, dsvFormat = D32_FLOAT, depthBias = 2000·depthBiasClamp = 0.01·slopeScaledDepthBias = 2.0, 스카이는 LessEqual에 쓰기 끔, 풀스크린 패스는 깊이 없음(dsvFormat = Unknown), UI는 알파 블렌딩과 UNORM 출력입니다. 마지막에 작은 키 캐시와 패스별 핸들을 전부 비웁니다. 셰이더를 추가하는 절차(ShaderId → kShaders → 필요하면 PassId·kPasses → BuildPassDescs)는 이 파일 머리 주석에 있고, 로드·핫리로드 감시·cbuffer 대조·바인딩 대조·해제는 모두 표를 돌기 때문에 다른 곳을 고칠 필요가 없습니다.

6-2. 작은 키

Renderer::GetPipelineFor는 BuildDrawList에서 드로우 항목마다 매 프레임 불립니다. 여기서 매번 PipelineStateDesc 전체를 복사하고 해시하면 낭비라서, 메인 PSO를 가르는 몇 가지만 비트로 접어 m_mainPipelines(unordered_map<uint32_t, PipelineHandle>)에서 먼저 찾습니다.

각 비트가 Desc에서 바꾸는 것은 다음과 같습니다. vertexFormat은 정점 레이아웃과 스킨 VS(Pass_MainSkin), mirrored(월드 행렬의 행렬식이 음수)는 frontCounterClockwise 반전, wireframe은 FillMode, cullBack은 CullMode, blended는 프리멀티플라이드 블렌드·깊이 쓰기 끔·속도 RT(1번) 쓰기 막기(independentBlend), ocean은 Pass_Ocean(Gerstner VS)입니다. 바다 VS는 스킨 정점을 읽지 않으므로 스킨 포맷이면 비트 12를 켜지 않습니다. RTV는 항상 FP16 HDR + 속도(R16G16_FLOAT), rtvCount = 2, 깊이 D24_UNORM_S8_UINT입니다. sRGB 출력에 따라 달라지는 것은 톤 패스 PSO(m_tonemapPipelines[2])뿐입니다(색공간 문서 5장).

이 키로 나올 수 있는 PSO 수는 메인 48(스킨 아닌 포맷 2⁵ + 스킨 2⁴), G-buffer 24, 그림자 8입니다 계산값. 여기에 패스마다 한두 개인 것(스카이 1, 톤 2, 후처리 2, 디퍼드 라이팅 1, SSAO 2, 시간 패스 3, 파티클 1, 디버그 선 1, UI 2)을 더하면 그래픽스 PSO는 많아야 약 95개입니다 계산값. 실제 씬은 그중 쓰는 조합만 만듭니다.

6-3. 찾는 흐름

두 단계를 두는 이유는 하는 일이 다르기 때문입니다. 작은 키는 "드로우마다 싸게 찾기"이고, Desc 키는 "내용이 같으면 객체 하나"를 보장합니다. 예를 들어 메인과 G-buffer는 작은 키 모양이 같아도 Desc가 달라 다른 PSO가 되고, 반대로 다른 경로에서 같은 Desc를 만들면 Device가 같은 핸들을 돌려줍니다.

처음 만나는 조합은 그 프레임에 생성 비용을 치릅니다. 그래서 Renderer::Initialize는 첫 프레임 전에 기본 PSO 열 개(메인·그림자·스카이·톤·후처리 둘·G-buffer·디퍼드 라이팅·SSAO 둘)를 만들어 보고, 하나라도 실패하면 초기화를 실패시킵니다. 생성 실패를 시작할 때 보게 하려는 것입니다.

찾은 핸들은 정렬에도 쓰입니다. BuildDrawList는 드로우 목록을 불투명 → 블렌딩, 그 안에서 pipeline.index → 재질 → 메시 순으로 정렬하고, DrawItems는 직전 드로우와 핸들이 같으면 SetPipelineState를 건너뜁니다(lastPipeline, 통계 pipelineSwitches). "직전" 기억은 패스 안에서만 유효해서, ImGui나 다른 패스가 상태를 바꿔도 패스의 첫 드로우에서 다시 겁니다.

6-4. 세대로 한꺼번에 버리기

PSO는 하나씩 지우지 않습니다. 셰이더 핫리로드(Renderer::ReloadShaders)는 새 셰이더를 컴파일한 뒤 BuildPassDescs로 새 셰이더 핸들을 Desc에 넣고 작은 키 캐시를 비운 다음, Device::InvalidatePipelines로 Device 캐시를 비웁니다. 캐시의 Clear는 세대를 1 올리므로, 이전 세대의 핸들은 Get에서 nullptr가 됩니다. 캐시가 비면 인덱스가 0부터 다시 시작해서, 세대가 없으면 옛 핸들이 엉뚱한 새 PSO를 가리킬 수 있었습니다. 컴퓨트 PSO도 같은 세대를 씁니다(D3D11은 m_pipelines.GetGeneration()을 빌려 쓰고, D3D12는 같은 캐시 클래스 안에 둠).

두 백엔드의 차이는 해제 시점입니다. D3D11 PipelineStateCache::Clear는 객체를 바로 놓습니다. D3D12 D3D12PipelineStateCache::Clear는 GPU가 앞 프레임에서 아직 그 PSO를 쓰고 있을 수 있으므로 Detach한 ID3D12PipelineState를 DeferRelease에 넘기고, 그 프레임의 펜스가 지난 뒤 해제합니다(동기화 문서). 컴파일이 실패하면 ReloadShaders가 이전 셰이더를 그대로 두고 캐시도 비우지 않습니다.

7. 두 백엔드의 PSO

7-1. D3D11: 상태 객체를 묶어 흉내 낸다

RHI/D3D11/PipelineState.cpp의 PipelineState::Create는 Desc 하나로 입력 레이아웃·래스터라이저·깊이스텐실·블렌드 상태 객체 네 개를 만들고 VS·PS·토폴로지와 함께 보관합니다. 입력 레이아웃은 정점 셰이더 바이트코드로 시그니처를 검증하므로, D3D11Shader가 바이트코드 사본을 들고 있습니다. Bind는 D3D12의 SetPipelineState 한 번에 해당하는 호출 일곱 개(IASetInputLayout, IASetPrimitiveTopology, VSSetShader, PSSetShader, RSSetState, OMSetDepthStencilState, OMSetBlendState)를 합니다. 1단계의 완료 기준은 "Renderer 코드에 개별 상태 호출이 남지 않는다"였고, grep으로 이 일곱 줄만 남았음을 확인했습니다 확인함 (2026-09-23) (1단계 검증).

상태 객체는 PSO마다 따로 만듭니다. 같은 래스터라이저 설정을 여러 PSO가 공유하게 하는 하위 캐시는 "PSO 수가 늘어나면 추가"한다고 주석에 남아 있습니다. D3D11CommandList::SetPipelineState는 같은 핸들이어도 Bind를 다시 하는데, 건너뛰기는 Renderer의 lastPipeline이 맡습니다. 이 함수는 PSO의 깊이 쓰기 여부(m_pipelineDepthWrite)도 기억해 둡니다.

7-2. D3D12: 진짜 PSO와 공유 루트 시그니처

RHI/D3D12/D3D12PipelineState.cpp의 D3D12PipelineState::Create는 먼저 D3D12Device::GetOrCreateRootLayout에서 레이아웃 조합에 맞는 루트 시그니처를 얻고(같은 조합이면 shared_ptr로 공유), D3D12_GRAPHICS_PIPELINE_STATE_DESC를 채워 CreateGraphicsPipelineState를 부릅니다. rtvFormats·dsvFormat·sampleCount가 실제로 쓰이는 곳이 여기입니다. D3D12CommandList::SetPipelineState는 같은 핸들이면 건너뛰고, 루트 시그니처가 바뀌었을 때만 SetGraphicsRootSignature를 부르며 그때 모든 셋의 테이블을 dirty로 표시합니다. 루트 파라미터 배치는 바인딩 문서에서 다룹니다.

7-3. 컴퓨트 PSO

ComputePipelineDesc는 셰이더 하나와 레이아웃 목록뿐이라 그래픽스 Desc와 따로 둡니다. 정점 레이아웃·블렌드 같은 의미 없는 필드가 해시에 섞이지 않게 하려는 것입니다. 두 백엔드 모두 레이아웃의 슬롯이 전부 ShaderStageMask_Compute여야 받아들입니다. D3D11에는 컴퓨트 PSO 객체가 없어서 D3D11Device::CreateComputePipeline이 Desc와 ID3D11ComputeShader를 벡터에 넣고, D3D12는 CreateComputePipelineState로 만듭니다. 캐시 키 ComputePipelineDesc::Hash(RHI/PipelineTypes.h)는 그래픽스 쪽과 섞는 방식이 다릅니다. h ^= v; h *= 1099511628211을 되풀이하는 진짜 FNV-1a이고, 그래픽스 PipelineStateDesc::Hash는 시드만 FNV offset basis이고 섞기는 HashCombine입니다(5-2). 그래서 헤더 주석의 "PipelineStateDesc::Hash 와 같은 방식"은 정확하지 않습니다. 두 Desc는 서로 다른 캐시에 들어가므로 동작에는 영향이 없습니다. Renderer 쪽 GetComputePipeline은 실패를 m_computeTried로 기억해 매 프레임 다시 묻지 않습니다. 컴퓨트 경로 전체는 컴퓨트·UAV 문서에 있습니다.

8. 셰이더 컴파일, 리플렉션, 바인딩 대조

8-1. fxc, DXBC, SM 5.0

셰이더는 kShaders 표의 42개입니다 계산값. 빌드 때 MSBuild FxCompile(SherlockEngine.vcxproj, <ShaderModel>5.0)이 .cso를 만들고, 실행 시 ShaderCompiler::LoadOrCompile이 이를 읽습니다. Debug 빌드에서는 소스 .hlsl이나 그것이 include 하는 헤더 중 하나라도 .cso보다 새로우면 D3DCompileFromFile로 다시 컴파일합니다(D3DCOMPILE_DEBUG | D3DCOMPILE_SKIP_OPTIMIZATION, Release는 OPTIMIZATION_LEVEL3). 프로파일은 RHI/DXBC/ShaderCompiler.cpp의 GetTargetProfile이 스테이지로 정합니다(vs_5_0, ps_5_0, cs_5_0). 호출자는 셰이더 모델을 모릅니다.

D3D12는 DXBC(SM 5.x)와 DXIL(SM 6.x)을 모두 받습니다. 이 엔진은 두 백엔드에 같은 DXBC를 넘깁니다. D3D12Device.h 주석의 이유는 "두 백엔드가 같은 .cso를 쓰므로 픽셀 비교가 의미 있다"는 것이고, DXIL(dxc)은 SM 6 기능이 필요해지면 들인다고 적혀 있습니다. SM 5.0 DXBC라서 D3D12 루트 시그니처의 레지스터 space도 전부 0입니다(D3D12PipelineState.h 주석).

8-2. 리플렉션으로 C++와 HLSL을 대조한다

Renderer::LoadShaders는 바이트코드를 얻은 뒤 두 가지를 검사하고, 통과해야 CreateShader로 핸들을 바꿉니다. 둘 다 D3DReflect(ID3D11ShaderReflection)로 DXBC를 읽습니다.

  1. cbuffer 크기 (Debug만). ReflectConstantBuffers가 셰이더의 cbuffer를 전부 읽어 kConstantBuffers 표의 C++ 구조체 크기와 맞춥니다. 표에 없거나 크기가 다르면 로드 실패입니다. HLSL 패킹 규칙(float3 뒤 스칼라)이 어긋나면 화면이 조용히 깨지는 대신 여기서 잡힙니다.
  2. 바인딩 대조 (Renderer::ValidateBindings). 패스마다 (1) 그 패스의 레이아웃끼리 같은 레지스터를 같은 스테이지에 선언하지 않았는지, (2) VS·PS가 실제로 쓰는 b#/t#/s#/u#가 그 패스의 레이아웃 중 하나에 그 스테이지로 선언됐는지 봅니다. 컴퓨트 패스도 같은 규칙(스테이지 Compute)입니다.

로그는 슬롯마다 한 줄입니다. 통과하면 바인딩 대조: [Main] BasicPS t0 ('…') OK처럼, 빠지면 바인딩 대조: [패스] 셰이더가 t3 ('…')를 쓰지만 이 패스의 BindingLayout에 그 스테이지로 선언되지 않음. 꼴로 찍힙니다([패스]는 kPasses의 이름, 셰이더는 kShaders의 디버그 이름). Debug에서는 실패하면 로드가 실패하고(핫리로드라면 이전 셰이더 유지), Release에서는 에러 로그만 남기고 계속합니다. 검사 단위가 패스인 이유는 레지스터가 PSO 하나 안에서만 유일하면 되기 때문입니다. 다른 패스는 같은 번호를 다른 용도로 써도 됩니다.

이 검사가 RHI에 특히 중요한 이유는 D3D11과 D3D12가 실수에 다르게 반응하기 때문입니다. D3D11은 선언 안 된 슬롯에 남아 있던 리소스를 그대로 읽어 "우연히 맞는" 화면을 낼 수 있고, D3D12는 루트 시그니처에 없는 레지스터를 쓰는 셰이더로 PSO를 만들지 못합니다. 셰이더를 고칠 때 한쪽 백엔드에서만 드러나는 오류를 로드 시점의 같은 메시지로 바꿔 줍니다.

9. 리소스 생성 규칙 (짧게)

리소스도 "Desc → 핸들"입니다. 규칙 중 두 백엔드가 똑같이 지켜야 하는 것은 RHI 헤더의 constexpr 함수로 올려 두어, 두 CreateBuffer·CreateTexture가 같은 이유로 거절합니다.

  • RHI/ResourceDesc.h의 ValidateBufferDesc: Raw·간접 인자·UAV 버퍼는 Default usage만, Raw는 stride 0·크기 4의 배수, 간접 인자는 Raw 필수. Dynamic 버퍼는 D3D12에서 업로드 링 조각이라 GPU가 쓸 수 없습니다.
  • CanBeUnorderedAccess: 텍스처 UAV는 2D만, 깊이·MSAA·sRGB·블록 압축은 안 됨.
  • 바인드 플래그(TextureBind_*, BufferBind_*)는 생성할 때 정합니다. DepthStencil | ShaderResource(그림자 맵·씬 깊이)와 렌더 타깃 + SRV인 UNORM 색 텍스처는 백엔드가 TYPELESS 리소스로 만들고 뷰마다 포맷을 줍니다(색공간 문서 5장).
  • Format 열거형은 DXGI 포맷의 부분집합이고, 헤더 주석은 "새 값은 끝에 붙임 (기존 값의 번호가 PSO 캐시 키에 들어감)"이라고 적습니다.

바인딩 레이아웃과 리소스 셋은 바인딩 문서, 배리어·펜스·Dynamic 버퍼 링은 동기화 문서, 텍스처 로딩과 포맷 선택은 텍스처 파이프라인 문서에 있습니다.

11. 실험

에디터에서 바로 할 수 있는 것부터 적었습니다. 코드를 잠깐 바꾸는 실험(E4, E5)은 확인한 뒤 되돌립니다.

E1. 캐시 적중을 로그로 보기 확인함 (2026-09-23)

F1(와이어프레임)과 컬링을 토글하면 새 조합마다 PSO 생성 #N (fill=…, cull=…, layouts=…, gen=…). 캐시 크기 M이 한 번씩 찍히고, 같은 조합으로 돌아가면 찍히지 않아야 합니다. 1단계 때는 #1 (fill=wire, cull=2). 캐시 크기 2 → #2 (fill=wire, cull=0). 캐시 크기 3이었습니다(1단계 검증). 지금은 시작할 때 기본 PSO 열 개를 먼저 만들고 로그 형식에 layouts·gen이 붙어서 번호와 크기는 그때와 다릅니다.

E2. 핫리로드와 세대 예상

Debug 실행 중 Shaders/BasicPixelShader.hlsl을 고쳐 저장합니다. PSO 캐시 비움 (N개). 이전 세대 1 의 핸들은 무효. 뒤에 gen=2로 PSO가 다시 생성되고, Stats의 reloads가 1 늘어야 합니다. 일부러 문법 오류를 내면 "셰이더 핫리로드 실패. 이전 셰이더를 유지한다."가 찍히고 화면은 그대로여야 합니다.

E3. 두 백엔드 비교 확인함 (2026-11-23)

같은 씬을 --backend=d3d11과 --backend=d3d12로 찍어 비교합니다. Gerstner 바다를 넣을 때 기록된 결과는 "D3D11 = D3D12 픽셀 동일"입니다(바다 구현 기록). 같은 DXBC를 두 백엔드에 넘기는 설계(8-1)가 이 비교를 가능하게 합니다.

E4. RTV 포맷을 틀리게 넣어 보기 예상

GetPipelineFor에서 desc.rtvFormats[1] = kVelocityFormat을 잠깐 Format::R16G16B16A16_FLOAT로 바꿉니다. D3D11은 이 필드를 읽지 않아 화면이 그대로이고, D3D12는 Debug Layer가 드로우마다 PSO와 RTV의 포맷 불일치를 보고해야 합니다. "D3D11이 감춰 주는 것"을 직접 보는 실험입니다.

E5. 바인딩 대조를 깨 보기 예상

Renderer::CreateLayouts에서 Layout_Material의 슬롯 하나(예: Shaders/Material.hlsli가 선언하는 t3 AO)를 잠깐 뺍니다. Debug 실행은 그 레지스터를 실제로 쓰는 셰이더와 패스마다(예: [Main] BasicPS, [MainSkin] BasicPS, G-buffer 패스는 GBufferPS) "선언되지 않음" 에러를 남기고 셰이더 로드에 실패해야 합니다. Release에서는 같은 에러가 찍히고 실행은 계속됩니다.

E6. 정렬이 PSO 전환을 줄이는가 예상

Stats 창에서 draws와 PSO switches를 봅니다. 불투명 재질이 모두 같은 설정이면 메인 패스의 전환은 거의 1입니다. 재질 하나를 양면(doubleSided)으로 바꾸면 메인·G-buffer 키의 cullBack과 그림자 키의 비트 9가 함께 달라지므로, PSO cache는 패스마다 하나씩 최대 세 개 늘고(그 경로가 이번 프레임에 쓰일 때) 각 패스의 전환도 하나씩 늘어야 합니다. 재질의 alphaCutoff를 0보다 크게 하면 메인·G-buffer 키는 그대로이고 그림자 키의 비트 10만 달라지므로 그림자 쪽만 하나 늘어야 합니다. 전환 수가 드로우 수에 가까우면 정렬이 동작하지 않는 것입니다.

12-1. 알려진 한계

  • 조합 폭발. PSO 수는 재질 옵션 × 정점 포맷 × 설정 × 패스의 곱입니다. 지금 상한은 약 95개(6-2)라 문제가 없지만, 키 비트가 하나 늘 때마다 메인 조합이 두 배가 됩니다. 대응은 관리입니다(캐시, 개수 통계, 필요하면 미리 생성).
  • 디스크 캐시와 비동기 생성이 없음. D3D12 PSO는 실행마다 처음부터 만들고(ID3D12PipelineLibrary나 cached blob을 쓰지 않음), 생성은 렌더 스레드에서 동기로 합니다.
  • D3D11 상태 객체를 PSO끼리 공유하지 않음. 하위 캐시는 PSO 수가 늘면 넣는다고 주석에만 있습니다.
  • 스텐실 연산·참조값, 블렌드 팩터가 없음. 쓰는 단계가 오면 Desc와 CommandList에 더합니다.
  • 셰이더 모델이 두 곳에서 정해짐. 런타임은 GetTargetProfile, 빌드는 .vcxproj의 <ShaderModel>5.0. 올릴 때 둘을 같이 바꿔야 합니다(22.4).
  • SM 5.0 고정. 웨이브 연산, 16비트 타입, 메시 셰이더 같은 SM 6 기능은 dxc·DXIL을 들여야 쓸 수 있고, 그 순간 리플렉션 경로(ID3D11ShaderReflection)도 바뀝니다.
  • 핸들의 대소 비교는 쓰는 곳이 없음. <=>가 만든 연산자이고, 정렬은 pipeline.index를 직접 비교합니다(D21).
