1. 왜 컴퓨트 셰이더가 필요한가

1-1. 그래픽스 파이프라인은 "자기 픽셀"에만 쓴다

픽셀 셰이더의 출력은 래스터라이저가 정해 준 한 픽셀, 그것도 렌더 타깃(RTV)의 그 자리 하나로만 갑니다. 화면 크기의 이미지를 만드는 일에는 이 제약이 문제가 되지 않습니다. 반면 결과가 이미지가 아닌 일, 예를 들어 조명 목록을 상자별로 나누거나 살아 있는 파티클 수를 세는 일은 출력 위치를 셰이더가 정해야 하고, 여러 스레드가 같은 카운터를 늘려야 합니다. 이런 일은 픽셀 셰이더로 하기 어렵습니다.

컴퓨트 셰이더에는 정점·래스터라이저·출력 병합 단계가 없습니다. CPU가 "그룹을 몇 개 돌려라"(Dispatch)라고 부르면 GPU가 그만큼 스레드를 띄우고, 각 스레드는 자기 번호로 무엇을 할지 정합니다. 쓰기는 UAV(Unordered Access View)를 거쳐 리소스의 아무 자리에나 할 수 있고, 같은 그룹의 스레드끼리는 공유 메모리(groupshared)로 값을 주고받을 수 있습니다.

2. 스레드·그룹·디스패치

2-1. 세 단계의 묶음

셰이더 함수 위의 [numthreads(X, Y, Z)]가 그룹 하나의 스레드 배치를 정하고, CPU의 Dispatch(gx, gy, gz)가 그룹을 몇 개 띄울지 정합니다. 스레드 수는 X·Y·Z × gx·gy·gz입니다. 그룹은 GPU의 한 연산 유닛 위에서 함께 돌아가므로 공유 메모리와 그룹 동기화는 그룹 안에서만 뜻이 있고, 그룹끼리는 실행 순서도 정해져 있지 않습니다.

2-2. 시스템 값 네 개

시맨틱뜻우리 셰이더
SV_GroupID디스패치 안에서 이 그룹의 번호 (uint3)쓰는 셰이더 없음
SV_GroupThreadID그룹 안에서 이 스레드의 번호 (uint3)쓰는 셰이더 없음
SV_DispatchThreadID디스패치 전체에서의 번호. GroupID × numthreads + GroupThreadID블러·가중치·파티클·클러스터 대부분
SV_GroupIndex그룹 안 번호를 1차원으로 편 값. z·X·Y + y·X + xClusterScanComputeShader.hlsl 의 CS_ClusterScan (그룹 하나라 이것이 곧 전체 번호)

우리 셰이더는 한 스레드가 원소 하나(픽셀 하나, 파티클 칸 하나, 상자 하나)를 맡는 단순한 배치가 대부분이라 SV_DispatchThreadID만으로 충분합니다. 그룹 번호와 그룹 안 번호를 따로 쓰는 것은 그룹이 타일 하나를 공유 메모리에 올려 같이 처리하는 경우인데, 지금 엔진에는 그런 셰이더가 없습니다.

2-3. 그룹 크기와 가장자리 스레드

블러는 [numthreads(8, 8, 1)], 1차원 작업(가중치, 파티클, 클러스터 대부분)은 [numthreads(64, 1, 1)]입니다. 크기를 왜 이렇게 정했는지 적힌 주석은 없습니다. 일반적인 이유는 이렇습니다. GPU는 스레드를 32개(NVIDIA warp)나 64개(AMD wave) 단위로 함께 실행하므로 그룹 크기가 그 배수여야 놀리는 레인이 없습니다. 64는 두 쪽 모두의 배수입니다. 2차원 작업을 8×8 정사각형으로 묶으면 이웃 픽셀을 읽는 패턴이 캐시에 잘 맞습니다. 그룹이 너무 크면 레지스터와 공유 메모리를 많이 잡아 한 유닛에 동시에 올라가는 그룹 수가 줄어듭니다.

이미지 크기가 8의 배수가 아니면 그룹 수를 올림으로 잡으므로 마지막 줄의 그룹에 텍스처 밖 스레드가 생깁니다. 그래서 블러 CS의 첫 줄은 if (id.x >= (uint)postView.z || id.y >= (uint)postView.w) return;이고, 가중치 CS는 if (i > radius) return;입니다. 예를 들어 1366×768이면 그룹은 (171, 96)이고 오른쪽 마지막 그룹 열의 8 열 중 6 열만 텍스처 안입니다(171 × 8 = 1368) 계산값. 1920×1080과 1280×720은 8로 나누어떨어져 남는 스레드가 없습니다.

2-4. 공유 메모리와 그룹 동기화

groupshared 변수는 그룹의 스레드들이 함께 보는 빠른 메모리입니다(cs_5_0에서 그룹당 32 KB). 한 스레드가 쓴 값을 다른 스레드가 읽으려면 그 사이에 GroupMemoryBarrierWithGroupSync()를 둬야 합니다. 이 함수는 그룹의 모든 스레드가 이 지점에 올 때까지 기다리고, 그때까지의 공유 메모리 쓰기가 보이게 합니다. 엔진에서 이것을 쓰는 셰이더는 클러스터 누적합 하나입니다.

groupshared uint gsScan[SCAN_THREADS];   // 1024 × 4 B = 4 KB

for (uint offset = 1; offset < SCAN_THREADS; offset <<= 1)
{
    uint add = 0;
    if (t >= offset) add = gsScan[t - offset];
    GroupMemoryBarrierWithGroupSync();   // 모두 읽은 뒤에
    gsScan[t] += add;
    GroupMemoryBarrierWithGroupSync();   // 모두 쓴 뒤에 다음 단계
}

CS_ClusterScan은 [numthreads(1024, 1, 1)](cs_5_0의 그룹당 최대 스레드 수) 그룹 하나로 상자 3456개의 누적합을 냅니다. 스레드 하나가 상자 4개를 맡아서(SCAN_PER_THREAD = 4) 1024 × 4 = 4096칸으로 3456개를 덮습니다. 주석에 적힌 주의가 둘 있습니다. 반복 횟수가 상수라서 루프 안의 그룹 동기화가 문제없다는 것(스레드마다 반복 횟수가 다르면 일부 스레드가 동기화 지점에 오지 않습니다), 그리고 삼항 연산자 대신 if를 쓴 이유가 공유 메모리의 범위 밖 읽기를 막기 위해서라는 것입니다. 알고리즘 자체는 클러스터드 라이팅 학습에서 다룹니다.

3. UAV와 SRV, 버퍼와 텍스처

3-1. 뷰는 "어떻게 접근할지"의 약속

같은 GPU 메모리라도 셰이더가 어떻게 접근하는지는 뷰가 정합니다. SRV(Shader Resource View, t#)는 읽기 전용이고 텍스처는 샘플러로 필터링할 수 있습니다. UAV(u#)는 읽기·쓰기를 아무 자리에나 할 수 있지만 필터링은 없고, 원자 연산(InterlockedAdd 등)은 UAV와 공유 메모리에만 됩니다. 한 리소스가 두 뷰를 다 가지려면 만들 때 두 바인드 플래그를 모두 줘야 합니다.

3-3. float4 UAV는 읽을 수 없다 — 입력은 SRV로

D3D11.0(기능 수준 11_0)이 반드시 지원하는 typed UAV 읽기는 R32_FLOAT·R32_UINT·R32_SINT 같은 단일 32비트 포맷뿐이라, RWTexture2D<float4>(FP16 RGBA) 읽기는 보장되지 않습니다. D3D11.3·D3D12는 TypedUAVLoadAdditionalFormats를 지원하는 GPU에서 FP16도 읽을 수 있지만, 이 엔진은 그 기능에 기대지 않습니다. 그래서 블러는 같은 텍스처를 제자리에서 읽고 쓰지 않고, 입력을 SRV(t13)로 읽어 다른 텍스처의 UAV(u0)에 씁니다. 가로 패스는 hdr → PostTemp, 세로 패스는 PostTemp → hdr로 핑퐁합니다(TextureBind_UnorderedAccess 주석, BlurComputeShader.hlsl 머리 주석). 이웃 픽셀을 읽는 블러는 어차피 제자리 쓰기를 할 수 없기도 합니다. 다른 스레드가 아직 읽어야 할 픽셀을 먼저 덮어쓰기 때문입니다.

세로 패스가 hdr에 되돌려 쓰므로 씬 HDR 타깃도 UAV 플래그를 갖고 만들어집니다. Renderer::CreateViewTarget(Graphics/RendererTargets.cpp)의 hdr Desc가 TextureBind_RenderTarget | TextureBind_ShaderResource | TextureBind_UnorderedAccess입니다.

4. RHI가 컴퓨트를 드러내는 모양

4-1. 컴퓨트 PSO: 셰이더 하나 + 레이아웃 나열

ComputePipelineDesc(RHI/PipelineTypes.h)는 cs 셰이더 핸들과 bindingLayouts[]·bindingLayoutCount뿐입니다. 정점 레이아웃·래스터라이저·블렌드·RTV 포맷은 컴퓨트에 뜻이 없어서, 그래픽스 PipelineStateDesc에 끼우지 않고 따로 뒀다고 주석에 적혀 있습니다(해시·비교에 의미 없는 필드가 섞이지 않게). 모양은 D3D12_COMPUTE_PIPELINE_STATE_DESC와 같고, 핸들 타입도 ComputePipelineHandle로 따로라 그래픽스 PSO 핸들과 섞으면 컴파일 에러가 납니다(RHI/Handle.h).

렌더러 쪽은 Renderer::kComputePasses 표(패스 이름, CS, 레이아웃 목록)와 Renderer::GetComputePipeline(ComputePassId)입니다. 처음 부를 때 만들고 m_computePipelines[]에 캐시합니다. 실패하면 m_computeTried[]에 표시해 매 프레임 다시 시도하지 않습니다. BlurCompute PSO나 블러 셋이 없으면 블러는 PS 경로로 가고, 클러스터 비닝은 CPU 경로로 내려갑니다. 단, 가중치 PSO(BlurWeights)가 없으면 PS 블러도 가중치 버퍼를 읽으므로 블러 자체를 건너뛰고 오류 로그를 한 번 남깁니다(Renderer::ApplyHdrEffects). 셰이더 핫리로드(BuildPassDescs)가 이 표시를 되돌립니다.

4-2. 레이아웃은 컴퓨트 전용 슬롯만

컴퓨트 PSO에 들어가는 BindingLayout의 슬롯은 모두 ShaderStageMask_Compute여야 합니다. D3D11Device::CreateComputePipeline과 D3D12ComputePipelineState::Create가 같은 검사로 거부합니다. 그래서 블러는 PS 블러가 쓰는 Layout_Post를 같이 쓰지 않고 Layout_BlurCompute를 따로 둡니다(Renderer::CreateLayouts).

Dispatch(gx, gy, gz)렌더 패스 밖에서만(안에서 부르면 오류 로그 1회 후 무시). 그룹 수가 0이면 아무 일도 없음(D3D11)
DispatchIndirect(args, offsetBytes)그룹 수 {X, Y, Z}를 GPU 버퍼에서 읽음. BufferBind_IndirectArgs 버퍼, IndirectArgument 상태, 오프셋은 4의 배수
Barrier(tex/buf, after)상태 전이. 백엔드가 리소스마다 현재 상태를 추적해서 호출 코드는 "이제 무엇으로 쓸지"만 말함
UavBarrier(tex/buf)상태를 바꾸지 않는 UAV → UAV 의존. 리소스가 UnorderedAccess 상태여야 함

5. 상태 전이와 UAV 배리어

5-1. 왜 상태를 말해 줘야 하나

GPU는 앞 명령이 끝나기 전에 다음 명령을 시작합니다. 컴퓨트가 텍스처에 쓰는 도중에 다음 패스가 그 텍스처를 읽기 시작하면 반쯤 쓰인 값을 읽습니다. 또 쓰기는 캐시에 남아 있을 수 있어서, 다른 단계가 읽기 전에 캐시를 비우거나 무효화해야 합니다. D3D12는 이 일을 앱이 배리어로 알려 주게 하고, D3D11은 드라이버가 바인딩을 보고 알아서 합니다. 우리 RHI는 D3D12 쪽 모델을 따르고, D3D11에서는 같은 호출을 기록과 검사에 씁니다.

호출언제D3D12에서 하는 일
Barrier(x, UnorderedAccess)Dispatch가 x를 UAV로 쓰기 전ResourceBarrier(Transition) before → UNORDERED_ACCESS
Barrier(x, ShaderResource)쓴 결과를 SRV로 읽기 전→ PIXEL_SHADER_RESOURCE | NON_PIXEL_SHADER_RESOURCE (PS와 CS 둘 다 읽을 수 있게)
Barrier(args, IndirectArgument)*Indirect가 인자를 읽기 전→ INDIRECT_ARGUMENT
UavBarrier(x)같은 x를 UAV로 연달아 쓰거나 읽는 두 Dispatch 사이D3D12_RESOURCE_BARRIER_TYPE_UAV (상태는 그대로)

UavBarrier를 Barrier와 따로 둔 이유는 주석에 있습니다. Barrier는 "이미 그 상태면 아무 일도 없음" 규칙이라 UAV → UAV 의존을 표현할 수 없습니다. 다른 텍스처나 다른 밉에 쓰거나, 사이에 SRV 전이가 있으면 UAV 배리어는 필요 없습니다.

5-2. 블러 한 번의 상태 흐름

블러는 매번 다른 리소스에 쓰고, 쓴 뒤에는 반드시 SRV로 전이한 다음 읽으므로 UavBarrier를 한 번도 부르지 않습니다. 같은 버퍼를 연달아 쓰는 클러스터 비닝은 정반대입니다. Graphics/RendererClusterBin.cpp 의 Renderer::DispatchClusterBinning은 다섯 Dispatch 사이마다 cmd.UavBarrier(m_clusterGridGpu) 같은 UAV 배리어를 겁니다. 버퍼들이 처음부터 끝까지 UnorderedAccess 상태라 전이가 없기 때문입니다.

5-3. 버퍼 상태는 프레임마다 Common으로

D3D12에서 버퍼는 ExecuteCommandLists가 끝나면 COMMON으로 감쇠(decay)합니다. 우리 RHI는 이것을 숨기지 않고 규칙으로 올렸습니다. 두 백엔드의 EndFrame이 ResetBufferStates()로 추적 상태를 Common으로 되돌리고(D3D11도 같게 맞춤), 그래서 UAV 버퍼는 프레임마다 처음 쓰기 전에 다시 Barrier해야 합니다(CommandList::Barrier(BufferHandle, …) 주석). Renderer::Render가 첫 후처리 패스 전에 Barrier(m_blurWeights, ShaderResource)를 부르는 것이 그 때문입니다. 블러가 꺼진 프레임에도 톤 패스가 t20을 포함한 같은 레이아웃을 바인딩하므로 필요합니다.

6-1. D3D11의 "같은 리소스가 SRV와 UAV에 동시에" 문제

D3D11 런타임은 한 리소스가 SRV 슬롯과 UAV 슬롯에 동시에 꽂히는 것을 허용하지 않습니다. 이때 런타임은 "still bound" 경고를 내고 한쪽 바인딩을 NULL로 만듭니다. Microsoft 문서(OMSetRenderTargets, PSSetShaderResources 설명)는 NULL이 되는 쪽을 입력(SRV)으로 적습니다. 우리 코드 주석은 둘이 서로 다르게 적혀 있고(D3D11CommandList::Barrier는 "다음 바인딩 쪽", Renderer::DispatchBlurCompute는 "UAV 쪽"), 어느 쪽인지 측정한 기록은 없습니다. 어느 경우든 블러 핑퐁에서 세로 패스가 hdr를 u0에 꽂을 때 hdr가 PS t13에 남아 있으면 결과가 깨집니다. 그래서 D3D11CommandList::Barrier는 UnorderedAccess로 들어갈 때 그 리소스의 SRV 바인딩을 모두 풀고, 나올 때 UAV 바인딩을 풉니다. 푼 횟수는 CommandList::Stats의 srvUnbinds·uavUnbinds에 셉니다. D3D12에는 슬롯에 "꽂혀 있는" 상태가 없으므로 이 문제가 없습니다.

E1. PS 블러와 CS 블러 비교 확인함 (2026-11-17)

--compute-blur=1과 --compute-blur=0으로 같은 씬을 연달아 찍어 픽셀을 비교합니다. 로그에 "블러 경로: 컴퓨트 (BlurCS)" 또는 "픽셀 셰이더 (PostPS)"가 한 번 나옵니다. 기록된 결과는 7-4 표와 같습니다. 기록에 따르면 씬 파일이 다시 저장돼 카메라가 바뀐 적이 있으므로, 같은 씬 상태의 연속 실행끼리만 비교합니다(구현 기록 7장).

E2. 그룹 수를 내림으로 바꿔 보기 예상

DispatchBlurCompute의 (width + 7) / 8을 width / 8로 바꾸고, 에디터 씬 뷰 폭을 8의 배수가 아닌 값(예: 730)으로 둡니다. 91 그룹 × 8 = 728 열만 덮이므로 오른쪽 2 열은 세로 패스가 쓰지 않아 블러 전 hdr 값이 남습니다. 블러 반경이 크면 오른쪽 두 열만 선명하게 보입니다.

E3. 출력의 SRV 전이를 빼 보기 예상

DispatchBlurCompute 끝의 Barrier(output, ShaderResource)를 주석 처리합니다. D3D11에서는 다음 패스가 셋을 꽂을 때 CheckSrvState가 "SRV 로 읽는 텍스처 … 가 아직 UnorderedAccess 상태" 오류를 한 번 내고, 출력 텍스처가 CS u0에 남아 있어 런타임이 SRV 쪽을 NULL로 만들므로 블룸·톤 패스가 0을 읽어 화면이 검게 됩니다. D3D12 백엔드는 텍스처의 SRV 상태를 검사하지 않으므로 RHI 로그는 없고, 화면은 GPU에 따라 맞게 나올 수도 있습니다. 디버그 레이어만으로는 잡히지 않고 GPU 기반 검증(--gpu-validation=1)을 켜야 잡힐 것으로 봅니다.

E4. 같은 버퍼를 연달아 쓰는 곳에서 UAV 배리어 빼 보기 예상

Graphics/RendererClusterBin.cpp에서 ClusterScan 앞의 cmd.UavBarrier(m_clusterGridGpu)를 뺍니다. D3D11에서는 드라이버가 대기를 넣으므로 결과가 같아야 합니다. D3D12에서는 Count가 다 쓰기 전에 Scan이 읽을 수 있어 조명 목록이 가끔 틀릴 수 있습니다(깜빡이는 타일). 다만 드라이버와 GPU에 따라 눈에 보이는 차이가 없을 수도 있고, 디버그 레이어나 GPU 기반 검증은 빠진 UAV 배리어를 보고하지 않습니다. 이 실험은 "차이가 안 보인다"가 "배리어가 필요 없다"는 뜻이 아님을 확인하는 데 의미가 있습니다.

11. 함정과 알려진 한계

증상원인이 엔진에서
D3D11에서 CS 결과가 깨지거나 다음 패스가 0을 읽음같은 리소스가 SRV와 UAV에 동시에 꽂혀 런타임이 한쪽을 NULL로 만듦Barrier가 UAV 상태에 드나들 때 겹치는 바인딩을 풂 (6-1). Barrier를 빼먹으면 이 보호도 빠짐
D3D12에서 Dispatch가 셋을 못 봄컴퓨트 루트 인자는 그래픽스와 별개SetComputeResourceSet으로 꽂아야 함. 없으면 "셋 인덱스 … 에 ResourceSet 이 바인딩되지 않음" 로그
오른쪽·아래 가장자리가 처리되지 않음그룹 수를 내림으로 계산(w + 7) / 8·(n + 63) / 64로 올림, 셰이더는 범위 검사 후 return (E2)
float4 텍스처를 UAV로 읽는 셰이더가 GPU에 따라 동작하지 않음FL11_0에서 보장되는 typed UAV 읽기는 단일 32비트 포맷만입력은 SRV, 출력은 다른 텍스처의 UAV로 핑퐁 (3-3)
sRGB·깊이·MSAA·BC 텍스처를 UAV로 못 만듦D3D의 UAV 생성 규칙CanBeUnorderedAccess가 CreateTexture에서 거부
둘째 프레임부터 UAV 버퍼 상태 오류버퍼 상태가 프레임 끝에 Common으로 감쇠프레임마다 처음 쓰기 전에 다시 Barrier (5-3)
렌더 패스 안에서 Dispatch가 무시됨RHI 규칙오류 로그 1회. EndRenderPass 뒤에 부를 것
UAV 슬롯이 모자람D3D11.0 CS UAV 슬롯 8개kMaxUavRegister = 8. 파티클 시뮬레이션 셋이 u0~u5를 씀
그룹 동기화 뒤 결과가 GPU마다 다름일부 스레드만 동기화 지점에 오거나, 공유 메모리를 범위 밖으로 읽음CS_ClusterScan은 반복 횟수를 상수로, 범위 밖 읽기는 if로 막음 (2-4)
D3D11에서 PS 블러와 CS 블러가 1 픽셀 다름원인 미확정(mad 합치기가 스테이지마다 다른 것으로 추정)받아들임, precise는 넣지 않음 (7-4)
밉 단위 UAV를 쓸 곳이 없음—ResourceBinding::mip과 GetUAV(device, mip)는 있지만 지금 Graphics에서 mip을 채우는 셋은 없음. 큐브 UAV도 아직 없음
UAV 배리어가 필요한지 헷갈림전이와 UAV 의존은 다른 문제다른 리소스에 쓰거나 사이에 SRV 전이가 있으면 불필요(블러), 같은 UAV를 연달아 쓰면 필요(클러스터·파티클)
기록 문서와 다른 점. 구현 기록(2026-11-17)은 blurWeights(t20)와 kMaxBlurRadius가 Common.hlsli에 있다고 적고 있지만, 지금은 Shaders/Post.hlsli에 있습니다. 또 기록의 버퍼 상태 목록(Common·ShaderResource·UnorderedAccess)과 두 칸짜리 kComputePasses 표는 그 뒤 GPU 파티클과 클러스터 비닝이 들어오면서 IndirectArgument 상태와 13개 패스로 늘었습니다.
