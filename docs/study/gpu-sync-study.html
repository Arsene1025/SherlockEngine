1. 왜 CPU 와 GPU 를 동기화해야 하는가

1-1. GPU 는 나중에 실행한다

CPU 가 DrawIndexed 를 부르는 순간 GPU 가 그리는 것은 아닙니다. D3D12 백엔드에서 명령은 커맨드 리스트에 쌓이기만 하고, D3D12Device::EndFrame 이 Close → ExecuteCommandLists 로 큐에 넣은 뒤에야 GPU 가 실행합니다. D3D11 도 즉시 컨텍스트가 명령을 드라이버 버퍼에 모아 두었다가 보내므로 사정은 같고, 드라이버가 그 차이를 숨겨 줄 뿐입니다.

둘이 서로 기다리지 않고 겹쳐 돌아야 둘 다 쉬지 않습니다. CPU 가 프레임 N+1 의 명령을 만드는 동안 GPU 는 프레임 N 을 그립니다. 대신 같은 메모리를 서로 다른 시점에 만지게 되므로 세 가지 위험이 생깁니다.

위험예이 엔진의 장치
GPU 가 아직 읽는 메모리를 CPU 가 덮어씀프레임 N 의 상수버퍼를 프레임 N+1 이 같은 자리에 씀프레임 슬롯(2장)과 업로드 링(5장)
GPU 가 아직 쓰는 객체를 CPU 가 해제함창 크기가 바뀌어 씬 뷰 텍스처를 다시 만듦지연 해제(9장), WaitForGpu(3장)
GPU 안에서 앞 패스의 쓰기와 뒤 패스의 읽기가 겹침HDR 타깃에 그린 직후 톤 패스가 읽음리소스 상태와 배리어(6장)

앞의 둘은 CPU 와 GPU 사이의 문제이고 펜스로 풉니다. 셋째는 GPU 명령 사이의 순서 문제이고 배리어로 풉니다. D3D11 은 셋을 모두 드라이버가 처리하고, D3D12 는 셋을 모두 애플리케이션이 처리합니다. 그래서 RHI/Device.h 머리 주석은 "D3D11 에서만 편한 것(즉시 Map, 자동 밉 생성, 암묵적 동기화)은 인터페이스에 넣지 않았음"이라고 적고, 두 백엔드가 D3D12 쪽 규칙을 따르게 했습니다.

2. 프레임 슬롯 — kFrameCount

RHI/GraphicsConfig.h 의 kFrameCount = 2 가 "동시에 진행 중일 수 있는 프레임 수"입니다. 프레임 N 은 슬롯 N % kFrameCount 를 쓰고(BeginFrame 이 m_frameIndex 로 계산), 슬롯을 다시 쓰기 전에 그 슬롯을 마지막으로 쓴 프레임 N−2 가 GPU 에서 끝났는지 펜스로 확인합니다. CPU 는 GPU 보다 최대 한 프레임 앞서 기록할 수 있다는 뜻입니다.

3. 펜스와 CPU 가 기다리는 지점

3-1. 펜스 하나, 값은 계속 올라감

ID3D12Fence 는 GPU 쪽에 있는 64비트 정수입니다. 큐에 Signal(fence, v) 를 넣으면 GPU 가 그 앞의 명령을 다 실행한 시점에 값이 v 가 됩니다. CPU 는 GetCompletedValue() 로 읽고, 아직이면 SetEventOnCompletion(v, event) + WaitForSingleObject 로 잠듭니다. 큐가 하나이고 명령이 순서대로 끝나므로, 값 v 가 지났다면 v 를 Signal 하기 전에 넣은 모든 일이 끝났다는 뜻입니다.

// D3D12Device::EndFrame (뒷부분)
m_queue->ExecuteCommandLists(1, lists);
m_commandList.ResetBufferStates();
m_swapChain->Present(m_vsync ? 1 : 0, flags);
m_queue->Signal(m_fence.Get(), m_nextFenceValue);
m_fenceValues[m_frameIndex] = m_nextFenceValue++;

// D3D12Device::BeginFrame (앞부분)
m_frameIndex = m_frameCounter % kFrameCount;
if (m_fenceValues[m_frameIndex] != 0 && m_fence->GetCompletedValue() < m_fenceValues[m_frameIndex])
    { SetEventOnCompletion(...); WaitForSingleObject(m_fenceEvent, INFINITE); }
ReleaseGarbage(m_frameIndex);  ReadTimestamps(m_frameIndex);  m_rings[m_frameIndex].offset = 0;
m_allocators[m_frameIndex]->Reset();  m_list->Reset(...);

펜스 값은 프레임 번호가 아닙니다. m_nextFenceValue 는 EndFrame 과 WaitForGpu 가 함께 올리므로, 로드 중에 업로드를 여러 번 기다리면 값이 프레임보다 빨리 커집니다. 기준은 "슬롯마다 마지막으로 Signal 한 값"(m_fenceValues)이고, 처음 쓰는 슬롯은 0 이라 기다리지 않습니다.

4. Present · 스왑체인 · vsync

두 백엔드 모두 flip 모델 DXGI_SWAP_EFFECT_FLIP_DISCARD 입니다. 백버퍼는 D3D12 가 3장(D3D12Device::kBackBufferCount), D3D11 이 2장(D3D11Device::InitDirect3D 의 BufferCount = 2)입니다. 백버퍼 수와 kFrameCount 는 따로 정해진 값입니다. D3D12 는 이번 프레임에 그릴 백버퍼를 BeginFrame 이 GetCurrentBackBufferIndex() 로 얻고, 백버퍼 텍스처 핸들(GetBackBuffer)은 그 인덱스를 따라갑니다.

설정Present 인자결과
vsync 켬Present(1, 0)모니터 주사율에 맞춰 화면을 바꿈. 큐가 차면 Present 가 CPU 를 붙잡아 프레임률이 주사율로 묶임
vsync 끔 + tearing 지원Present(0, DXGI_PRESENT_ALLOW_TEARING)기다리지 않고 바로 바꿈. 화면 중간에 찢김이 생길 수 있음
vsync 끔 + tearing 미지원Present(0, 0)창 모드 flip 에서는 컴포지터가 주사율로 묶을 수 있음 (D3D11Device::EndFrame 주석)

tearing 지원은 IDXGIFactory5::CheckFeatureSupport(DXGI_FEATURE_PRESENT_ALLOW_TEARING) 로 확인하고, 지원하면 스왑체인을 DXGI_SWAP_CHAIN_FLAG_ALLOW_TEARING 로 만듭니다(ResizeBuffers 도 같은 플래그). vsync 는 engine.vsync(기본 끔), Render Settings 의 VSync 체크박스(Editor/DebugUI.cpp), 에디터의 F3(EditorApp)으로 바꿉니다.

입력 지연은 CPU 가 GPU 보다 얼마나 앞서 가는가로 정해집니다. D3D12 에서는 kFrameCount 의 펜스 대기가 CPU 를 붙잡는 첫 장치이고, DXGI 의 Present 큐가 둘째입니다. D3D11Device.h 의 타임스탬프 주석은 "DXGI 가 최대 3프레임을 큐에 둘 수 있어"라고 적고 있고, D3D11 에서는 이것이 유일한 제한입니다. 엔진은 SetMaximumFrameLatency 나 waitable 스왑체인(GetFrameLatencyWaitableObject)을 쓰지 않습니다.

5. CPU 가 매 프레임 쓰는 메모리 — Dynamic 버퍼

상수버퍼(PerFrame, PerObject, Lights, Material …)는 BufferUsage::Dynamic 입니다. 인터페이스의 약속은 하나입니다. UpdateBuffer 는 "이 프레임 슬롯의 내용을 통째로 교체"합니다. 부분 갱신도, 이전 내용 읽기도 없습니다. 같은 버퍼를 드로우마다 다시 써도 각 드로우가 자기 값을 봐야 한다는 점이 어렵습니다. GPU 는 프레임이 제출된 뒤에 모든 드로우를 실행하기 때문입니다.

D3D11 — Map(WRITE_DISCARD)D3D12 — 프레임별 업로드 링
메모리Dynamic 버퍼마다 D3D11_USAGE_DYNAMIC 버퍼 kFrameCount 개버퍼 자체에는 리소스가 없음 (D3D12Buffer::resource 비어 있음). 슬롯마다 UPLOAD 힙 8 MB 하나, 영구 매핑
UpdateBuffer이번 슬롯 버퍼를 Map(D3D11_MAP_WRITE_DISCARD) → memcpy → UnmapAllocateUpload 가 링에서 256 B 정렬 조각을 잘라 줌 → memcpy → gpuAddress 에 주소 기억
드로우마다 다른 값드라이버가 Map 마다 새 메모리를 줌 (이름 바꾸기, renaming)엔진이 Map 마다 새 조각을 줌. 드로우 직전 ApplyBindings 가 그 주소를 루트 CBV 로 넘김
재사용드라이버가 GPU 가 다 쓴 메모리를 회수그 슬롯의 펜스를 지난 BeginFrame 이 offset = 0
가득 차면드라이버 몫ErrorOnce "프레임 업로드 링이 가득 참" 후 갱신을 건너뜀

그래서 Dynamic 버퍼는 "쓰는 프레임에 반드시 갱신"해야 합니다. D3D11 에서는 다음 프레임에 다른 복제본이 바인딩되고, D3D12 에서는 지난 프레임의 조각이 이미 재사용됐을 수 있습니다. D3D12 의 ApplyBindings 는 updatedFrame 이 이번 프레임이 아닌 Dynamic 상수버퍼를 바인딩하면 "이번 프레임에 갱신되지 않음"을 한 번 로그로 남깁니다. D3D11 에서 복제본을 kFrameCount 개 두는 것은 기능상 필요하지 않습니다. GraphicsConfig.h 주석은 "D3D12 때문"이라고만 적고, rendering-analysis 8.9절은 이전 슬롯에 기대는 코드가 D3D11 에서도 드러나게 하려는 것이라고 설명합니다.

링은 UploadRing::peak 로 최고 사용량을 기록하지만 지금은 어디에도 표시하지 않습니다. 8 MB 에 얼마나 여유가 있는지는 측정 기록이 없습니다.

6. 리소스 상태와 배리어

6-1. 상태가 왜 있나

GPU 는 렌더 타깃에 쓸 때와 텍스처로 읽을 때 메모리를 다르게 다룹니다. 타깃 쓰기는 압축·캐시에 남아 있을 수 있어서, 같은 텍스처를 읽기 전에 캐시를 비우고 압축을 풀고 앞 패스의 쓰기가 끝나기를 기다려야 합니다. D3D12 는 리소스가 매 순간 하나의 상태에 있다고 보고, 용도가 바뀌는 자리에 애플리케이션이 전이 배리어(ResourceBarrier 의 Transition, before → after)를 넣게 합니다. 드라이버는 그 자리에서 필요한 일을 합니다.

6-3. 호출 규칙: "이제 무엇으로 쓸지"만 말한다

CommandList::Barrier(texture, after) 는 before 를 받지 않습니다. 백엔드가 텍스처마다 state 를 기억하고, D3D12CommandList::Barrier 는 그 값을 before 로, 인자를 after 로 ResourceBarrier(1, &barrier) 를 기록한 뒤 state = after 로 고칩니다. 이미 그 상태면 아무것도 하지 않고 통계(Stats::barriers)에도 세지 않습니다. 그래서 "그림자가 꺼진 프레임에도 Barrier(m_shadowMap, ShaderResource)"처럼 상태를 보장하는 호출을 부담 없이 넣을 수 있습니다(Renderer::Render).

  • 텍스처 상태는 프레임을 넘어 유지됩니다. 프레임 끝에 되돌리지 않으므로, 다음 프레임 첫 배리어의 before 는 지난 프레임의 마지막 상태입니다.
  • 버퍼 상태는 프레임마다 Common 으로 돌아갑니다. D3D12 에서 버퍼는 ExecuteCommandLists 가 끝나면 COMMON 으로 감쇠(decay)하므로, EndFrame 이 D3D12CommandList::ResetBufferStates 로 이번 프레임에 건드린 버퍼(m_touchedBuffers)를 Common 으로 돌립니다. D3D11 도 같게 맞춥니다. 그래서 m_blurWeights 같은 버퍼는 매 프레임 처음 쓰기 전에 다시 Barrier 합니다.
  • 버퍼 배리어는 상태 추적 버퍼만. Barrier(BufferHandle) 는 Common · ShaderResource · UnorderedAccess · IndirectArgument 만 받고, 리소스가 없는 Dynamic 버퍼는 거부합니다. 그 밖의 Default 버퍼(정점·인덱스)는 쓰기가 없어 Common 그대로 읽힙니다(ResourceDesc.h 의 IsStateTrackedBuffer).
  • 배리어는 호출마다 하나씩 기록합니다. 여러 전이를 모아 한 번의 ResourceBarrier 로 보내는 묶음도, 시작과 끝을 나누는 split 배리어(BEGIN_ONLY/END_ONLY)도 없습니다. Flags 는 늘 NONE, 서브리소스는 늘 ALL_SUBRESOURCES 입니다(D3D12Convert::TransitionBarrier).

UAV 를 연달아 쓰는 두 Dispatch 사이의 UavBarrier(상태는 그대로, 앞 쓰기가 보이게만 함)와 클러스터 비닝·파티클의 전이 순서는 컴퓨트·UAV 학습에 있습니다.

6-4. 한 프레임 동안의 상태 — 게임 모드, 포워드 경로, 파티클이 있는 프레임

엔진의 Barrier 를 거치지 않는 전이도 있습니다. 초기 데이터 업로드와 UpdateTexture 의 COPY_DEST → 최종 상태(업로드 리스트에 직접 기록, 끝난 텍스처는 ShaderResource 로 기록됨)와, 스크린샷 프레임에 D3D12Device::RecordBackBufferReadback 이 거는 PRESENT → COPY_SOURCE → PRESENT 입니다.

7. 같은 API 를 D3D11 은 어떻게 처리하나

D3D11 에는 상태와 배리어가 없습니다. 드라이버가 바인딩을 보고 해저드를 추적합니다. 대신 런타임 규칙이 하나 있습니다. 같은 리소스가 읽기(SRV)와 쓰기(RTV·DSV·UAV)에 동시에 꽂히면, 런타임이 "still bound" 경고와 함께 한쪽을 NULL 로 만듭니다. 그래서 D3D11CommandList 는 상태를 기록만 하면서, 겹침을 푸는 일을 RHI 호출 자리에서 합니다.

8. GPU 결과를 CPU 로 읽기 — 리드백

GPU 가 만든 값을 CPU 가 읽으려면 그 GPU 일이 끝났어야 합니다. 바로 읽으면 기다려야 하므로, 엔진은 프로파일러와 통계에서 몇 프레임 늦게 읽는 비동기 방식을 쓰고 스크린샷만 동기 방식으로 읽습니다.

Profiler::BeginFrame 은 Engine::BeginFrame 에서, 즉 장치의 BeginFrame 보다 먼저 결과를 가져가므로 패널에는 프레임 N+3 에 나타납니다. D3D11 은 같은 식으로 N+7 입니다 계산값. Profiler 는 결과에 붙은 frameNumber 로 그 프레임에 열었던 구간 목록(gpuPending)을 찾아 짝을 맞추므로 지연이 달라도 구간 이름이 어긋나지 않습니다.

D3D11 이 6세트를 쓰는 이유는 D3D11Device.h 주석에 있습니다. DXGI 가 최대 3프레임을 큐에 둘 수 있어 2~3프레임 전 세트가 아직 GPU 에 있을 수 있고, 결과를 읽지 않은 쿼리에 다시 End 를 부르면 Debug Layer 가 경고합니다. Staging 리드백에서 비슷한 증상이 나온 기록이 있습니다. 처음에 kFrameCount(2)칸 링으로 복사하고 같은 칸을 복사 직전에 읽었을 때 ManyLights256 의 2단계 쌍 수가 77,320 으로 1단계(77,258)보다 많게 나왔고, 4칸 링으로 바꾸고 읽지 못한 칸을 건너뛰게 하자 75,141 로 여러 번 실행해도 같았습니다 확인함 (2026-11-21) (클러스터 비닝 기록 6장). 기록은 원인을 "D3D11 드라이버가 프레임을 2개 넘게 쌓아 읽기가 밀린 것"으로 추정하고, 직접 확인하지는 않았다고 적습니다.

9. 해제 미루기 — 지연 해제

D3D11 은 ComPtr 을 놓아도 GPU 가 다 쓸 때까지 드라이버가 객체를 붙들어 줍니다. D3D11Device::DestroyTexture 는 풀에서 지우기만 합니다. D3D12 는 그렇지 않아서, 이미 기록·제출된 명령이 참조하는 리소스를 지우면 GPU 가 해제된 메모리를 읽습니다. 그래서 D3D12Device::DeferRelease(object) 와 DeferFree(heap, start, count) 가 현재 슬롯의 m_garbage 에 넣어 두고, 그 슬롯의 펜스를 지난 BeginFrame 의 ReleaseGarbage 가 비웁니다. 해제가 최대 2프레임 늦어지고 계산값, 그동안 옛것과 새것이 같이 살아 있습니다.

11. 실험

E1. 백엔드를 바꿔 barriers 값 비교 예상

같은 씬을 --backend=d3d11 과 --backend=d3d12 로 열고 Render Settings 의 "passes … barriers …" 줄을 봅니다. 클러스터 비닝(--cluster-gpu=0)과 파티클을 끈 씬이면 두 값이 같아야 합니다. 켜면 D3D12 쪽이 UavBarrier 호출 수만큼 커야 합니다(7장). 그 밖의 차이는 한쪽 백엔드의 "이미 그 상태면 아무 일도 없음" 처리가 어긋났다는 뜻입니다.

E2. vsync 와 tearing 예상

에디터에서 F3 으로 vsync 를 켜고 끄며 프로파일러의 CPU "Present" 구간과 프레임률을 봅니다. vsync 를 켜면 프레임률이 주사율에 묶이고 대기가 Present(또는 D3D12 의 BeginFrame 펜스 대기)로 옮겨 가야 합니다. 체크박스 옆의 "(tearing OK)"가 안 보이는 환경에서는 vsync 를 꺼도 창 모드에서 주사율에 묶일 수 있습니다.

E3. kFrameCount 를 1, 3 으로 빌드 예상

GraphicsConfig.h 의 값을 바꿔 다시 빌드하고 같은 씬의 스크린샷을 비교합니다. 화면은 같아야 하고, 1 에서는 렌더 기록과 GPU 실행이 겹치지 않아 GPU 시간이 큰 씬에서 프레임 시간이 늘어야 합니다. Staging 리드백은 kFrameCount 프레임 지난 복사만 읽으므로 3 에서도 규칙이 지켜집니다.

E4. 배리어 하나를 빼고 검증 레이어 보기 예상

실험 프로젝트 사본에서 RenderScenePass 끝의 Barrier(view.hdr, ShaderResource) 를 지우고 Debug 빌드 D3D12 로 실행합니다. 톤 패스가 RENDER_TARGET 상태의 텍스처를 SRV 로 읽으므로 Debug Layer 가 상태 불일치 에러를 내야 합니다(GPU 기반 검증을 켜면 셰이더 실행 시점에서 잡음). 같은 사본을 D3D11 로 실행하면 화면이 그대로일 수 있습니다. 7장에서 말한 "D3D11 로는 배리어 실수가 보이지 않는다"를 직접 보는 실험입니다.

통계·타이밍 값이 이상하게 남아 있음아직 끝나지 않은 GPU 결과를 읽었거나, 읽지 못한 칸을 덮어씀8장의 77,320 사례. Staging 링 4칸 + 읽지 못한 칸 건너뛰기
로드·리사이즈 때 끊김WaitForGpu 가 큐를 비움로드 중 업로드는 BeginResourceUploads 로 묶어 대기 횟수를 줄임
업로드 링이 가득 참한 프레임에 갱신한 Dynamic 버퍼 크기 합이 8 MB 초과에러 1회 뒤 그 갱신을 건너뜀. kUploadRingSize 를 키워야 함. 사용량(peak)은 표시하지 않음

구조상의 한계

  • 큐는 직접 큐 하나. CreateCommandQueue 는 한 번이고 컴퓨트·복사 큐가 없습니다. 비동기 컴퓨트(그래픽스와 컴퓨트를 겹쳐 돌리기)와 백그라운드 복사 큐 업로드가 없고, 초기 데이터 업로드도 같은 직접 큐에서 실행한 뒤 기다립니다.
  • 커맨드 리스트는 프레임에 하나. 여러 스레드가 리스트를 나눠 기록하는 구조가 아닙니다. ImGui 도 같은 리스트에 기록합니다.
  • 배리어 묶음·split 배리어 없음. 전이마다 ResourceBarrier 한 번, 항상 전체 서브리소스입니다. 밉 단위 전이가 필요한 기능(예: 컴퓨트 밉 생성)은 지금 인터페이스로 표현할 수 없습니다.
  • 프레임 지연 제어 없음. SetMaximumFrameLatency·waitable 스왑체인을 쓰지 않아, 입력 지연은 kFrameCount 와 DXGI 기본 큐 깊이로 정해집니다.
  • Enhanced Barriers 미사용. D3D12 의 새 배리어 API(ID3D12GraphicsCommandList7::Barrier)가 아니라 기존 D3D12_RESOURCE_BARRIER 를 씁니다. 상태 하나로 접근·동기화·레이아웃을 함께 나타내는 방식이라, 6-2절 표처럼 읽기 상태를 OR 로 합쳐 씁니다.
