1. 왜 필요한가

1-1. 픽셀 하나에 샘플 하나

래스터라이저는 픽셀 가운데 한 점에서만 삼각형을 덮었는지 판정하고, 픽셀 셰이더도 그 점에서 한 번 돕니다. 화면에 보이는 색은 픽셀 넓이의 평균이어야 하는데, 실제로는 한 점의 값입니다. 이 차이가 세 가지 증상으로 나타납니다.

  • 기하 계단: 비스듬한 가장자리가 픽셀 단위로 끊겨 보입니다. 카메라가 조금 움직이면 계단이 기어갑니다.
  • 셰이딩 깜빡임: 거칠기가 낮은 면의 하이라이트나 먼 곳의 가는 무늬가 픽셀보다 작으면, 가운데 점에 걸리는 프레임과 안 걸리는 프레임이 번갈아 나옵니다.
  • 잡음: SSAO 처럼 픽셀마다 적은 샘플로 근사하는 효과의 무늬가 그대로 남습니다.

해결은 픽셀 안의 여러 위치에서 값을 구해 평균하는 것입니다. 문제는 그 샘플을 언제 구하느냐입니다.

2. 원리 — 지터, 누적, 재투영, 거부

2-1. 지터와 지수 이동 평균

투영 행렬을 프레임마다 1 픽셀보다 작게 옮기면(지터), 같은 화면 픽셀이 장면의 조금 다른 위치를 샘플합니다. 이 결과를 지난 결과와 섞어 두면 여러 프레임에 걸쳐 픽셀 안의 여러 위치를 평균한 값이 됩니다. 모든 지난 프레임을 저장할 수는 없으므로 직전 결과 한 장(히스토리)만 두고 지수 이동 평균을 씁니다.

out(n) = α · current(n) + (1 − α) · history(n − 1)        α = taaFeedback (기본 0.1)

2-2. 재투영

카메라나 물체가 움직이면 히스토리의 같은 픽셀 자리에는 다른 표면이 있습니다. 그래서 히스토리를 읽을 위치를 속도로 옮깁니다. 우리 속도 버퍼는 uv(이번) − uv(지난) 를 UV 단위로 담으므로(Shaders/Temporal.hlsli 의 velocityTexture 주석), 지난 위치는 uv − velocity 입니다. 이 위치는 보통 텍셀 가운데가 아니어서 히스토리를 보간해 읽어야 하고, 보간 필터가 흐리면 매 프레임 조금씩 흐려진 값이 다시 쌓입니다(5-3).

2-3. 거부 — 히스토리를 믿을 수 없을 때

재투영이 맞아도 히스토리가 틀리는 경우가 있습니다. 앞 물체가 비켜나며 드러난 배경(disocclusion)은 지난 프레임에 아예 보이지 않았고, 조명이 바뀐 곳은 같은 표면이라도 색이 다릅니다. 속도가 없는 파티클·반투명은 뒤 표면의 속도로 재투영되어 엉뚱한 자리를 읽습니다. 이런 히스토리를 그대로 섞으면 잔상(고스팅)이 남습니다.

흔한 해법은 "이번 프레임의 3×3 이웃 색이 만드는 범위 밖의 히스토리는 틀렸다"고 보고 범위 안으로 끌어오는 것입니다. 범위를 이웃의 최솟값·최댓값 상자로 잡으면 이웃 클램프, 평균 ± 표준편차 상자로 잡으면 분산 클리핑입니다. 우리 엔진은 분산 클리핑만 씁니다(5-4). 상자가 좁으면 잔상은 줄지만 실제 서브픽셀 정보까지 잘려 깜빡임과 흐림이 돌아오고, 넓으면 반대입니다.

3. 한 프레임 안에서 TAA 가 끼는 자리

  1. 상수 올리기 — Renderer::UploadPerFrameConstants(Graphics/Renderer.cpp)가 이 뷰의 지터를 정해 b0 의 proj·viewProj·invViewProj 에 넣고, 지터 없는 unjitteredViewProj·prevUnjitteredViewProj 와 temporalParams(xy 지터, z 히스토리 유효, w 위상)를 함께 올립니다.
  2. 씬 패스 — 불투명·반투명이 지터된 행렬로 래스터화됩니다. 포워드는 바로 hdr(R16G16B16A16_FLOAT)에, 디퍼드는 G-buffer 에 쓴 뒤 라이팅 패스가 hdr 를 채우고, 깊이도 지터된 위치로 남습니다. 속도는 지터 없는 행렬로 계산되어 속도 RT 에 들어갑니다. 반투명은 속도 RT 쓰기 마스크가 0 입니다(Renderer::GetPipelineFor).
  3. Effects 패스 — 파티클, 비(빗줄기·튐), 디버그 선이 이 순서로 같은 hdr 에 그려집니다(DrawParticles → DrawRain → DrawDebugLines). RT 가 hdr 한 장이라 이들은 속도를 쓰지 않습니다.
  4. HDR 구간 — Renderer::ApplyHdrEffects(Graphics/RendererPost.cpp): (속도 디버그 뷰면 그것만) → TAA 리졸브 → 복사 → 모션 블러 → 블러 → 블룸.
  5. 톤 패스와 UI — 노출·ACES·색 효과 뒤 sRGB 로 인코딩하고, 게임 UI 는 그 위에 지터 없이 그립니다. 그래서 UI 는 TAA 를 받지 않습니다.

순서의 이유는 코드 주석과 계획에 적혀 있습니다. TAA 를 모션 블러 앞에 두는 것은 "지터가 남은 이미지를 정리한 뒤 번지게" 하려는 것이고(ApplyHdrEffects 의 TAA 절 주석, 계획 3.5, UE 도 같은 순서), 체인 전체의 순서는 후처리 학습에 있습니다. 하나 덧붙이면, 히스토리에는 모션 블러 전 결과가 저장되므로 블러가 다음 프레임의 히스토리로 되먹임되지 않습니다.

메인 뷰와 카메라 미리보기 뷰는 ViewTarget 을 따로 가지므로 지터 위상, 지난 행렬, 히스토리 두 장이 모두 뷰마다 따로입니다.

4. 서브픽셀 지터

4-1. Halton(2,3) 8 위상

지터 위치는 픽셀 안에 고르게 퍼져야 하고, 몇 프레임만 모아도 한쪽으로 몰리지 않아야 합니다. 난수는 뭉치는 곳이 생기므로 저불일치 수열인 Halton 수열을 씁니다. x 는 2 진, y 는 3 진으로 자릿수를 소수점 뒤로 뒤집은 값입니다. 코드는 UploadPerFrameConstants 안의 람다 halton 입니다.

phase = frameIndex % 8 + 1                      // 이 뷰를 그린 프레임 수 (TemporalState::frameIndex)
ox = Halton(phase, 2) − 0.5,  oy = Halton(phase, 3) − 0.5     // 픽셀 단위, −0.5 ~ 0.5
jitter.x =  2 · ox / width,   jitter.y = −2 · oy / height    // NDC (y 는 위가 +)
proj = P · Translation(jitter.x, jitter.y, 0)    // 행 벡터 관례: clip' = clip · P · J

원근 투영에서 J 를 뒤에 곱하면 clip.xy 에 jitter · w 가 더해지고, w 로 나눈 뒤 NDC 에서 정확히 jitter 만큼 옮겨집니다. 직교 투영은 w = 1 이라 그대로 더해집니다. 그래서 거리와 무관하게 화면 전체가 같은 서브픽셀 양만큼 움직입니다.

Shaders/TaaPixelShader.hlsl 의 PS_Taa 는 시간 셋(Layout_Temporal, Shaders/Temporal.hlsli)으로 t13 hdr(지터된 이번 프레임), t23 깊이, t7 속도, t24 지난 결과를 읽고, 이번 히스토리 한 장에 씁니다. 파일 머리 주석이 단계 번호 (1)~(6) 을 붙여 두었고, 코드 순서는 (1) (2) (3) (5)의 이웃 통계 (4) (5)의 클립 (6) 입니다.

5-1. (1) 바로 내보내기

α ≥ 1 이거나 temporalParams.z 가 0(히스토리 없음)이면 이번 색을 그대로 냅니다. 맨 앞에서 끝내는 이유는 주석에 있습니다. YCoCg 왕복과 가중치 계산을 거치지 않아야 "피드백 1 + 지터 끔" 배관 검증이 TAA 를 끈 화면과 비트 단위로 같습니다(9장 E1).

5-2. (2)(3) 속도 팽창과 재투영

3×3 이웃 깊이(LoadDeviceDepth, 표준 Z 라 작을수록 가까움) 중 가장 가까운 픽셀을 찾고, 그 픽셀의 속도를 씁니다. 물체 가장자리 픽셀은 지터와 안티에일리어싱 때문에 배경 깊이·속도를 가질 수 있는데, 그대로 쓰면 움직이는 물체의 테두리가 배경 속도로 재투영되어 끌립니다(셰이더 주석). 가장 가까운 표면의 속도를 1 픽셀 바깥까지 넓혀 테두리가 물체를 따라가게 합니다. 비교는 엄격한 < 라서 깊이가 같으면 먼저 본(왼쪽 위) 픽셀이 이기고, 아홉 개 모두 1(하늘)이면 가운데 픽셀의 속도를 씁니다.

지난 위치는 prevUv = position.xy · screenParams.zw − velocity 입니다. 0~1 밖이면 화면 밖에서 들어온 표면이므로 히스토리 없이 이번 색을 냅니다.

5-3. (4) Catmull-Rom 5 탭

쌍선형 보간은 텍셀 사이를 읽을 때마다 저역 통과 필터를 한 번 거는 것과 같아서, 카메라가 천천히 움직이면 프레임마다 흐림이 쌓입니다. Catmull-Rom 은 4×4 텍셀을 쓰는 3 차 보간이고 바깥 텍셀에 음수 무게를 줘 날카로움을 지킵니다. SampleHistoryCatmullRom 은 가운데 2×2 를 쌍선형 한 번으로 묶고 네 모서리 탭을 빼서 쌍선형 샘플 5 번으로 줄였습니다. 모서리 무게는 음수 로브 둘의 곱이라 f = 0.5 에서 탭당 +0.0039, 넷 합 +0.016 이라 빼도 차이가 작습니다 계산값. 음수 로브 때문에 음수가 나올 수 있어 0 에서 자릅니다.

속도가 0 인 정지 화면에서는 prevUv 가 텍셀 가운데에 정확히 떨어져 분수부 f = 0 이 되고, 무게가 (0, 1, 0, 0) 이 되어 텍셀을 그대로 읽습니다 계산값. 정지 화면이 끈 화면보다 부드러운 것은 리샘플링 때문이 아니라 지터 샘플들의 평균, 즉 안티에일리어싱 자체 때문입니다.

5-4. (5) YCoCg 분산 클리핑

이번 프레임 3×3 이웃 아홉 색을 YCoCg 로 바꿔 평균 μ 와 표준편차 σ 를 구하고(m1·m2 누적), 히스토리를 상자 [μ − γσ, μ + γσ] (γ = kClipGamma = 1.0) 안으로 넣습니다.

  • YCoCg (RgbToYCoCg): Y = (R + 2G + B)/4 밝기, Co = (R − B)/2, Cg = (−R + 2G − B)/4. 이웃 색은 보통 밝기 방향으로 길게 퍼지는데, RGB 축 상자는 그 방향을 비스듬히 감싸 빈 공간이 많습니다. 밝기를 한 축으로 떼면 상자가 덜 길쭉합니다(셰이더 주석).
  • 분산 상자: 최솟값·최댓값 상자는 튀는 이웃 하나에 크게 넓어지지만, μ ± σ 는 이웃 대부분이 모인 곳만 감쌉니다. 우리 셰이더는 min/max 클램프를 하지 않고, 분산 상자를 min/max 상자와 겹쳐 자르지도 않습니다.
  • 중심 방향 클립 (ClipTowardCenter): 히스토리가 상자 밖이면 μ 에서 히스토리로 가는 선분이 상자 면과 만나는 점으로 옮깁니다. 축마다 따로 자르면 색 비율이 바뀌어 색조가 틀어지는데, 한 선분 위에서 줄이면 덜 틀어집니다(주석: Playdead INSIDE 의 방식). 상자 안이면 그대로 둡니다.

5-5. (6) 휘도 역가중 섞기

섞기는 YCoCg 공간에서 두 색에 각각 무게를 주고 정규화합니다(Karis 2014).

wCurrent = α / (1 + Y_current),   wHistory = (1 − α) / (1 + Y_history)
result   = (current · wCurrent + history · wHistory) / (wCurrent + wHistory)

HDR 값은 1 을 훨씬 넘을 수 있어서, 아주 밝은 픽셀 하나(반딧불이)가 들어오면 평균이 크게 튀고 그 뒤 몇 프레임 동안 깜빡입니다. 밝은 쪽 무게를 줄여 이를 누릅니다. 두 밝기가 같으면 실제 비중은 α 그대로입니다. 실제 이번 프레임 비중은 다음과 같습니다(α = 0.1). 계산값

이번 Y히스토리 Y이번 프레임의 실제 비중뜻
110.100밝기가 같으면 α
100.50.015튄 밝은 샘플이 약 1/7 로 눌림
1000.50.0016태양 반사 같은 값은 거의 안 들어감
0.5100.449밝은 히스토리가 어두운 이번 값으로 빨리 바뀜

Y 는 노출·톤매핑 전 선형 HDR 값입니다. 가중은 노출을 곱하기 전 값에 걸리므로 노출 설정과 무관하고, 조명이 세서 HDR 값이 큰 씬일수록 세집니다. 마지막에 RGB 로 되돌리고 0 에서 자릅니다.

5-6. 섞지 않는 것

리졸브는 이번 프레임 값을 재구성 필터로 다시 거르지 않고 지터된 한 샘플을 그대로 씁니다. 그래서 결과에는 이번 지터가 α 만큼 남습니다. 리졸브 뒤 샤프닝 패스는 없고, 텍스처 밉 LOD 음수 바이어스도 없습니다(두 RHI 의 샘플러 생성이 MipLODBias = 0). 계획에서 범위 밖으로 둔 항목입니다(계획 3단계-3).

6. 히스토리 텍스처와 리셋

6-1. 두 장 핑퐁

같은 텍스처를 읽으면서 쓸 수는 없으므로 뷰마다 히스토리 두 장(ViewTarget::history[2], R16G16B16A16_FLOAT, hdr 와 같은 선형 FP16)을 둡니다. TemporalState::current 가 이번에 쓸 쪽이고, 다른 쪽을 읽습니다. 셋도 미리 두 벌 만들어 둡니다. taaSet[i] 는 t24 에 history[1 − i] 를 꽂은 시간 셋, historyPostSet[i] 는 history[i] 를 hdr 로 복사할 때 쓰는 후처리 셋입니다.

ApplyHdrEffects 의 TAA 절은 두 패스입니다. TaaResolve 가 taaSet[cur] 로 history[cur] 에 쓰고, TaaCopy 가 PS_Post 모드 0(복사)으로 history[cur] 를 hdr 에 옮깁니다. 그 뒤 historyValid = true, current ^= 1 입니다. 리졸브 앞의 Barrier(history[cur ^ 1], ShaderResource) 는 처음 만든 직후 한 번도 쓰지 않은 텍스처를 읽을 상태로 바꾸려는 것입니다.

텍스처는 TAA 가 처음 켜지는 프레임에 Renderer::EnsureTaaTargets 가 만듭니다. 크기는 1920×1080 에서 장당 16.6 MB, 두 장 33.2 MB 입니다(픽셀당 8 바이트) 계산값. 하나라도 실패하면 로그를 남기고 전부 지운 뒤 그 프레임은 TAA 를 건너뜁니다. 지우는 곳(DestroyTaaTargets)은 뷰 타깃을 없앨 때(DestroyViewTarget, 리사이즈 포함)와 생성 실패 때뿐이라, TAA 를 꺼도 히스토리 두 장은 남아 있습니다.

6-2. 히스토리 유효 플래그

셰이더가 보는 temporalParams.z 는 프레임 처음 UploadPerFrameConstants 가 TemporalState::historyValid 를 옮긴 값입니다. 이 플래그는 리졸브를 돌린 프레임 끝에 참이 되고, 아래 계기로 거짓이 됩니다. 거짓인 프레임의 리졸브는 5-1 의 (1) 로 이번 색을 그대로 히스토리에 쓰므로, 리셋 다음 프레임부터 새로 쌓입니다.

씬 불러오기, 재생 시작·정지, 되돌리기·다시 실행, 재생 중 카메라 컷, 미리보기 대상 변경은 속도 버퍼의 지난 값과 함께 버리는 계기라 속도 버퍼 학습 5-3 표에 정리되어 있습니다. 이 경로들은 Renderer::ResetTemporalHistory 를 부르거나 뷰의 lastCamera 를 지우고, 다음 UploadPerFrameConstants 가 그 뷰의 historyValid 를 내립니다. TAA 에만 있는 계기는 다음 둘입니다.

계기어디서무엇을 버림

6-3. 디버그 뷰

디버그 뷰(알베도·노멀·속도 …)가 켜지면 TaaActive 가 거짓이라 지터도 리졸브도 없습니다. 디버그 색을 여러 프레임 섞으면 읽을 수 없기 때문입니다(TaaActive 주석). 뷰 16·17(속도·속도 오차)은 TAA 절에 오기 전에 속도 디버그 패스만 그리고 함수를 끝냅니다. 디버그 뷰를 끈 첫 프레임은 히스토리가 없는 상태라 옛 디버그 색이 섞이지 않습니다. 블러·블룸은 뷰 16·17 을 빼면 디버그 뷰에서도 돕니다(계획 7.4).

9. 실험

모두 테스트 씬과 실행 인자로 할 수 있습니다. 스크린샷을 비교할 때는 --exit-after 를 고정하면 지터 위상까지 같아집니다.

E1. 배관 검증 확인함 (2026-11-23)

TaaPlumbing.json(피드백 1)을 --taa-jitter=0 으로 찍은 화면과 --taa=0 으로 찍은 화면을 비교합니다. 5-1 의 (1) 에서 이번 색을 그대로 내고 복사도 값을 바꾸지 않으므로 차이가 0 픽셀이어야 합니다. 기록은 0 px 이고, D3D11 과 D3D12 의 결과도 같았습니다(20.28).

E2. 지터가 보이는지 예상

같은 씬(피드백 1)에서 --taa-jitter=1 로 --exit-after=40 과 41 을 찍으면 위상이 하나 달라 화면이 1 픽셀 미만으로 어긋납니다. --taa-jitter=0 이면 두 장이 같습니다. 계획의 합격선(계획 3-2)이고 측정 숫자는 기록에 없습니다.

E3. 정지 화면 안티에일리어싱 예상

TaaEdges.json 을 --exit-after=40 으로 TAA 켬·끔 두 번 찍어 비스듬한 가장자리를 확대합니다. 40 프레임이면 반감기(6.6 프레임)의 여섯 배가 지나 거의 수렴한 상태입니다. 같은 인자로 두 번 실행하면 같은 화면이어야 합니다(결정적 지터).

E4. 피드백 바꿔 보기 예상

환경 패널에서 피드백을 0.02, 0.1, 0.5 로 바꾸며 --cam-orbit=1 같은 회전을 봅니다. 0.02 는 정지 화면이 가장 매끈하지만 움직일 때 흐림과 잔상이 길고(반감기 34 프레임 계산값), 0.5 는 반응이 빠르지만 가장자리 흔들림이 남습니다.

E5. 고스팅 예상

TaaMotionBlur.json 을 재생합니다. 헬멧이 Rotator 로 초당 360° 돌고 뒤에 바닥이 보입니다. TaaEdges.json 은 Sponza 한 덩어리(Sponza/node0)와 카메라뿐이라 --spin 을 주면 씬 전체가 돌아 잔상을 볼 배경이 없습니다. 회전하는 물체 뒤에 잔상 띠가 없어야 합니다(계획 3단계-5). kClipGamma 를 잠깐 3 으로 올리면 상자가 넓어져 드러난 배경에 옛 색이 남는 것을 볼 수 있습니다. 확인한 뒤 되돌립니다.

E6. 리셋 확인함 (2026-11-23)

CameraSwitch.json 같은 씬에서 --event-frame 을 exit-after − 1 로 두고 미리보기 전환(--select)·되돌리기(--undo)·재생 중 카메라 컷을 일으키면, 사건 직후 첫 프레임이 처음부터 새로 그린 화면과 같아야 합니다. 기록된 세 경우(미리보기 전환·되돌리기·카메라 컷) 모두 0 px 입니다(20.28). 씬 뷰 크기 변경은 자동화 수단이 없어 손으로 확인합니다.

10. 함정과 알려진 한계

증상원인이 엔진에서
정지 화면이 끈 화면보다 부드러움지터 샘플 평균 자체가 픽셀 넓이의 상자 필터샤프닝·밉 LOD 음수 바이어스 없음(5-6). 피드백을 올리면 덜하지만 가장자리가 흔들림
파티클·빗줄기·디버그 선 뒤로 옅은 잔상속도를 쓰지 않아 뒤 표면 속도로 재투영됨Effects 패스(3장). 빠른 파티클은 클리핑에 걸려 대체로 괜찮음. 빗줄기는 TAA 를 켜도 남고 1 픽셀 줄이 약간 흐려진다고 기록됨(비 구현 기록 9.3). 반응성 마스크는 남은 과제(계획 3단계-6, 22.4)
반투명 물체가 뒤 배경을 따라 끌림반투명 PSO 는 속도 RT 쓰기 마스크 0Renderer::GetPipelineFor. 반투명 밑 불투명 표면의 속도가 남음
SSAO 무늬가 사라지지 않음4×4 베이어 회전이 화면 픽셀에 고정되어 프레임마다 같은 잡음BAYER4 가 지터 위상을 쓰지 않음. 위상으로 돌리는 것은 선택 항목(계획 3단계-6)
드러난 배경에 짧은 옛 색γ = 1 상자 안에 우연히 들어온 히스토리는 그대로 섞임분산 상자 하나만 씀. 속도·깊이로 거부하는 조건은 없음
게임 코드의 순간 이동 뒤 한 프레임 겹침리셋 계기가 아님그 코드가 ResetTemporalHistory 를 불러야 함(6-2)
TAA 가 꺼졌는데 화면이 떨림지터는 TaaActive 만 보고 타깃 생성 성공을 보지 않음EnsureTaaTargets 실패 프레임은 지터만 남음(22.4 에 기록된 한계)
World 캔버스 UI 경계가 깜빡임UI 는 지터 없이, 가리는 깊이는 지터된 값Pass_UIWorld 주석의 1 px 한계
고정 스텝 물체 주변 잔상·번짐Rigidbody 는 렌더 보간이 없어 높은 fps 에서 계단처럼 움직임속도가 스텝 프레임에만 생김(22.4). 모션 블러 쪽 영향이 더 큼
밝은 하이라이트가 늦게 나타남휘도 역가중이 밝은 이번 값의 비중을 줄임5-5 표: Y 10 이면 실제 비중 0.015
계획 문서와 다른 곳. 계획 3단계-2는 섞기를 lerp(history, current, α) 로 적고 휘도 가중을 덧붙였는데, 코드는 처음부터 YCoCg 에서 휘도 가중으로 섞습니다(5-5). 또 계획은 히스토리 유효 검사를 화면 밖 검사와 같은 단계에 두었지만, 코드는 α ≥ 1 검사와 함께 맨 앞(1)에서 합니다. 계획 3.6 표의 "미리보기 포인터 비교"는 구현에서 오브젝트 id 비교로 바뀌었습니다(맨 위 "구현하면서 바뀐 점"에 기록됨).
