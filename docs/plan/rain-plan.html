  • SRV 슬롯. t0~t31 은 모두 어딘가에 선언되어 있지만, 한 PSO 안에서만 겹치지 않으면 됩니다. t24 는 TAA 히스토리(Layout_Temporal)와 정렬 개수 버퍼(Layout_ParticleSort)가 쓰는데, 두 셋은 프레임 셋(Layout_Frame)과 같은 패스에 묶이지 않습니다(Renderer.cpp 의 패스 표 kPasses 에서 확인). 그래서 t24 를 프레임 셋의 차폐 맵 자리로 쓸 수 있습니다. 프레임 셋의 SRV 는 지금 모두 PS 전용이고, 차폐 맵은 VS 에서도 읽어야 합니다.
  • 그리기 API. RHI 에 Draw(vertexCount, startVertex) 가 있어 정점 버퍼 없이 SV_VertexID 만으로 쿼드를 그릴 수 있습니다(RHI/CommandList.h). 파티클은 DrawInstancedIndirect 를 씁니다.
  • 레이아웃. Layout_Count 는 19 이고, PSO 하나가 쓰는 셋은 kMaxBindingSets = 4 까지입니다(RHI/PipelineTypes.h).
  • 컴포넌트와 씬 설정. 바다처럼 Behaviour 하위 클래스에 Reflect 와 SHERLOCK_BEHAVIOUR 만 두면 씬 저장, 에디터 속성 패널, --add-component 가 따라옵니다(Scene/Behaviour.h). 렌더러는 BuildDrawList 에서 CollectOcean 처럼 찾아 씁니다. 씬 전체 설정은 SceneEnvironment(Scene/Scene.h; 후처리·그림자·SSAO)도 있지만, 직렬화(SceneSerializer.cpp)와 에디터 UI(Editor/DebugUI.cpp)를 손으로 늘려야 합니다.
  • GPU 시간 측정. GpuProfileScope(Core/Profiler.h)로 ShadowPass, GBuffer, DeferredLight, MainPass, ParticleSim 같은 구간을 잽니다. 새 구간 이름만 붙이면 됩니다.
  • 시간. b0 time 은 일시정지를 뺀 경과 시간이고 편집 모드에서도 흐릅니다. 시간을 고정하는 플래그는 바다 전용 --ocean-time 만 있습니다.

2. 개념: 비를 이루는 세 가지

  • 빗줄기. 빗방울은 지름 1~5 mm 이고 금방 종단 속도(약 9 m/s)에 이릅니다. 그래서 속도가 일정하다고 놓아도 되고, 프레임마다 적분할 필요가 없습니다. 위치를 시작 위치 + 속도 × 시간 으로 바로 구할 수 있습니다. 눈에 보이는 "줄"은 빗방울이 노출 시간 동안 움직인 자취입니다(9 m/s × 1/30 s ≈ 0.3 m). 실제 물방울은 굴절로 주변 빛을 모아 보여 주지만, 여기서는 환경광 세기에 맞춘 밝기를 가산으로 더하는 것으로 근사합니다.
  • 차폐 맵. 비는 위에서 내려오므로, 하늘에서 아래로 직교 투영한 깊이 맵에 "이 xz 에서 비가 처음 닿는 높이"가 담깁니다. 그림자 맵과 같은 원리이고, 빛 방향 대신 비 방향(여기서는 바로 아래)을 쓴 것입니다. 어떤 점의 y 가 그 높이보다 충분히 아래면 지붕 밑입니다.
  • 젖은 표면. 다공성 표면(콘크리트, 흙, 천)은 물을 머금으면 표면 산란이 줄어 어두워집니다. 표면을 덮은 얇은 물막은 거울처럼 매끄러워서 거칠기가 내려갑니다. 금속은 물을 머금지 않아 어두워지지 않고 거칠기만 내려갑니다. 위를 보는 면은 물이 고이고, 벽은 흘러내려 덜 젖습니다(Lagarde, 9장).

3. 설계 결정

3.1 모든 단계에 걸리는 규칙

  • 비가 없는 씬은 지금과 같아야 합니다. Rain 이 없거나 꺼졌으면 화면(스크린샷), 드로우 수, 패스 수가 그대로여야 합니다. 차폐 맵 패스는 돌지 않고, b0 비 칸은 0, t24 에는 1×1 흰 깊이(= "어디나 열린 하늘")를 꽂습니다. 비 세기 0 이면 빗줄기를 그리지 않고, 젖음 0 이면 ApplyWetness 가 값을 바꾸지 않습니다.
  • D3D11 과 D3D12 의 결과가 같아야 합니다. 시작 로그의 바인딩 대조가 OK 이고 D3D12 Debug Layer 경고가 없어야 합니다.
  • 새 cbuffer·b0 칸은 ShaderConstants.h 구조체 + static_assert(크기·오프셋), HLSL 미러(Common.hlsli, 새 Rain.hlsli), kConstantBuffers, kCBSlot*·kSRVSlot* 를 같이 고칩니다.
  • 새 셰이더는 ShaderId/kShaders, PassId/kPasses, SherlockEngine.vcxproj 의 FxCompile, .filters 의 Shaders 필터에 모두 넣습니다. 새 .hlsli 는 None 항목입니다.
  • 테스트 씬은 기존 씬을 고치지 않고 생성기 스크립트로 만듭니다(Scripts/Tests/make_ocean_test_scenes.py 와 같은 방식).
  • 코드는 tools/format_code.py 로 포맷하고, 주석은 기존처럼 한국어로 씁니다. 문서는 UTF-8(BOM 없음), CRLF 입니다.

3.2 결정 표

사용자와 정한 것은 "GPU 파티클 방식의 빗줄기 + 젖은 표면, 두 효과가 차폐 맵을 같이 씀" 하나입니다. 나머지는 작성자가 정한 기본값입니다.

항목선택 제안이유검토한 다른 안
빗줄기를 만드는 법상태 없는 절차적 파티클. 파티클 버퍼와 컴퓨트 없이, RainVS 가 SV_VertexID / 6 을 빗방울 번호로 보고 번호의 해시와 시간으로 위치를 바로 계산합니다(3.5). DirectX::XMFLOAT4 rainMapXZ;    // xy = 맵 최소 모서리의 월드 xz, z = 1 / 한 변(m), w = 텍셀 크기(m)
DirectX::XMFLOAT4 rainMapY;     // x = 맵 윗면 y, y = 깊이 범위(m), z = 높이 비교 여유(m, 텍셀 2개 안팎), w = 0

// 차폐 맵의 한 점 → "비가 처음 닿는 높이". 직교라 깊이가 선형
float RainOccluderHeight(float3 worldPos)   // Rain.hlsli
{
    float2 uv = (worldPos.xz - rainMapXZ.xy) * rainMapXZ.z;
    if (any(uv < 0) || any(uv > 1)) return -1e30;            // 맵 밖 = 열린 하늘
    float d = rainOcclusionMap.SampleLevel(pointClamp, float2(uv.x, 1 - uv.y), 0);
    return rainMapY.x - d * rainMapY.y;
}
bool RainExposed(float3 p) { return p.y >= RainOccluderHeight(p) - rainMapY.z; }

// b8 RainConstants (새 Layout_Rain, VS|PS). Pass_Rain 은 {Frame, Rain, ParticleDepth} 세 셋
struct alignas(16) RainConstants
{
    XMFLOAT3 fallOffset; float boxBelow;       // 축마다 fmod(velocity_i × t, boxSize_i) (CPU, double), 상자에서 카메라 아래 몫(0..1)
    XMFLOAT3 boxSize;    uint32_t dropCount;   // 상자 크기(m), 이번 프레임 그릴 수
    XMFLOAT3 velocity;   float streakLength;   // (wind.x, −fallSpeed, wind.z)
    XMFLOAT3 color;      float streakWidth;    // color × brightness
    float nearFade; float softDistance; uint32_t seed; float padding;
};   // 80 B → 업로드 시 256 B 로 올라감. 뷰마다 다른 값은 넣지 않음 (아래)
  • 차폐 맵 SRV: t24 kSRVSlotRainOcclusion, 프레임 셋, VS|PS. 프레임 셋에 VS 가 읽는 SRV 가 처음 생기므로 D3D11 바인딩(단계별 SetShaderResources)과 D3D12 디스크립터 테이블 가시성을 같이 확인합니다(8장).
  • 뷰마다 다른 값은 b0 에서. b8 은 프레임에 한 번만 올립니다. 상자 중심(카메라 위치)과 픽셀 크기는 메인 뷰와 미리보기 뷰가 다르므로, RainVS 가 뷰마다 다시 올라오는 b0 의 cameraPosition·screenParams·proj 로 직접 구합니다.

  • b0 가 커지면 Layout_Post 가 b0 를 다시 쓰는 톤 패스도 같이 커집니다. 구조체 끝에 붙이므로 기존 오프셋은 그대로입니다.

// RainVertexShader.hlsl (요지). 정점 6개 = 쿼드 하나 = 빗방울 하나
uint  drop   = vertexId / 6;
float3 h     = Hash3(drop, seed);                       // [0,1)³, 빗방울마다 고정
float3 world = h * boxSize + fallOffset;               // 월드 격자 위에서 상자 크기 주기로 반복되는 궤적
float3 center = cameraPosition + float3(0, (0.5 - boxBelow) * boxSize.y, 0);   // b0 — 뷰마다 다름

if (!RainExposed(p)) → 쿼드를 접어 버림(위치를 NaN 이 아닌 클립 밖으로)
// 머리 p, 꼬리 p − normalize(velocity) · streakLength.
// 폭 방향 = normalize(cross(velocity, p − cameraPosition)), 폭 = max(streakWidth, 거리 × pixelScale)
// 밝기 × streakWidth / 폭 (가늘어진 만큼 어둡게), × 카메라 근접 페이드
  • frac 접기 때문에 방울 하나가 상자 경계를 넘는 순간 반대편으로 순간 이동합니다. 이때 길게 늘어난 쿼드가 화면을 가로지르지 않도록, 머리와 꼬리를 같은 접기 결과에서 만듭니다(꼬리를 따로 접지 않음). 상자 가장자리 10% 에서 밝기를 줄여 나타나고 사라지는 것을 감춥니다.
  • 시간이 오래 흐르면 velocity × t 가 커져 float 정밀도가 떨어집니다. 그래서 셰이더에 시간을 넘기지 않고, CPU 가 축마다 fmod(velocity_i × t, boxSize_i) 를 double 로 구해 fallOffset 으로 넘깁니다(바다의 위상 감기와 같은 이유). 위치가 상자 크기 주기의 frac 안에서만 쓰이므로 축마다 감아도 이어집니다. 시간 하나를 "상자 높이 / 낙하 속력" 주기로 감으면 y 는 이어지지만 바람이 있는 xz 는 감는 순간 모든 방울이 옆으로 한꺼번에 뜁니다.
  • 차폐 판정은 머리 한 점만 봅니다. 빗줄기 꼬리가 지붕 아래로 0.3 m 들어가는 것은 PS 의 장면 깊이 페이드가 가립니다.

// MaterialSurface.hlsli, roughness 를 정한 뒤, F0 를 정하기 전
void ApplyWetness(inout SurfaceData s, float3 worldPos, float3 vertexNormal)
{
#ifndef RAIN_NO_WETNESS                     // 바다 PS 는 이 매크로를 정의하고 include
    if (rainParams.y <= 0) return;          // 비가 없으면 값을 하나도 바꾸지 않음 (회귀 0)
    float exposed = RainExposed(worldPos) ? 1 : 0;
    float up      = saturate(normalize(vertexNormal).y);
    float wet     = rainParams.y * exposed * lerp(0.35, 1.0, up);     // 벽은 덜 젖음
    float porous  = (1 - s.metallic) * saturate(s.roughness * 1.5);   // 매끈한 재질·금속은 덜 어두워짐
    s.albedo     *= lerp(1.0, 0.55, wet * porous);
    s.roughness   = lerp(s.roughness, min(s.roughness, 0.12), wet);
#endif
}
  • 숫자(0.35, 0.55, 0.12)는 Lagarde 의 관찰값을 작성자가 단순화한 것입니다. 2단계 테스트 씬에서 다시 맞춥니다.
  • 차폐 판정을 한 점만 보면 지붕 가장자리 아래 바닥에 7.8 cm 계단이 생길 수 있습니다. 거슬리면 2×2 비교(PCF 처럼)로 가장자리를 부드럽게 합니다.

4. 부하 예상과 측정

결론(예상). 전체로 보면 무겁지 않은 기능입니다. 가장 큰 변수는 차폐 맵 패스입니다. 이 패스는 씬을 위에서 한 번 더 그리는 것이라 비용이 그림자 뷰 하나(캐스케이드 하나)와 비슷하고, 드로우가 많은 씬에서는 GPU 보다 CPU 드로우 제출이 먼저 늘어납니다. 그다음이 카메라 가까이 빗줄기가 겹쳐 생기는 오버드로입니다. 빗줄기 위치 계산과 젖음 계산은 거의 공짜에 가깝습니다. 아래 표의 순위와 크기는 측정이 아니라 구조로 본 예상입니다.

8. 미확인 사항 (구현 첫날 확인)

  1. 프레임 셋의 VS 용 SRV. 프레임 셋에 VS|PS SRV 를 넣었을 때 D3D12 루트 시그니처(테이블 수·크기)와 ValidateBindings 가 받아들이는지. D3D11 백엔드가 셋의 SRV 를 단계별로 나눠 꽂는지.
  2. b0 크기. 576 → 624 B 가 D3D12 업로드 링 조각 규칙(256 B 배수로 올림)과 미리보기 뷰의 b0 재업로드에서 문제없는지. 두 크기 모두 768 B 로 올라가므로 괜찮을 것으로 봄.
  3. b5 재업로드. 그림자 뷰마다 b5 를 올리는 방식이 링 조각이라 차폐 뷰 하나를 더 올려도 되는지(D3D12 "같은 Dynamic 버퍼를 한 프레임에 두 번" 규칙과 충돌하지 않는지).
  4. 그림자 PSO 로 차폐 맵 그리기. 그림자 PSO 의 깊이 바이어스(2000, 기울기 2.0)가 D32 차폐 맵에서 눈에 띄는 오프셋을 만들지 않는지. 블렌딩(유리) 재질에 shadowPipeline 이 있는지 — 없으면 유리 지붕 아래로 비가 샘.
  5. 그림자 뷰 컬링 입력. 그림자 본문의 절두체 컬링이 직교 뷰 행렬 하나로 동작하는지, 캐스케이드 전용 가정(텍셀 스냅·뷰 칸 번호)이 섞여 있지 않은지.
  6. 점 샘플러. 프레임 셋에 VS 에서 쓸 수 있는 점·클램프 샘플러가 있는지. 없으면 Load 로 읽음(샘플러 불필요).
  7. 레이아웃 수. Layout_Count 19 → 20 이 다른 고정 배열(예: 셋 캐시)에 걸리지 않는지.
  8. 디버그 뷰 번호. 뷰 18 이 비어 있는지, 에디터 디버그 뷰 목록에 이름을 넣는 곳.
  9. Sponza 테스트 씬의 바탕. ManyLights 생성기(make_deferred_test_scenes.py)가 쓰는 Sponza 경로와 하늘·IBL 설정을 그대로 가져올 수 있는지.
