2026-11-26 · 비 구현 계획의 1~3단계를 한 번에 구현한 기록입니다. 카메라 주변에 빗줄기가 내리고, 비를 맞는 표면이 젖어 어두워지고 매끈해지며, 지붕·회랑 아래는 빗줄기도 젖음도 없습니다. 3단계로 지붕·바닥에서 튀는 물방울, 젖은 바닥의 물결, 평평한 바닥의 웅덩이까지 넣었습니다.

4. 차폐 맵

빗줄기와 젖음이 같은 질문을 합니다: "이 점 위에 비를 막는 것이 있는가". 그 답을 위에서 바로 아래로 내려다본 깊이 텍스처 하나에 담았습니다. 텍셀 하나가 "이 xz 에서 비가 처음 닿는 높이"입니다.

4.1 위에서 내려다보는 카메라

  • 중심: 카메라 xz 를 텍셀 크기(occlusionSize / 해상도, 기본 80/1024 ≈ 7.8 cm)로 반올림. 카메라가 움직여도 텍셀 격자가 월드에 고정되어 지붕 가장자리가 지글거리지 않음(CSM 텍셀 스냅과 같은 생각).
  • 윗면: floor(카메라 y) + 100 m, 깊이 범위 200 m(kMapHeightAbove, kMapDepthRange). 윗면보다 높은 물체는 차폐로 보지 않음.
  • 행렬: XMMatrixLookToLH(eye, −Y, up = +Z) × XMMatrixOrthographicLH(size, size, 0, 200). 뷰의 +x 는 월드 +X, 뷰의 +y 는 월드 +Z 이므로 텍스처 좌표는 u = (x − minX)/size, v = 1 − (z − minZ)/size 입니다.
  • 깊이는 직교라 선형: 월드 y = 윗면 − depth × 200. 지운 값 1 은 "아무것도 없음 = 열린 하늘". 맵 밖도 열린 하늘.
  • 해상도는 512·1024·2048 중 가까운 것으로 자름(SnapResolution). 텍스처는 비가 처음 생길 때와 해상도가 바뀔 때만 만듦.

4.2 패스와 PSO

RenderRainOcclusionPass 는 맵을 DepthWrite 로 바꾸고 1 로 지운 뒤, 뷰포트를 맵 전체로 잡고 DrawDepthView(viewProj, cullSphere = 0, perspective = false, occluder = true) 를 부릅니다. 끝나면 ShaderResource 로 돌립니다.

  • 무엇을 그리나: 그림자를 만드는 항목과 같음 — unlit·블렌딩·바다는 빠짐. m_drawList 는 메인 카메라로 미리 컬링되어 있지 않으므로(컬링은 그릴 때) 카메라 뒤·위의 지붕도 맵에 들어감. 컬링은 맵 직교 상자의 절두체로만 함(near 평면은 뺌).
  • 알파 테스트: 컷아웃 재질과 디졸브 중인 오브젝트는 그림자의 알파 테스트 변형(Pass_ShadowAlpha)이라 잎 무늬대로 비가 샘.
  • 컬링 모드: 단면 재질은 뒷면 컬링이라 위에서 보면 판의 뒷면이 빠질 수 있음. 테스트 씬의 지붕을 판이 아니라 상자로 둔 이유. 양면 재질은 컬링 없음.
  • 바이어스: 그림자 PSO 의 깊이 바이어스 2000·기울기 2.0·클램프 0.01 을 모두 0 으로 둔 변형(키 비트 11). DrawItem::occluderPipeline 은 비가 있는 프레임에만 채워서 비가 없는 씬의 PSO 수는 그대로.

DrawDepthView 는 원래 RenderShadowAtlasPass 의 뷰 하나 본문(b5 올리기 → 절두체 → 범위 구 → 드로우 루프)을 그대로 옮긴 것입니다. 다른 점은 PSO 를 occluder 인자로 고르는 것과 통계 카운터를 인자로 받는 것뿐이고, "직전 PSO·메시·재질"은 DepthDrawState 로 같은 렌더 패스 안의 뷰끼리 이어 씁니다.

4.4 쓰면서 묶여 있는 맵

프레임 셋(t24 = 맵)은 패스 시작 전에 묶이고, 차폐 맵 패스가 같은 텍스처를 DSV 로 씁니다. 두 백엔드에서 문제가 되지 않는 이유는 이렇습니다.

  • D3D11: BeginRenderPass 가 쓰기 깊이 타깃의 SRV 바인딩을 풂(UnbindShaderResourcesOf). 다음 씬 패스의 DrawItems 가 프레임 셋을 다시 묶음 — 그림자 맵 t8 과 같은 길.
  • D3D12: 맵은 DepthWrite ↔ ShaderResource 배리어로 오감. 차폐 맵 패스 동안 테이블이 DepthWrite 상태의 맵을 가리키지만, 그림자 VS·알파 테스트 PS 는 t24 를 읽지 않음.
  • 새로 만든 맵은 Common 상태라 Render 가 프레임 셋을 묶기 전에 ShaderResource 로 돌려 둠. 맵을 다시 만들면 m_frameSetRainMap 을 비워 핸들 값이 재사용되어도 셋을 다시 만들게 함.

5. 빗줄기 (RainVertexShader.hlsl, RainPixelShader.hlsl)

빗방울은 종단 속도로 떨어지므로 위치 = 시작점 + 속도 × 시간입니다. 그래서 시뮬레이션 패스·버퍼 없이 정점 셰이더가 위치를 계산하는 상태 없는 절차적 파티클로 그렸습니다. Draw(빗방울 수 × 6), 정점 버퍼 없음. SV_VertexID / 6 이 빗방울 번호, % 6 이 쿼드 모서리입니다.

  1. 상자: 카메라 중심, 가로 2 × areaRadius, 세로 areaHeight(카메라 아래 1/3).
  2. 시작점: RainHash3(번호, seed) × 상자 크기 — 월드에 고정된 격자(상자 크기 주기).
  3. 감기: local = frac((시작점 + fallOffset − 상자 최소) / 상자 크기). 카메라가 움직여도 빗방울은 월드에 남고, 상자 가장자리에서만 반대편으로 넘어감. 가장자리 10% 에서 흐려져 넘어가는 순간이 보이지 않음.
  4. 시간: fallOffset 은 CPU 가 double 로 축마다 fmod(velocity_i × t, 상자 크기_i). 시간 하나를 "높이 / 낙하 속력"으로 감으면 바람이 있는 xz 에서 감는 순간 모든 빗방울이 옆으로 뜀.
  5. 차폐: 머리가 RainExposed 가 아니면 클립 공간 밖(z = −1)으로 보내 그리지 않음.
  6. 모양: 머리에서 속도 반대쪽으로 streakLength 만큼 늘인 선을 화면을 향한 쿼드로 폄. 폭은 max(streakWidth, 픽셀 하나의 월드 크기) 이고 키운 만큼 streakWidth / 폭 으로 어둡게 함 — 화면에 들어가는 빛의 양을 유지해 먼 빗줄기가 굵고 밝게 뜨지 않음.
  7. 색: color × brightness × 환경광 세기(environmentParams.x, 환경이 없으면 1) × 가장자리·가까운 거리(nearFade) 페이드. PS 는 가로 포물선 × 머리가 밝은 세로 기울기 × 소프트 페이드(t23, 0.3 m).
  8. 블렌드: 파티클과 같은 PSO 상태(One / InvSrcAlpha, 알파 0 을 내보냄 = 가산), 깊이 테스트만, 컬링 없음. 정렬이 필요 없음.

6. 젖은 표면

젖음은 재질 PS 의 EvaluateMaterialSurface 안에서 계산하므로 포워드·G-buffer 두 경로가 같은 값을 씁니다. 식은 Lagarde 의 "Water drop 2a"를 단순화했습니다.

wet    = rainParams.y(보간된 젖음) × RainExposure(p, n) × lerp(0.35, 1, saturate(n.y))   // 벽·아래를 보는 면 0.35
albedo *= lerp(1, 0.45, wet × (1 − metallic))        // 금속은 스며들지 않음
rough   = lerp(rough, min(rough, 0.12), wet × 0.85)
// 웅덩이 (7장)
albedo *= lerp(1, 0.6, puddle);  metallic = lerp(metallic, 0, puddle);  rough = lerp(rough, 0.03, puddle)
  • 순서: 거칠기 다음, F0 전. 금속의 F0 = 알베도이므로 F0 를 만들기 전에 바꿔야 함. 이 시점에는 s.geometricNormal 이 아직 없어서 input.normal 과 isFrontFace 로 기하 노멀을 따로 구함. SurfaceData 가 다 채워지기 전이라 ApplyWetness 는 칸 셋을 따로 받음(inout SurfaceData 는 FXC 가 거부, 10장).
  • 비가 없으면 rainParams.y = 0 이라 wet = 0, 모든 lerp 가 그대로 — 화면이 바뀌지 않음(9.4).
  • 보간: PrepareRain 이 wetness × intensity 를 목표로 지수 보간(1 − exp(−dt/τ), 젖을 때 wetTime 20 s, 마를 때 dryTime 60 s, dt 는 0.25 s 로 자름). 씬 불러오기·재생 전환(ResetTemporalHistory)·Rain 이 새로 생김·--rain-time 이면 바로 목표값.
  • 바다: OceanPixelShader.hlsl·OceanGBufferPixelShader.hlsl 이 include 앞에 RAIN_NO_WETNESS 를 정의해 젖음·웅덩이·물결을 뺌.

7. 튐·물결·웅덩이

7.1 빗방울이 닿는 자리 (RainImpactInCell)

튐과 물결은 같은 함수로 "빗방울이 어디에, 언제 떨어졌나"를 구하므로 늘 짝을 이룹니다. 튐이 터진 자리에서 같은 순간 물결 링이 퍼지기 시작합니다.

  • 위를 보는 면을 0.35 m 칸(kRainImpactCell)으로 나누고, 칸 두 겹을 (0.5, 0.37) 칸만큼 엇갈려 겹칩니다. 격자 좌표 = 월드 xz / 칸 + 겹 어긋남.
  • 칸마다 1.3 Hz(kRainImpactRate)로 빗방울이 하나씩 떨어집니다. 시작 시각은 칸 해시라 칸끼리 엇갈립니다. 시간은 b0 rainParams.w(1000 초로 감음) 하나라 PS 와 VS 가 같은 값을 봅니다.
  • 주기 번호를 해시에 섞어 떨어질 때마다 칸 안의 자리(칸 가운데 절반 — 링이 칸을 넘지 않음)와 "이번에 떨어지는지"를 새로 정합니다. 떨어지는 칸의 비율은 rainSurface.z = 빗방울 비율 min(maxDrops / 20000, 1) × 세기입니다.

2026-11-26 변경. 처음 구현에서는 튐이 자기 해시로 카메라 주변에 따로 흩뿌려져 물결과 자리가 맞지 않았고, 물결은 칸의 중심이 고정이라 같은 점에서 1.3 Hz 로 계속 링이 생겼습니다. 지금은 둘 다 위 함수를 쓰고, 칸의 중심도 주기마다 바뀝니다. 물결 세기를 잠시 8 배로 키워 튐(초록)과 물결(빨강)을 겹쳐 보니 튐마다 발밑에 링이 있었습니다. 튐이 없는 링은 튐(0.35 s)이 끝난 뒤 계속 퍼지는 링(한 주기 0.77 s)입니다.

7.2 튐 (RainSplashVertexShader.hlsl, RainSplashPixelShader.hlsl)

  • 빗줄기처럼 상태 없음. 튐 하나 = 카메라 주변 격자의 칸 하나. 격자 한 변은 splashGrid = ⌈2 × splashRadius / 0.35⌉ + 2 칸(최대 256, splashRadius = 0.8 × areaRadius), 겹 둘이라 Draw(2 × splashGrid² × 6). 기본값이면 한 변 71 칸, 튐 칸 10,082 개.
  • VS 가 튐 번호를 (겹, 칸)으로 바꾸고 — 카메라 xz 가 든 칸이 가운데라 카메라가 움직여도 칸은 월드에 고정 — RainImpactInCell 을 부릅니다. 이번 주기에 떨어지지 않은 칸, 떨어진 지 0.35 s(kSplashPeriod)가 지난 칸, 원 반지름 splashRadius 밖은 버립니다. 그래서 실제로 보이는 튐은 원 안 칸 × rainSurface.z × 0.35 × 1.3 정도입니다.
  • y: 그 xz 의 차폐 맵 높이 = 비가 처음 닿는 면(지붕 윗면·잎 판·열린 바닥). 맵 밖·빈 곳·빗줄기 상자보다 멀리 위아래면 그리지 않음.
  • 쿼드는 세로축이 월드 +y 이고 카메라 쪽을 보는 원통형 빌보드(아래 끝이 면 위 1 cm). PS 가 진행도에 따라 커지는 왕관 고리(가시 cos 6θ, (1 − u)² 로 사라짐)를 그림. 소프트 페이드 거리는 빗줄기의 0.15 배 — 면에 붙어 있으므로.
  • 예전 maxSplashes 는 없앴습니다. 튐 수는 물결과 같이 maxDrops·세기를 따릅니다. 에디터 통계 줄은 그린 칸 수(splash cells)를 보여 줍니다.

7.3 물결 (RainRipple)

픽셀이 든 칸을 겹마다 하나씩 찾아 RainImpactInCell 로 그 칸의 떨어진 자리와 지난 몫(phase)을 얻고, 그 자리에서 반지름 phase × 0.25 칸으로 퍼지는 링 단면의 기울기를 노멀의 xz 에 더합니다((1 − phase)² 로 사라짐). 위를 보는 젖은 면에서 웅덩이일수록 세고, 카메라에서 25 m 밖은 0(멀면 픽셀보다 작아 반짝이기만 함). 빗방울이 적거나 비가 약하면 링이 드문드문 생기고, 링 하나의 세기는 그대로입니다. 비가 그치면(세기 0) 물결도 없습니다. (maxDrops 20000 → 5000 에서 물결로 바뀌는 픽셀 577 → 69, 튐과 맞추기 전 측정)

7.4 웅덩이 (RainPuddle)

값 노이즈 두 옥타브(0.35·1.1 회/m)를 문턱 lerp(0.85, 0.3, puddles) 와 비교합니다(기본 0.5 → 0.575, 평평한 바닥의 약 1/4). 젖음이 0.5 를 넘은 뒤부터 자라고, 기울기 약 18° 이하인 면에만, 컷아웃 재질이 아닐 때만 생깁니다. 웅덩이는 노멀을 기하 노멀 쪽으로 평평하게 만듭니다(ApplyWetNormal).

9.1 백엔드·경로 네 조합

11. 한계와 남은 일

  • 반사: 젖은 바닥·웅덩이의 반사는 IBL 큐브맵뿐. 주변 기둥·깃발이 비치지 않아 "젖은 느낌"이 약함. 화면 공간 반사(SSR)나 평면 반사가 있어야 함.
  • 차폐 맵 범위: 카메라 중심 80 m 밖은 열린 하늘로 봄. 큰 지붕이 80 m 를 넘으면 가장자리에서 비가 샘. occlusionSize 를 키우면 텍셀이 굵어짐.
  • 빗줄기 조명: 환경광 세기만 곱함. 지역광·그림자에 따라 밝기가 바뀌지 않음(가로등 아래 빗줄기가 빛나지 않음).
  • 튐 모양: 원통형 빌보드라 바로 위에서 보면 선이 됨. 면의 재질(물·흙)을 구분하지 않음.
  • 디버그 뷰 18 의 B: 재질을 모르므로 컷아웃 면에도 웅덩이 자리를 보여 줌.
  • 여러 비: 첫 번째 Rain 만. 구역별로 다른 비는 없음.
  • CPU: 차폐 맵 패스가 드로우 목록 전체를 한 번 더 돎. 드로우가 많은 씬에서는 GPU 보다 CPU 제출이 먼저 늚(계획 4장 예상).

13. 코드 읽는 순서

  1. Scene/Rain.h — 필드와 기본값.
  2. Graphics/RendererRain.cpp 의 PrepareRain — 차폐 맵 행렬, 젖음 보간, b0·b8 값.
  3. Graphics/RendererShadow.cpp 의 DrawDepthView, RendererRain.cpp 의 RenderRainOcclusionPass.
  4. Shaders/Rain.hlsli — 맵 읽기, 젖음, 웅덩이, 물결, RAIN_DRAW 구역.
  5. Shaders/MaterialSurface.hlsli 의 ApplyWetness·ApplyWetNormal 과 호출 자리.
  6. Shaders/RainVertexShader.hlsl → RainPixelShader.hlsl → 튐 셰이더 둘.
  7. Graphics/Renderer.cpp 의 Render(호출 순서), UpdateFrameSet(t24), RenderScenePass(Effects 패스).
