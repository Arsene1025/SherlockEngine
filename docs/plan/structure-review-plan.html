구조 점검과 수정 제안

2026-11-10 · 프로젝트 코드 전체를 읽고, 비효율적인 부분과 앞으로의 확장(라이트 컬링 → 디퍼드 → SSAO → 컴퓨트 → 클러스터드)에 걸림돌이 될 부분을 정리한 제안서입니다. 이 문서를 쓴 시점에는 코드를 한 줄도 고치지 않았습니다.

결론: 지금 구조는 디퍼드 단계에서 막힙니다. D3D12 커맨드 리스트가 바인딩 레이아웃을 4종류까지만 기억하는데 이미 4개를 다 쓰고 있고, 레지스터 여유도 거의 없으며, 메인 깊이 버퍼를 셰이더에서 읽을 수 없습니다. 급한 것은 A 그룹 네 가지이고, B(비효율)와 C(유지보수)는 그 뒤입니다.

기준: 커밋 64c02b9 + 작업 트리(2026-11-10). 경로는 SherlockEngine/ 기준이고 행 번호는 이 시점의 참고용입니다. 성능 항목(B)은 코드를 읽고 판단한 것이며 프로파일링으로 재지는 않았습니다.

2. A — 다음 로드맵을 막는 것

A1. D3D12 커맨드 리스트가 레이아웃을 4종류까지만 기억함

  • D3D12CommandList::SetResourceSet (RHI/D3D12/D3D12CommandList.cpp 약 170~197행)은 셋의 레이아웃 핸들로 슬롯을 찾고, 없으면 kMaxBindingSets(4)까지만 새로 추가합니다. 한 번 들어간 슬롯은 비워지지 않습니다.
  • 지금 레이아웃은 frame / object / material / post 네 개라 이미 가득 찼습니다. Renderer::Initialize 의 주석(Graphics/Renderer.cpp 약 152행)이 b5·b6 을 새 레이아웃이 아니라 프레임 레이아웃 끝에 붙인 이유로 이것을 적어 두었습니다.
  • GBuffer 라이팅이나 SSAO 용 레이아웃을 하나 더 만들면 "셋 슬롯이 가득 참" 에러와 함께 그 셋은 바인딩되지 않습니다. D3D11 은 레지스터에 직접 꽂으므로 이 제한이 없어, D3D12 에서만 깨집니다.
제안: SetResourceSet(setIndex, handle) 처럼 셋 번호를 명시하고(Vulkan 의 set 번호), PSO 의 bindingLayouts[i] 와 인덱스로 대응시킵니다. "레이아웃이 같은 슬롯을 찾아 교체"하는 탐색이 사라지고, PSO 가 바뀌면 그 PSO 의 셋 수만큼만 유효합니다.

  • GBuffer 3~4장 + 깊이 + AO 를 읽으려면 SRV 가 5~6개 필요한데 자리가 없습니다.
  • 원인은 "D3D11 의 t#/s# 는 번호 공간이 하나이므로 셋끼리 겹치지 않게 전역으로 나눈다"는 규칙입니다. 패스가 늘수록 번호가 소진됩니다.
제안: 전역 배정 규칙을 버리고 패스별 레이아웃이 레지스터를 재사용하게 합니다(라이팅 패스의 t0 과 재질의 t0 은 동시에 바인딩되지 않음). A1 이 선행돼야 합니다. 상한(kMaxSrvRegister, kMaxBindingSlots)도 함께 올립니다.

A3. 메인 깊이 버퍼를 셰이더에서 읽을 수 없음

  • 씬 뷰와 미리보기의 깊이 텍스처는 TextureBind_DepthStencil 만 갖습니다 (Renderer::SetSceneTarget 약 2227행, SetPreviewTarget 약 1890행).
  • 게임 모드는 Device::GetDepthBuffer() 를 그대로 씁니다 (Renderer::RenderMainPass 약 1657행). 장치가 소유한 깊이 버퍼라 SRV 로 만들 수 없습니다.
  • 백엔드는 D24S8 + SRV 조합의 TYPELESS 변환을 이미 갖고 있으므로(D3D12Convert.cpp 약 229~244행) RHI 쪽 변경은 작습니다.
제안: Renderer 가 모드와 무관하게 자기 깊이 텍스처(DepthStencil | ShaderResource)를 소유하고, Device::GetDepthBuffer 는 인터페이스에서 뺍니다. 같이 Format 에 GBuffer·AO 용 포맷(R8_UNORM, R16G16_FLOAT, R10G10B10A2_UNORM 등)을 추가합니다. 포맷마다 두 백엔드의 Convert 표에 한 줄씩 들어갑니다.

A4. 조명이 GPU 구조체의 벡터이고 8개로 고정

  • Scene::m_lights 는 LightData 의 벡터입니다 (Scene/Scene.h 약 202행). LightData 는 cbuffer 레이아웃 그대로라 shadowIndex·패딩까지 씬 데이터에 들어 있습니다 (Scene/Light.h).
  • GameObject 가 아니라서 계층·스크립트·안정 ID 가 없습니다. 에디터는 m_selectedLight 인덱스로 따로 선택하고(Editor/Editor.h), 기즈모·아이콘·픽킹 코드도 오브젝트용과 별도로 있습니다.
  • MAX_LIGHTS = 8 이 cbuffer 크기(656B)에 박혀 있고, 씬을 읽을 때도 8개에서 자릅니다 (Scene/SceneSerializer.cpp 716행, 795행).
  • SRV 바인딩이 텍스처만 받습니다. ResourceBinding 의 SRV 는 texture 필드뿐이고 CreateResourceSet 이 텍스처인지 검사합니다 (D3D12Device.cpp 약 1194행). 조명 리스트를 구조화 버퍼로 넘길 길이 없습니다 (BufferBind_ShaderResource 플래그는 있지만 쓰는 경로가 없음).
제안: 씬 쪽은 LightComponent(또는 최소한 씬용 Light 구조체)로 분리하고, GPU 용 LightData 는 Renderer 가 매 프레임 만듭니다. BindingType 에 버퍼 SRV 를 추가합니다. CPU 라이트 컬링이 조명별 바운드와 가변 개수를 전제로 하므로 그 전에 하는 것이 맞습니다.

3. B — 비효율

B1. 메인 패스와 CSM 에 컬링이 없고, 월드 행렬을 패스마다 다시 계산

  • Renderer::BuildDrawList (약 1473행)에 프러스텀 컬링이 없습니다. 그림자 패스는 지역광만 구 컬링을 하고 캐스케이드 뷰는 하지 않습니다 (RenderShadowAtlasPass 약 1608행, cullSphere.w = 0). Sponza 는 캐스케이드 4번 + 메인 1번을 전부 그립니다.
  • UploadObjectConstants (약 1516행)가 드로우마다 GameObject::GetWorldMatrix() 와 역행렬을 구합니다. GetWorldMatrix 는 부모를 재귀로 올라가며 오일러 → 행렬을 매번 다시 만들고 캐시가 없습니다 (Scene/GameObject.cpp 40행).
  • 한 드로우 항목이 프레임당 반복하는 횟수: BuildDrawList 1 + 경계 구 1 + 그림자 뷰 수 + 메인 1 + 미리보기 1.
제안: 프레임 초에 오브젝트별 월드 행렬·역행렬·월드 바운드를 한 번 계산해 DrawItem 에 담고, 뷰(메인·캐스케이드·지역광)별 가시성 리스트를 만듭니다. 이 바운드와 컬링 코드는 A4 뒤의 라이트 컬링에서 그대로 씁니다.

B2. GPU 리소스를 드로우 루프 안에서 만들고, 업로드마다 GPU 를 기다림

  • GetOrCreateGpuMesh / GetOrCreateGpuMaterial → GetOrLoadTexture 가 렌더 패스 도중 처음 만난 리소스를 그 자리에서 디코딩·밉 생성·업로드합니다 (Renderer::DrawItems 약 1795행, 1804행).
  • D3D12 는 리소스 하나마다 ExecuteUploadSync → WaitForGpu 입니다 (D3D12Device.cpp 약 375~387행). Sponza 는 메시·텍스처를 합쳐 수백 번 플러시합니다.
제안: 씬 로드 직후에 메시·재질·텍스처를 미리 만드는 단계를 두고, 업로드를 한 커맨드 리스트에 모아 한 번만 기다립니다. 비동기 로딩은 그 다음 문제입니다.

B3. 매 프레임 반복되는 재질·PSO 조회

  • GetOrCreateGpuMaterial (약 2096~2101행)이 재질마다 매 프레임 텍스처 이름으로 캐시 키 문자열(name + "|srgb")을 5번 만들어 해시 조회하고, 값이 그대로여도 상수를 다시 올립니다. 미리보기 패스가 있으면 두 번입니다.
  • GetPipelineFor (약 2153행)는 드로우 항목마다 PipelineStateDesc 전체를 복사·해시합니다. GetShadowPipelineFor 는 그림자 패스에서 뷰 × 항목마다 반복합니다 (약 1622행).
제안: 재질에 변경 카운터를 두어 바뀐 때만 텍스처 해석과 상수 업로드를 하고, PSO 핸들은 (재질 플래그, mirrored, 렌더 설정) 작은 키로 캐시합니다. 핫리로드 때 이 캐시도 같이 비웁니다.

B4. 씬 조회가 전부 선형

  • Scene::FindById (Scene/Scene.cpp 97행), IndexOf (206행), RemoveObject (115행)가 모두 오브젝트 벡터를 훑습니다.
  • FlushDestroyed (182행)는 지울 루트마다 FindById + IndexOf 를 부릅니다. Spawner 처럼 생성·파괴가 많으면 O(n²)입니다.
  • 에디터 선택이 인덱스 기준이라 ID ↔ 인덱스 동기화 코드(Editor::SyncSelection)가 따로 필요합니다.
제안: id → 오브젝트 맵을 두고, 에디터 선택과 콜백(deleteObject(int) 등)도 ID 를 기준으로 바꿉니다.

B5. 모델 데이터가 메모리에 두 벌

  • Scene::AddModel 이 AssetManager 캐시의 메시를 복사합니다 (Scene/Scene.cpp 434행, Mesh copy = model.meshes[i]). 이미지 바이트도 AddModelImages 로 씬에 다시 넣습니다.
  • 되돌리기 이력은 메시를 다루지 않아, 모델 배치를 되돌려도 메시가 씬에 남습니다 (Editor/EditorHistory.h 주석).
제안: 메시·이미지를 shared_ptr<const> 또는 에셋 핸들로 공유합니다. 씬이 사본을 갖지 않으면 "되돌린 뒤 남는 메시"도 참조가 없어질 때 자연히 정리됩니다. Renderer 의 포인터 키 캐시와 InvalidateScene 호출 순서 계약도 같이 단순해집니다.

4. C — 구조·유지보수

C1. Renderer 가 한 클래스에 다 들어 있음

  • Renderer.cpp 2,244줄 + RendererPost.cpp 287줄에 패스, GPU 캐시, 텍스처 파일 IO·디코딩, 셰이더 로드, 그림자 뷰 계산이 모두 있습니다.
  • 메인과 미리보기가 같은 멤버 묶음(color / depth / hdr / 상태 / post set / scratch)을 두 벌 갖습니다 (Graphics/Renderer.h 약 437~470행). 디퍼드가 들어오면 GBuffer 도 두 벌이 됩니다.
  • 리소스 상태를 Renderer(m_*State 10여 개)와 백엔드가 이중으로 추적합니다. D3D12 는 before 인자를 믿지 않고 자기 추적 값을 씁니다 (D3D12CommandList::Barrier 약 328행).
제안:
  • 출력 하나의 타깃 묶음을 ViewTarget 구조체로 만들고, 패스 함수가 그것과 카메라를 받게 합니다. 메인·미리보기가 같은 코드 경로를 탑니다.
  • CommandList::Barrier 에서 before 인자를 없애고 Renderer 의 상태 멤버를 지웁니다.
  • 텍스처 이름 해석(builtin:, asset:, 씬 이미지)과 파일 IO 는 TextureCache 로, 그림자 뷰·아틀라스는 별도 파일로 뺍니다.

C2. 셰이더 하나 추가에 9군데 수정

  • 셰이더 8개가 멤버, LoadShaders 의 두 분기, cbuffer 검증, 생성, 실패 시 파괴, 교체, Shutdown, ReloadShaders, 감시 목록에 각각 손으로 나열돼 있습니다 (Renderer.cpp 약 632~790행, 867~895행).
  • ValidateBindings (약 792행)는 벡터 8개를 인자로 받고, PSO 의 레이아웃이 아니라 모든 레이아웃의 합집합과 대조합니다. 스카이박스 셰이더가 재질 슬롯을 써도 통과합니다.
제안: {파일, 엔트리, 스테이지, 핸들} 테이블로 바꿔 루프로 처리하고, 검증은 PSO Desc 의 bindingLayouts 기준으로 합니다. A2 에서 레지스터를 재사용하기 시작하면 합집합 검증은 어차피 쓸 수 없습니다.

C3. 스크립트 DLL 의 ABI 검사가 없음

  • Scene·GameObject·Transform 은 STL 멤버와 인라인 접근자를 가진 채 export 되고, "멤버는 끝에만 덧붙임"이라는 주석 규율에 의존합니다 (Scene/Scene.h 약 213행, Scene/GameObject.h 약 140행).
  • ScriptModule::Load (Core/ScriptModule.cpp 70행)에 버전 확인이 없습니다. 엔진 헤더가 바뀐 뒤 오래된 DLL 이 올라오면 조용히 메모리가 깨집니다.
제안: 엔진 API 버전 상수를 헤더에 두고 SHERLOCK_SCRIPT 쪽에서 DLL 에 심은 뒤 로드 때 비교합니다. 다르면 올리지 않고 기존 "Missing Script" 경로로 보냅니다.

C4. EditorApp 에 자동 검증 코드가 섞여 있음

  • ParseAutomation / RunAutomation (Editor/EditorApp.cpp 약 952~1240행)이 프레임 번호를 하드코딩한 실행 인자 30여 개를 처리하고, Automation 구조체가 EditorApp.h 의 절반을 차지합니다.
제안: 별도 클래스로 떼고, 단계를 (프레임, 동작) 테이블로 만듭니다. 새 검증 인자를 추가할 때 프레임 번호 충돌을 눈으로 찾지 않아도 됩니다.

6. 살펴봤지만 제외한 것

  • 되돌리기의 전체 씬 스냅샷 방식 — 편집이 끝난 프레임에만 직렬화하고 단계·바이트 상한이 있어 지금 규모에서는 문제없습니다.
  • 업로드 링 크기(8MB) — 드로우마다 256B 를 쓰므로 프레임당 약 3만 번까지 됩니다. B1 을 하면 더 여유가 생깁니다.
  • 단일 정점 포맷(64B) — 그림자 패스도 전체 정점을 읽지만, 스키닝 등 두 번째 포맷이 필요해질 때 다루면 됩니다.
  • 에디터 코드가 엔진 DLL 안에 있는 것 — ImGui 전역 컨텍스트 때문에 의도한 구조입니다 (App/EntryPoints.h).
