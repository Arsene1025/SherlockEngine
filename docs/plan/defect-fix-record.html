1. Release 삭제·복제 자동 검증 segfault

1.2 원인 — 증분 LTCG

엔진 Release 구성은 WholeProgramOptimization=true(/GL)이고 링크 방식(LinkTimeCodeGeneration)은 적지 않았습니다. 이때 Visual Studio 기본값은 증분 LTCG(/LTCG:incremental)입니다. 이 모드는 바뀌지 않았다고 판단한 함수의 기계어를 지난 링크 결과(.iobj)에서 그대로 복사합니다. 실제 빌드 로그에도 0 of 214 functions compiled, the rest were copied from previous compilation 이 찍혀 있었습니다.

EditorApp 에 멤버가 추가돼 레이아웃이 바뀐 뒤, 다른 번역 단위에 인라인된 일부 함수가 "바뀌지 않음"으로 판정돼 옛 오프셋 그대로 복사된 것으로 보입니다. Debug 는 LTCG 를 쓰지 않아서 이 문제가 없습니다.

원인 확인 방법. 소스는 그대로 두고 .iobj·.ipdb 만 치운 뒤 다시 링크했습니다. 옛 오프셋을 쓰는 복사본이 0 곳이 됐고, delete, duplicate, delete+undo, duplicate+undo+redo 네 가지가 모두 종료 코드 0 이었습니다. 코드를 하나도 고치지 않고 링크 캐시만 버려서 사라졌으므로 원인은 증분 링크입니다.

왜 링커가 레이아웃 변경을 놓쳤는지(어떤 조건에서 함수를 "바뀌지 않음"으로 보는지)는 확인하지 못했습니다. 다만 그 판정을 믿지 않으면 되므로, 수정은 증분 모드를 쓰지 않는 것으로 했습니다.

2. 테스트 솔루션의 C1083

처음 기록구조 검토 수정 기록, Undo · 프리팹 구현 기록 증상Projects/SherlockTestScenes/SherlockTestScenes.sln, Projects/QuaternionLookTest/QuaternionLookTest.sln 에서 빌드하면 SherlockEditor\EditorMain.cpp(2,10): error C1083 'App/EntryPoints.h'. 엔진 솔루션에서는 빌드됨

2.1 원인

SherlockEditor.vcxproj 와 SherlockGame.vcxproj 는 include 경로와 디버거 작업 폴더를 $(SolutionDir)SherlockEngine 으로 적고 있었습니다. $(SolutionDir) 은 "지금 빌드하는 솔루션의 폴더"입니다. 엔진 솔루션은 저장소 루트에 있어서 맞는 경로가 되지만, 프로젝트 솔루션은 Projects/SherlockTestScenes/ 에 있어서 있지도 않은 Projects/SherlockTestScenes/SherlockEngine 이 됩니다.

엔진 프로젝트는 이미 출력 폴더를 $(ProjectDir).. 기준으로 고쳐 두었는데, 에디터·게임 프로젝트에는 그 수정이 빠져 있었습니다. 출력 폴더도 기본값($(SolutionDir)x64\…)이라, include 만 고쳤다면 exe 가 엔진 DLL 과 다른 폴더에 생겼을 것입니다.

2.2 수정과 검증

  • 두 vcxproj 의 $(SolutionDir)SherlockEngine 8 곳(구성마다 include 경로와 LocalDebuggerWorkingDirectory)을 $(ProjectDir)..\SherlockEngine 으로 바꿨습니다. 프로젝트 파일 위치는 솔루션과 상관없이 고정이므로 어느 솔루션에서 열어도 같은 경로가 됩니다.
  • x64 출력 폴더를 $(ProjectDir)..\x64\$(Configuration)\ 로 고정했습니다. 엔진과 같은 규칙이라 exe 가 SherlockEngine.dll 옆에 생깁니다.

3. D3D12 GPU 기반 검증 멈춤

처음 기록디퍼드·클러스터드·SSAO 구현 기록 8.4, rendering-analysis 22.4 증상Debug, --backend=d3d12 --gpu-validation=1 로 실행하면 첫 프레임 전에 멈춤. 기록에는 다섯 번 중 한 번 통과로 적혀 있었고, 이번에는 네 번 중 네 번 재현됨

3.1 추적

  • 매번 시작 후 약 0.6 초, 로그의 "PSO 생성 #10" 다음에서 멈췄습니다.
  • 데드락이 아니었습니다. 메인 스레드가 코어 하나를 계속 쓰면서 메모리가 늘었습니다. 6 분 동안 CPU 시간 378 초, 전용 메모리 7.4 GB 까지 간 것을 보고 직접 종료했습니다.
  • 멈춘 스택: RenderDeferredScene → SetPipelineState(디퍼드 라이팅 PSO) → D3D12 디버그 레이어의 GBV → NVIDIA 셰이더 컴파일러(nvgpucomp64). GBV 는 PSO 가 처음 쓰일 때 셰이더에 검증 코드를 끼워 넣고 드라이버가 그것을 다시 컴파일합니다. 그 컴파일이 끝나지 않고 있었습니다.

이후 실험은 전용 메모리 1.5 GB 나 90~180 초를 넘으면 프로세스를 죽이는 감시 스크립트를 붙여 돌렸습니다. 처음 900 초짜리 실행에서 시스템 메모리가 부족해진 일이 있었기 때문입니다.

3.3 원인 — 펼친 PCF

SherlockEngine/Shaders/Shading.hlsli 의 SampleShadowViewCoverage 는 5×5 PCF 를 [unroll] 로 펼치고 SampleCmpLevelZero(…, int2(dx, dy)) 의 정수 오프셋으로 이웃 텍셀을 읽었습니다. SM 5.0 에서 이 오프셋 인자는 컴파일 타임 상수여야 해서 루프를 펼칠 수밖에 없었습니다.

이 함수는 그림자를 받는 모든 곳에 인라인됩니다. CSM 캐스케이드와 캐스케이드 블렌드, 스팟, 포인트 큐브 면이 있고, 이것이 전체 조명 순회와 클러스터 순회 양쪽에 들어갑니다. 아틀라스(지역광 / CSM)마다 분기가 따로 있으니 25 탭 × 2 가 호출 지점 수만큼 곱해집니다.

3.4 수정

PCF 를 [loop] 로 바꾸고, 정수 오프셋 대신 아틀라스 텍셀 크기를 곱해 UV 에 직접 더했습니다. 텍셀 크기는 상수 버퍼에 이미 있던 값을 씁니다. 지역광 아틀라스는 shadowAtlasParams.x(= 1 / 아틀라스 크기), CSM 아틀라스는 csmAtlasParams.xy(= 1 / 너비, 1 / 높이)입니다. 둘 다 Graphics/RendererShadow.cpp 가 채웁니다. 원래 타일 여백 계산에 쓰던 같은 값을 texel 변수 하나로 묶었으므로 2048 같은 숫자를 셰이더에 새로 적지 않았습니다.

// 수정 전
const float2 border = shadowAtlasParams.y * (csm ? csmAtlasParams.xy : shadowAtlasParams.xx);
...
[unroll] for (int cy = -2; cy <= 2; ++cy)
    [unroll] for (int cx = -2; cx <= 2; ++cx)
        lit += csmMap.SampleCmpLevelZero(shadowSampler, uv, depth, int2(cx, cy));

// 수정 후
const float2 texel = csm ? csmAtlasParams.xy : shadowAtlasParams.xx;   // 아틀라스 텍셀 크기 (UV)
const float2 border = shadowAtlasParams.y * texel;
...
[loop] for (int cy = -2; cy <= 2; ++cy)
    [loop] for (int cx = -2; cx <= 2; ++cx)
        lit += csmMap.SampleCmpLevelZero(shadowSampler, uv + float2(cx, cy) * texel, depth);

지역광 분기(shadowMap)도 같은 모양입니다. 텍스처는 변수로 고를 수 없어서 아틀라스마다 루프를 따로 두는 구조는 그대로입니다. 분기 조건은 뷰 단위라 한 드로우 안에서 균일합니다.

5. 확인하지 못한 것

  • 다른 GPU. GBV 멈춤과 그 수정은 NVIDIA 드라이버 하나에서만 확인했습니다. AMD·Intel 드라이버에서 원래 코드가 멈췄는지도 모릅니다.
  • 기록에 있던 다른 멈춤 자리. 디퍼드 기록 8.4 의 "루트 시그니처 생성" 줄에서의 멈춤(약 8 GB)은 이번에 재현되지 않았습니다. 같은 원인인지 모릅니다. 기록상 한 번 끝까지 돈 이유도 모릅니다.
  • 증분 LTCG 가 레이아웃 변경을 놓친 조건. 링커가 어떤 기준으로 함수를 "바뀌지 않음"으로 보는지는 확인하지 않았습니다. 수정은 그 판정을 쓰지 않는 쪽입니다.
  • 스크립트 DLL 의 증분 LTCG. 스크립트 DLL 에서 같은 문제가 실제로 난 것은 본 적이 없습니다. 전체 LTCG 로 바꾼 것은 예방입니다.
  • 화면 비교 범위. PCF 수정의 화면 비교는 Debug D3D11 세 씬입니다. D3D12 와 Release 는 실행과 로그만 확인했습니다. 같은 HLSL 이라 결과가 다를 이유는 없지만 이미지로 확인하지는 않았습니다.
  • 별개의 GBV 오류. 구조 검토 기록과 컴퓨트 RHI 기록의 일회성 Incompatible texture barrier layout(builtin:flatnormal)은 다른 결함입니다. 이번 작업과 관계없고 여전히 원인을 모릅니다.
