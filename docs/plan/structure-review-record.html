2. A1 · A2 — 셋 인덱스와 레지스터 여유

A1. 셋을 레이아웃이 아니라 인덱스로 기억

왜. 계획의 진단: D3D12CommandList::SetResourceSet 이 셋의 레이아웃 핸들로 슬롯을 찾고 없으면 kMaxBindingSets(4)까지만 추가하며, 한 번 들어간 슬롯은 비워지지 않습니다. frame / object / material / post 네 레이아웃으로 이미 가득 차 있어 다섯 번째 레이아웃(G-buffer 라이팅, SSAO)의 셋은 바인딩되지 않습니다.

A2. 레지스터·슬롯 상한과 겹침 검사

왜. 계획의 진단: CBV 8 / SRV 16 / 레이아웃당 슬롯 16 상한에 남은 자리가 b7, t5~t7, t15, 슬롯 4개뿐이었고, 원인은 "D3D11 의 t#/s# 는 번호 공간이 하나이므로 셋끼리 겹치지 않게 전역으로 나눈다"는 규칙이었습니다.

수정 전 / 후 (RHI/BindingTypes.h):

// 전
constexpr uint32_t kMaxBindingSlots = 16;
constexpr uint8_t kMaxCbvRegister = 8;
constexpr uint8_t kMaxSrvRegister = 16;
constexpr uint8_t kMaxSamplerRegister = 8;

// 후
constexpr uint32_t kMaxBindingSlots = 24;   // 레이아웃 하나의 슬롯 수
// 레지스터 번호는 "한 PSO 가 쓰는 레이아웃들 안에서만" 겹치지 않으면 됨. ...
constexpr uint8_t kMaxCbvRegister = 14;
constexpr uint8_t kMaxSrvRegister = 32;
constexpr uint8_t kMaxSamplerRegister = 16;

겹침 검사는 두 곳에서 패스(PSO) 단위로 합니다.

  • D3D12Device::GetOrCreateRootLayout: 한 PSO 의 셋끼리 같은 (레지스터 문자, 번호)를 같은 스테이지에 선언하면 "루트 시그니처 : 셋 %u (%s) 와 셋 %u (%s) 가 같은 레지스터 %c%u 를 같은 스테이지에 선언함." 로그와 함께 nullptr. 텍스처와 구조체 버퍼는 같은 t 공간으로 봅니다(RegisterClassOf).
  • 같은 함수가 루트 파라미터 비용(루트 디스크립터 2, 테이블 1 DWORD)을 더해 64 를 넘으면 거절하고, 성공하면 "루트 시그니처 생성: 셋 %u개, 루트 파라미터 %u개, %u / 64 DWORD …" 를 남깁니다.
  • Renderer::ValidateBindings: kPasses 의 패스마다 그 패스 레이아웃끼리 겹치는지 봅니다 (C2).

달라진 것. 서로 다른 PSO 는 같은 번호를 다른 용도로 써도 되는 구조가 됐습니다. 예: G-buffer 를 읽는 라이팅 패스의 t0~t3 과 재질의 t0~t4.

남은 한계. 지금 있는 레이아웃의 번호는 바꾸지 않았습니다. 재질 t0~t4, 프레임 t8~t15, 후처리 t13 처럼 전역 배정 번호를 그대로 쓰고, Shaders/Common.hlsli 머리 주석의 "재질 셋 t0..t7 / 프레임 셋 t8..t15" 배정표도 남아 있습니다. 재사용은 새 패스를 만들 때 처음 쓰게 됩니다. 프레임 셋은 이제 t8~t12, t14, t15 를 쓰고(t13 은 후처리 셋), 계획 문서의 "남은 것" 표에 있던 t15 는 조명 버퍼가 차지했습니다.

8. C3 · C4 — 스크립트 ABI 검사, 자동 검증 분리

C3. 스크립트 DLL 의 ABI 표식

왜. 계획의 진단: Scene·GameObject·Transform 이 STL 멤버와 인라인 접근자를 가진 채 export 되고 "멤버는 끝에만 덧붙임" 규율에 의존하며, ScriptModule::Load 에 버전 확인이 없어 엔진 헤더가 바뀐 뒤 오래된 DLL 이 올라오면 조용히 메모리가 깨집니다.

// Core/EngineApi.h
#define SHERLOCK_SCRIPT_API_VERSION 1

// Scene/Script.h
struct SherlockScriptAbi
{
    uint32_t apiVersion;         // SHERLOCK_SCRIPT_API_VERSION (사람이 올리는 번호)
    uint32_t iteratorDebugLevel; // _ITERATOR_DEBUG_LEVEL. Debug 와 Release 는 std::string·vector 의 배치가 다름
    uint32_t sizeofBehaviour;    // 아래 넷은 자동 검사
    uint32_t sizeofScript;
    uint32_t sizeofGameObject;
    uint32_t sizeofTransform;
    constexpr bool operator==(const SherlockScriptAbi&) const = default;
};
inline constexpr SherlockScriptAbi kSherlockScriptAbi{
    SHERLOCK_SCRIPT_API_VERSION, _ITERATOR_DEBUG_LEVEL,
    sizeof(Behaviour), sizeof(Script), sizeof(GameObject), sizeof(Transform),
};
#ifndef SHERLOCK_ENGINE_EXPORTS
extern "C"
{
    __declspec(dllexport) __declspec(selectany) SherlockScriptAbi SherlockScriptAbiInfo = kSherlockScriptAbi;
}
#endif
// Core/ScriptModule.cpp — ScriptModule::Load 에서 LoadLibraryW 전에
bool CheckAbi(const std::wstring& path, std::string& error)
{
    HMODULE probe = LoadLibraryExW(path.c_str(), nullptr, DONT_RESOLVE_DLL_REFERENCES);
    ...
    const SherlockScriptAbi* abi = reinterpret_cast<const SherlockScriptAbi*>(GetProcAddress(probe, "SherlockScriptAbiInfo"));
    if (abi == nullptr)
        error = "the script DLL has no ABI stamp (built before the script API check). Rebuild the script project.";
    else if (!(*abi == kSherlockScriptAbi))
        error = std::format("script ABI mismatch — rebuild the script project. DLL / engine: api {} / {}, ...", ...);
    else ok = true;
    FreeLibrary(probe);
    return ok;
}

if (!CheckAbi(copy.wstring(), m_lastError))
{
    Log::Error("스크립트 DLL 을 올리지 않음: %s (%s)", m_lastError.c_str(), ...);
    if (copyBeforeLoad) fs::remove(copy, ec);
    return false;
}

달라진 것. 스크립트 헤더(Scene/Script.h)를 include 한 스크립트 DLL 은 빌드될 때 본 값을 데이터 심볼로 내보내고, 엔진은 그 DLL 의 코드(DllMain·정적 초기화)를 실행하지 않고 비교합니다. 맞지 않으면 LoadLibraryW 까지 가지 않으므로 그 DLL 의 컴포넌트 타입은 등록되지 않습니다. 메시지는 영어로 m_lastError 에 남습니다.

남은 한계. 자동으로 잡는 것은 _ITERATOR_DEBUG_LEVEL 과 네 클래스의 크기뿐입니다. Scene·Camera·Input 의 크기, 크기가 같은 배치·가상 함수 순서 변경은 SHERLOCK_SCRIPT_API_VERSION 을 사람이 올려야 잡힙니다. 이번에 Scene 끝에 m_objectsById 를 붙였지만 버전은 처음 도입한 1 이고, 이전 DLL 은 표식이 없어서 어차피 거부됩니다.

9. 계획과 다르게 한 것 / 알아둘 점

주제내용
A4 조명 표현계획은 씬 쪽을 LightComponent(또는 최소한 씬용 Light 구조체)로 나누자고 했고, 이번에는 뒤쪽을 택했습니다. 씬의 Light 구조체를 벡터로 유지하고 GPU 배치(GpuLight)만 분리했습니다. 조명을 GameObject 로 만드는 일(계층·스크립트·안정 ID, 에디터의 별도 선택·기즈모 코드 통합)은 남았습니다.
C4 --stop-at 순서--stop-at=N 은 이제 같은 프레임의 고정 프레임 단계가 모두 끝난 뒤에 실행됩니다. 예전 코드에서는 StopPlay 줄이 프레임 7 의 --set-parent, 8 의 --set-position·--set-rotation, 12 의 --save, 16 의 --load, 20 의 --dump-objects 보다 앞에 있었습니다(나머지 2~6, 7 의 --drop-texture, 9~11, 14, 15, 18 은 예전에도 앞). 그래서 N 이 7·8·12·16·20 일 때만 결과가 달라질 수 있습니다. 문서들의 예시 --stop-at=15 는 영향이 없습니다.
배리어 통계두 백엔드 모두 Stats::barriers 가 실제 상태 전이만 셉니다. 예전에는 Barrier 호출 수(전이 없음 포함)였으므로 패널의 숫자가 전보다 작게 나옵니다. 예전 수치와 비교할 때 주의.
스크립트 DLL 다시 빌드스크립트 DLL 에는 ABI 표식이 있어야 하므로, 이 엔진으로 바꾼 뒤에는 프로젝트의 스크립트 DLL 을 다시 빌드해야 합니다. 표식이 없는 옛 DLL 은 "스크립트 DLL 을 올리지 않음: the script DLL has no ABI stamp …" 로그와 함께 거부됩니다.
테스트 솔루션의 에디터 빌드Projects/SherlockTestScenes/SherlockTestScenes.sln, Projects/QuaternionLookTest/QuaternionLookTest.sln 안의 SherlockEditor 프로젝트는 EditorMain.cpp(2,10): error C1083 'App/EntryPoints.h' 로 빌드에 실패합니다($(SolutionDir) 기준 include 경로 문제). 이번 수정 이전부터 있던 문제이고, 같은 솔루션의 스크립트 DLL 프로젝트는 빌드됩니다.
B3 방법계획의 "재질 변경 카운터" 대신 GPU 재질이 입력 사본을 들고 비교합니다. Material 구조체를 고치지 않아도 되지만, 비교가 문자열 다섯 개입니다.
B2 시점계획의 "씬 로드 직후 미리 만드는 단계"를 따로 두지 않고, 매 Render 의 그리기 전 구간을 업로드 묶음으로 감쌌습니다. 새로 만들 것이 없는 프레임에는 묶음이 비어 아무것도 제출하지 않습니다.
그림자 없는 프레임그림자 패스를 건너뛰는 프레임에도 Render 가 m_shadowMap·m_csmMap 을 ShaderResource 로 맞춥니다(이미 그 상태면 아무 일도 없음). 예전에는 이 분기가 없었습니다.
