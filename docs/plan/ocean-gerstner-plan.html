Gerstner 바다 구현 계획

플레이어가 멈춰 있는 배 위에서 전투를 하고, 배경으로 잔잔한 바다가 보이는 장면을 위한 계획입니다. 바다는 분위기를 만드는 배경이라 가까이서 들여다보지 않습니다. 배는 흔들리지 않으므로 파도는 GPU 정점 셰이더에서만 계산하고, CPU 에서 파도 높이를 읽는 일은 없습니다.

진행 방식. 1단계에서 작은 균일 평면에 Gerstner 변위, 노멀, 이전 위치(속도 버퍼)를 넣고 검증합니다. 2단계에서 평면을 수평선까지 넓히고 거리 감쇠를 넣습니다. 3단계는 2단계 화면을 보고 멀리서 반짝임(노멀 앨리어싱)이 거슬릴 때만 합니다. 단계마다 4장의 검증을 통과해야 다음 단계로 갑니다.

2026-11-23 작성. 기준: 커밋 a46262a. 제안 표시는 코드에 아직 없는 설계 권고입니다. 이 문서를 쓰는 동안 코드는 고치지 않았고, 빌드나 실행으로 확인한 것도 없습니다. 지금 코드에 대한 서술은 코드를 읽어 확인한 것이고, 확인하지 못한 것은 7장에 모았습니다. (같은 날 1~3단계를 구현했습니다. 계획과 달라진 곳은 아래 "구현하면서 바뀐 점" 상자에, 지금 코드와 검증 결과는 Gerstner 바다 구현 기록에 있습니다.)

2. 개념: Gerstner 파도

수면의 점을 위아래로만 움직이는 사인파와 달리, Gerstner 파도는 점을 원을 그리며 움직입니다. 마루 쪽으로 점이 모여 마루가 뾰족해지고 골은 넓어집니다. 실제 물결과 비슷한 모양이 수식 몇 줄로 나오고, 노멀도 해석적으로 구해집니다. 파도 여러 개를 더해 씁니다.

평면 위 원래 위치를 x₀ = (x, z), 파도 i 의 방향(단위 2D 벡터)을 Dᵢ, 파장을 Lᵢ, 진폭을 Aᵢ, 경사를 sᵢ(0 이상, 차원 없음)라고 하면 (Y 가 위):

kᵢ = 2π / Lᵢ                        // 파수
ωᵢ = sqrt(g · kᵢ) · speed           // 깊은 물의 분산 관계 (g = 9.81). 긴 파도가 더 빠름
θᵢ = kᵢ (Dᵢ · x₀) − φᵢ(t)           // φᵢ(t) = ωᵢ t + 초기 위상, CPU 가 2π 로 감아서 넘김

P.xz = x₀ + Σ (sᵢ / kᵢ) Dᵢ cos θᵢ     // 수평 변위: 마루 쪽으로 점이 모임
P.y  =      Σ  Aᵢ          sin θᵢ     // 높이

// 편미분 (구현 첫날 유한 차분으로 부호를 확인 — 4장)
∂P/∂x = ( 1 − Σ sᵢ Dᵢx² sin θᵢ,   Σ kᵢAᵢ Dᵢx cos θᵢ,   − Σ sᵢ Dᵢx Dᵢz sin θᵢ )
∂P/∂z = ( − Σ sᵢ Dᵢx Dᵢz sin θᵢ,  Σ kᵢAᵢ Dᵢz cos θᵢ,   1 − Σ sᵢ Dᵢz² sin θᵢ )
N = normalize( cross(∂P/∂z, ∂P/∂x) )   // 평평할 때 (0, 1, 0) 이 나오는 순서. 엔진의 왼손 좌표계에서 확인
T = normalize( ∂P/∂x )                // 탄젠트 (노멀 맵 재질 대비)
  • 꼬임 조건. Σ sᵢ ≤ 1 이어야 마루에서 표면이 겹쳐 뒤집히지 않습니다. 잔잔한 바다는 0.3~0.5 면 충분합니다.
  • 진폭과 경사. 물리적인 파도 가파름은 kᵢAᵢ 입니다. 잔잔한 바다는 0.05 안팎입니다. sᵢ 는 수평으로 얼마나 모이는지를 따로 정하는 값이라 두 값을 독립으로 둡니다.
  • 위상 정밀도. ωᵢ t 를 셰이더에서 곱하면 실행 시간이 길어질수록 float 정밀도가 떨어집니다. CPU 가 double 로 fmod(ωᵢ t, 2π) 를 구해 넘깁니다. kᵢ (Dᵢ · x₀) 는 x₀ 가 수 km 여도 오차가 1e-3 rad 수준이라 괜찮습니다.

3.6 격자와 수평선 (2단계)

  • 문제. 파장 4 m 파도를 그리려면 정점 간격이 1 m 안팎이어야 합니다(파장당 4개 이상). 그런데 바다는 수평선까지 가야 하므로, 균일 평면으로 2 km 를 1 m 간격으로 덮으면 정점이 400만 개가 됩니다.
  • 선택. MeshSource 평면의 쓰지 않는 params[2] 를 "간격 증가" g(0 = 지금과 같은 균일, 기본값)로 씁니다. 축마다 t ∈ [−1, 1] 을 x = half · sign(t) · ((1 − g)|t| + g|t|³) 로 바꿔, 가운데는 촘촘하고 가장자리는 성기게 만듭니다. g 가 0 이면 씬 파일과 결과가 지금과 똑같습니다. UV 는 지금처럼 t 기준 균일로 둡니다. 정확한 곡선은 구현할 때 정해도 됩니다. 목표: 원점에서 80 m 안은 간격 1.5 m 이하, 512×512(26만 정점) 이하, 가장자리까지 끊김 없음.
  • 거리 감쇠. 가장자리 쪽 성긴 격자는 짧은 파도를 담을 수 없으므로, fadeStart~fadeEnd 사이에서 진폭과 경사를 함께 0 으로 줄입니다. 먼 바다는 평평한 거울처럼 하늘을 비추는데, 잔잔한 바다를 멀리서 볼 때의 모습과 가깝습니다.
  • 수평선. 갑판 높이 8 m 에서 실제 수평선은 약 10 km 앞입니다. 바다가 짧으면 바다 끝과 하늘 사이에 틈이 보입니다. 테스트 씬은 카메라 far 를 5000 m, 바다 한 변을 10 km 로 잡습니다(끝이 약 0.09° 아래 → 1080p·세로 FOV 60° 에서 2 픽셀 안팎). 스치는 각도의 프레넬 반사가 하늘색을 띠므로 틈의 대비도 작습니다. 그래도 보이면 7장 대안(far 를 늘림 또는 수평선 쪽 색 섞기)을 씁니다.
  • 대안으로 본 것. 가까운 촘촘한 평면과 먼 성긴 평면 두 장(평평한 구간이 겹쳐 z-파이팅), 정점 셰이더에서 격자를 늘이기(에디터 선택·경계 구가 실제 모양과 달라짐), 카메라를 따라오는 투영 격자(배와 카메라가 고정이라 이득이 없음).

  • Shaders/OceanVertexShader.hlsl 새: 3.5 의 요지. VSInput/VSOutput 은 Mesh.hlsli 그대로, UV·색은 통과, 탄젠트 손잡이는 +1.
  • Renderer.h/.cpp: Shader_OceanVS, Pass_Ocean(OceanVS + BasicPS, 메인과 같은 레이아웃), Pass_GBufferOcean(OceanVS + GBufferPS). Layout_Object 에 b9. m_oceanCB 생성과 오브젝트 셋 바인딩.
  • BuildDrawList: CollectOcean(object, world)(첫 번째 하나만, 꺼진 컴포넌트는 무시, 둘째부터 경고 한 번), ObjectData::ocean. 바다 드로우는 GetPipelineFor(..., ocean)·GetGBufferPipelineFor(..., ocean), shadowPipeline 비움, 경계 구 패딩.
  • UploadOceanConstants: 파도 생성, 위상 감기(double), m_oceanPrevTime, 바다가 없으면 파도 0개. ResetTemporalHistory 에서 지난 시간 무효화.
  • --ocean-time: RenderSettings::oceanTimeOverride, AppBase.cpp 에서 읽기.
  • 테스트 씬 Ocean.json: 하늘·환경 맵이 있는 기존 씬을 복사해 시작. 200 m × 200 m, 256×256 평면 + Ocean, 원점에 배 자리 상자 하나(그림자 받기 확인용), 카메라 높이 8 m.

1단계 검증

  • 솔루션 전체 빌드(Debug·Release). 시작 로그 바인딩 대조 OK, D3D12 Debug Layer 경고 0.
  • Ocean.json 을 D3D11·D3D12 × 디퍼드·포워드 네 조합으로 --ocean-time=10 스크린샷. 네 장이 눈으로 같고, 백엔드끼리는 픽셀 차가 기존 씬 수준.
  • 뷰 2(노멀): 마루·골에서 노멀이 기울고 평평한 곳은 위를 봄. 와이어프레임으로 마루가 뾰족하고 꼬이지 않음(steepness = 1 로 올려 최악의 경우도 확인).
  • --ocean-time 고정 + --cam-orbit: 뷰 17 에서 바다가 검정(카메라 속도와 일치). 고정을 풀면 뷰 16 에서 바다 속도가 바람 방향으로 부드럽게 이어지고 프레임마다 튀지 않음.
  • TAA·모션 블러 켜고 재생: 파도 위 번짐·고스팅 없음. 재생 시작/정지 직후 한 프레임 튐 없음(리셋 경로).
  • 배 자리 상자의 그림자가 바다 위에 떨어짐. 바다는 그림자를 만들지 않음(뷰 4).
  • 회귀: Ocean 이 없는 기존 테스트 씬(최소 MotionBlur, TaaEdges, ManyLights64) 스크린샷이 변경 전과 같고, 드로우 수가 같음.
  • 에디터: Ocean 추가·값 변경·되돌리기·씬 저장 후 다시 불러오기에서 값이 유지됨. --add-component=Ocean 동작.

1단계 위험

  • 노멀 부호가 틀리면 조명이 뒤집혀 "어두운 마루"가 됩니다. 수식 확인 스크립트를 먼저 하는 이유입니다.
  • b9 를 Layout_Object 에 붙이면 D3D12 루트 시그니처가 커집니다. 루트 파라미터 한도·ValidateBindings 대조를 첫날 확인합니다(7장).
  • 에디터 피킹이 변위 전 평면으로 맞춰지는 정도의 차이는 무시합니다(진폭 0.25 m).

2단계 — 수평선까지 RHI 확장 없음

2단계 작업 순서

  • Mesh::CreatePlane 에 간격 증가 인자 g(기본 0)를 추가하고, MeshSource 평면의 params[2] 로 저장·복원. 씬 JSON 에 이 값이 들어가는지와 g = 0 일 때 결과가 완전히 같은지 확인(7장).
  • 에디터에서 평면을 만들 때(또는 메시 출처 편집이 있으면 그곳) g 를 고칠 수 있게 할지 확인. 없으면 씬 JSON 으로만 넣어도 됩니다.
  • Ocean 에 fadeStart·fadeEnd, Ocean.hlsli 에 감쇠(진폭과 경사에 같이 곱함, smoothstep).
  • 테스트 씬을 키운 OceanHorizon.json: 평면 10 km × 10 km, 512×512, g 는 3.6 목표에 맞춰 정함, 카메라 far 5000 m.

2단계 검증

  • 갑판 높이 카메라에서 수평선 쪽 스크린샷: 바다 끝과 하늘 사이 틈이 2 픽셀 이하이고 대비가 낮음.
  • 먼 바다에 계단·물결무늬(모아레) 없음. 감쇠 구간에서 파도가 서서히 잦아듦.
  • GPU 프로파일러로 G-buffer 패스 시간을 바다 있음/없음으로 기록(1080p). 바다 몫이 0.5 ms 를 넘으면 정점 수부터 줄입니다.
  • 1단계 검증 항목을 OceanHorizon.json 으로 다시 한 번(특히 뷰 17, TAA).

3단계 — 픽셀 단위 노멀 선택

2단계 화면에서 먼 바다나 해 하이라이트가 프레임마다 반짝이면 합니다. 정점 노멀은 격자 간격보다 촘촘한 굴곡을 담지 못하고, 성긴 격자에서는 삼각형 단위로 꺾입니다. 픽셀 셰이더가 원래 xz(VS 출력에 추가)로 GerstnerSample 을 다시 불러 노멀을 구하면 격자 밀도와 무관한 매끈한 노멀이 나옵니다. 파도 8개라 비용은 작습니다.

  • OceanPixelShader.hlsl(BasicPS 와 같은 셰이딩, 노멀만 교체), OceanGBufferPixelShader.hlsl(GBufferPS 와 같음, 노멀만 교체). 중복을 줄이려면 두 PS 의 노멀 입력을 함수로 빼는 정도만 합니다.
  • PS 가 b9 를 읽어야 하므로 b9 의 셰이더 단계를 VS|PS 로 넓힙니다(PS 쪽 b9 도 비어 있음).
  • 먼 거리에서 노멀이 감쇠로 평평해지는 것은 그대로 둡니다(앨리어싱 방지).

7. 미확인 사항 (구현 첫날 확인)

  1. D3D12 루트 시그니처. Layout_Object 에 CBV 를 하나 더 붙였을 때 루트 파라미터 수·크기 한도 안인지, ValidateBindings 가 새 슬롯을 받아들이는지.
  2. 평면 직렬화. SceneSerializer 가 평면의 params 를 몇 개까지 쓰고 읽는지. params[2] 가 저장되지 않으면 키를 하나 추가합니다(없으면 0 → 기존 씬 그대로).
  3. 에디터 평면 생성 UI. 평면 크기·분할 수를 에디터에서 고칠 수 있는지(Editor.cpp 의 메시 출처 표시 근처). 없으면 1·2단계 테스트 씬은 JSON 으로 만듭니다.
  4. 안개. 엔진에 거리 안개가 있는지. 있으면 수평선 이음매를 안개로 덮을 수 있고, 없으면 3.6 의 far·크기 조정으로 갑니다.
  5. 설정 구조체 위치. RenderSettings 의 정확한 파일과 ssaoOverride 같은 기존 오버라이드가 읽히는 순서.
  6. 미리보기 뷰. 카메라 미리보기가 같은 b9 를 쓰는 데 문제가 없는지(시간이 같으므로 문제없을 것으로 봄).
  7. SSAO. 바다 위 넓은 평면에서 SSAO 가 배 근처를 지나치게 어둡게 만들지 않는지 눈으로 확인.
