클립 전환(SetClip)과 루트 모션

2026-11-13 · Animator 가 클립 하나만 재생하는 지금 구조를, 런타임 클립 전환 → 크로스페이드 → 루트 모션 순서로 넓히는 구현 계획입니다. 이 문서를 쓴 시점에는 이 계획의 코드를 한 줄도 쓰지 않았습니다. (선행 작업인 스킨 계층 순서 계산만 이미 끝났습니다. 아래 0단계.)

결론: 순서는 FindAnimation → Start 분리 → SetClip → 크로스페이드 → 루트 모션입니다. 가장 먼저 부딪힐 문제는 두 가지입니다. (1) Animator 가 모델 루트가 아니라 메시 오브젝트마다 하나씩 붙어 있어서(MasterChief 는 4개), 루트 모션을 그대로 넣으면 이동량이 4배가 됩니다. (2) mixamo 클립 이름이 전부 Armature|mixamo.com|Layer0 로 같아서, 파일이 여러 개면 이름으로 클립을 고를 수 없습니다.

기준: 커밋 985fed6 (브랜치 refactor/skin-eval-order). 경로는 SherlockEngine/ 기준이고 행 번호는 이 시점의 참고용입니다. Transform 클래스의 API 와 Behaviour 업데이트 순서는 읽지 않았으므로 해당 부분은 구현할 때 확인합니다.

1. 현재 구조 (코드로 확인한 사실)

항목지금위치
재생 클립const AnimationClip* m_clip 하나. 클립 데이터는 Model::animations 에 있고 Animator 는 비소유 포인터만 가짐Scene/Animator.cpp
클립 선택직렬화되는 clip 이름 문자열. Start 에서 model->animations 를 선형 탐색, 빈 문자열이면 첫 클립, 못 찾으면 m_clip = nullptr 로 멈춤Animator::Start
Start 가 하는 일모델 바인딩(스킨 탐색, m_rest·m_global·m_meshRest)과 클립 바인딩(단일 노드 모드 검증, m_base)을 한 함수에서 함Animator::Start
포즈 계산m_current = m_rest 로 기본 포즈를 깔고 채널이 덮은 노드만 갱신 → evalOrder 순으로 노드 월드 → 팔레트Animator::UpdateSkin
배치와 포즈스킨 모드는 Transform 을 건드리지 않고 팔레트만 올림. 배치(이동·회전·스케일)는 모델 루트 오브젝트의 TransformScene::AddModel
Animator 개수메시 오브젝트(01.Arms·02.Chest·03.Helmet·04.Legs)마다 하나. 모델 루트 오브젝트의 자식들임. 같은 클립을 4번 계산함MasterChiefWalk.json
루트 본 정보ModelSkin::rootJoints, jointParent, evalOrder 가 임포트 때 만들어짐 (아직 쓰는 곳 없음)Graphics/Model.h

2. SetClip 설계

2-1. Model::FindAnimation (선형 탐색)

  • int FindAnimation(const std::string& name) const. 못 찾으면 -1. 클립이 수 개~수십 개라 선형 탐색으로 충분하고, 해시 맵은 animations 와 어긋날 수 있는 상태를 하나 더 만듭니다. 호출부는 FindAnimation 만 쓰므로 나중에 내부만 맵으로 바꿀 수 있습니다.
  • "빈 이름이면 첫 클립" 규칙은 Model 이 아니라 호출부(Animator)에 둡니다.

2-2. Start 분리

함수하는 일언제
BindModel()메시 소스 → Model, 스킨 탐색, m_rest·m_global·m_meshRest 준비Start 에서 한 번
BindClip(const AnimationClip*)단일 노드 모드 검증(채널 노드가 하나이고 루트인지), m_clip·m_base 설정, m_time = 0, 스킨 모드면 m_current = m_restStart 와 SetClip
검증이 실패하면 이전 클립을 그대로 유지하고 false 를 돌려줍니다. 지금 Start 처럼 nullptr 로 만들면 전환 한 번 잘못에 캐릭터가 멈춥니다.

2-3. 공개 API

bool SetClip(const std::string& name);   // 내부에서 FindAnimation → SetClip(int)
bool SetClip(int index);                  // 상태 머신이 매 프레임 이름을 조회하지 않도록
int  GetClipCount() const;
const char* GetClipName(int index) const;
int  GetClipIndex() const;                // 지금 재생 중인 클립 (-1 = 없음)
  • 같은 클립을 다시 요청하면 무시할지 처음부터 다시 틀지는 6장에서 정합니다. 권장은 무시입니다(걷기 중 걷기 입력이 들어와도 튀지 않도록).
  • m_model 이 없으면(Start 실패) 경고만 남기고 false.

2-4. 직렬화 필드 clip 의 의미

  • 씬 파일에는 시작 클립 이름만 저장되게 두고, SetClip 은 clip 문자열을 덮지 않습니다. 런타임 상태는 m_clip 에만 둡니다. 플레이 중 전환한 결과가 씬에 저장되는 사고를 막습니다.

3. 크로스페이드

  • 즉시 전환이 먼저 동작한 뒤에 붙입니다. SetClip(index, blendSeconds = 0) 로 시간을 받고, 0 이면 즉시 전환입니다.
  • 방식: 전환하는 순간 마지막 포즈(m_current 의 TRS)를 스냅샷으로 저장하고, 새 클립을 샘플링한 포즈와 blendSeconds 동안 노드 TRS 단위로 섞습니다. 이동·스케일은 lerp, 회전은 slerp(부호가 반대면 한쪽을 뒤집어 짧은 쪽으로).
  • 스냅샷 방식은 이전 클립을 계속 샘플링하지 않으므로 구현이 가장 작습니다. 이전 클립이 전환 중에도 계속 움직여야 하는 요구가 생기면 두 클립을 동시에 샘플링하는 방식으로 바꿉니다.
  • 섞는 위치는 m_current 가 채워진 직후, evalOrder 순회 이전입니다. 팔레트 계산 코드는 바뀌지 않습니다.
  • 스냅샷은 TRS 만 있으면 됩니다. 지금 ModelNode 는 std::string name 을 갖고 있어 복사가 무겁습니다. 전환 순간에만 복사하므로 지금은 감수하고, 프레임마다 복사하는 m_current = m_rest 와 함께 TRS 전용 구조로 줄이는 것은 별도 최적화로 뺍니다.

4. 루트 모션

루트 모션은 클립 안의 루트 본 이동을 포즈에서 빼서 오브젝트 Transform 의 이동으로 옮기는 것입니다. 지금은 루트 본 이동이 팔레트에 그대로 들어가 메시가 오브젝트 기준으로 움직이고, 루프 경계에서 제자리로 튑니다.

4-1. 먼저 해결할 구조 문제: 누가 Transform 을 움직이나

  • MasterChief 는 모델 루트 아래 메시 오브젝트 4개에 Animator 가 각각 있습니다. 모두 루트 모션을 적용하면 이동량이 4배가 되고, 적용 대상도 메시 오브젝트 자신의 Transform 이 아니라 모델 루트의 Transform 이어야 합니다.
  • 1안 (권장, 작음): Animator 에 rootMotion bool 을 Reflect 로 추가하고, 모델 루트당 하나의 Animator 에만 켭니다. 켜진 Animator 는 자기 부모(모델 루트)의 Transform 에 delta 를 더합니다. 다른 Animator 는 포즈에서 루트 이동 성분만 뺍니다(메시가 서로 어긋나지 않도록 모든 Animator 가 같은 규칙으로 성분을 제거해야 합니다).
  • 2안 (큼): 모델 루트에 포즈 계산을 하는 컴포넌트를 하나만 두고, 메시 오브젝트는 팔레트만 받습니다. 4번 중복 계산도 함께 사라지지만 Scene::AddModel, 씬 직렬화, 에디터 표시를 모두 건드립니다. 이번 범위에서는 제외하고 후속 과제로 둡니다.

4-2. 루트 본 이동의 추출

  • 루트 본 = ModelSkin::rootJoints[0] 의 노드(joints[j]). 이 모델은 루트 본 1개(Hips 계열)입니다. 루트 본이 여럿이면 첫 번째만 쓰고 경고합니다.
  • 그 노드의 Translation 채널을 시간 t 에서 샘플링한 값이 루트 본의 로컬 이동입니다. 클립에 그 채널이 없으면 루트 모션은 0 입니다.
  • 어느 축을 옮길지: 기본은 수평(X·Z)만 옮기고 높이(Y)는 포즈에 남깁니다. 걷기의 위아래 흔들림을 유지하기 위해서입니다. 점프 같은 클립에서 Y 도 옮기려면 축 마스크가 필요하므로 rootMotionAxes 는 후속으로 두고 첫 구현은 XZ 고정으로 합니다.
  • 포즈에서 제거: 노드 TRS 를 덮은 직후, 루트 본의 Translation X·Z 를 클립 첫 프레임 값으로 바꿉니다. 그러면 메시는 오브젝트 기준 제자리에서 걷습니다.

4-3. delta 계산과 적용

단계내용
1. 이전 값 저장프레임마다 이전 루트 이동(m_prevRoot)을 보관. SetClip 과 Start 에서 첫 프레임 값으로 초기화
2. 로컬 deltadelta = root(t) - m_prevRoot (XZ)
3. 루프 경계시간이 duration 을 넘어 되감기면 delta = (root(duration) - m_prevRoot) + (root(0) - root(0))… 가 아니라, 끝까지 간 양과 처음부터 간 양을 따로 더합니다: (root(duration) - prev) + (root(t) - root(0)). 그렇지 않으면 한 프레임에 한 걸음 거꾸로 순간이동함
4. 공간 변환로컬 delta 를 루트 본의 부모 노드 월드(m_global[부모])로 메시 공간에 옮기고, 모델 루트 Transform 의 회전·스케일을 곱해 월드 이동량으로 만듦
5. 적용모델 루트 Transform 의 위치에 더함 (Transform 의 API 는 구현 때 확인)
6. 비반복 클립loop = false 에서 끝에 도달한 뒤에는 delta 0
  • 좌표계는 이미 엔진 좌표계(flipZ 반영)로 변환된 값입니다. Animator 는 임포트 때 쓴 루트 스케일(options.scale)을 1 로 가정하므로(기존 주석), 루트 모션도 같은 가정을 씁니다.
  • 이동 적용은 Update 안이므로, 스크립트가 같은 프레임에 같은 Transform 을 쓰면 실행 순서에 따라 덮일 수 있습니다. Behaviour 업데이트 순서를 읽고 정합니다.
  • 편집 모드에서는 루트 모션이 씬의 Transform 을 바꾸지 않아야 하고, 플레이 중 바뀐 값이 씬에 저장되지 않아야 합니다. 현재 플레이/정지 시 씬 복원 방식을 확인한 뒤 같은 경로를 따릅니다.

4-4. 회전(요) 루트 모션

  • 루트 본의 회전은 첫 구현에서 제외합니다. 이동만으로 "걸어서 앞으로 간다"가 해결되고, 회전 루트 모션이 필요한 클립(제자리 회전 등)이 생기면 같은 구조로 요(Y 회전) delta 를 추가합니다.

5. 구현 순서

각 단계는 따로 커밋하고, 앞 단계가 검증된 뒤에 다음으로 갑니다. 1~3단계의 SetClip 관련 부분은 사용자가 직접 구현합니다.

단계내용파일검증
1Model::FindAnimation 추가, Start 가 사용 (동작 불변)Model.h, Animator.cpp기존 씬 로그가 이전과 같음 (MasterChiefWalk, ArmBone, BoxAnimation)

8(후속) 회전 루트 모션, 축 마스크, 2안(모델 루트에 포즈 계산 컴포넌트 하나)—별도 계획

검증 방법

  • 빌드: SherlockEngine.sln 을 /p:Configuration=Debug /p:Platform=x64 로 통째로 빌드. 실행은 SherlockGame.exe --project=<.sherlock> --scene=Assets/Scenes/MasterChiefWalk.json --exit-after=120 의 로그로 확인합니다. 애니메이션은 실시간 dt 로 움직이므로 스크린샷 비교는 매번 달라서 로그와 수치 비교가 낫습니다.
  • 동작이 변하지 않아야 하는 1·2단계는 0단계처럼 임시 비교 코드(옛 경로와 새 경로의 팔레트·포즈 최대 차이를 로그로)를 넣었다 확인 후 지우는 방식이 가장 확실합니다.
  • 검증용 스크립트(예: 키 입력으로 SetClip 호출)는 Sample 프로젝트가 아니라 별도 실험 프로젝트(Projects/SherlockTestScenes 등)에 둡니다.
  • 루트 모션 검증에는 루트 이동이 들어 있는 클립이 필요합니다. 지금 MasterChief walk 가 "In Place" 인지 아닌지부터 확인해야 합니다. 루트 이동이 없다면 mixamo 에서 "In Place" 를 끈 클립을 받아 임포트합니다.

6. 먼저 정할 것

#질문권장이유
1클립을 여러 개 쓰려면 어떻게 모으나한 Model 안에 클립이 모두 있는 경우만 먼저 지원클립의 channel.node 는 그 파일의 노드 번호이므로, 다른 파일의 클립은 노드 번호가 달라서 그대로는 못 씀. 이름으로 리타겟하거나 클립을 병합하는 일은 별도의 큰 작업
2mixamo 클립 이름이 전부 같음 (Armature|mixamo.com|Layer0)임포트 때 파일 이름 등으로 이름을 바꾸거나, 이름 대신 인덱스로 선택이름 탐색은 첫 번째 것만 돌려주므로 두 번째 이후 클립을 고를 수 없음. 파일이 여러 개일 때 반드시 부딪힘
3같은 클립 재요청무시걷기 입력이 계속 들어와도 처음부터 다시 틀지 않도록
4clip 직렬화 값을 SetClip 이 덮을지덮지 않음 (시작 클립)플레이 중 전환이 씬에 저장되는 사고 방지
5크로스페이드 기본 시간0.2초걷기↔뛰기 정도에서 자연스러운 값. 호출마다 지정 가능하게 함
6루트 모션을 누가 적용하나모델 루트당 Animator 하나에 rootMotion 켬 (1안)2안은 AddModel·직렬화·에디터를 건드려서 범위가 큼
7루트 모션 축XZ 고정걷기 위아래 흔들림 유지. Y 는 후속

7. 위험과 제외

위험
  • 이동량 4배: 4장의 구조 문제. 7단계 검증에 "여러 Animator 가 있어도 이동량이 한 번만 적용됨"을 반드시 넣습니다.
  • 메시끼리 어긋남: 일부 Animator 만 루트 이동을 빼면 메시들이 서로 다른 위치에 그려집니다. 포즈에서의 제거는 모든 Animator 가 같은 규칙으로 해야 합니다.
  • 스크립트와의 충돌: 같은 프레임에 스크립트가 Transform 을 쓰면 루트 모션이 덮이거나 덮습니다. Behaviour 업데이트 순서 확인 필요(읽지 않음).
  • 회귀: 2단계의 Start 분리가 가장 회귀 위험이 큽니다. 동작 불변 리팩터링으로 따로 커밋해 두면 문제가 생겼을 때 원인을 나누기 쉽습니다.
이 계획에서 제외한 것: 상태 머신·블렌드 트리, 레이어/마스크 블렌딩, 클립 간 리타겟, 모프 타깃(Weights) 애니메이션, 루트 회전 루트 모션, 모델 루트에 포즈 계산 컴포넌트를 하나만 두는 구조 변경(4-1의 2안), 프레임마다의 m_current = m_rest 복사 최적화(TRS 전용 구조).

이 계획은 코드를 읽고 쓴 것이며, 위의 "읽지 않음" 항목 외에도 실제 구현에서 달라질 수 있습니다. 구현이 끝나면 별도 구현 기록 문서(*-record.html)로 남깁니다.
