GPU 클러스터 비닝 구현 기록 — 컴퓨트 셰이더 다섯 개, 타일 → 상자 2단계

2026-11-21 · 디퍼드 기록 2.7절의 CPU 비닝(Renderer::BuildClusters)을 컴퓨트 셰이더로 옮긴 기록입니다. 로드맵 4단계의 선택 항목 "클러스터 비닝 컴퓨트 이식"에 해당합니다. 처음 계획은 상자마다 조명을 직접 검사하는 1단계였는데, 같은 작업에서 화면 타일로 먼저 거르는 2단계 비닝까지 넣었습니다.

CPU, GPU 1단계, GPU 2단계 세 경로를 씬별로 잰 결과는 별도 문서 GPU 클러스터 비닝 측정에 있습니다. 이 문서는 설계, 코드, 화면 검증을 다룹니다.

기준: 커밋 1c763bf + 작업 트리(2026-11-21, 아직 커밋하지 않음). 코드 위치는 "파일 + 함수/타입 이름"으로 적었고, 경로는 SherlockEngine/ 프로젝트 폴더 기준입니다. 숫자는 이 문서를 쓰면서 Release 빌드, D3D11, RTX 3070 Ti 한 대에서 실행해 얻은 값입니다.

1. 요약

클러스터 비닝이 이제 기본으로 GPU에서 돕니다 (RenderSettings::clusterGpu = true). 결과 형식은 CPU 경로와 같습니다. t30에는 상자마다 (시작, 개수)가, t31에는 조명 번호가 들어가고, 상자 안 번호는 오름차순입니다. 그래서 셰이더 쪽 조회 코드(Shading.hlsli 의 ShadeClusteredLights)는 고치지 않았습니다.

세 경로(CPU, GPU 1단계, GPU 2단계)의 화면은 클러스터 없이 전체 조명을 도는 기준 화면과 0 px 차이입니다. 확인한 범위는 테스트 씬 6개, 포워드 경로, 직교 카메라 미리보기, D3D12, Intel Sponza 촛불 1만 개 씬 4개 시점입니다 (9장). D3D12 GPU 기반 검증에서도 메시지가 없었습니다.

항목값
CPU 비닝 시간 (촛불 씬, 2층 회랑 시점)약 15 ms → 0.01 ms (CPU에는 입력 업로드만 남음)
GPU 비닝 시간 (같은 시점)2단계 약 1.1 ms, 1단계 약 3.6~4.9 ms. 첫 2단계 구현(타일 목록)은 2.85 ms였음 (5장). 촛불 씬 다른 시점은 2단계 1.0~1.9 ms
프레임 전체촛불 씬은 GPU가 병목이라 2단계도 프레임이 비슷하거나(3개 시점) 약 3 ms 늘어남. CPU 비닝은 GPU 작업과 겹쳐 돌았기 때문 (측정 문서)
되돌리기--cluster-gpu=0 은 CPU 비닝, --cluster-tiles=0 은 GPU 1단계. Render Settings 의 "GPU clustering"·"Tile pre-pass" 체크박스로도 바꿀 수 있음

2. 계획과 달라진 점

작업 전 계획(대화로 정한 7단계)과 실제 구현을 나란히 적습니다.

계획구현이유
CPU가 "화면에 보이는 지역광 번호"를 따로 올림CullLights 가 이미 만든 m_lightBounds(조명마다 월드 경계 구, t15와 같은 번호)를 그대로 t7에 올림번호를 다시 매기면 t15 번호로 되돌리는 표가 하나 더 필요함. 방향광은 w < 0, 빛 없음은 w = 0이라 셰이더가 건너뜀
상자 하나를 그룹 하나가 맡고, 조명 64개씩 groupshared 누적합으로 자리를 정함상자 하나를 스레드 하나가 맡아 조명을 번호 순으로 차례로 돎반복 횟수가 버퍼 값인 루프 안에 그룹 동기화를 두면 fxc(SM 5.0)가 X3663 오류를 냄. 원자 연산 없이 오름차순을 지키는 가장 단순한 방법
커널 3개 (Count, Scan, Fill)커널 5개 (View, Tile, Count, Scan, Fill)View는 경계 구를 뷰 공간으로 한 번만 옮겨 둠. Tile은 2단계 비닝의 1단계
2단계 비닝은 "나중에 최적화할 거리"같은 작업에서 구현. 비교용으로 1단계도 남김 (--cluster-tiles=0)사용자 요청. 촛불 씬에서 Count+Fill이 3.6 ms → 1.0 ms
미리보기 카메라는 메인 라이팅 뒤에 같은 버퍼로 다시 디스패치계획대로. 미리보기 장면 패스 직전에 DispatchClusterBinning(cmd, 1)—
버퍼 리드백을 두 백엔드에 추가Device::ReadStagingBuffer 와 4칸 리드백 링 (6장)처음에는 kFrameCount(2)칸이었음. 통계가 이상해서(2단계 쌍 수가 1단계보다 많음) 4칸으로 늘리고 읽지 못한 칸은 건너뛰게 함

4. 커널 다섯 개

공통 헤더 Shaders/ClusterBin.hlsli

상자 계산과 겹침 검사는 CPU 코드와 같은 식으로 옮겼습니다. BinToViewX/Y 는 BuildClusters 의 toViewX/Y, BinClusterBox 는 상자 AABB, BinSphereIntersectsBox 는 SphereIntersectsBox 와 같습니다. 슬라이스 경계 z는 셰이더가 pow 로 다시 계산하지 않습니다. CPU가 std::pow 로 구한 값 25개를 b13으로 받아, 두 경로의 상자가 비트 단위로 같습니다. Count와 Fill은 같은 함수 BinWalkCluster 를 부릅니다. 개수를 셀 때와 채울 때 검사가 다르면 채운 칸 수가 개수와 어긋나기 때문입니다.

순서 불변식 — 왜 상자마다 스레드 하나인가

CPU 경로는 조명을 번호 순으로 돌며 상자에 넣으므로 상자 안 목록이 오름차순입니다. 셰이더는 그 순서대로 조명 기여를 더하고, 전체 순회도 같은 순서로 더합니다. 덕분에 클러스터를 켜든 끄든 결과가 비트 단위로 같습니다 (디퍼드 기록 2.4절). 조명마다 스레드를 두고 원자 연산으로 상자에 추가하면 실행할 때마다 순서가 바뀌어 이 성질이 깨집니다. 그래서 스레드 하나가 상자 하나를 맡아 번호 순으로 차례로 돌게 했습니다. 2단계에서는 타일 마스크를 낮은 비트부터 읽으므로 이 순서가 그대로 지켜집니다.

// ClusterBin.hlsli — BinWalkCluster 의 2단계 부분
for (uint w = 0; w < BinWordCount(); ++w)
{
    uint bits = binTileMasks[base + w];
    while (bits != 0)
    {
        const uint light = w * 32 + firstbitlow(bits);   // 낮은 비트부터 = 번호 순
        bits &= bits - 1;
        if (!BinSphereIntersectsBox(binViewBounds[light].xyz, binViewBounds[light].w, mn, mx)) continue;
        if (write) binClusterLights[start + n] = light;
        ++n;
    }
}

5. 2단계 비닝 — 타일로 먼저 거르기

1단계 비닝은 상자 3,456개가 모두 조명 N개 전체를 검사합니다 (검사 3,456 × N번). 2단계 비닝에서는 먼저 화면 타일 144개(16 × 9)마다 타일 절두체와 겹치는 조명만 고르고, 상자는 자기 타일에 고른 조명만 검사합니다. 같은 타일의 상자 24개(깊이 슬라이스)가 같은 후보를 함께 씁니다.

타일 검사

  • 원근: 타일 절두체를 눈을 지나는 옆면 평면 4개로 표현합니다. 왼쪽 면은 x_ndc ≥ nx0 ⇔ P11·x + (P31 − nx0)·z ≥ 0 입니다. 평면을 정규화해 두고, 구 중심의 부호 거리가 네 면 모두에서 −r 이상이면 겹친다고 봅니다. 모서리 바깥을 지나는 구도 통과하는 보수적인 검사입니다.
  • 직교: 옆면이 축에 평행하므로 뷰 공간 x·y 구간과 비교합니다.
  • 깊이: 구가 [near, far] 밖에 있으면 버립니다.
  • 타일 AABB로 검사하지 않은 이유: 타일 하나의 AABB는 near~far 전체를 감싸서 화면의 절반 가까이를 덮습니다. 그래서 거의 걸러 내지 못합니다.

CPU 경로의 타일 범위는 경계 구를 감싼 상자의 꼭짓점 8개를 투영한 NDC 사각형으로 구합니다. 그래서 GPU 2단계의 (상자, 조명) 쌍 수가 CPU보다 조금 적습니다 (ManyLights64: 16,313 대 16,883). 두 방법 모두 보수적이고, 더 걸러진 쌍은 그 상자에 빛이 0인 조명입니다. 따라서 화면은 같습니다.

처음 구현: 타일 목록 (버림)

처음에는 스레드 하나가 타일 하나를 맡아 조명 전체를 돌며 번호 목록을 만들었습니다. 타일 t의 목록은 u2[t · 용량 …] 고정 구간이었습니다. 목록이 오름차순으로 쌓이고 누적합도 필요 없지만, 스레드가 144개뿐입니다. 촛불 1만 개 씬에서는 스레드 하나가 1만 번을 차례로 돌아 이 단계만 1.63 ms였습니다. 비닝 전체 2.85 ms 중 절반이 넘습니다.

지금 구현: 타일 비트마스크

스레드 하나가 (타일, 조명 32개) 하나를 맡습니다. 32개를 검사해 워드 하나를 만들고 u2[타일 · stride + 워드] 에 통째로 씁니다. 원자 연산도 그룹 동기화도 필요 없고, 비트 위치가 곧 조명 번호라 순서 정보가 남습니다. 스레드 수는 144 × ⌈N/32⌉로, 1만 개면 약 4.5만 개입니다. 버퍼도 144 × 용량 × 4 바이트에서 그 32분의 1로 줄었습니다.

6. 통계 리드백

GPU 비닝에서도 Render Settings 의 통계 줄과 자동 검증의 "렌더 통계" 로그(clusterRefs, clusterMax, overflow, tileRefs, tileMax)가 계속 나오게 하려면 GPU 값을 CPU로 읽어야 합니다. 그래서 RHI에 버퍼 리드백을 추가했습니다.

  • Device::ReadStagingBuffer(buffer, out, size) (RHI/Device.h): Staging 버퍼를 기다리지 않고 읽습니다.
    • D3D11 (D3D11Device::ReadStagingBuffer): Map(D3D11_MAP_READ, D3D11_MAP_FLAG_DO_NOT_WAIT) 로 엽니다. GPU가 아직 복사 중이면 DXGI_ERROR_WAS_STILL_DRAWING 이 나오고 false를 돌려줍니다.
    • D3D12 (D3D12Device::ReadStagingBuffer): 리드백 힙을 Map 해서 복사합니다. 완료를 확인하지 않으므로, 호출하는 쪽이 kFrameCount 프레임 지난 복사만 읽어야 합니다. 그만큼 지난 프레임은 BeginFrame 이 펜스로 이미 기다렸습니다.
  • 4칸 링 (Renderer::ReadGpuClusterStats, DispatchClusterBinning): 메인 뷰 디스패치마다 통계를 다음 칸에 복사합니다. 읽을 때는 가장 오래된 칸부터 읽을 수 있는 만큼 읽고, 가장 최근 값을 씁니다. 아직 읽지 못한 칸은 덮어쓰지 않고 그 프레임의 복사를 건너뜁니다.

처음 2칸 링에서 본 것. 처음에는 GetFrameIndex() % kFrameCount 칸에 복사하고, 같은 칸을 복사하기 직전에 읽었습니다. 이때 ManyLights256 의 2단계 쌍 수가 77,320으로 나왔습니다. 1단계(77,258)보다 많아서 이상한 값입니다. 4칸 링으로 바꾸고 읽지 못한 칸은 건너뛰게 하자 75,141이 됐고, 그 뒤로는 여러 번 실행해도 같습니다.

원인은 추정입니다. D3D11 드라이버는 프레임을 2개 넘게 쌓아 둘 수 있습니다. 그러면 2프레임 전 복사가 아직 끝나지 않아 읽기가 실패하고, 그 칸에 새 복사를 덮어써서 읽기가 계속 밀렸을 수 있습니다. 그동안 처음 몇 프레임(씬 뷰가 1280×670으로 그려지던 때)의 값이 남아 있었다고 보면 숫자가 설명됩니다. 직접 확인하지는 않았습니다.

7. 렌더러 연결

  • 설정: RenderSettings::clusterGpu(기본 켬, --cluster-gpu=1|0)와 clusterGpuTiles(기본 켬, --cluster-tiles=1|0). 인자는 App/AppBase.cpp, 체크박스는 Editor/DebugUI.cpp 의 Render Settings 에 있습니다. 통계 줄은 "cluster refs … GPU"와 "GPU binning: tile refs … (max … per tile)"을 보여 줍니다.
  • 대체 경로: PrepareGpuClusters 는 설정이 꺼졌거나, 컴퓨트 파이프라인 5개 중 하나라도 없거나, 버퍼 생성에 실패하면 false를 돌려줍니다. 그러면 그 프레임은 CPU 비닝으로 돕니다. 생성 실패는 m_clusterGpuFailed 로 기억해 다시 시도하지 않습니다.
  • 디스패치 위치: 메인 뷰는 프레임 셋을 꽂기 전, 렌더 패스 밖에서 "ClusterBin" 구간으로 돌립니다. D3D11 백엔드는 버퍼를 UnorderedAccess 로 바꿀 때 그 버퍼의 SRV 바인딩을 풀기 때문에, 셋을 꽂기 전에 끝내야 합니다. 미리보기는 미리보기 장면 패스 직전에 "PreviewClusterBin" 으로 같은 버퍼에 다시 비닝합니다. 메인 패스의 그리기는 명령 순서상 이미 앞에 있고, 배리어가 그 순서를 지킵니다.
  • 측정 도구:
    • 단계마다 GPU 구간(BinView, BinTile, BinCount, BinScan, BinFill)을 메인 뷰에만 남깁니다.
    • 그만큼 슬롯이 더 필요해서 RHI/GraphicsConfig.h 의 kMaxTimestamps 를 32 → 64로 올렸습니다. D3D11·D3D12 모두 쿼리 힙과 리드백 크기를 이 상수로 정합니다.
    • 자동 검증에 --avg-frames=N 을 추가했습니다 (Editor/EditorAutomation.cpp). 종료 직전 N 프레임의 구간 시간 평균을 "구간 평균 ms" 줄로 남깁니다.
    • 종료 로그의 "렌더 통계"에 clusterGpu, tileRefs, tileMax 가 추가됐습니다.

8. 설계 결정·함정

  • 누적합의 삼항 연산자. t >= offset ? gsScan[t − offset] : 0 은 양쪽을 모두 계산합니다. 그래서 t < offset 인 스레드가 groupshared 를 범위 밖으로 읽습니다 (D3D11에서 정의되지 않은 동작). if 로 막았습니다.
  • X3663. fxc SM 5.0은 반복 횟수가 UAV 값인 루프 안의 GroupMemoryBarrierWithGroupSync 를 거부합니다. 누적합은 반복 횟수가 상수(10번, [unroll])라 문제없습니다. 상자 루프에는 그룹 동기화를 두지 않았습니다.
  • 슬라이스 경계를 CB로. GPU pow 와 CPU std::pow 는 마지막 비트가 다를 수 있습니다. 상자 경계가 어긋나면 쌍 수 비교가 흐려지므로 CPU 값을 그대로 넘깁니다.
  • 1 px 깜박임 (비닝과 무관). 처음 ManyLights64 비교에서 GPU 경로만 1 px(최대 7단계)이 달라 보였습니다. GPU 목록을 CPU 목록과 전부 대조했고(빠진 쌍 570개는 모두 타일 평면이 더 거른 것, 남는 쌍 0개), 정렬과 누적합도 확인했습니다. 원인은 그쪽이 아니었습니다. 클러스터 없는 전체 순회를 여러 번 찍어도 같은 픽셀이 실행마다 바뀌었습니다. 그래서 지금 검증은 기준 화면을 2~6번 찍고, 기준끼리도 다른 픽셀은 제외합니다 (9장). 이 깜박임의 원인은 찾지 못했습니다.
  • D3D12 Dynamic 버퍼. 프레임마다 써야 바인딩됩니다. 조명이 0개여도 t7에 한 칸을 올립니다 (UploadLightBounds).
  • 전역 치환 사고. 코드에서 t32 를 t7 로 한꺼번에 바꾸다가 uint32_t 가 uint7_t 로 바뀐 일이 있었습니다. 되돌린 뒤 diff로 의도한 줄만 바뀌었는지 확인했습니다. 슬롯 번호를 바꿀 때는 상수 이름으로 찾아야 합니다.

9. 검증

방법. 에디터 씬 뷰(1280×720 스크린숏의 씬 뷰 영역)를 비교했습니다. 기준은 클러스터 없이 조명 전체를 도는 화면(--clustered=0)이고, 2~6번 찍어 기준끼리도 다른 픽셀(위 깜박임)은 제외했습니다. 시험 화면이 기준 중 하나와 같으면 그 픽셀은 같다고 봅니다. 시험 경로는 CPU(--cluster-gpu=0), GPU 2단계(기본), GPU 1단계(--cluster-tiles=0) 세 가지입니다. 쌍 수는 종료 로그의 "렌더 통계"에서 읽었습니다.

확인하지 못한 것

  • 게임 exe 화면 비교. 시작 씬이 애니메이션이라 픽셀 비교가 어렵습니다. 대신 D3D11·D3D12 로 한 번씩 실행했고, GPU 비닝 버퍼가 만들어지고 오류 없이 끝나는 것만 확인했습니다. 시작 씬(MasterChiefWalk)에는 방향광뿐이라 지역광 비닝은 비어 있는 경우였습니다.
  • 실행 중에 체크박스를 켜고 끄는 경우 (프레임 셋 재생성 경로). 자동 검증은 시작할 때 정한 값으로만 돌았습니다.
  • 조명 용량이 바뀌어 용량에 묶인 버퍼를 다시 만드는 경로. 로그의 "GPU 클러스터 비닝 : 조명 용량" 줄이 실행마다 한 번뿐이었으므로, 테스트 씬에서는 처음 만들 때만 지나갔습니다.
  • 넘침이 실제로 생기는 경우 (모든 시점에서 0이었음)
  • 다른 GPU, Debug 셰이더에서의 시간

11. 남은 일

  • Count·Fill 병렬화. 지금은 상자마다 스레드 하나가 자기 타일 후보(촛불 씬에서 타일당 최대 1,763~4,268 개)를 차례로 돕니다. 이 두 단계가 촛불 씬에서 0.8~1.9 ms로, 비닝 시간의 대부분입니다. 타일 하나를 그룹 하나가 맡아 후보를 groupshared 에 올리고, 깊이 슬라이스 24개를 그룹 안 스레드가 나눠 맡는 방식을 생각해 볼 수 있습니다. 개수 세기와 채우기를 한 번에 하는 방법(상자마다 상한 칸을 미리 잡기)도 있습니다.
  • GPU 병목 씬. 촛불 씬은 그림자 패스(15~17 ms)가 병목이라 GPU 2단계 비닝으로도 프레임이 비슷하거나 약 3 ms 늘어납니다 (측정 문서). CPU가 병목인 씬에서만 이득입니다. 씬에 따라 자동으로 고르는 기능은 넣지 않았습니다.
  • 라이팅 시간 차이의 원인. D3D11의 조명 64·256개 씬에서 CPU 비닝일 때만 DeferredLight GPU 시간이 몇 배 깁니다. 목록은 거의 같고, D3D12에서는 차이가 없습니다. 측정 문서에 조사한 내용을 적었습니다 (측정 문서).
  • 1 px 깜박임의 원인 (비닝과 무관, 8장).
