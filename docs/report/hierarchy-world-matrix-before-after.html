월드 행렬 계층 순회 비포/애프터

2026-11-16 · Renderer::BuildDrawList 의 오브젝트 루프에서 월드 행렬을 구하는 방식을 "오브젝트마다 부모를 재귀로 올라가며 다시 계산" 에서 "루트에서 children 을 따라 내려가며 한 번씩만 계산" 으로 바꾸고, 같은 7,000개 규모 씬에서 시간과 결과 동일성을 확인한 기록입니다.

조건: Release 빌드, 같은 프로세스·같은 프레임 안에서 구 경로와 신 경로를 번갈아 실행해 비교(아래 2절). 7,000개 씬은 이 작업을 위해 만든 합성 씬이며 OL_TestScene 은 이 PC 에 없습니다. 아직 커밋하지 않았습니다.

1. 한눈에 보기

부모-자식 계층이 있는 7,000개 씬에서 루프가 약 18~28% 줄었고(0.82 → 0.59ms, 0.64 → 0.53ms), 결과는 비트 단위로 같았습니다. 계층이 없는 평평한 씬은 +0.02ms(약 +4%) 소폭 느려졌습니다.
범위: GameObject::GetWorldMatrix 함수 자체는 빨라지지 않았습니다(그대로 재귀). BuildDrawList 가 그 함수를 부르지 않도록 우회한 것이라, 오브젝트마다 GetWorldMatrix() 를 부르는 다른 곳(스켈레톤 디버그, 카메라 컴포넌트 등)은 그대로입니다.

같은 7,000개 씬을 변경 전·후 별도 바이너리로 재면(7절) 계층 씬에서 BuildDrawList 가 21~27%, CPU frame 이 11~13% 줄었습니다.

2. 무엇을 어떻게 바꿨나

Before — 오브젝트마다 부모 체인을 재귀로 올라감

for (const auto& objectPtr : scene.GetObjects())
{
    const GameObject& object = *objectPtr;
    ...
    const XMMATRIX world = object.GetWorldMatrix();   // local * parent->GetWorldMatrix() (재귀)
    ...
}

GameObject::GetWorldMatrix 는 호출마다 자기 GetLocalMatrix(S·R·T 곱)를 만들고, 부모가 있으면 부모의 GetWorldMatrix 를 다시 부릅니다. 캐시가 없어서 깊이 d 인 오브젝트는 로컬 행렬을 d+1 번 만듭니다. 형제가 많으면 같은 부모의 행렬을 형제 수만큼 다시 계산합니다.

After — 루트에서 children 을 따라 내려가며 부모 월드를 넘겨 줌

// 루트마다: 로컬 = 월드. 자식이 있으면 스택(m_hierarchyStack)에 올려 자식을 하나씩 방문
const XMMATRIX world = child.GetTransform().GetLocalMatrix() * XMLoadFloat4x4(&frame.world);
addObject(child, world);          // 기존 루프 본문을 그대로 람다로 옮긴 것
if (!child.GetChildren().empty()) // 자식이 있을 때만 이 월드를 저장해 스택에 올림
  • 오브젝트당 GetLocalMatrix 가 정확히 한 번이고, 곱셈 순서(local × parentWorld)는 GetWorldMatrix 와 같습니다.
  • 순서 보장 방법: Scene::m_objects 는 생성 순서라 부모가 자식보다 앞에 온다는 보장이 없습니다 (SetParent 는 아무 두 오브젝트 사이에서나 가능). 그래서 배열 순서에 기대지 않고 parent == nullptr 인 루트에서 children 을 따라 내려갑니다. 구조가 순서를 만들므로 별도의 불변식이나 재배열이 필요 없습니다.
  • 스택 칸 하나 = 자식이 있는 오브젝트와 그 월드 행렬, 다음에 방문할 자식 번호입니다. 깊이만큼만 쌓이고 매 프레임 재사용합니다. 루트 아래에 평평하게 7,000개가 있는 씬에서도 자식마다 행렬을 복사하지 않습니다.
  • 방문한 오브젝트 수가 씬의 오브젝트 수와 다르면(parent/children 불일치) 조용히 안 그려지는 오브젝트가 생기므로 한 번만 오류 로그를 냅니다.
  • 방문 순서는 바뀌지만 DrawItem 목록은 이어서 PSO → Material → Mesh → 인덱스 범위로 정렬하므로 그리는 결과에는 영향이 없어야 합니다 (정렬 키가 같은 인스턴스끼리의 상대 순서만 달라질 수 있음, 5절 참고).
  • 변경 파일: Renderer.cpp (BuildDrawList), Renderer.h (HierarchyFrame 와 m_hierarchyStack 멤버 추가). GameObject 는 건드리지 않았으므로 스크립트 DLL ABI 에 영향이 없습니다.

측정 방법

  • 임시 코드로 같은 프로세스 안에서 구 경로(예전 방식 그대로: 모든 오브젝트에 GetWorldMatrix() 를 불러 같은 본문 실행)와 신 경로를 번갈아 돌렸습니다. 홀수 프레임은 구 경로를 먼저, 짝수 프레임은 신 경로를 먼저 돌려 캐시가 데워진 상태의 유리함을 상쇄했습니다.
  • 프레임 30~129 의 100프레임에서 구간 시간을 모아 중앙값·평균·최소·최대를 냈고, 씬마다 3회 실행했습니다(D3D12 는 1회).
  • 구·신 두 경로가 DrawItem 본문을 같은 코드로 실행하므로 차이는 "월드 행렬을 구하는 방식과 순회" 에서만 납니다. 정렬은 두 경로가 같은 코드라 이 표에 넣지 않았습니다.
  • 이 임시 계측과 합성 씬 파일은 저장소에 넣지 않았고, 소스는 계측 코드를 뺀 상태(Release·Debug 모두 오류 없이 빌드)입니다.

4. 결과가 같은지 확인한 것

월드 행렬은 모든 검사에서 구 방식과 비트 단위로 같았고, 드로우 목록도 같았으며, 스크린샷 차이는 같은 바이너리를 여러 번 돌릴 때의 잡음과 구별되지 않았습니다.

4-1. 월드 행렬 비트 대조 (신 경로가 계산한 값 vs GetWorldMatrix())

신 경로가 오브젝트마다 구한 월드를 같은 순간 GetWorldMatrix() 결과와 memcmp 로 비교했습니다 (부동소수 부호 0 까지 구별). 아래 모두 불일치 0 입니다.

4-2. 드로우 목록 대조

같은 프레임에서 신 경로의 DrawItem 목록과 구 경로의 목록을 각각 (PSO, 재질, 메시, 인덱스 범위, 오브젝트의 월드·역행렬·경계 구)로 직렬화해 정렬한 뒤 통째로 비교했습니다. 위 모든 씬에서 항목 수와 내용이 같았습니다 (7,000 / 7,000, Sponza 103 / 103, MasterChiefWalk 16 / 16 등).

4-3. 스크린샷 대조 (Before 바이너리 vs After 바이너리)

5. 해석과 주의

  • 이득의 크기: 가장 큰 경우(계층 깊이 2)에서 0.23ms 입니다. 60fps 의 프레임 예산 16.7ms 에서 약 1.4% 이고 같은 규모의 평평한 씬은 거의 변화가 없습니다. 이번 변경으로 FPS 가 눈에 띄게 달라지지는 않습니다. 계층이 깊고 오브젝트가 많은 씬에서 CPU 시간이 깊이에 비례해 늘던 것이 사라졌다는 의미입니다.
  • 평평한 씬은 +0.02ms: 루트를 하나씩 돌며 스택 준비와 children 확인이 더해진 것으로 보이지만 원인을 따로 재지는 않았습니다 (추정). 3회 반복에서 방향이 같았습니다.
  • 루트 하나 아래에 평평한 경우(D)는 -18%: 부모(OL_Map 같은 루트)의 월드를 자식마다 재귀로 다시 만들던 것이 사라졌습니다. OL_TestScene 이 이 모양이지만 이 PC 에 없어서 같은 모양의 합성 씬으로 쟀습니다. 실제 씬의 절대값은 다를 수 있습니다.
  • 남은 비용: 로컬 행렬을 매 프레임 오브젝트마다 새로 만드는 일(약 20ns/오브젝트), 재질 GPU 캐시 확인 때의 문자열 5개 비교, DrawItem·ObjectData 쓰기, 범용 역행렬은 그대로입니다. 월드 행렬을 캐시(dirty 플래그)하면 더 줄일 수 있지만 무효화 누락 위험이 있어 이번에는 하지 않았습니다.
  • 정렬 키가 같은 인스턴스의 그리는 순서: 같은 PSO·재질·메시·범위를 쓰는 오브젝트들의 상대 순서는 예전에도 std::sort 가 보장하지 않았고 이번에 방문 순서가 바뀌어 달라질 수 있습니다. 서로 겹치는 같은 모양 오브젝트(z-fighting)에서만 화면에 보일 수 있습니다. 이번 비교 씬에서는 보이지 않았습니다.
  • 측정 과정에서 한 번 틀렸습니다: 처음에는 검증용 GetWorldMatrix() 호출을 신 경로 타이머 안에 넣어서 신 경로가 오히려 느리게 나왔습니다. 검증을 시간 재는 프레임에서 끄고 처음부터 다시 쟀고, 위 표는 그 재측정 값입니다.
  • Debug 빌드의 시간은 재지 않았습니다. Debug 는 STL·DirectXMath 가 느려서 비율이 다를 수 있습니다 (컴파일 확인만 했습니다).
  • 1~3절의 시간은 같은 프로세스 안의 번갈아 비교입니다. 별도 바이너리로 프레임 구간까지 잰 결과는 7절에 있습니다(스크린샷 비교에도 별도 바이너리를 썼습니다).

6. 재현 방법

  1. 합성 7,000개 씬: 큐브·구·실린더·평면 메시와 서로 다른 재질을 번갈아 쓰는 오브젝트를 격자로 배치한 씬 JSON 을 만듭니다. 계층 씬은 오브젝트 JSON 의 "parent" 에 objects 배열 인덱스를 적습니다 (C: 앞 인덱스가 부모인 5단 체인, E: 뒤 인덱스가 부모, D: 모두 첫 오브젝트 아래).
  2. SherlockEditor.exe --project=Projects\SherlockTestScenes\SherlockTestScenes.sherlock --scene=<씬.json> --backend=d3d11 --exit-after=140 을 Release 로 실행합니다. 로그에서 BENCH, VERIFY 줄을 읽습니다 (임시 계측 코드가 있는 빌드에서만 나옵니다).
  3. 재부모화 검증: --set-parent="O0;O6999" 를 같이 줍니다.
  4. 스크린샷: --exit-after=40 --screenshot=out.png 로 Before·After 바이너리를 각각 찍어 같은 위치 픽셀을 비교합니다 (노이즈 띠 제외).

7. 별도 바이너리로 프레임 구간까지 비교 (추가 측정)

1~3절은 같은 프로세스 안에서 구·신 경로를 번갈아 돌린 루프 구간의 비교였습니다. 아래는 GetWorldMatrix 를 거치는 변경 전 소스와 거치지 않는 변경 후 소스를 각각 따로 Release 로 빌드해서, 같은 7,000개 씬에서 프레임 전체의 CPU 구간을 잰 결과입니다.

  • Before = 변경 전 커밋 소스(Renderer.cpp·Renderer.h 를 HEAD 로 되돌림), After = 변경 후 소스. 두 바이너리에 똑같은 로그 코드(직전 프레임의 Profiler CPU 구간을 모아 중앙값을 냄)만 넣었고 다른 차이는 없습니다.
  • 씬마다 Before·After 를 번갈아 3회씩 실행(D3D11, --exit-after=140). 프레임 30~129 의 100프레임에서 구간별 중앙값을 구하고, 3회 실행의 평균을 적었습니다.
  • BuildDrawList 는 정렬을 포함합니다(0.04~0.18ms). Renderer::Render 는 그림자·메인 패스의 드로우 제출까지 포함하고, CPU frame 은 그 프레임의 최상위 CPU 구간 합(Update, GUI, 렌더, Present)입니다. GPU 시간은 재지 않았습니다.

  • 루프 비교와 맞는 점: 변경 전 C 의 BuildDrawList 1.02ms 는 2절 방식의 루프 0.82ms + 정렬 0.18ms 와 맞고, 변경 후 0.76ms 도 루프 0.59ms + 정렬 0.18ms 와 맞습니다.
  • CPU frame 의 감소량이 BuildDrawList 와 거의 같은 이유: 줄어든 시간은 BuildDrawList 에서만 나옵니다. 그림자·메인 패스의 제출 시간은 두 버전에서 같습니다.
  • 평평한 씬(A·B)은 달랐습니다: 별도 바이너리에서는 BuildDrawList 가 0.03~0.05ms(−5~−10%) 줄었는데, 1절의 번갈아 돌린 비교에서는 +0.02ms(+4%)였습니다. 부호가 방법에 따라 다르므로 평평한 씬은 "거의 같다(±0.05ms)" 로 읽어야 합니다. 원인은 따로 찾지 않았습니다(두 빌드의 코드 배치·인라이닝 차이일 수 있으나 확인하지 못했습니다).
  • FPS 영향은 재지 않았습니다. 에디터에서는 GPU 시간과 화면 동기화가 FPS 를 정하는 경우가 많아서, 이 CPU 시간 감소가 FPS 로 얼마나 이어지는지는 별도 측정이 필요합니다. CPU frame 2.9ms → 2.6ms 정도는 60fps 프레임 예산 16.7ms 의 약 2% 입니다.
