BuildDrawList 가 GetWorldMatrix 를 거치지 않기로 한 결정

2026-11-16 · 결정 기록. Renderer::BuildDrawList 가 오브젝트마다 GameObject::GetWorldMatrix() 를 부르는 대신, 루트에서 children 을 따라 내려가며 월드 행렬을 한 번씩 계산하기로 한 이유, 대안, 잠재 위험을 7,000개 오브젝트 측정값과 함께 정리했습니다. 측정 과정과 표는 월드 행렬 계층 순회 비포/애프터 에 있습니다.

상태: 구현과 검증 완료, 아직 커밋하지 않음. 측정은 Release 빌드, D3D11, 합성 7,000개 씬(OL_TestScene 은 이 PC 에 없음).

1. 결정 요약

결정: BuildDrawList 안에서만 GetWorldMatrix 를 쓰지 않고 계층을 위에서 아래로 한 번 훑으며 월드 행렬을 구한다. GameObject::GetWorldMatrix 함수와 캐시는 건드리지 않는다.
항목내용
바꾼 것Graphics/Renderer.cpp 의 BuildDrawList, Graphics/Renderer.h 의 순회 스택 멤버 (HierarchyFrame, m_hierarchyStack)
안 바꾼 것GameObject (스크립트 DLL ABI 무영향), GetWorldMatrix 자체와 그 다른 호출처 (스켈레톤 디버그, 카메라 컴포넌트, 피킹, 기즈모), 월드 행렬 캐시(D7)
얻은 것계층이 있는 7,000개 씬에서 BuildDrawList −21~27%, CPU frame −11~13% (0.30~0.33ms). 월드 행렬은 비트 단위로 같음
치른 것월드 행렬 규칙이 두 곳(GetWorldMatrix, BuildDrawList)에 생김, children/parent 일치에 의존, 평평한 씬은 이득 없음(±0.05ms)
성격지금 씬 규모에서 FPS 를 바꾸는 최적화가 아니라, 계층 깊이에 비례하던 비용을 낮은 위험으로 없앤 것입니다. 가장 큰 절대 이득이 0.23~0.33ms 입니다.

2. 어떻게 이 결정에 이르렀나

  1. 정렬은 병목이 아니었습니다. 7,000개 씬에서 BuildDrawList 의 정렬은 0.04~0.18ms 였고, 같은 구간의 오브젝트 루프는 0.4~0.8ms 였습니다. 그래서 정렬 최적화는 하지 않기로 했습니다.
  2. 루프 안에서는 월드 행렬이 가장 컸습니다. 구간을 떼어 반복 측정한 값입니다(오브젝트당).
    구간평평한 씬깊이 2 씬
    GetWorldMatrix21.5ns (0.151ms/7,000개)73ns (0.509ms)
    재질 GPU 캐시 확인11~12ns12ns
    DrawItem·ObjectData 쓰기11ns11ns
    범용 XMMatrixInverse8~9ns8ns
    경계 구, 해시 조회들각 3~5ns각 3~5ns
    GetWorldMatrix 만 깊이에 따라 3.4배로 커졌고(21.5 → 73ns), 깊이 2 씬에서는 루프의 절반 안팎을 차지했습니다(한 번의 계측 실행 기준 0.51 / 1.10ms).
  3. 원인: 이 함수는 호출마다 자기 로컬 행렬(S·R·T 곱)을 만들고 부모의 GetWorldMatrix 를 다시 부릅니다. 캐시가 없어서 깊이 d 인 오브젝트는 로컬 행렬을 d+1 번 만들고, 형제가 많으면 같은 부모의 행렬도 형제 수만큼 다시 만듭니다.
  4. 그래서 "이 호출을 줄이는 방법"을 비교했고(3절), 가장 국소적이고 검증하기 쉬운 계층 순회를 골랐습니다.

3. 고려한 선택지

선택지요약장점단점결과
0. 그대로 둠변경 없음위험 0깊이에 비례하는 비용 유지. 계층이 큰 씬에서 CPU 시간이 계속 늘어남기각
A. children 을 따라 내려가기루트에서 시작해 부모 월드를 자식에게 넘김순서가 구조로 보장됨. 불변식·ABI 변경 없음. Renderer 만 수정월드 행렬 규칙이 두 곳. children 일치에 의존채택
B. m_objects 에 "부모가 앞" 불변식 유지SetParent·추가·로드 때 재배열선형 순회서브트리를 옮기면 인덱스가 바뀜. 직렬화의 parent 인덱스, 에디터 선택, 되돌리기가 인덱스에 기대면 깨질 수 있음기각
C. A + 정렬된 순서 캐시계층이 바뀔 때만 순서 인덱스 배열을 다시 만듦평소 선형 순회이득이 A 보다 작고 무효화 누락 위험 추가보류
D. 필요할 때 부모를 먼저 계산(메모이제이션)목록 순서로 돌며 부모를 재귀로 먼저 구함순서 보장 불필요"이번 프레임에 계산됨" 표식과 저장 공간이 GameObject 에 필요해 스크립트 DLL ABI 규칙(멤버는 끝에만 덧붙임)에 걸림기각
E. 월드 행렬 캐시(dirty 플래그)GetWorldMatrix 자체를 캐시모든 호출처가 이득. 정적 오브젝트가 많은 씬에서 가장 큼무효화 누락 시 "바꿨는데 안 바뀜" 버그. GameObject·Transform 의 모든 변경 경로를 막아야 함보류 (D7 유지)
F. 루프 병렬화월드·경계 구 계산을 스레드로 분산수만 개에서 유리7,000개의 0.5ms 정도 일에는 스레드 오버헤드와 비슷보류

4-3. 이 수치가 결정에 준 근거

  • 계층이 있으면 이득이 분명합니다. 계층 씬 세 종(C·D·E)에서 두 방법이 모두 같은 방향이고, 3회 실행의 범위가 구·신 사이에서 겹치지 않았습니다. 이득의 출처가 BuildDrawList 하나라는 점도 두 방법에서 일치합니다(CPU frame 감소량 ≈ BuildDrawList 감소량).
  • 이득의 크기는 작습니다. 가장 큰 경우가 루프 0.23ms, CPU frame 0.33ms 로 60fps 프레임 예산(16.7ms)의 1.4~2% 입니다. 그래서 이 결정은 "지금 빨라진다"보다 "계층이 크고 깊어져도 비용이 깊이에 비례해 늘지 않는다"가 이유입니다. FPS 변화는 재지 않았습니다.
  • 평평한 씬은 이득이 없다고 보는 것이 맞습니다. 두 방법의 부호가 달랐습니다(번갈아 비교 +0.02ms, 별도 바이너리 −0.03~−0.05ms). 원인은 찾지 못했고, 어느 쪽이든 크기는 ±0.05ms 입니다. 이 범위의 손해는 계층 씬의 이득에 비해 감수할 수 있다고 판단했습니다.
  • 다른 안과 비교한 위험 대비 이득. 이득이 같은 방향인 캐시(E)는 모든 호출처가 이득을 보지만 무효화 누락이라는 찾기 어려운 버그가 따라옵니다. A 는 이득이 BuildDrawList 에 한정되는 대신 GameObject 를 건드리지 않고, 결과를 비트 단위로 검증할 수 있었습니다.

5. 잠재 위험

#위험왜 생기나지금 상태대응
1두 경로가 갈라짐 (가장 현실적)월드 행렬을 만드는 규칙이 GetWorldMatrix 와 BuildDrawList 두 곳에 있음. 나중에 GetWorldMatrix 가 바뀌면(캐시, 피벗, 스케일 상속 방식 등) BuildDrawList 가 따라가지 않아 렌더링과 피킹·기즈모 위치가 어긋날 수 있음지금은 비트 단위로 같음곱셈 규칙을 한 함수로 모으고(6절 1번) 회귀 검증을 남김(6절 2번). 아직 하지 않음
2children/parent 불일치 시 오브젝트가 안 그려짐옛 방식은 parent 만 보면 됐지만 새 방식은 children 목록에 있어야 방문됨방문 수가 씬 오브젝트 수와 다르면 오류 로그를 한 번 냄. 씬 로드, 재부모화(부모가 뒤 인덱스, 루트로 되돌리기, 실행 중 재부모화)는 검증함. 삭제·복제·되돌리기·프리팹은 실행으로 검증하지 못함코드를 읽으면 Scene::RemoveObject 가 서브트리를 지우며 링크를 정리함. 실행 검증은 아래 8번이 풀려야 가능
3정렬 키가 같은 인스턴스의 그리는 순서가 달라짐방문 순서가 바뀌고 std::sort 는 안정 정렬이 아님같은 PSO·재질·메시·범위의 오브젝트끼리만 해당. 서로 겹치는 같은 모양에서만 z-fighting 으로 보일 수 있음. 비교 씬에서는 안 보였고 스크린샷 차이는 잡음 수준필요하면 정렬 키에 오브젝트 인덱스를 추가 (비용 작음)
4부동소수 결과가 환경에 따라 달라짐두 경로의 곱셈 순서가 같아야 하고, 컴파일 옵션에 따라 결과가 달라질 수 있음Release 에서 모든 검사 비트 일치 (7,000개 씬들, Sponza, MasterChiefWalk 재생, ArmBone 등). Debug 는 컴파일만 확인하고 비트 대조는 하지 않음같은 XMMatrixMultiply 와 같은 순서를 씀. Debug 대조는 6절 2번의 회귀 검증에 포함
5평평한 씬에서 이득이 없거나 약간 느려짐루트마다 스택 준비와 children 확인이 추가됨(추정)±0.05ms. 방법에 따라 부호가 다름감수. 문서에 명시
6순회 스택이 멤버라 재진입·다중 스레드에 약함m_hierarchyStack 을 프레임마다 재사용BuildDrawList 는 렌더 스레드 한 곳에서만 불림병렬화나 두 번째 호출처를 만들 때 지역 스택이나 호출자 소유로 바꿀 것
7"월드 행렬이 빨라졌다"는 오해함수 자체는 그대로 재귀임다른 호출처는 이득 없음. 대부분 선택·디버그 오브젝트에만 불려 비용이 작음문서와 D7 카드에 범위를 명시함
8삭제·복제 자동 검증이 비정상 종료 (이번 변경과 무관)--delete, --duplicate 를 Release 에디터에서 실행하면 segfault(종료 코드 139). 변경 전 바이너리에서도, 계층 없는 floor_cube 에서도 같음원인 미조사별도로 조사. 이 문제가 풀리면 위험 2의 미검증 경로를 돌려 볼 수 있음
9합성 씬의 대표성OL_TestScene 이 이 PC 에 없어 같은 모양(루트 하나 아래 7,000개)의 합성 씬으로 측정실제 씬의 절대값은 다를 수 있음. 비율은 비슷할 것으로 보이나 확인하지 못함실제 씬에서 같은 방법으로 재측정

6. 위험을 줄이는 후속 작업 (권장 순서)

  1. 월드 행렬 규칙을 한 함수로 모으기. 예: GameObject 에 "부모 월드를 받아 이 오브젝트의 월드를 돌려주는" 함수를 두고 GetWorldMatrix 와 BuildDrawList 가 같이 부릅니다. 위험 1 을 가장 직접적으로 줄입니다. 레이아웃을 바꾸지 않는 비가상 함수 추가가 스크립트 DLL ABI 에 안전한지는 확인이 필요합니다.
  2. 회귀 검증을 남기기. Debug 에서만 신 경로의 월드와 GetWorldMatrix() 를 비교하거나, 자동 검증 플래그로 한 번 대조하는 코드를 둡니다. 이번에 쓴 임시 검증(memcmp)과 같은 방식입니다.
  3. 자동 검증 --delete/--duplicate 크래시 조사 후 삭제·복제·되돌리기·프리팹 경로를 위험 2 의 검증에 포함합니다.
  4. 실제 7천 개 씬(OL_TestScene)에서 재측정해 4절의 비율이 맞는지 확인합니다.
  5. 월드 행렬 캐시(D7)는 그 뒤에. 루프 비용이 프레임에서 의미 있는 비중이 되거나 정적 오브젝트가 대부분인 큰 씬이 생기면 다시 엽니다. 지금 수치(루프 0.4~0.8ms, CPU frame 2~3ms)로는 근거가 부족합니다.

7. 이 결정을 되돌리거나 다시 열 조건

  • 되돌리기: Renderer.cpp·Renderer.h 의 변경만 되돌리면 됩니다. GameObject 를 건드리지 않았으므로 다른 코드나 스크립트 DLL 에 영향이 없습니다.
  • 되돌려야 하는 경우: 위험 1 이 실제로 발생(렌더링과 피킹 위치가 어긋남)했는데 곧바로 6절 1번으로 합치지 못할 때, 또는 위험 2 로 오브젝트가 안 그려지는 사례가 나올 때.
  • 다시 열 경우: GetWorldMatrix 가 캐시되어 빨라지면 이 우회의 이득이 사라지므로, 그때는 공통 함수(6절 1번)로 되돌리는 것이 자연스럽습니다.

8. 이 기록이 확인하지 못한 것

  • FPS 로의 영향 (GPU 시간과 동기화가 FPS 를 정하는 경우가 많아 CPU 시간 감소가 그대로 이어지지는 않음).
  • OL_TestScene 실측, Debug 빌드의 시간·비트 대조, D3D12 의 프레임 구간(루프 구간은 C·D 에서 D3D11 과 같았음).
  • 삭제·복제·되돌리기·프리팹 경로의 실행 검증.
  • 평평한 씬에서 방법마다 부호가 다른 이유.
  • 임시 계측 코드와 합성 씬 파일은 저장소에 넣지 않았으므로, 같은 측정을 다시 하려면 비교 문서 6절의 방법으로 다시 만들어야 합니다.
