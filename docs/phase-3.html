3단계 · Scene과 리소스 래퍼

모든 GPU 리소스를 Desc → 핸들 한 가지 모양으로 만들고, 상수버퍼를 갱신 빈도로 셋으로 나누고, 씬 데이터를 Renderer 밖으로 꺼내고, D3D11 헤더를 Graphics/D3D11/ 안에 가둔 단계입니다. 원문은 이 단계를 "아직 가상 인터페이스는 없고 D3D11 전용 클래스지만 이름과 시그니처는 RHI 최종형과 같게" 만드는 단계라고 했습니다. 7단계에서 RHI::Device 인터페이스를 뽑을 때 호출 코드가 바뀌지 않도록, 지금 Device의 공개 함수가 곧 그 인터페이스입니다.

Device는 이제 CreateBuffer(BufferDesc) → BufferHandle, CreateTexture, CreateShader, CreatePipeline, UpdateBuffer, BeginFrame/EndFrame, Bind*/DrawIndexed만 밖으로 내놓습니다. 실제 객체는 세대 카운터가 붙은 풀에 있고, 핸들은 정수 두 개입니다. 2.핸들과 풀

2.1 왜 포인터가 아니라 핸들인가

원문 D21은 RHI 추상화의 세 갈래(가상 인터페이스 / 핸들+풀 / 컴파일 타임 선택) 중 "리소스는 핸들, Device와 CommandList만 가상"인 혼합형을 권했습니다. 리소스에 핸들을 쓰는 이유를 Weissflog[1]와 Frykholm[2]의 글이 잘 정리합니다.

  • 소유권이 한 곳에 있다. 모든 ID3D11Buffer는 Device의 풀 안에 있습니다. 누가 몇 개의 참조를 갖고 있는지 세지 않아도 ReleaseDevice()가 풀을 비우면 전부 사라집니다. 종료 시 Live Object 문제가 구조적으로 없어집니다.
  • 호출 코드가 백엔드 타입을 모른다. Renderer.h에는 BufferHandle만 있고 ID3D11Buffer가 없습니다. 8단계에서 D3D12 백엔드가 같은 BufferHandle을 돌려주면 Renderer는 재컴파일만 하면 됩니다. 이것이 3단계 완료 기준 "Graphics/D3D11/ 밖에서 ID3D11이 검색되지 않는다"의 실체입니다.
  • 값이다. 정수 두 개라 복사·비교·해시가 자유롭습니다. PipelineStateDesc가 셰이더를 핸들로 참조할 수 있었던 것도(1단계) 이 때문입니다.
  • 해제 후 접근이 널이 된다. 다음 절의 세대 카운터 덕분입니다. 댕글링 포인터는 "가끔 다른 객체를 가리키고" 크래시가 나지 않아 찾기 어렵지만, 세대가 다른 핸들은 항상 nullptr를 돌려주고 로그를 남깁니다.

sokol_gfx.h[3]와 NVRHI[4]가 같은 구조의 실전 예입니다. sokol은 sg_buffer{uint32_t id} 핸들과 풀, NVRHI는 참조 카운트 핸들(BufferHandle = RefCountPtr<IBuffer>)을 씁니다. 후자는 스마트 포인터에 가깝지만 D3D11/D3D12/Vulkan 백엔드가 같은 BufferDesc를 받는 모양은 같습니다.

2.2 세대 카운터와 free list

// Graphics/D3D11/ResourcePool.h
template <typename T, typename HandleT>
class ResourcePool
{
    struct Slot { T item{}; uint32_t generation = 1; bool alive = false; };
    std::vector<Slot> m_slots;
    std::vector<uint32_t> m_free;
public:
    HandleT Add(T&& item);     // free list에서 꺼내거나 push_back. {index, slot.generation}
    T* Get(HandleT h);         // index 범위 밖 / !alive / generation 불일치 → nullptr
    void Remove(HandleT h);    // item = T{} (ComPtr 해제), alive = false, ++generation (0 건너뜀), free에 push
    void Clear();
};

슬롯을 해제하면 세대가 1 올라갑니다. 같은 슬롯이 재사용되어 새 핸들 {7, 3}이 나가더라도, 옛 핸들 {7, 2}로 Get하면 세대가 달라 nullptr입니다. 세대 0은 "빈 핸들"로 예약되어 있으므로(Handle::IsValid가 generation != 0을 봄) 오버플로 시 0을 건너뜁니다. 32비트 세대가 넘치려면 같은 슬롯을 40억 번 재사용해야 합니다.

Remove가 item = T{}로 대입하는 것이 ComPtr을 해제하는 지점입니다. D3D11Texture의 경우 텍스처와 RTV/DSV/SRV가 이때 함께 놓입니다. Resize가 이 성질에 기댑니다(6절).

세 풀(m_buffers, m_textures, m_shaders)과 PSO 캐시는 Device에서 m_device 뒤에 선언되어 먼저 파괴되고, ReleaseDevice()도 pipelines → shaders → textures → buffers → swapchain → context → (보고) → device 순으로 비웁니다. PSO가 셰이더 ComPtr을 복사해 두므로 셰이더 풀보다 PSO 캐시를 먼저 비워야 합니다(순서가 반대여도 ComPtr이라 누수는 없지만, "풀을 비웠는데 객체가 살아 있는" 상태가 잠깐 생깁니다).

debugName은 const char*이지만 Device는 그 포인터를 보관하지 않고 즉시 std::string으로 복사한 뒤 SetPrivateData(WKPDID_D3DDebugObjectName)로 D3D 객체에 붙입니다. Debug Layer 메시지에 "CB_PerObject[1]"처럼 이름이 나오므로 어느 버퍼가 문제인지 바로 보입니다. 이 GUID는 dxguid.lib에 있어 링크 에러 하나를 만났습니다(10절).

BindConstantBuffer가 stageMask를 받는 것은 D3D11 특유의 사정입니다. D3D11은 VS와 PS의 상수버퍼 슬롯이 따로라서 PS가 b0의 cameraPosition을 읽으려면 PSSetConstantBuffers(0, …)도 불러야 합니다. D3D12에서는 루트 시그니처의 가시성(visibility)에 해당하고, 4단계 BindingLayoutDesc의 슬롯별 "셰이더 스테이지" 항목이 이 마스크를 흡수합니다.

4.프레임과 Dynamic 버퍼 링

4.1 BeginFrame / EndFrame

// Graphics/D3D11/Device.cpp
uint32_t Device::BeginFrame()
{
    m_frameIndex = static_cast<uint32_t>(m_frameCounter % kFrameCount);
    D3D11Texture* bb = m_textures.Get(m_backBuffer);   D3D11Texture* db = m_textures.Get(m_depthBuffer);
    ID3D11RenderTargetView* rtv = bb ? bb->GetRTV(m_device.Get()) : nullptr;   // 지연 생성
    ID3D11DepthStencilView* dsv = db ? db->GetDSV(m_device.Get()) : nullptr;
    m_context->OMSetRenderTargets(1, &rtv, dsv);
    m_context->ClearRenderTargetView(rtv, m_clearColor);
    m_context->ClearDepthStencilView(dsv, D3D11_CLEAR_DEPTH | D3D11_CLEAR_STENCIL, 1.0f, 0);
    m_context->RSSetViewports(1, &m_viewport);
    return m_frameIndex;
}
void Device::EndFrame()
{
    m_swapChain->Present(m_vsync ? 1 : 0, 0);
    DumpDebugLayerMessages();
    ++m_frameCounter;
}

예전 Clear()/Present()가 BeginFrame()/EndFrame()이 된 것은 이름만의 변화가 아닙니다. 프레임의 시작과 끝이 한 곳에 생겼고, 그 안에서 프레임 인덱스가 돌아갑니다. 렌더 타깃을 매 프레임 다시 바인딩하는 것도 여기서 정해졌습니다. 1단계 문서가 언급한 flip 모델 스왑체인의 요구 사항("Present 뒤 백버퍼 재바인딩")이 자연히 충족되고, 6단계에서 RenderPassDesc(타깃 + Load/Store)가 OMSetRenderTargets와 Clear의 자리를 차지하게 됩니다.

4.2 Map(WRITE_DISCARD)의 의미론

세 상수버퍼는 전부 BufferUsage::Dynamic이고 UpdateBuffer는 Map(D3D11_MAP_WRITE_DISCARD)를 씁니다. Microsoft 문서[5]의 설명을 이 프로젝트 맥락으로 옮기면:

  • GPU를 기다리지 않는다. GPU가 아직 그 버퍼로 그리고 있어도 Map은 새 메모리 영역의 포인터를 돌려줍니다(드라이버가 이름 바꾸기, renaming, 를 합니다). 이전 내용은 GPU가 다 쓰면 자동으로 버려지거나 재사용됩니다. 앱은 메모리 관리를 하지 않습니다.
  • 따라서 한 프레임에 같은 버퍼를 여러 번 Map해도 된다. Renderer::Render는 오브젝트마다 PerObject를 Map하고 DrawIndexed합니다. 7개 오브젝트면 7번 Map입니다. 각 드로우는 자기가 Map했을 때의 데이터를 봅니다. D3D11의 표준 패턴이고, D3D12에서는 이것이 링 버퍼 서브할당이 됩니다(4.3절).
  • 전체를 다시 써야 한다. DISCARD는 항상 버퍼 전체를 버립니다. 일부만 갱신하려고 오프셋을 줄 수 없습니다. 그래서 UpdateBuffer의 size는 "쓰는 바이트 수"이지 부분 갱신이 아니고, 이 프로젝트의 상수버퍼 구조체는 매번 전부 채워서 넘깁니다.
  • Map한 메모리를 읽지 말 것. 쓰기 결합(write-combined) 메모리라 읽으면 매우 느립니다. memcpy로 통째로 쓰기만 합니다. 문서는 *p = 0 같은 코드도 컴파일러가 read-modify-write로 바꿀 수 있다고 경고합니다.

BufferUsage::Default는 UpdateSubresource로 갱신하되 전체 크기만 받습니다. 문서에 "상수버퍼는 pDstBox를 NULL로 두어야 하며 부분 갱신은 불가능하다"고 명시되어 있고[6], pDstBox = NULL이면 ByteWidth만큼 원본에서 읽으므로 size < ByteWidth인 데이터를 넘기면 원본 뒤쪽을 읽어 넘칩니다. 그래서 size != desc.size면 거부합니다. 정점·인덱스 버퍼는 Default + 초기 데이터로 만들고 갱신하지 않습니다. Staging은 Desc에는 있지만 아직 쓰는 곳이 없습니다(스크린샷·리드백은 나중).

어느 usage를 고를지는 D3D11_USAGE 문서[7]의 표를 따랐습니다. 매 프레임 CPU가 쓰는 것 → Dynamic + Map. 한 번 만들고 GPU만 읽는 것 → Default(초기 데이터). 문서는 "Dynamic 리소스는 특정 하드웨어 능력을 소모하므로 아껴 쓰라"고도 하지만, 상수버퍼 세 개는 그 범주가 아닙니다.

4.3 kFrameCount 복제가 D3D12에서 하는 일

// Graphics/GraphicsConfig.h
constexpr uint32_t kFrameCount = 2;

// Graphics/D3D11/D3D11Resources.h
struct D3D11Buffer
{
    BufferDesc desc;  std::string name;
    ComPtr<ID3D11Buffer> buffers[kFrameCount];              // Dynamic만 전부 채운다
    ID3D11Buffer* Get(uint32_t frameIndex) const
    { return buffers[desc.usage == BufferUsage::Dynamic ? frameIndex % kFrameCount : 0].Get(); }
};

D3D11에서 이 복제는 아무 일도 하지 않습니다. WRITE_DISCARD가 이미 동기화를 해 주므로 복제본 1개면 충분합니다. 그런데도 넣은 이유는 원문 3단계 설계 결정의 "프레임 인덱스를 지금부터 노출한다"입니다. D3D12에는 DISCARD가 없습니다. 업로드 힙의 메모리를 CPU가 직접 쓰고, GPU가 그 메모리를 아직 읽고 있는지는 앱이 펜스로 추적해야 합니다. Microsoft의 Fence-Based Resource Management[8]가 설명하는 링 버퍼가 그것입니다. 프레임 N의 업로드는 슬롯 N % kFrameCount에 쓰고, 그 슬롯을 다시 쓰기 전에 프레임 N − kFrameCount의 펜스가 완료됐는지 기다립니다. 8단계 D3D12 백엔드는 BeginFrame에서 그 대기를 추가하고 buffers[frameIndex]에 해당하는 업로드 힙 영역을 돌려주면 됩니다. Renderer는 바뀌지 않습니다.

이 구조가 "투명한지"를 확인하는 방법은 kFrameCount를 1, 2, 3으로 바꿔 빌드해 화면이 같은지 보는 것입니다. 다르다면 어딘가가 "이전 프레임 슬롯의 내용이 남아 있다"에 기대는 버그입니다. 세 값 모두 같은 화면이었습니다(11절). Information 패널의 frame slot이 0·1·2로 도는 것도 볼 수 있습니다.

Dynamic 버퍼의 계약

Dynamic 버퍼의 내용은 UpdateBuffer를 부른 그 프레임에서만 유효합니다. 다음 프레임은 다른 슬롯을 바인딩하므로, "지난 프레임에 올렸으니 이번엔 안 올려도 되겠지"는 D3D12에서 옛 데이터를 읽거나 쓰레기를 읽습니다. Renderer는 PerFrame과 Lights를 매 프레임, PerObject를 드로우마다 올립니다. 조명이 바뀌지 않아도 올립니다. 최적화가 필요해지면 "바뀐 프레임에만 올리되 모든 슬롯에 올린다"가 맞는 방향입니다.

5.상수버퍼 3분할

5.1 갱신 빈도로 나눈다

이전 b0 ConstBuffer는 world·worldInvTranspose·view·proj·wvp 다섯 행렬(320B)을 드로우마다 통째로 올렸습니다. view와 proj는 프레임 내내 같은데 오브젝트 수만큼 반복 업로드되고, wvp는 셰이더가 mul(pos, world) 뒤 mul(·, viewProj)로 두 번 곱하면 필요 없습니다. 원문 D2의 분할을 그대로 적용했습니다.

슬롯구조체크기갱신스테이지내용
b0PerFrameConstants208B프레임에 1회VS + PSview, proj, viewProj, cameraPosition, time
b1PerObjectConstants128B드로우마다VSworld, worldInvTranspose
b2LightConstants672B프레임에 1회PSLightData[8], ambientColor, lightCount, specularColor, shininess

드로우당 업로드가 320B에서 128B로 줄었다는 것보다 중요한 것은 바인딩 레이아웃이 생겼다는 점입니다. "이 파이프라인은 b0·b1·b2를 쓴다"가 4단계 BindingLayoutDesc이고, D3D12의 루트 시그니처입니다. specularColor와 shininess가 조명 버퍼에 있는 것은 임시이며 4단계에서 Material 상수버퍼로 갑니다(원문 4단계 작업 항목).

5.2 HLSL 패킹 규칙

C++ 구조체와 HLSL cbuffer가 바이트 단위로 같아야 합니다. HLSL의 규칙[9]은 세 줄로 요약됩니다.

  1. 변수는 16바이트 레지스터(float4) 단위로 채워지며, 한 변수(벡터)가 레지스터 경계를 넘을 수 없다. 넘칠 것 같으면 다음 레지스터로 밀린다.
  2. 구조체와 배열의 각 원소는 새 레지스터에서 시작한다. float2 arr[32]는 32개 레지스터를 쓴다(원소마다 8바이트가 낭비됨).
  3. 4바이트 스칼라끼리는 붙어서 채워진다.

C++에는 이 규칙이 없습니다. C++ float3 a; float3 b;는 24바이트지만 HLSL은 b가 첫 레지스터에 안 들어가므로(12+12 > 16) 16바이트 오프셋으로 밀어 32바이트가 됩니다. 이때 alignas(16)과 sizeof % 16 == 0은 필요조건일 뿐입니다. 크기가 맞아도 오프셋이 어긋난 채 조용히 잘못된 값을 읽습니다. 그래서 규칙을 손으로 맞춥니다. float3 다음에는 반드시 4바이트 스칼라를 둬서 정확히 16을 채웁니다.

// Scene/Light.h — 80바이트 = 레지스터 5개. float3 뒤에 스칼라를 두어 경계를 맞춘다.
struct alignas(16) LightData
{
    XMFLOAT3 position;    float intensity;      // [0, 16)
    XMFLOAT3 direction;   float range;          // [16, 32)
    XMFLOAT3 color;       uint32_t type;        // [32, 48)
    XMFLOAT3 attenuation; float innerConeCos;   // [48, 64)
    float outerConeCos;   XMFLOAT3 padding;     // [64, 80) — float 뒤 float3도 한 레지스터 안이면 허용
};

// Graphics/ShaderConstants.h
struct alignas(16) PerFrameConstants  { XMFLOAT4X4 view, proj, viewProj; XMFLOAT3 cameraPosition; float time; };   // 192 + 16
struct alignas(16) PerObjectConstants { XMFLOAT4X4 world, worldInvTranspose; };                                   // 128
struct alignas(16) LightConstants     { LightData lights[MAX_LIGHTS]; XMFLOAT3 ambientColor; uint32_t lightCount;
                                        XMFLOAT3 specularColor; float shininess; };                                // 640 + 32
// Shaders/Common.hlsli — 같은 순서, 같은 이름
cbuffer PerFrame  : register(b0) { matrix view; matrix proj; matrix viewProj; float3 cameraPosition; float time; }
cbuffer PerObject : register(b1) { matrix world; matrix worldInvTranspose; }
cbuffer Lights    : register(b2) { LightData lights[MAX_LIGHTS]; float3 ambientColor; uint lightCount;
                                   float3 specularColor; float shininess; }

LightData의 마지막 줄 float outerConeCos; float3 padding;은 float(4) + float3(12) = 16으로 한 레지스터에 딱 들어가므로 규칙 위반이 아닙니다. 반대로 float3 padding; float outerConeCos;여도 같은 크기입니다. 중요한 것은 float3가 오프셋 4·8·12에서 시작하지 않는다는 것입니다(4에서 시작하면 4..16이라 경계 안이지만, 8이나 12에서 시작하면 넘칩니다). 이 규칙은 원문 5절이 옛 LightBuffer(688B로 잘못 계산했던)를 설명할 때도 등장했고, 지금 LightConstants는 정확히 8×80 + 16 + 16 = 672B입니다.

5.3 세 겹의 검사

  1. 컴파일 시점 — static_assert. sizeof뿐 아니라 offsetof를 단언합니다. 크기만 맞는 float3/float3 실수를 잡는 것은 오프셋 검사입니다. 
    static_assert(sizeof(PerFrameConstants) == 208);
static_assert(offsetof(PerFrameConstants, cameraPosition) == 192);
static_assert(offsetof(PerFrameConstants, time) == 204);
static_assert(sizeof(LightConstants) == 672);
static_assert(offsetof(LightConstants, lightCount) == 652);
static_assert(offsetof(LightConstants, shininess) == 668);
  2. 초기화 시점 — 리플렉션. HLSL 쪽이 바뀌었을 때는 C++ 단언이 잡지 못합니다. Debug 빌드의 Renderer::Initialize는 컴파일된 바이트코드에 D3DReflect[10]를 걸어 GetConstantBufferByName("PerFrame")->GetDesc().Size를 sizeof(PerFrameConstants)와 대조합니다. 불일치면 초기화 실패입니다. GetConstantBufferByName은 없는 이름에도 더미 객체를 돌려주므로 GetDesc의 HRESULT로 존재 여부를 판단합니다. 셰이더가 쓰지 않는 cbuffer는 리플렉션에 나오지 않으므로(예: PS는 PerObject를 안 씀) 그 경우는 "검사 생략"으로 통과시킵니다. 로그: 
    [정보] cbuffer 'PerFrame' 크기 일치: 208 바이트 (변수 5개)
[정보] cbuffer 'PerObject' 크기 일치: 128 바이트 (변수 2개)
[정보] cbuffer 'PerFrame' 크기 일치: 208 바이트 (변수 5개)
[정보] cbuffer 'Lights' 크기 일치: 672 바이트 (변수 5개)
  3. 실행 시점 — RenderDoc. 드로우를 캡처하면 VS에 b0·b1, PS에 b0·b2가 208/128/672 바이트로 바인딩된 것과 각 변수의 값이 보입니다. 이 문서 작성 시점의 검증은 1·2번으로 했습니다.

5.4 행렬 전치 관례와 역전치

HLSL은 기본으로 행렬을 column_major로 읽습니다. 즉 상수버퍼의 연속된 16바이트 4개를 열 4개로 해석합니다. DirectXMath의 XMMATRIX는 행우선(row-major) 메모리라 그대로 올리면 HLSL이 전치된 행렬을 봅니다. 셰이더가 행벡터 곱 mul(v, M)을 쓰므로, 우리는 C++에서 XMMatrixTranspose(M)을 올려 두 전치가 상쇄되게 합니다. 이것이 이전 코드부터 이어진 관례이고, 원문 D13이 "#pragma pack_matrix(row_major)로 전치를 없앨 수도 있지만 관례를 섞지 말라"고 한 지점입니다. 섞으면 어떤 행렬은 전치하고 어떤 것은 안 하는 상태가 되어 화면이 조용히 깨집니다.

노멀 변환 행렬은 (W⁻¹)ᵀ입니다. 이것을 "전치해서 올려야" 하므로 실제로 메모리에 쓰는 값은 ((W⁻¹)ᵀ)ᵀ = W⁻¹, 즉 역행렬을 전치 없이 그대로입니다.

// Graphics/Renderer.cpp
XMStoreFloat4x4(&perObject.world,             XMMatrixTranspose(world));
XMStoreFloat4x4(&perObject.worldInvTranspose, XMMatrixInverse(nullptr, world));   // ((W⁻¹)ᵀ)ᵀ = W⁻¹

이전 MeshRenderer의 Transpose(Transpose(Inverse(world)))는 결과적으로 같은 값을 계산하고 있었습니다(원문 5절 콜아웃 "역전치 행렬의 이중 전치는 맞게 동작합니다"). 이제 그 이유가 주석과 이 문서에 적혀 있습니다. 비균등 스케일(3단계 데모의 맥동하는 구는 균등 스케일이라 해당 없음)에서 노멀이 표면에 수직을 유지하는지가 이 행렬의 존재 이유입니다.

6.텍스처: 백버퍼·깊이 버퍼·Resize

백버퍼는 스왑체인이 이미 만든 텍스처라 CreateTexture로 만들 수 없습니다. IDXGISwapChain::GetBuffer(0)으로 얻은 ID3D11Texture2D를 D3D11Texture로 감싸 풀에 넣는 전용 경로(CreateBackBufferTexture)를 두었습니다. 깊이 버퍼는 TextureDesc{w, h, D24_UNORM_S8_UINT, DepthStencil}로 일반 CreateTexture입니다. 둘 다 TextureHandle이고 GetBackBuffer()/GetDepthBuffer()로 얻습니다. 뷰(RTV/DSV/SRV)는 D3D11Texture::GetRTV(device)가 첫 요청에서 만들어 보관합니다. bindFlags에 없는 뷰를 요청하면 nullptr입니다.

Resize의 순서는 ResizeBuffers 문서[11]가 정합니다. "백버퍼에 대한 모든 직접·간접 참조를 해제해야 성공한다. 간접 참조에는 뷰, 컨텍스트에 바인딩된 뷰가 포함된다."

// Graphics/D3D11/Device.cpp — Resize()
m_context->OMSetRenderTargets(0, nullptr, nullptr);   // (1) 바인딩 해제
DestroyTexture(m_backBuffer);                        // (2) 풀에서 제거 → 텍스처·RTV ComPtr 해제
DestroyTexture(m_depthBuffer);
m_swapChain->ResizeBuffers(0, w, h, DXGI_FORMAT_UNKNOWN, 0);   // (3)
CreateBackBufferTexture();                           // (4) 새 핸들. 이전 핸들은 세대가 올라가 무효
CreateDepthTexture();
UpdateViewport();

(2)에서 풀의 Remove가 item = T{}로 ComPtr을 놓는 것이 참조 해제입니다. 누군가 이전 TextureHandle을 들고 있어도 그것은 값이라 참조를 유지하지 않으므로 ResizeBuffers를 막지 못하고, 다음 Get에서 nullptr를 받습니다. 그래서 헤더에 "Resize마다 새로 만들어진다. 프레임을 넘겨 보관하지 말 것"이라고 적었습니다. WM_SIZE는 메시지 루프에서만 오므로 프레임 도중에 핸들이 무효화되는 일은 없습니다. 창 크기를 여섯 번 바꾸고 최소화/복원해도 Debug Layer 메시지가 0건이었습니다(11절).

7.Scene · GameObject · Renderer

7.1 CPU 데이터와 GPU 캐시의 경계

원문 D3는 Renderer가 씬·조명·ImGui 패널을 함께 소유하는 것을 지적하며, "Scene은 CPU 데이터, GPU 자원은 Renderer 측 캐시(Mesh → GpuMesh)"라는 경계를 제안했습니다. 그대로 만들었습니다.

// Scene/Scene.h — GPU를 모른다
class Scene
{
    Mesh* AddMesh(Mesh&& mesh);                       // vector<unique_ptr<Mesh>> → 포인터가 안정적
    GameObject& AddObject(const Mesh* mesh, const char* name);
    std::vector<GameObject>& GetObjects();
    std::vector<LightData>&  GetLights();             // ≤ MAX_LIGHTS, 넘치면 Renderer가 자름
    XMFLOAT3 ambientColor, specularColor;  float shininess;  float clearColor[4];
};
// Scene/GameObject.h
class GameObject { Transform transform; const Mesh* mesh; std::string name; };
// Graphics/Renderer.h — GPU 쪽. 핸들만 있고 D3D 타입이 없다
struct GpuMesh { BufferHandle vertexBuffer, indexBuffer; uint32_t indexCount; };
std::unordered_map<const Mesh*, GpuMesh> m_gpuMeshes;
const GpuMesh* GetOrCreateGpuMesh(const Mesh&);   // 처음 보는 메시면 Default VB/IB 생성
void InvalidateMesh(const Mesh*);                 // 메시가 사라지거나 바뀌면

원문 3단계 작업 항목은 "Mesh의 GPU 버퍼는 Buffer 핸들 두 개"라고 했고, 핸들은 API 중립이라 Mesh가 직접 들어도 규칙 위반은 아닙니다. 그래도 Renderer 측 캐시를 택한 이유는 수명입니다. Mesh가 핸들을 들면 Mesh의 소멸자가 Device를 알아야 하고, Scene이 Device보다 오래 살거나 Device가 없는 곳(에디터의 씬 로딩, 헤드리스 도구)에서 Mesh를 만들 수 없게 됩니다. 캐시 키가 const Mesh*인 것은 Scene이 unique_ptr로 소유해 주소가 안정적이기 때문이고, 메시를 지울 때 InvalidateMesh를 부르지 않으면 재사용된 주소가 옛 GPU 버퍼에 걸리는 위험이 있습니다. 9단계 모델 로딩 때 Mesh에 고유 ID를 붙여 키를 바꾸는 것이 맞습니다.

같은 메시를 여러 오브젝트가 참조하면 GPU 버퍼는 하나입니다. 데모 씬의 구 3개는 GPU meshes: 4(바닥·구·큐브·실린더)에 포함된 하나의 VB/IB를 공유합니다.

7.2 Render(Scene, Camera)

// Graphics/Renderer.cpp — Render()의 흐름
m_device->BindPipeline(GetPipelineForSettings());                          // 1단계 PSO

PerFrameConstants perFrame;  // view·proj·viewProj (전치), cameraPosition, time
m_device->UpdateBuffer(m_perFrameCB, &perFrame, sizeof(perFrame));
LightConstants lights;       // scene.GetLights() 최대 8개, 방향 정규화, ambient/specular/shininess
m_device->UpdateBuffer(m_lightCB, &lights, sizeof(lights));
m_device->BindConstantBuffer(kCBSlotPerFrame, m_perFrameCB, ShaderStageMask_Vertex | ShaderStageMask_Pixel);
m_device->BindConstantBuffer(kCBSlotLights,   m_lightCB,    ShaderStageMask_Pixel);

for (const GameObject& object : scene.GetObjects())
{
    const GpuMesh* gpuMesh = GetOrCreateGpuMesh(*object.GetMesh());
    PerObjectConstants perObject;   // world (전치), worldInvTranspose (= W⁻¹)
    m_device->UpdateBuffer(m_perObjectCB, &perObject, sizeof(perObject));   // Map DISCARD, 드로우마다
    m_device->BindConstantBuffer(kCBSlotPerObject, m_perObjectCB, ShaderStageMask_Vertex);
    m_device->BindVertexBuffer(gpuMesh->vertexBuffer);
    m_device->BindIndexBuffer(gpuMesh->indexBuffer, Format::R32_UINT);
    m_device->DrawIndexed(gpuMesh->indexCount);
}

이 함수에는 D3D 호출이 하나도 없습니다. 전부 Device의 핸들 API입니다. 6단계에서 m_device->가 commandList->로 바뀌는 것 말고는 이 모양이 유지될 예정입니다. 오브젝트 정렬(PSO → Material → Mesh)은 4단계 몫입니다. 지금은 PSO가 하나라 정렬할 것이 없습니다.

7.3 프리미티브

Mesh::CreateCube / CreatePlane / CreateCylinder를 추가했습니다. 전부 Luna의 GeometryGenerator[12] 관례를 따릅니다. 왼손 좌표계, 시계방향이 앞면(RasterizerDesc::frontCounterClockwise = false가 기본), 노멀은 바깥쪽. 기존 구 생성기도 같은 관례라서 컬링을 켰을 때 넷 다 올바르게 보입니다.

  • 큐브는 정점 24개(면당 4개)입니다. 8개로 공유하면 한 정점이 세 면의 노멀을 평균 내야 해서 모서리가 둥글게 음영집니다. 면마다 정점을 따로 두어야 면 노멀이 정확합니다.
  • 평면은 m×n 격자입니다. 셰이딩만 보면 정점 4개로 충분하지만, 6단계 그림자 검증과 점광원의 감쇠가 넓은 면에서 정점 보간 없이 픽셀 단위로 계산되는지 보려면 격자가 있는 편이 낫습니다. 데모는 21×21입니다.
  • 실린더(원뿔대)의 옆면 노멀은 접선 T = (−sinθ, 0, cosθ)와 종접선 B = (Δr·cosθ, −h, Δr·sinθ)의 외적 normalize(T × B)입니다. Δr = bottomRadius − topRadius가 0이면(원기둥) (cosθ, 0, sinθ)로 줄어들고, 0이 아니면 경사면에 수직인 벡터가 나옵니다. 데모의 실린더는 아래 1.5, 위 1.0이라 원뿔대이며 스크린샷에서 옆면 음영이 위로 갈수록 밝아지는 것이 이 노멀의 결과입니다.

8.ShaderCompiler · DebugUI · ImGuiBackend

  • ShaderCompiler (Graphics/D3D11/) — Shader::ShaderCompile의 본문을 그대로 옮긴 CompileFromFile(absPath, entry, target, vector<uint8_t>&)와 5.3절의 ValidateConstantBufferSize. Device는 컴파일러를 모르고 바이트코드만 받습니다. 원문 3단계의 "RHI는 바이트코드만 받음"이며, 4단계의 .cso 사전 컴파일과 핫리로드가 이 파일에 붙습니다. D3D12용 DXIL 컴파일러(dxc)가 오면 ShaderCompiler가 백엔드를 물어 fxc/dxc를 고르게 됩니다.
  • DebugUI (App/) — 조명·렌더 설정·카메라 패널을 자유 함수 세 개로. Renderer는 <imgui.h>를 include하지 않습니다. 패널은 데이터를 편집하는 쪽이지 소유하는 쪽이 아니므로 App 계층입니다.
  • ImGuiBackend (Graphics/D3D11/) — ImGui_ImplDX11_Init이 ID3D11Device*를 받으므로 그것을 부르는 코드는 D3D11 폴더 안에 있어야 합니다. Init(Device&)/NewFrame/Render/Shutdown 네 함수로 감쌌고 AppBase는 Win32 백엔드와 ImGui 컨텍스트만 다룹니다. D3D12 백엔드는 Graphics/D3D12/ImGuiBackend가 될 것입니다.

9.pch 정리와 ID3D11 격리

pch.h에서 d3d11.h·dxgi.h·d3dcompiler.h·wrl/client.h와 #pragma comment(lib)를 지웠습니다. 0단계에서 D3D11Common.h를 만들고 D3D11 폴더의 모든 헤더가 그것을 include하게 해 두었기 때문에 컴파일 에러가 하나도 나지 않았습니다. 계획은 "컴파일 에러 목록이 곧 남은 누출 목록"이었는데 목록이 비어 있었던 셈입니다. grep이 잡은 것은 주석 속 문자열 세 곳("ComPtr<ID3D11Buffer>를 돌려줬다" 같은 설명)뿐이라 문구를 고쳤습니다. 완료 기준은 문자열 검색이므로 주석도 대상입니다.

# 3단계 완료 기준 검사. 둘 다 출력이 없어야 한다.
grep -rn "ID3D11\|d3d11\.h\|dxgi\.h\|d3dcompiler\.h\|imgui_impl_dx11" --include=*.h --include=*.cpp . | grep -v "^./Graphics/D3D11/"
grep -rn "ComPtr" --include=*.h --include=*.cpp . | grep -v "^./Graphics/D3D11/"

이 규칙이 지키는 것은 "Graphics/D3D11/ 밖의 파일은 재컴파일 없이 D3D12 백엔드로 바꿀 수 있는가"입니다. 지금 답은 "헤더 기준으로는 그렇다"입니다. Renderer.cpp와 DebugUI.cpp가 Graphics/D3D11/Device.h를 include하는 것은 남아 있고, 7단계에서 그것이 RHI/Device.h(가상 인터페이스)로 바뀝니다. 그때 바뀌는 것은 include 한 줄과 Device* → RHI::Device*뿐이어야 하며, 지금 Device의 공개 함수는 그 인터페이스와 이름·시그니처가 같게 설계되었습니다.

10.함정과 해결

  • WKPDID_D3DDebugObjectName 링크 에러. SetPrivateData용 GUID는 dxguid.lib에 정의되어 있습니다. D3D11Common.h에 #pragma comment(lib, "dxguid.lib") 추가. 3단계에서 만난 유일한 빌드 에러였습니다.
  • LightData 크기. 계획 단계의 설계 문서는 64바이트로 잘못 계산했습니다. 실제는 80(5 레지스터)이고 static_assert(sizeof(LightData) == 80)이 있습니다. 5.2절의 규칙을 손으로 세어 보면 바로 나오는 값이라, "계산이 아니라 단언을 믿어라"의 예입니다.
  • GetConstantBufferByName이 없는 이름에도 객체를 돌려준다. nullptr 검사로는 못 잡고 GetDesc의 HRESULT를 봐야 합니다. PS에는 PerObject가 없어 이 경로를 실제로 탔습니다.
  • debugName의 수명. Desc의 const char*를 풀 항목에 그대로 저장하면 호출자의 임시 문자열이 사라진 뒤 댕글링이 됩니다. 항목에는 std::string으로 복사하고 저장된 Desc의 포인터는 nullptr로 비웁니다.
  • UpdateSubresource에 작은 데이터. Default 상수버퍼를 부분 크기로 갱신하면 원본 버퍼 뒤를 읽습니다. 4.2절의 size == desc.size 검사가 이것을 막습니다. 상수버퍼 크기는 16 올림된 값을 desc.size에 저장해 검사가 실제 ByteWidth와 맞게 했습니다.
  • ImGui 창 위치 ini. 1단계와 같은 문제. 자동 검증 전에 x64\Debug\imgui.ini를 지웁니다.

12.4단계로 가는 길

3단계가 끝난 지금의 Device 공개 API를 원문 9절 개념 대응표에 비추면 남은 조각은 명확합니다.

  • BindingLayout / ResourceSet (4단계) — BindConstantBuffer(slot, handle, stageMask) 호출 세 개가 SetResourceSet(set) 하나가 됩니다. PipelineStateDesc에 BindingLayoutHandle 필드가 추가됩니다(D3D12의 pRootSignature 자리).
  • Material (4단계) — LightConstants의 specularColor·shininess가 Material 상수버퍼로 옮겨 가고, GameObject가 Mesh* 옆에 Material*을 듭니다. Renderer::Render의 오브젝트 루프가 PSO → Material → Mesh로 정렬됩니다.
  • Sampler / SRV (5단계) — TextureDesc에 이미 TextureBind_ShaderResource와 GetSRV()가 있습니다. CreateTexture(desc, initialData)의 SysMemPitch 계산이 4바이트 포맷만 다루므로 압축 포맷은 그때 추가합니다.
  • RenderPass / CommandList (6단계) — BeginFrame의 OMSetRenderTargets·Clear·뷰포트가 BeginRenderPass(RenderPassDesc)로, Bind*/DrawIndexed가 CommandList 메서드로 옮겨 갑니다. Renderer.cpp의 m_device->가 cmd->로 바뀌는 기계적 변경입니다.
