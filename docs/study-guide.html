SherlockEngine 읽기 가이드

프로젝트를 문서와 함께 읽는 순서

docs/에는 렌더러 해부와 로드맵(rendering-analysis.html) 한 편과 단계별 상세 문서(phase-0 ~ phase-11, 그리고 에디터 확장 phase-11b·phase-11c) 열네 편이 있습니다. 문서는 단계 순서로 쓰였고 소스도 그 순서로 자랐으므로, 로드맵으로 지도를 펴고 → 앱 골격을 잡은 뒤 → 단계 문서를 번호 순으로 소스와 짝지어 읽는 것이 가장 덜 헤매는 길입니다. 이 문서는 그 길을 14개 스텝으로 나누고, 스텝마다 "먼저 읽을 문서 → 함께 볼 소스 → 확인 포인트"를 적었습니다.

단계 문서 한 편은 항상 같은 네 박자로 읽습니다. ① 1절 요약 표와 "한 줄 요약" → ② 그 단계가 만든 헤더의 맨 위 주석 → ③ .cpp의 핵심 함수 두세 개 → ④ 실행해서 완료 기준을 눈으로 확인. 문서 본문(설계 근거·함정·참고 문헌)은 ③에서 "왜 이렇게 했지?"가 생겼을 때 돌아가서 읽습니다.

1.요약: 전체 순서

스텝 번호는 단계 번호와 다릅니다. 앱 골격은 10단계에서 만들어졌지만 가장 먼저 읽어야 하고, 2단계(입력·카메라)는 RHI와 무관하니 골격 바로 뒤에 붙였습니다. 나머지는 단계 번호 순서 그대로입니다.

2.읽기 원칙

2.1 문서 두 종류의 구조

rendering-analysis.html은 한 편이지만 시점이 셋입니다. §1~§7은 2026년 7월의 초기 코드를 해부한 스냅샷이라 지금 소스와 이름이 다릅니다(Shader·MeshRenderer·struct.h는 이제 없습니다). 적용 기록과 §8의 설계 결정 D1~D22는 "무엇을 왜 바꾸기로 했나"이고, §9 로드맵의 PHASE 카드 12장은 각 단계의 요구·완료 기준·완료 보고를 담은 현재까지의 지도입니다. 그래서 처음에는 §1과 §9의 단계 구성 표만 읽고, 나머지는 각 스텝에서 필요한 D 항목과 PHASE 카드만 찾아 읽은 뒤, 마지막 스텝에서 통독합니다.

phase-N.html은 전부 같은 뼈대입니다. 상단 facts 격자(상태·파일 수·완료 기준), "한 줄 요약" 콜아웃, 1절 요약(이전 단계 vs 이 단계의 표), 설계 절들, 함정과 해결, 검증과 스크린샷, 참고 문헌. 요약 표와 함정 절만 읽어도 그 단계가 코드에 남긴 흔적을 알 수 있고, 설계 절은 소스를 읽다가 이유가 궁금할 때 돌아오면 됩니다. 검증 절의 스크린샷은 images/2026-09-23-phaseN-*.png에 있으니 직접 실행한 화면과 비교하세요.

2.2 소스를 읽는 법

  • 헤더 맨 위 주석이 설계 문서입니다. RHI/Device.h, Graphics/Renderer.h, Scene/Scene.h, Core/Engine.h의 첫 20줄은 그 클래스가 무엇을 소유하고 무엇을 소유하지 않는지, 어느 단계·어느 D 항목에서 왔는지를 적어 둡니다. 헤더를 다 읽고 .cpp로 갑니다.
  • "N단계" 주석으로 검색하세요. 소스 곳곳에 // 6단계:, // 11단계 (D19) 같은 표시가 있습니다. 스텝을 읽을 때 grep -rn "6단계" SherlockEngine/으로 그 단계가 손댄 자리를 한 번에 모을 수 있습니다.
  • 큰 파일은 함수 단위로. Renderer.cpp(1,109줄), D3D11Device.cpp(934줄), D3D12Device.cpp(1,428줄)는 통째로 읽지 말고 각 스텝이 지목한 함수만 읽습니다. 스텝 13에서 Renderer.cpp만 처음부터 끝까지 다시 읽습니다.
  • 백엔드는 항상 두 개를 나란히. 스텝 9부터는 같은 이름의 함수를 D3D11Device.cpp와 D3D12Device.cpp에서 나란히 열어 두고 비교합니다. RHI가 감춘 것이 무엇인지 그 차이에서 보입니다.
  • 실행 파일을 켜 두고 읽으세요. Debug|x64로 빌드해 두면 Debug Layer 메시지, ImGui 콘솔, Stats 패널이 코드의 주장을 즉시 확인해 줍니다(8절).

3.스텝 0~2: 지도와 골격

S0

지도 펴기 약 1시간

코드를 한 줄도 읽기 전에, 무엇이 어디에 있고 어떤 순서로 만들어졌는지 알아 둡니다. 빌드가 되는 상태를 여기서 확보합니다.
먼저 읽을 문서
  • README.md 전체 — 빌드 준비, 실행, 소스 폴더 표, 소스 규약(UTF-8 BOM, ComPtr, bool 반환)
  • rendering-analysis §1 프로젝트 현재 상태 — 파일 표는 옛 것이니 "역할" 열만
  • rendering-analysis §9의 "단계 구성" 표와 12장의 PHASE 카드 제목·완료 줄만
함께 볼 소스
  • 폴더 트리 한 번 훑기: App/ Core/ Graphics/ Scene/ RHI/ RHI/D3D11/ RHI/D3D12/ RHI/DXBC/ Shaders/ Assets/
  • vcpkg.json — 의존성 목록(DirectXTK·DirectXTex·ImGui·cgltf 등)
  • Assets/Config/engine.ini — 백엔드·씬·로그 레벨을 고르는 곳
확인 포인트 — Debug|x64 빌드가 성공하고 x64\Debug\SherlockEngine.exe를 탐색기에서 직접 실행해도 데모 씬이 뜬다. engine.ini의 backend를 d3d12로 바꾸면 창 제목·Stats 패널의 백엔드 이름이 바뀐다.
S1

앱 골격과 프레임 루프 약 3시간

"프로그램이 켜져서 한 프레임을 그리고 꺼지기까지"를 따라갑니다. 이 뼈대를 알아야 이후 스텝에서 읽는 모든 클래스가 어느 시점에 불리는지 알 수 있습니다. 골격은 10단계에서 지금 모양이 됐으므로 10단계 문서의 해당 절을 먼저 봅니다.
먼저 읽을 문서
  • phase-10 §5 Engine과 AppBase (D14), §3 Config, §4 Time: 고정 스텝 누적기
  • phase-0 전체 — dt 전달, exe 기준 셰이더 경로(Core/Paths), 폴더 재배치. 짧고 기초적
  • rendering-analysis §3 초기화 과정·§4 프레임 루프 — 옛 코드 기준이지만 "초기화 순서와 실패 시 false" 규약은 그대로
  • D14(전역 g_appBase와 앱 골격), D13(가변/고정 스텝)
함께 볼 소스
  • main.cpp → App/AppBase.h(헤더 주석) → AppBase.cpp의 Initialize·Run·MsgProc
  • Core/Engine.h 전체(멤버 선언 순서 = 생성 순서 주석) → Engine.cpp의 Initialize·BeginFrame·Render·EndFrame
  • App/TestApp.h만 — OnInitialize / OnUpdate / OnFixedUpdate / OnGUI 네 훅과 자동 검증 인자 목록. .cpp는 아직
  • Core/Config.h, Core/Time.h, Core/Paths.h, pch.h(D3D 헤더가 없음을 확인)
확인 포인트 — Engine::Render에 적힌 순서(Device::BeginFrame → 그림자·메인 → UI 패스 → EndFrame)를 종이에 그릴 수 있다. engine.ini의 fixedstep을 0.1로 바꾸면 패널의 OnFixedUpdate 호출 수가 초당 10회로 준다. 로그 파일이 exe 옆 Logs\에 생긴다.
S2

입력과 카메라 약 2시간

RHI와 무관하지만 이후 모든 검증을 "카메라를 움직여 본다"로 하므로 먼저 익혀 둡니다. 뷰행렬을 역행렬로 만드는 수학과 Win32 마우스 캡처의 함정이 핵심입니다.
먼저 읽을 문서
  • phase-2 전체. 특히 §2.2 "공급은 무조건, 소비 측에서 판단", §3.2 "뷰행렬 = 카메라 월드 변환의 역행렬", §4.2 WM_CAPTURECHANGED
  • D8 오일러 각과 LookAt 카메라 · 부록 B. 좌표계와 행렬 규약
함께 볼 소스
  • Core/Input.h/.cpp — 메시지 → 프레임 상태(IsKeyPressed vs IsKeyDown), EndFrame이 델타를 지우는 자리
  • Scene/Camera.h/.cpp — Rotate·Move·뷰행렬 계산, Debug에서 LookToLH와 대조하는 검사
  • Scene/Transform.h/.cpp — 월드행렬 = S·R·T
  • App/TestApp.cpp의 UpdateCamera·BeginLook·EndLook·OnFocusLost, AppBase::MsgProc의 마우스 메시지 분기
확인 포인트 — WASD/QE와 우클릭 드래그로 공전하는 구 주위를 돈다. Alt-Tab 후 돌아와도 키가 고착되지 않는다. ImGui 창 위에서 드래그하면 카메라가 돌지 않는다(WantCaptureMouse). images/2026-09-23-phase2-*.png와 비교.

4.스텝 3~7: RHI 조각 다섯 개

로드맵이 강조한 1·3·4·6단계(그리고 텍스처를 실전에 쓰는 5단계)는 각각 RHI의 조각 하나를 만듭니다. PSO → 핸들·Desc → 바인딩 레이아웃 → 텍스처·샘플러 → 렌더 패스·커맨드 리스트. 이 다섯 스텝을 지나면 RHI/의 헤더 전부와 Renderer.cpp의 대부분을 읽은 셈이 됩니다.

S3

핸들 · Desc · PSO: RHI의 어휘 약 4시간

이 프로젝트의 모든 GPU 리소스는 {index, generation} 값 핸들이고, 생성은 Desc 구조체 하나로, 파이프라인 상태는 PSO Desc 하나로 통합돼 있습니다. 이 어휘를 먼저 익히지 않으면 Renderer를 읽을 수 없습니다. 1단계(PSO)와 3단계(핸들·풀·Dynamic 버퍼 링)를 묶었습니다.
먼저 읽을 문서
  • phase-1 §2 "D3D11의 상태 모델과 D3D12의 PSO", §3 PipelineStateDesc 설계(값 타입·해시), §5 D3D11 구현
  • phase-3 §2 핸들과 풀(세대 카운터·free list), §3 Desc → 핸들 API, §4 프레임과 Dynamic 버퍼 링, §6 텍스처
  • D21 RHI 추상화의 형태, D22 D3D11 위 PSO 에뮬레이션, D1 ComPtr
함께 볼 소스
  • RHI/Handle.h → RHI/ResourcePool.h — 세대가 use-after-free를 어떻게 잡는지
  • RHI/PipelineTypes.h/.cpp — Format·CullMode 열거, PipelineStateDesc와 해시·비교
  • RHI/ResourceDesc.h, RHI/GraphicsConfig.h(kFrameCount)
  • RHI/D3D11/PipelineState.h/.cpp, PipelineStateCache.h/.cpp — D3D11 상태 객체 5개를 하나로 묶는 자리
  • RHI/D3D11/D3D11Resources.h, D3D11Device.cpp의 CreateBuffer·UpdateBuffer·CreateTexture·BeginFrame만

D3D12를 모르는 경우

S9 전에 phase-8 §2와 rendering-analysis §9의 개념 대응표를 먼저 읽고, 문서의 참고 문헌(Microsoft의 "D3D12 for D3D11 programmers" 계열)을 하루 곁들이면 됩니다. 이 프로젝트는 D3D12의 개념(PSO·루트 시그니처·디스크립터 테이블·배리어·펜스)을 1~6단계에서 D3D11 위에 미리 그려 두었으므로, S3~S7을 충실히 지나왔다면 낯선 것은 API 이름뿐입니다.

이미 D3D11을 잘 아는 경우

S2·S6은 문서의 1절 요약과 확인 포인트만 하고 지나가도 됩니다. 대신 S3의 D21·D22, S5의 §2(루트 시그니처를 D3D11에 미리 그리기), S7의 Barrier 설계, S8·S9 전체에 시간을 몰아 주세요. 이 프로젝트의 고유한 부분이 거기 있습니다.
